# Basic queries

> **In this section** — the `FROM` query shape, `SERIES` row sources, WHERE operators, logical operators, nested fields, JOIN, ORDER BY, SKIP / LIMIT, SELECT, EXPLAIN.

## FROM

```
FROM [Namespace].[Collection] [alias]
  [AS OF <instant>]                    -- temporal collections only
  [IN BETWEEN <instant> AND <instant>] -- temporal collections only
  [JOIN clause]*
  [WHERE expression]
  [NEAREST [APPROXIMATE] vector-field TO vector-value USING COSINE|L2|DOT TOP n|@k
    [WITH (SEARCH_LIST = n)]]
  [ORDER BY field [ASC|DESC] [, ...]]
  [SKIP n]
  [LIMIT n]
  [SELECT field [, ...]]
```

An `<instant>` is a timestamp string, `NOW`, an `@parameter` or an instant expression such as `DATEADD('MONTH', -1, NOW)`; in an APPLY body or a correlated subquery it may read the enclosing row's columns ([instant expressions](temporal.md#instant-expressions)).

A derived source uses `FROM (<query-expression>) [alias]`. The enclosed read expression may contain WITH bindings or set operators. Its ordering/paging is local to that source; the outer clauses consume the resulting relation.

A FROM source is a collection, a CTE, a view, a `[Mnemic].*` system collection, a derived source, or a generated [`SERIES`](#series) of calendar steps or integers (`FROM SERIES 1 TO 11 [s]`), which reads no collection.

`FROM` is required. All other clauses are optional. Clause order matters — follow the order shown above. `AS OF` and `IN BETWEEN` only apply to temporal collections; running either against a non-temporal collection is rejected (silently ignoring the clause would mask typos), before any mistake in a later clause is reported, by execution, schema discovery and `EXPLAIN` alike. A `SELECT` that writes one output name twice (`DUPLICATE_NAME`: two plain fields, an `AS` alias or an aggregate alias spelled alike) is a property of the `SELECT` alone and is reported before the temporal clause and every other mistake of its query, including one in a non-recursive CTE definition the statement reads. A recursive CTE is bound before the main query, so its mistakes are reported first, before the main query's repeated output name (see [CTEs](cte.md)). A collision only the source's fields produce, such as a wildcard's expanded or renamed field (`SELECT *, [Qty] AS [Id]`, `SELECT * RENAME ([Qty] AS [Name])`) or the container a nested plain path emits (`SELECT [Dims].[W], [Qty] AS [Dims]`), is reported when the projection is admitted, after the temporal clause and the `WHERE`. See [Temporal queries](temporal.md) for details.

`NEAREST` performs a top-k vector search with explicit `TOP`; see [Vector values and nearest-neighbour search](vectors.md). It follows `WHERE` so the filter remains part of the authoritative result contract. Ranking accepts joined, derived, CTE and temporal sources, retains `TOP` nearest rows, and passes them to grouping, projection, explicit sorting and final paging.

```sql
-- All documents, all fields
FROM [Store].[Products];

-- Filtered with projection and pagination
FROM [Store].[Products]
WHERE [Price] > 10 AND [Active] = TRUE
ORDER BY [Price] DESC
SKIP 20 LIMIT 10
SELECT [Name], [Price];
```

## WHERE operators

| Operator | Example | Description |
|----------|---------|-------------|
| `=` | `[Name] = 'Widget'` | Equality |
| `!=` | `[Status] != 'inactive'` | Inequality |
| `>` | `[Price] > 100` | Greater than |
| `>=` | `[Rating] >= 4.5` | Greater than or equal |
| `<` | `[Count] < 10` | Less than |
| `<=` | `[Age] <= 65` | Less than or equal |
| `CONTAINS` | `[Name] CONTAINS 'widget'` | Substring match (strings) |
| `STARTSWITH` | `[Email] STARTSWITH 'admin'` | Prefix match (strings) |
| `LIKE` | `[Name] LIKE 'Wid%et_'` | ANSI SQL pattern match — `%` = any sequence, `_` = exactly one character (one Unicode codepoint, so an emoji or other astral character counts as one; two `_` wildcards cannot split it). Wildcards match any character including `\n` / `\r`. Optional `ESCAPE 'c'` clause makes the next char after `c` a literal. Comparison is a simple case-insensitive fold of the text as stored — no Unicode normalization, so a decomposed `e` + combining accent does not match precomposed `é`. Identical semantics in WHERE and in expressions (CASE WHEN / SELECT). |
| `NOT LIKE` | `[Name] NOT LIKE '%test%'` | Negated pattern match |
| `IN` | `[Status] IN ('active', 'pending')` | Matches when the field equals any value in the list |
| `NOT IN` | `[Status] NOT IN ('archived', 'banned')` | Matches when the field equals none of the values. NULL matches only if NULL is absent from the list. |
| `= NULL` | `[Notes] = NULL` | Null check (`IS NULL` is accepted as a synonym) |
| `!= NULL` | `[Email] != NULL` | Not-null check (`IS NOT NULL` is accepted as a synonym) |

An `ESCAPE` value is exactly one well-formed, non-surrogate UTF-16 code unit, and a pattern may not end with it, since a trailing escape escapes nothing: `LIKE 'ab!' ESCAPE '!'` is `INVALID_VALUE` when the statement parses, and a parameter pattern that ends that way is `INVALID_VALUE` when its value is bound. An astral character requires a surrogate pair and therefore cannot be used as the single escape value. This applies equally to parsed text and directly constructed AST or filter objects.

> **NULL equality:** `NULL = NULL` is TRUE; exactly one NULL operand makes equality FALSE. Inequality is its complement. `IN` is a disjunction of those equalities and `NOT IN` is its exact complement, including NULL list members. Ordered and text comparisons with NULL remain UNKNOWN, also under NOT. `BETWEEN a AND b` is `>= a AND <= b` and `NOT BETWEEN a AND b` is `< a OR > b`, so a NULL bound leaves the result to the other comparison. WHERE and FILTER retain only TRUE. The rules are identical in scalar expressions, native filters, arrays, joins, CHECKs, subqueries, and windows.

Absent `[Meta].[ValidFrom]` and open-ended `[Meta].[ValidTo]` use these NULL rules as well. They match `IN (NULL)`, reject date range comparisons, and are distinct from a present minimum timestamp. The same rules select UPDATE and DELETE targets.

`IN (NULL)` and `NOT IN (NULL)` retain these rules when a literal query plan is cached, including on non-temporal collections. A NULL-only list contains no empty String or Bytes member and needs no conversion to the field's type, for every field type including `BOOL`.

An `IN` member bound through a string parameter keeps every character, including NUL, exactly as an equality operand does: `[Name] IN (@p)` with `@p = "a\0b"` matches only `"a\0b"`, in native `WHERE`, OR-to-`IN` folding, index probes, and `CASE` alike.

Members that name one value, written twice, spelled differently (`7`, `7.0`, `'7'`) or bound twice through parameters, are one member: a list, and OR groups whose lists overlap, select each row once, through a primary-key or secondary-index probe and a scan alike, in a query, a history or `AS OF` read and an UPDATE or DELETE.

Field paths and operator domains are validated before scanning. An unknown `WHERE` field is an error rather than an implicit NULL, and string-only operators (`LIKE`, `CONTAINS`, `STARTSWITH`) reject non-string fields. A NULL right-hand value is a null check only for `=` / `!=`; with any other comparison it is a valid never-match predicate.

Ordinary WHERE expressions keep their meaning when distributing `AND` across `OR` would exceed native preparation's local bound. The engine evaluates the complete Boolean tree before grouping, projection, counting, or paging, while retaining bounded native predicates for source access where possible. Field, operator, and parameter validation still happens during preparation, before residual evaluation. The same predicate evaluation selects write targets, and EXPLAIN describes it without executing it. `LAST PER` instead enforces the native preparation limit before sampling; see [temporal downsampling](temporal.md#last-per-temporal-downsampling).

BYTES equality and ranges compare raw unsigned bytes, with shorter strict prefixes first. Bind byte parameters or use Base64 literals; neither Base64 text order, case folding, nor UTF-8 decoding participates. Empty bytes remain distinct from NULL, and range predicates never match NULL operands. This is the same value order used by ORDER BY and projected comparison expressions, including `Meta.CreatedBy` when stored attribution is absent.

> **String case-sensitivity:** All string comparisons (`=`, `!=`, `LIKE`, `CONTAINS`, `STARTSWITH`, `IN`, `ORDER BY`, expression-level `=` / `<` / `>` inside `CASE` / computed columns / `CHECK`, and the `POSITION` / `REPLACE` functions) are **Unicode-aware case-insensitive** — the engine compares after the active .NET invariant-culture *simple lowercase mapping*, ordinally. `'WIDGET' = 'widget'`, `'café' = 'CAFÉ'`, `'Åland' = 'ÅLAND'`, and `'ДЕНЬ' = 'день'` all match. Secondary index keys, sort keys, IN-set bytes, and join hash keys all use the same normaliser, so case variants that map to the same lowercase key remain findable through differently-cased queries. Documents preserve their original casing in storage — only comparison and indexing use the lowercase-normalized key. This is **ordinal after lowercasing**, not linguistic collation or Unicode Default Case Folding: it ignores no characters (a soft hyphen `U+00AD` is significant), performs no Unicode normalization, and orders by code point. The lowercase mapping can change with the .NET runtime, Unicode data, or active globalization backend. Each database persists a fingerprint of the exact effective mapping and policy. On mismatch, open invalidates and rebuilds all derived indexes from original documents before publishing the new profile; a crash repeats that sequence rather than accepting mixed-profile keys.

### Per-operator examples

Correlated EXISTS and IN subqueries retain full CASE and NOT predicate semantics. Those predicates use the inner query's residual evaluation when a generated semi/anti join cannot represent them. An inner-only scalar predicate can still participate in scalar-aggregate decorrelation through a complete inner CTE query; one that depends on the outer row stays in per-row evaluation.

```sql
-- Equality / inequality
FROM [Store].[Products] WHERE [Sku] = 'W-17';
FROM [Store].[Products] WHERE [Category] != 'archive';
FROM [HR].[Employees]   WHERE [HireDate] = '2024-06-01';

-- Ordered comparisons on numbers, dates, datetimes, strings, and bytes
FROM [Store].[Products] WHERE [Price] >= 100 AND [Price] < 500;
FROM [HR].[Employees]   WHERE [HireDate] < '2020-01-01';                  -- DateOnly
FROM [App].[Events]     WHERE [OccurredAt] >= '2024-06-15T10:30:00Z';      -- DateTimeOffset (UTC)
FROM [App].[Events]     WHERE [OccurredAt] >= '2024-06-15T10:30:00+02:00'; -- DateTimeOffset with offset
FROM [App].[Events]     WHERE [OccurredAt] >= '2024-06-15T10:30:00';       -- no offset ⇒ assumed UTC
FROM [Store].[Products] WHERE [Name] >= 'M' AND [Name] < 'N';              -- alphabetical bucket

-- Substring and prefix
FROM [Store].[Products] WHERE [Name] CONTAINS 'widget';
FROM [HR].[Employees]   WHERE [Email] STARTSWITH 'admin@';

-- Pattern match (case-insensitive, like all string comparisons).
-- Wildcards span line terminators: '%' and '_' both match '\n' and '\r'.
FROM [Store].[Products] WHERE [Name] LIKE 'Wid%';           -- prefix
FROM [Store].[Products] WHERE [Name] LIKE '%dget';           -- suffix
FROM [Store].[Products] WHERE [Name] LIKE '%dge%';           -- substring
FROM [Store].[Products] WHERE [Sku]  LIKE 'W-_';             -- exactly one trailing char
FROM [Store].[Products] WHERE [Name] NOT LIKE '%test%';      -- negation

-- Pattern match with ESCAPE: the next character after the escape char is a literal,
-- letting you match a literal '%' or '_' that would otherwise be a wildcard.
-- The escape character must be a single-character string literal containing
-- one well-formed, non-surrogate UTF-16 code unit.
-- A trailing escape char with nothing to escape is rejected as an invalid escape sequence.
FROM [Store].[Products] WHERE [Sku] LIKE '50\%' ESCAPE '\';   -- matches the literal "50%"
FROM [Store].[Products] WHERE [Code] LIKE 'A!_B' ESCAPE '!';  -- matches the literal "A_B"

-- Set membership
FROM [App].[Orders] WHERE [Status] IN ('pending', 'paid', 'shipped');
FROM [App].[Orders] WHERE [CustomerId] IN (@c1, @c2, @c3);
FROM [App].[Orders] WHERE [Status] NOT IN ('archived', 'cancelled');

-- Subqueries inside WHERE — three forms.
-- (1) IN (FROM ... SELECT col): probe membership against the inner result.
--     A non-correlated inner executes once; a correlated inner may reference
--     the outer row and is decorrelated when its exact shape permits it.
FROM [App].[Orders] WHERE [CustomerId] IN (FROM [App].[Customers] WHERE [Region] = 'EU' SELECT [Id]);

-- (2) Scalar subquery on the RHS of a comparison — the inner query must
--     return at most one row. Zero rows yields ordinary NULL (compared using the same
--     NULL-safe equality rules, so = matches a NULL [Target]). More than one row is a runtime
--     error. May reference outer columns (correlated form). Eligible equality
--     correlations decorrelate set-wise; other shapes evaluate per outer row.
--     The per-row form freezes the inner result schema before consuming a lazy
--     stream, so emitted bytes cannot be reinterpreted under later metadata.
--     LIKE / NOT LIKE / CONTAINS / STARTSWITH use the same field typing,
--     lowercase normalization, ESCAPE, and NULL rules as an ordinary WHERE predicate.
FROM [Sales].[Customers]
  WHERE [Target] IS NOT NULL
    AND [Target] = (FROM [Sales].[Orders]
                    WHERE [CustomerId] = [Sales].[Customers].[Id]
                    SELECT MAX([Total]));

-- Alias-qualified and namespace/collection-qualified inner paths are
-- equivalent. Eligible unfiltered SUM/AVG/MIN/MAX/COUNT equality shapes are
-- decorrelated set-wise when their live field types share a join equality
-- domain. SUM/AVG require numeric fields and use exact typed equality across
-- widths. COUNT uses a null-preserving grouped plan and substitutes zero only
-- when no correlated group exists; COUNT(field)=0 for a real group remains 0.
-- Cross-domain coercions stay per-row.
-- An aggregate FILTER keeps the exact per-outer-row evaluator; it is never
-- discarded merely to make the query decorrelatable.

-- (3) EXISTS (FROM ...) / NOT EXISTS (FROM ...) — top-level boolean.
--     The inner projection is ignored; only row presence matters.
--     Eligible equality correlation decorrelates to a SEMI / ANTI join;
--     other correlated forms evaluate per outer row. A non-correlated form
--     is effectively constant TRUE/FALSE. CTE and derived outer sources,
--     and CTE references inside the EXISTS query, use the same rules.
--     The set-wise forms of (1)-(3) apply only when no sibling WHERE leaf
--     needs the complete row: beside a negated or scalar leaf (such as
--     NOT ([Id] = 5) or [Total] + 1 > 0), or an aggregate FILTER with one, in
--     a JOIN query that composes its rows before WHERE for another clause, and
--     in a JOIN query over a CTE, view, derived or system FROM input, every
--     correlated predicate evaluates per outer row. A JOIN query's correlated
--     WHERE composes its merged rows either way; over a stored FROM input the
--     set-wise joins filter that composition. EXPLAIN's Notes state which
--     applies.
FROM [Sales].[Customers]
  WHERE EXISTS (FROM [Sales].[Orders] WHERE [CustomerId] = [Sales].[Customers].[Id]);
FROM [Sales].[Customers]
  WHERE NOT EXISTS (FROM [Sales].[Orders] WHERE [CustomerId] = [Sales].[Customers].[Id]);

-- Projection and DISTINCT run after a still-correlated predicate. A
-- polymorphic extension value is read from the surviving row's active subtype
-- before typed deduplication.
FROM [Fleet].[Vehicles]
  WHERE EXISTS (FROM [Sales].[Inspections]
                WHERE [Score] > [Fleet].[Vehicles].[MinimumScore])
  SELECT DISTINCT [Seats];

-- When the outer collection has a virtual computed column, a residual
-- correlated predicate evaluates after that column is injected. Downstream
-- grouping, total count, projection, and paging therefore see only survivors.
FROM [Sales].[Customers]
  WHERE EXISTS (FROM [Sales].[Orders]
                WHERE [Total] > [Sales].[Customers].[CreditLimit])
    AND [AvailableCredit] > 0;

-- (4) Correlated EXISTS / scalar against a temporal target. NOW remains
--     statement-pinned across every outer-row dispatch; only the correlated
--     outer value changes per row. The bound outer Guid flows through to the
--     temporal predecessor probe (AS OF), full overlap scan (IN BETWEEN), or
--     bucketing executor (LAST PER) the same as a hand-written query.
FROM [App].[Invoices]
  WHERE EXISTS (FROM [App].[Tariffs] AS OF NOW
                WHERE [Id] = [App].[Invoices].[TariffRef]);

-- Null checks — `= NULL` / `!= NULL` are accepted as Mnemic-style
-- shorthand for IS NULL / IS NOT NULL (see "= NULL semantics" below),
-- and the ANSI forms `IS NULL` / `IS NOT NULL` are also supported.
FROM [HR].[Employees] WHERE [ManagerId] = NULL;          -- top-level (CEO has no manager)
FROM [HR].[Employees] WHERE [ManagerId] IS NULL;         -- equivalent ANSI form
FROM [HR].[Contracts] WHERE [Meta].[ValidTo] = NULL;     -- currently active
FROM [HR].[Employees] WHERE [Email] != NULL;             -- has email
FROM [HR].[Employees] WHERE [Email] IS NOT NULL;         -- equivalent ANSI form

-- Range filtering — BETWEEN is inclusive on both ends.
FROM [Sales].[Orders] WHERE [Total]  BETWEEN 100 AND 500;
FROM [Sales].[Orders] WHERE [Total]  NOT BETWEEN 100 AND 500;
```

Residual correlated predicates evaluate against the complete joined row, with references bound to the original relation aliases. Physical, CTE, derived, and computed sources share this behavior. Filtering precedes grouping, aggregation, projection, total count, and paging; proven set-wise decorrelation remains the preferred plan when its type, null, and cardinality requirements hold. Correlated parameters and scalar comparisons preserve a present empty Object (`()`) as distinct from NULL, including nested and subtype fields. A missing subtype field or NULL parent remains NULL; pinned references compare through their logical identifiers. A scalar subquery that produces NULL or no row keeps ordered and text comparisons UNKNOWN, including beneath `NOT`. A non-NULL scalar operand still undergoes the native field's validation when the outer value is NULL: invalid binary text and out-of-range ordered integer operands are not skipped. Inner schema, cardinality and execution errors are resolved before this operand validation. A missing descendant below a present scalar or empty Object is NULL; the ancestor's presence does not make the child present.

An uncorrelated scalar subquery returning `()` also remains a present empty Object when used in a WHERE comparison. A NULL result or no result row remains NULL, including for nested and subtype projections.

Native `IN (NULL)` and `NOT IN (NULL)` use the same presence rule: an empty Object is a non-NULL value, including inside array predicates and `MATCH`.

### Comparison value notes

- **Mixed numeric comparisons are lossless.** `INT64`, `DECIMAL`, and floating-point operands are compared by their mathematical values without first rounding both sides to `FLOAT64`. For example, integer `9007199254740993` is greater than (and not equal to) floating-point `9007199254740992.0`. This applies to `=`, ordered comparisons, `IN`, `BETWEEN`, `NULLIF`, joins, grouping/deduplication, and window ordering/peer checks. A typed `FLOAT64` or `FLOAT32` value — a caller's parameter, an enclosing row's value, a nested query's value or an `IN` subquery's member — meets an integer or `DECIMAL` field by that value too: a `FLOAT64` 2^60 equals the `INT64` `1152921504606846976` although its text `1.152921504606847E+18` names `1152921504606847000`. Such a value past 2^53 whose text names another integer is compared by a scan rather than an integer index. Large literal `IN` sets hash the same exact numeric identity, so distinct high-precision `DECIMAL` members do not collapse through `FLOAT64` into one collision chain. Mixed `DECIMAL`/floating comparison uses scaled fixed-width coefficients and does not allocate temporary arbitrary-precision numbers per comparison. Arithmetic keeps its normal promotion rules; this guarantee is comparison-specific.
- **Correlated `IN` preserves tuple boundaries.** Its set-based plan requires both the correlation equality and the projected-value equality to hold for the same inner row. Embedded zero bytes and variable-width numeric encodings cannot make two unequal field pairs compare as one compound key. The projected inner field is validated against the live inner schema before the compound join runs; a missing field or an incompatible polymorphic shape is an error, just as it is for the unreduced inner `SELECT`. Every present outer component must also share a compatible equality domain with its projected inner component; a pair of unrelated scalar types never reaches hashing and keeps the per-row membership. The rewrite always has exactly two equality components (the primary correlation plus one projected-value pair); a hidden/programmatic form carrying further pairs is rejected before join setup.
- **BYTES strings are Base64, never text bytes.** When a `BYTES` field is compared with a string literal or parameter, that string is decoded as Base64 before `=`, `!=`, ordering, `IN`, or `BETWEEN` compares it. Invalid Base64 is rejected during native validation when the candidate fields are all binary. In a mixed subtype domain that admits the text through another type, the operand cannot equal a binary value; `IN` / `NOT IN` retain their membership polarity. Expression and window comparisons likewise retain their binary non-match policy; no path compares the operand against the binary payload as UTF-8 text. A present zero-length byte sequence is distinct from NULL. It remains a real equi-join key under every execution plan, including left-deep and bushy joins; NULL values match other NULL values in their own equality class. The same distinction holds in correlated `MATCH`, including fields on polymorphic array elements. Large `IN` lists over `BYTES` or `ARRAY` hash each complete binary value, so equal-length values with a common prefix do not collapse into one lookup chain; equality still compares the complete payload after any hash collision.
- **Numeric text is coerced consistently.** A string literal or parameter compared with a numeric value is read by the one [numeric text grammar](document-literals.md#numeric-text) — so `'(5)'`, `'1,000'` and `'¤8'` name no number and match nothing — and parsed invariantly as exact `INT64`, then exact `DECIMAL`, or otherwise directly as `FLOAT64`, then compared in the exact mixed-numeric domain. Decimal parsing must preserve the text's value; successful parsing that rounds does not select Decimal. The Float64 fallback follows its ordinary rounding and range limits, preserving values such as `'1e-300'` without first rounding them to Decimal zero. Thus `[Count] = '5'` and `[Count] IN ('4', '5')` are valid, while a large integer is not rounded merely because the other operand is floating point. This applies to native `WHERE`, `IN`, expression comparisons, and `UPDATE`/`DELETE` target selection. A stored `FLOAT64` value `0.1` differs from the exact decimal value `'0.1'`; a typed Double parameter retains its binary value and can equal that stored value. Scalar and `IN` subqueries retain the projected numeric kind too: a `FLOAT64` `0.1` from an inner query equals the same stored floating value, and remains unequal to a `DECIMAL` `0.1` target, including when membership spills to disk. Numeric literals retain their normal exact numeric value, also against integer fields: `[Count] > 0.5` matches `1` and above, `[Count] = 1.5` matches nothing, and `[Count] != 1.5` matches every row, including NULL (which is unequal to a present value). Numeric text such as `'0.5'` behaves the same. A vector or index path is eligible only when its narrowed operand preserves the exact comparison; otherwise the engine evaluates the original operand in a scalar scan, so a fractional bound on an indexed integer field or primary key reads the collection instead of the index. Nonnumeric text is a non-match for every scalar comparison arm, including `!=`, independent of whether the predicate uses an index or a full scan (even when the text's UTF-8 length equals the field's binary width). This includes primary-key point, range, temporal, and OR predicates: `'ABCD'` cannot become an `INT32` key by treating its text bytes as a stored integer. In an `IN` list, an unparseable numeric member contributes no match while parseable siblings retain their normal meaning. A well-formed value outside a field's storage width remains a non-match for equality/IN, apart from the native `INT8`/`INT16` bit-pattern exception below, and follows the range-operator rules below. If a polymorphic extension path has different declared types across subtypes, a value compatible with one subtype simply does not match incompatible subtype instances.
- **A STRING value compares with a number as text.** When a STRING field, expression or enclosing row's value meets a number, the number is read as its canonical text and compared with the STRING by the STRING order and (case-insensitive) identity: `[S] = [N]` holds for `'1'` and `N = 1`, never for `'01'`, `'1.0'`, `' 1'` or `'1,000'`, and `[S] < [N]` orders the two texts. The canonical text of an integer is its plain digits (`-42`); of a DECIMAL, its digits with the scale it carries (`1.0`, `2.50`); of a FLOAT64, the shortest text that reads back as the same value, in plain digits for decimal exponents -4 to 16 (`1.5`, `1E+20`, `1E-05`), a FLOAT32 reading as the FLOAT64 holding its exact value (`0.10000000149011612` for a stored `0.1`), and a negative zero as `0`. NaN and the infinities have none: comparing one with a STRING is `INVALID_VALUE`. The canonical text is a number's only text: `CAST` and `TRY_CAST` to STRING, `TO_STRING`, `||`, `CONCAT`, `JOIN_STRING`, a STRING result and a number written to a STRING field render it, so a number equals its own cast text (`CAST([N] AS STRING) = [N]` holds for every finite `[N]`), and converting NaN or an infinity to text is `INVALID_VALUE`, which `TRY` and `TRY_CAST` recover as NULL (a write has no recovery form). This holds in one row, between joined rows, in a nested query with either value enclosing, for an element path, `IN`, `BETWEEN`, every ordering, CASE, CHECK, computed columns, views and triggers. A number literal or parameter compared with a STRING is read the same way (`[S] = 1.0` matches only `'1.0'`), while a text literal or parameter compared with a number keeps the numeric reading described above (`[Count] = '05'` matches 5).
- **A nested query's value is a row's value, not a literal.** A scalar subquery's value and an `IN` subquery's members, correlated or not, compare with a field — a row's metadata (`[Meta].[Revision]`, `[Meta].[Sealed]`, …) and a `LENGTH(element predicate)` count included — exactly as the same comparison of two fields of one row does, in `WHERE` (over a join, with the field of the relation the comparison names, whatever another relation declares at the same path), in a scalar expression and in a write's `WHERE`: text a subquery yields meets a number as text (`[Count] = (… SELECT [Code])` with `'05'` matches no 5, and no count or revision 5 either), a number it yields meets a STRING as its canonical text and a narrower integer field as a number (`200` is no INT8 `-56`, and every INT8 is less than it, where the literal `200` reads INT8's bit pattern and refuses the ordering), a fractional number meets a count as a number, and a value that names nothing of the field's type equals none of its values instead of being refused (`[Day] = (… SELECT [Note])` with `'1'` is a non-match, not `INVALID_VALUE`). A count orders only with a value whose type has an order with a number: `<`, `<=`, `>` or `>=` against a GUID, temporal, BYTES, ARRAY or OBJECT value, from a nested query or an enclosing row, is `TYPE_MISMATCH` when the statement is bound, by the value's type alone, whatever the arrays hold. A value the field's type reads natively, or converts to exactly (text naming a GUID or a date, a number against a STRING, an integer's canonical text against an integer field under `=` and `IN`), keeps the field's index and the native comparison; any other is compared row by row by the scalar rule, and the statement then reads its source without an index, its other conditions included (a GUID, temporal, BOOL or BYTES value against a STRING field, whose text any spelling of the value equals, is one).
- **Bool text is coerced consistently.** A string compared with a `BOOL` value is interpreted through the Bool accept set — `'true'` / `'false'` (case-insensitive) and `'1'` / `'0'` — so `[Active] = 'true'` matches `[Active]: true`. This holds in every expression seam (`WHERE`, `CHECK` constraints, `CASE`, `HAVING`, computed columns). Text outside the accept set (`'yes'`) is a typed query error rather than a silent non-match.
- **Materialized `IN` subqueries compare their members as row values.** A non-NULL member equals a field value exactly when the same two fields of one row would be equal: a member of the field's type, or a number against a number, natively; text naming a GUID, BOOL, date, time, timestamp or Base64 payload as that value; a number against a STRING field as its canonical text (NaN or an infinity is `INVALID_VALUE` where a present STRING meets it, and no refusal where none does); text against a number field as the number's canonical text; a STRING field's text read as a BOOL, temporal, GUID or BYTES member. A member that names no value of the field's type equals none, and no member is refused. A syntactically valid integer outside a narrower target width remains a non-match. For a polymorphic path, each row compares by its own declaration. The members keep their spill and admission budget.
- **DateTime / DateTimeOffset literals** compare by instant (UTC ticks). A literal that carries an explicit offset (`…Z`, `…+02:00`) keeps that offset; a literal with **no** offset (`'2024-06-15T10:30:00'`) is assumed to be **UTC** — never the server's local time zone — so the same query returns the same rows on every host.
- **DATEONLY and TIMEONLY compare with a DATETIME by its offset-local date or time.** `[Day] = [At]`, `[Clock] > [At]` and `[Day] IN ([At])` read the DATETIME's date (or time of day) in its own offset, on either side and in every predicate position, so `[Day] < [At]` is false for a timestamp on that day. CAST the date to `DATETIME` to compare instants (`CAST([Day] AS DATETIME) < [At]`). A nested query compares its own row's field with an enclosing row's by the same rule, whichever side holds the DATETIME: inside a nested query of `[a]`, `[b].[At] = [a].[Day]` and `[b].[Day] = [a].[At]` select what `[At] = [Day]` selects in one row.
- **A nested query compares with an enclosing row as one row compares two fields.** For every pair of types — the enclosing value on either side of the comparison, as an `IN` member, against an element path (`[b].[Tags][]`) or inside a `MATCH` body — `EXISTS`, `NOT EXISTS`, `IN`, a scalar subquery, `CROSS APPLY` and `EXPLAIN` give what the same comparison of two fields of one row gives: values of unrelated types are unequal, a BOOL orders with a number as 0 / 1, text converts as the values meet, and an ordering without a common order is a `TYPE_MISMATCH` before rows are read. The field's index serves the comparison whenever the enclosing value is of the field's own type, a number meets a numeric field, or the value converts exactly to the field's type for that row: text naming a GUID, a timestamp, a date, a time, a BOOL or a Base64 payload against a GUID, DATETIME, DATEONLY, TIMEONLY, BOOL or BYTES field, a DATETIME's offset-local date or time against a DATEONLY or TIMEONLY field, `0` or `1` against a BOOL, a BOOL against a numeric field, a number against a STRING field (as its canonical text), and, for `=`, `!=` and `IN`, an integer's canonical text (`'42'`) against an integer field. Any other comparison is evaluated row by row instead of through the field's index: a DATETIME field against an enclosing DATEONLY or TIMEONLY, a STRING field against a BOOL, temporal, GUID or BYTES value (the field's text is read as that value), a numeric field against other enclosing text (which compares with the number's canonical text), a value that names nothing of the field's type for that row (which then gives the rule's result: unequal, or `TYPE_MISMATCH` for an ordering), and unrelated types. An element compares by the same rule, so `[Tags][] = [Name]` in one row and `[b].[Tags][] = [a].[Name]` in a nested query read each element as `[Tag] = [Name]` would.
- **ARRAY and OBJECT values compare only with their own type.** An ARRAY or OBJECT equals a value of the same layout when the two are one value, and is unequal to a value of any other type — a scalar, BYTES holding its stored payload, text from a row, the other composite — in one row, in a nested query with the composite on either side, and as an `IN` member; an ordering of an ARRAY or OBJECT is a `TYPE_MISMATCH` (composites have no order; `MIN` / `MAX` still order extrema by payload). A Base64 text literal names a composite's payload, so `[Body] = 'AQ=='` compares payloads; any other literal against a composite is `INVALID_VALUE`.
- **An ordered comparison needs a common order.** `<`, `<=`, `>`, `>=` and the bounds of `BETWEEN` order values of one type, numeric values (`BOOL` reads as 0 / 1), text against another type (the text converts as the values meet; a STRING and a number order as texts), and DATEONLY or TIMEONLY against DATETIME. Any other pair — DATEONLY with TIMEONLY, a temporal value with a number, GUID or BYTES with another type — is a `TYPE_MISMATCH`: the statement, EXPLAIN and a stored definition's creation refuse it before rows are read when both operand types are known (a field, an element path, a CAST, `NOW`, a typed parameter, a nested query's column), in WHERE, HAVING, aggregate FILTER, CASE, projections, writes, computed columns and CHECK; text that names no date fails the same way as the row is read. Equality between unrelated types is no error: the values are unequal (`[Day] = [Clock]` matches only when both are NULL).
- **A literal is read as a value of the type it is compared with.** Compared with a field or expression of a known type — by `=`, `!=`, an ordering, a `BETWEEN` bound or an `IN` member, on either side, against a field or an array element, and by every form that compares its arguments for equality (`NULLIF` in either argument order and the simple `CASE [x] WHEN v` form, which compare as `=` does) — a literal must name a value of that type, on the native and the scalar route alike: `NULLIF([Count], '05')` is NULL exactly where `[Count] = '05'` holds, and `NULLIF([Day], 1)` is refused as `[Day] = 1` is. A number, BOOL or timestamp (`NOW` included) against a temporal or GUID value is refused (`TYPE_MISMATCH` for an ordering, whose types have no common order; `INVALID_VALUE` for equality and `IN`), and so is text that names no value of the type (`INVALID_VALUE`): `'10:00:00'` and `'1'` name no date and no timestamp (they write no date, and are never read as today's or as a day number), `'2024-06-15'` names no time of day, and `'yes'` no BOOL. Timestamp text keeps naming its date and its time (`[Day] = '2024-06-15T10:00:00Z'`). A BOOL reads the literals a BOOL parameter accepts: `TRUE` / `FALSE`, `'true'` / `'false'` / `'1'` / `'0'` and the integers `0` and `1`; any other number (`[Flag] = 5`, `[Flag] < 1.0`) and a timestamp are `INVALID_VALUE`. A numeric field reads a BOOL literal as 0 / 1, refuses a timestamp, and keeps its reading of non-numeric text (a non-match). A STRING field reads any literal as the text the literal names, a number as its canonical text: `[Code] = 1.0` compares with `'1.0'` and `[Code] = TRUE` with `'True'` (case-insensitively). A BYTES, ARRAY or OBJECT field reads Base64 text only, and an ARRAY or OBJECT refuses every ordering (`TYPE_MISMATCH`). WHERE, scalar expressions (projections, CASE, HAVING, FILTER), writes, computed columns, CHECK and stored definitions refuse a literal alike before rows are read; a window FILTER keeps its rule that malformed literal text is a non-match. A literal stored into a DATEONLY or TIMEONLY field follows the same text rule.
- **Integer range comparisons** (`>`, `>=`, `<`, `<=`) require a literal inside the field's *signed* range (`INT8`: −128…127, `INT16`: −32768…32767, `INT32`: ±2,147,483,647, `INT64`: ±9,223,372,036,854,775,807). All integer types are stored signed, so a range comparison against a valid integer literal outside that range (e.g. `[Status] > 200` on an `INT8`, or `[Count] < 5000000000` on an `INT32`) has no defined ordering and is rejected with `RANGE_LITERAL_OUT_OF_SIGNED_RANGE` — rather than silently matching no rows — whatever the literal's width (`[Id] < 99999999999999999999` included) and in every position: a `WHERE` leaf, a `BETWEEN` bound, a `CASE` condition and a projected comparison alike. Equality against an out-of-range literal is still allowed and exact: no stored integer equals it, so `=` and `IN` match no row while `!=` and `NOT IN` match every row, a NULL value included (equality is NULL-safe), in `WHERE` and in `CASE` alike (except for the `INT8` / `INT16` bit-pattern case which can match). For native equality predicates, `200` or `'2E+2'` matches stored `INT8` `-56`, and `40000` matches stored `INT16` `-25536`, including primary keys and temporal queries. Bound parameters still require the signed range, even when supplied as strings; see [parameter validation](parameters.md).

## Logical operators

`NOT` binds more tightly than `AND`, which binds more tightly than `OR`. Use parentheses for grouping:

```sql
WHERE [Status] = 'active' AND [Price] > 100
WHERE [Status] = 'active' OR  [Status] = 'pending'
WHERE ([Status] = 'active' OR [Status] = 'pending') AND [Price] > 0
```

`NOT ([Price] > 100)` negates a predicate. NULL ordered comparisons remain unknown under `NOT` and do not match. Equality keeps MQL's null semantics: `NULL = NULL` is true, while `NULL !=` a non-null value is true.

Scalar expressions work on either side of comparisons, including function calls, arithmetic and ordinary field references:

```sql
WHERE LENGTH([Name]) >= 4 AND [Price] > [Cost]
WHERE NOT (ABS([Price] - [Cost]) < 1 OR [Name] IS NULL)
```

The same expression forms work in DML `WHERE`, `HAVING`, and aggregate `FILTER`. WHERE filters rows before grouping and windows; HAVING filters grouped rows; FILTER controls the input of its own aggregate. Indexable AND conjuncts remain eligible for source index scans; the scalar remainder streams over candidate rows.

Scalar WHERE expressions can read a compatible subtype leaf beneath differently shaped parent Objects, regardless of subtype declaration order. A subtype without that leaf supplies NULL. Unknown or incompatible leaves fail before row evaluation, including for empty inputs and static EXPLAIN. Boolean branches retain ordinary short-circuiting; filtering does not add private fields to the selected row shape.

**OR-to-IN optimization** — multiple OR conditions on the same field (`[Status] = 'a' OR [Status] = 'b' OR [Status] = 'c'`) are automatically converted to a single `IN` predicate. Cross-field OR (`[A] = 1 OR [B] = 2`) is supported — each branch is evaluated independently and a document matches if any branch is satisfied. AND/OR nesting composes freely — a branch may itself be an AND of further ORs (`[A] = 1 OR ([B] = 2 AND ([C] = 3 OR [D] = 4))`); the query normalises to disjunctive groups internally. Works in SELECT, UPDATE, DELETE, and REPLACE WHERE clauses.

A single statement's expression trees are capped at **256 binary/logical operators total** (parenthesis nesting is separately capped at 100 levels). The count covers every `AND` and `OR` and every binary operator of a scalar expression (arithmetic, `||`, and a comparison inside `CASE`, a projection or a computed column); the comparison a `WHERE` predicate makes is not counted, so `[a] = 1 AND [b] = 2` counts one. This is a denial-of-service guard: a chain far longer than any real query (`[a] = 1 AND [a] = 1 AND …` hundreds of times, or `1 + 1 + …`) is rejected with a catchable `LIMIT_EXCEEDED` parse error rather than being allowed to exhaust the server's stack. Express large value sets with `IN (…)` — one predicate node — instead of a long chain of `OR`/`AND`/arithmetic operators.

The public programmatic AST surface is fail-closed too: scalar expression trees deeper than 512 nodes are rejected before printing, public type inference, or execution. That bound preserves every parser-produced mixed expression (the parser's 100-level nesting and 256-operator limits remain tighter) while preventing a plugin or direct AST caller from bypassing the textual denial-of-service guards. Explicit `IN` / `NOT IN` lists are non-empty and contain at most **32,766 values**, the largest list representable within the 65,536-token statement ceiling. Direct AST validation and evaluation enforce those bounds before traversing entries or the operand, or allocating descriptor state. This does not limit `IN (subquery)` result cardinality: subquery membership uses an admission-controlled spill-backed set rather than an explicit AST list. Scalar function calls contain at most **32,767 arguments**, the largest call representable within the same token ceiling. A host-registered function may narrow its accepted arity but cannot authorize a larger direct AST; validation rejects the count before traversing arguments or renting an evaluation buffer. `CASE` expressions contain between 1 and **16,383** `WHEN` branches. The upper bound is the largest searched `CASE` representable within the same token ceiling; direct AST validation and evaluation reject an invalid count before branch traversal.

## Nested field access

WHERE resolves source aliases and collection qualifiers before looking up the field. Stored collections use their captured declarations; derived queries and CTEs use their emitted schema and retained subtype declarations. `Body` is an optional prefix only when the source has no declared Body root, including in its subtypes. A real Body root owns the complete suffix: `[Body].[Code]` reads that nested child, and a missing child cannot fall back to `[Code]` or slot metadata. Ordinary predicates, IN-subquery target types and EXPLAIN use the same field identity. Reusing a prepared query after replacing the collection binds against the replacement schema.

JOIN ON key paths use the same rule after their relation qualifier is selected. With a stored Body Object, `[r].[Body].[Code]` matches on that child's value; a missing child cannot borrow the root `[r].[Code]`. When no base or subtype Body root is declared, `[r].[Body].[Code]` remains shorthand for `[r].[Code]`. Native execution and EXPLAIN admit the same key declaration. A virtual computed inner key is evaluated before matching, even when SELECT only returns outer fields. Generated inner residual conditions likewise observe computed values through their already-bound source paths.

A plain nested SELECT path retains its complete parent container. Every named child must exist in the declared base or a subtype, even though the complete parent is returned. Dotted Array child paths permit implicit element navigation. A missing child or scalar traversal fails query and schema-only validation. Every computed child in that emitted container is evaluated, including siblings of the explicitly selected leaf. An aliased source has the same result shape. Use a scalar expression alias to return only the leaf as a separate column. Computed aliases must also be distinct from the emitted parent name. Selecting `[Detail].[Code]` beside `9 AS [Detail]` is a duplicate-column error, even on empty input. Selecting different plain children of `[Detail]` still emits one complete `[Detail]` container.

A direct pinned-reference projection, such as `SELECT [Ref]`, `SELECT *` or the alias `SELECT [Ref] AS [Alias]`, returns the complete stored pin: the result field keeps the key type and its reference metadata, is marked as a pinned reference, and holds both the identifier and the stored revision. This also holds beside scalar subqueries or window functions, across alias chains, through views and CTEs, in RETURNING, and in JOIN output. The typed .NET client reads such a field as `PinnedRef<TKey>`, and Studio shows it as `PIN(id, revision)`, the literal that writes it. `[Ref].[Id]` projects the identifier alone as a plain value of the key type, and `[Ref].[Revision]` the revision as `INT64`. Ordinary scalar expressions over the reference, such as `CAST([Ref] AS STRING)`, continue to use its identifier.

<a id="createdby-attribution-columns"></a>

A result column that holds a row's [CreatedBy attribution](dml.md#createdby-attribution) is marked as one in the result schema, so a client can tell its bytes are an actor and decode them by the database's [CreatedBy policy](maintenance.md#set-createdby) (`[Mnemic].[CreatedBy]`): `[Meta].[CreatedBy]` itself, and every column that passes its bytes through unchanged, such as the alias `SELECT [Meta].[CreatedBy] AS [Author]`. The mark follows the value as a pin's does, across alias chains, `SELECT *` and the `[Meta]` object, beside scalar subqueries and window functions, through views, materialized views, CTEs and derived tables, in the FROM side's metadata of a JOIN, as a GROUP BY key, under `SELECT DISTINCT` and in RETURNING. A set operation's column (`UNION`, `INTERSECT`, `EXCEPT`) is marked only when every branch's column is, and a [recursive CTE](cte.md#recursive-cte)'s column only when its seed's column is and its recursive member's column is on every level: a member column that passes the frontier's column through (`[t].[Author] AS [Author]`) is marked only where that column of the CTE is, and a member that reads the frontier's rows keeps the mark only on a column that names one field of a relation directly, as a plain item or its `AS`, not through another item's alias. A value an expression computes carries no mark even when it holds the same bytes: `CAST`, `COALESCE`, `CASE`, any other function, an aggregate (`MIN`, `MAX`, the elements of `COLLECT_ARRAY`), a window function (`LAG`) and a scalar subquery. The mark is the result field's `IsCreatedBy` flag (`SchemaField.IsCreatedBy` in .NET), in process and over TCP alike.

Single-source SELECT fields and expressions accept source aliases and bare or namespace-qualified collection names. The source qualifier is resolved first, then Body is shorthand only if that source has no declared Body root, including in a later subtype. With alias `[r]` and a stored Body Object, `[r].[Body].[Code]` reads its nested Code; `[r].[Code]` reads the root Code. A declared Body owns a missing child too: the path cannot borrow a same-named root field. Plain projection rejects that missing path; an ordinary scalar expression retains its existing NULL behavior for a missing input.

Without a declared Body root, `[r].[Body].[Detail].[Code]` and `[Body].[r].[Detail].[Code]` name the source's Detail.Code. A plain selection retains the complete Detail parent in authored item order; `AS` emits the selected field separately. An explicit alias named `[Body]` still selects the relation: `[Body].[Code]` reads its root Code, and `[Body].[Body].[Code]` reads its stored Body.Code when that Object exists. Buffered and streaming execution, static EXPLAIN, alias dependencies, window inputs and scalar correlation use the same source address. Native plain JOIN fields preserve this alias-before-Body rule for ordinary and polymorphic inputs before grouping and copying their complete parent output. Native merged JOIN ordering uses that same source rule: `ORDER BY [Body].[Body].[Code]` with alias `[Body]` sorts the stored nested Code, while `[Body].[Code]` sorts the root Code, even when SELECT is omitted. A missing nested sort field cannot borrow a same-named root. Over a join, a key spelled through Body, in any case, names a computed output only where no joined relation declares a Body root: `ORDER BY [Body].[Total]` then sorts by `... AS [Total]`, its children included, on every route and projection shape, a `SELECT DISTINCT` whatever identities its projection captures (a polymorphic or APPLY relation, a window or nested query item, `NEAREST` and `LAST PER` included), as over a single source, while where a relation declares one it names that root's child (`Cannot sort by 'Body.Total': field does not exist in the joined result schema.` when the root declares none, or, under `DISTINCT`, `... in the SELECT DISTINCT result schema.` when no selected path names it). Computed enrichment preserves it, so qualification cannot expose the stored NULL placeholder of a virtual field. A plain nested selection also computes virtual siblings in the complete parent it returns. For example, if Body contains stored Source and computed Derived, `SELECT [Body].[Source]` returns Body with both values. `SELECT [Body].[Source] AS [Value]` returns only the stored leaf and does not require its computed sibling. Ordering by the source's Body.Derived computes that value even when SELECT omits it; EXPLAIN reports the same enrichment requirement.

For collection-level subtypes, computed enrichment preserves access to base and extension values through filtering and plain or scalar SELECT projection. A nested scalar operand uses its active subtype's object layout, even when another subtype declares the same leaf inside a differently shaped object. Absent extension values become NULL. Row-wise polymorphic CTE filtering and projection stream; ordering and total-count requests use bounded spill-capable state rather than requiring the complete source to fit in memory.

Use dot notation for nested object fields:

```sql
WHERE [Address].[City] = 'Stockholm'
SELECT [Address].[City], [Address].[Zip]
ORDER BY [Details].[Priority] DESC
```

The canonical spelling brackets each path segment separately, but compact single-token paths remain accepted: `[Address.City]` normalizes to `[Address].[City]`, and `[Items[]]` normalizes to `[Items][]`. Empty logical segments such as `[Address..City]` and nested bracket syntax inside one path token are rejected.

Selecting an `ARRAY OBJECT` child path validates that the child exists and projects the complete parent array, preserving element boundaries and sibling fields. For example, `SELECT [Items].[Name]` returns the `Items` array shape; `SELECT [Items].[Missing]` is an error.

<a id="array-element-paths-read-no-single-value"></a>

An array element path (`[Items][]`, `[Items][].[Name]`, `[Matrix][][]`) is a predicate operand, never a single per-row value: it addresses every element, while a projection, a key or an operand reads one value per row. Each of these positions rejects it with `FEATURE_NOT_SUPPORTED` before any row is read, also by `EXPLAIN`, a write, and a view, materialized view, trigger, computed column or `CHECK` definition:

| Position | Example |
|---|---|
| Projected column — plain or `DISTINCT` SELECT item, nested `IN` or derived query column, `RETURNING` item | `SELECT [Items][]` |
| `GROUP BY` key, plain or inside an expression | `GROUP BY [Items][].[Sku]` |
| `ORDER BY` key — query, set operation, `DISTINCT`, aggregate-local ordering | `ORDER BY [Tags][]` |
| Window `PARTITION BY` or `ORDER BY` key, inline or in `WINDOW` | `OVER (PARTITION BY [Tags][])` |
| Aggregate or window function argument | `COUNT([Tags][])`, `MIN([Items][].[Sku])` |
| Function argument, operator operand, `CAST` operand, `CASE` result | `UPPER([Tags][])`, `[Code] \|\| [Tags][]` |
| `SET` or `ON CONFLICT DO UPDATE SET` value, array-edit position | `SET ([Name]: [Tags][])` |
| Computed column expression | `[First] STRING AS ([Tags][])` |
| `JOIN` key, `NEAREST` vector | `ON [i].[Tags][] = [d].[Code]` |
| Outer reference — an enclosing row's field read by a nested query | `WHERE EXISTS (FROM [App].[Docs] [d] WHERE [d].[Code] = [i].[Tags][])` |

The message names the position: `Array element path '[Tags][]' cannot be an ORDER BY key: ordering compares one value per row and an element path addresses every element. Use a scalar field instead, or test the array's elements in a predicate (WHERE, MATCH, LENGTH(...)).` A projected element path reads `cannot be projected: a projection emits one value per row …` and suggests projecting the array field (`[Items]`) instead.

An element path keeps its meaning where it is tested: the element side of a comparison (on either side, with an optional trailing `ANY` / `ALL`), `IN`, `LIKE`, `CONTAINS`, `STARTSWITH`, `BETWEEN` and `IS [NOT] NULL`, in `WHERE`, `HAVING`, aggregate `FILTER`, `CASE WHEN`, computed and `CHECK` expressions; `MATCH`; a counted `LENGTH(element predicate)`; the target of a wildcard `REPLACE` and the per-element expression it maps; and array-element index keys. The other operands of such a predicate are values, and a value may be a field of the same row or an expression over fields: `[Tags][] = [Name]`, `[Name] = [Tags][]`, `[Tags][] > [Low] + 1`, `[Tags][] IN ([Name], 'x')` and `LENGTH([Tags][] = [Name]) > 0` compare each element with that row's value. A second element path is no value: `[Tags][] = UPPER([Items][].[Sku])` is rejected. A trailing `ANY` / `ALL` or a `MATCH` body tests the elements against values fixed for the evaluation, so its operands cannot be fields of the filtered row ([quantifier operands](arrays.md#quantifier-and-match-operands)). A nested query binds one value of its enclosing row, so an outer row's element path is no outer reference. See [Array queries](arrays.md). INSERT values reject every field reference (`INVALID_STATEMENT`), and a partial index filter rejects array-traversing paths with its own message.

The virtual `[Meta]` object on every result row uses the same dot notation — see [Query metadata](system-collections.md#meta-fields).

`ORDER BY` rejects fields absent from its applicable source or output schema, including on base collections, virtual results, and joins. A computed SELECT alias takes precedence over same-named source fields; qualifying a source field retains that source identity, including when the source field is itself virtual computed. Explicit source qualification in SELECT expressions and ORDER BY continues to refer to the source when SELECT publishes an alias with the same name. A computed Object alias retains its children too: after `SELECT [Detail] AS [Body]`, `ORDER BY [Body].[Code]` reads that output child, unless Body is an explicit source qualifier in the query. EXPLAIN, saved views, and nested queries use the same binding rules. String sort fields retain Unicode scalar order after invariant lowercasing in every tuple, including when another field is a GUID. Full, partial, in-memory, and spilled sorts use the same order.

One query-level `ORDER BY` may contain at most 64 fields.

## JOIN

```sql
-- Inner join (JOIN without prefix = inner; INNER JOIN is an accepted synonym)
FROM [Orders].[Orders] [o]
JOIN [Store].[Products] [p] ON [o].[ProductId] = [p].[Id];

-- INNER JOIN — explicit synonym for plain JOIN (PostgreSQL portability)
FROM [Orders].[Orders] [o]
INNER JOIN [Store].[Products] [p] ON [o].[ProductId] = [p].[Id];

-- Left join (unmatched outer rows included with null inner)
FROM [Orders].[Orders] [o]
LEFT JOIN [Store].[Customers] [c] ON [o].[CustomerId] = [c].[Id];

-- Suppress the joined relation's duplicate key from wildcard output
FROM [Orders].[Orders] [o]
JOIN [Store].[Customers] [c] ON [o].[CustomerId] = [c].[Id] OMIT INNER KEY
SELECT [c].*;

-- Cross join (cartesian product, no ON clause)
FROM [Config].[Regions] [r]
CROSS JOIN [Config].[Categories] [c];
```

The join condition must be a single field equality (`outer.field = inner.field`). The result schema nests fields under `{ outer: Object, inner: Object? }` (inner is nullable for LEFT JOIN).

The joined relation may be a [`SERIES`](#series) (`JOIN SERIES 1 TO 100 [s] ON [o].[Slot] = [s].[Value]`, `CROSS JOIN SERIES ... EVERY 1 DAY [d]`); its bounds read no field of the joined relations.

`ORDER BY`, `SKIP`, and `LIMIT` apply to the final joined result, not to the outer collection before joining.

A JOIN input is any named read relation: a stored collection, a plain view, a CTE, or a virtual `[Mnemic].*` [system collection](system-collections.md). A derived table is no JOIN input: `JOIN (FROM …) [x] ON …`, and its `LEFT JOIN` and `CROSS JOIN` forms, are parse errors; name the query in a `WITH` and join the CTE, make it the join's `FROM` relation (`FROM (FROM …) [x] JOIN …`), or read it per row as an [APPLY](#cross-apply) body. A system input is the same caller-visible, point-in-time snapshot it yields as a FROM source, read once per statement before join planning, so it takes part in INNER, LEFT and CROSS joins, reordered and bushy join trees, composed joins, APPLY bodies and correlated `EXISTS` / `IN` alike:

```sql
-- Rows whose [Coll] names an existing collection, with its committed row count
FROM [App].[Refs] [r]
JOIN [Mnemic].[CollectionStats] [s] ON [r].[Coll] = [s].[Name]
SELECT [r].[Id] AS [Id], [s].[DocumentCount] AS [Rows];
```

`OMIT INNER KEY` is available after an `INNER JOIN` / `JOIN` or `LEFT JOIN` equality. "Inner" means the relation introduced by that written JOIN, even when its operand appears on the left of `=` or the optimizer changes physical join order. The modifier removes that relation's exact key leaf from an omitted `SELECT`, `SELECT *`, or `SELECT [alias].*`; nested keys retain their parent Object and sibling fields. A key inside a polymorphic object's subtype fields (`ON [o].[N] = [p].[Part].[K]`, where subtypes of `[Part]` declare `[K]`) is the leaf of every subtype that declares its whole path: each of those subtypes loses it, and each value the copy its own subtype holds, while a subtype that does not declare the path keeps its fields and a key among the object's base fields leaves its subtype fields as they are. The object's discriminator (`[p].[Part].[_type]`) is no removable leaf, since its values' subtype fields are read by it: a result that would publish the object without it is refused with `INVALID_STATEMENT`, while one that does not publish the object (an explicit projection, an `EXCLUDE` of its column, a `REPLACE` that supplies the column's whole value) returns the rows the join returns. The leaf is the one the ON key resolves to under the Body rule of [nested field access](#nested-field-access): `ON [i].[Id] = [d].[Body].[Size] OMIT INNER KEY` removes `Size` from a declared Body root of `[d]`, while without one `[d].[Body].[Id]` removes `[d]`'s `Id`. An explicit projection such as `SELECT [c].[Id]` still returns the key. Over a polymorphic relation the modifier removes the leaf from the fields a result publishes, while that relation's private `Envelope` stays its byte-exact original row, the key included. A result that does not publish the key as a field (a compatible leaf under a root the subtypes declare differently, or a subtype field of a CTE or derived relation, which its implicit row carries only in that `Envelope`) returns the rows it returns without the modifier, whatever its projection. An unqualified `SELECT *` with modifiers projects each relation envelope (`outer`, `inner`) as a nullable column without the omitted key, also after `RENAME ([inner] AS [I])`; a `REPLACE` of an envelope supplies its whole value.

Omission changes only the final result. The complete key remains available to later JOIN edges, `WHERE`, `ORDER BY`, and expressions, and bare same-named fields remain ambiguous. With a qualified wildcard, repeating the omission as `EXCLUDE ([Id])` is harmless, while `REPLACE (... AS [Id])` or `RENAME ([Id] AS [...])` is rejected with `INVALID_STATEMENT` because that slot is no longer in the wildcard result. When the omitted key is nested, as in `ON [d].[Id] = [i].[Dims].[W] OMIT INNER KEY`, `SELECT [i].*` keeps the `Dims` column without `W`; `REPLACE ([Qty] AS [Dims])` supplies that column's whole value, so the omission no longer applies to it, while `RENAME ([Dims] AS [Body])` keeps the omission under the new name. A qualified wildcard that would contain no fields is also rejected with `INVALID_STATEMENT`. `OMIT INNER KEY` is not accepted on `CROSS JOIN` or lateral APPLY and does not consume the 1,024-target wildcard-modifier limit.

JOIN equality follows the same lossless numeric doctrine as `WHERE =`. Compatible numeric fields may use different storage types (`INT32` versus `INT64`, integer versus `DECIMAL`, or exact decimal/binary-float values); the planner's nested-loop, hash, PK-targeting fallback, and bushy shapes all produce the same answer. A mixed numeric edge targeting a primary key uses a scan-based strategy because its common comparison key is not a physical PK encoding. Values are not rounded through `FLOAT64`: integer `9007199254740993` does not join to floating-point `9007199254740992.0`, while decimal `0.5` joins to floating-point `0.5`. JOIN equality is also NULL-safe like `WHERE =`: a NULL key (including a key below a NULL parent Object) matches another NULL key and no present value, under every plan shape — nested-loop, hash, primary-key probe and statistics-selected bushy trees — so a CROSS JOIN filtered by the same equalities returns the same rows. LEFT JOIN still null-extends an outer row only when no inner row matches. Outside the numeric promotion domain, both join keys must have the same scalar type. `OBJECT` and `ARRAY` are not join keys. Incompatible types are rejected before execution; the engine never compares untagged raw bytes from different types, even when their stored byte sequences happen to be identical.

Virtual computed columns are enriched before any JOIN consumer can observe them. A computed-bearing outer is enriched before joining. A physical inner is materialised through the statement-owned, spill-bounded virtual replay only when an ON key, residual filter, ordering, grouping, aggregate, or projection references one of its computed slots. If no consumer references those slots, the inner keeps its ordinary physical scan and index path. An explicit CTE has the same semantics and may still be used to name that boundary. Plain nested projections and `AS` expressions both read those computed values, including when either JOIN input is polymorphic.

For a polymorphic input, each join-key path and every projected or ordered extension path must have one structurally identical schema across the subtypes that declare it. A compatible nested scalar key remains usable in later JOINs even when its parent Object has different sibling fields in those subtypes; the complete Object still requires full structural compatibility for projection. This includes plain JOIN projections, `AS` aliases, and field references nested inside computed JOIN projections. Row-wise `WHERE` and `MATCH` may resolve a same-named path through each row's active subtype, but a join, ordering, or result projection has one fixed schema and rejects an incompatible union instead of decoding the bytes through the first subtype declaration.

When a joined query has `SKIP` / `LIMIT` but no residual post-join filter, field equality, `ORDER BY`, aggregate, total-count request, or projection, pagination is lazy: the executor streams the merged rows and stops reading as soon as `LIMIT` is satisfied. `ORDER BY` and the other whole-result operators still observe the complete joined multiset before pagination.

When the wire/client requests `IncludeTotalCount`, a JOIN reports the complete filtered joined cardinality before `SKIP` / `LIMIT`, just like a base-collection query. For a non-polymorphic left-deep JOIN without aggregation, ordinary post-join residuals are evaluated while the full count is collected in spill-bounded state. Optional `ORDER BY` then uses stable external runs, and plain or computed/`AS` projection is applied after ordering during replay. The page is returned lazily through `RowsAsync`.

For a non-aggregate JOIN tree with polymorphic collections on any side, plain nested and flat computed/`AS` `SELECT`, `SKIP` / `LIMIT`, ordering, and total count all use spill-bounded replay. Envelope-aware post-join predicates (including mixed outer/inner OR groups) run before counting and optional stable external `ORDER BY`, then pagination, with projection applied per emitted row. Subtype fields used by plain columns or expressions on either side are read from that side's original envelope and evaluate to null for rows of other subtypes. A joined polymorphic side is physically materialised as its valid base document plus a private byte-exact `Envelope`; framing bytes are never decoded as base values. Extension sort keys are typed private columns that are removed before projection, and fields declared incompatibly across subtypes are rejected before replay. Filtering, ordering, projection values and shape, and pre-pagination cardinality remain exact. The selected left-deep or bushy tree carries one alias-to-envelope map through every merge. Native WHERE/MATCH reads each predicate's original source and active subtype at any join depth, including a leaf below differently shaped parents. Typed sort and aggregation keys, plain nested projection, flat computed/`AS` projection, and scalar expressions still require one compatible complete declaration. Aggregate FILTER retains its native or scalar predicate domain. Unmatched LEFT sides remain `NULL`: native `= NULL` matches an absent owner, absent subtype member, NULL parent or NULL leaf; `!= NULL` requires a present value. These filters run before count, aggregation, ordering and paging under both ordinary groups and over-budget Boolean execution. Flat projection and top-level AND field equality use the same declared field domains in execution and `EXPLAIN`. Enum labels and structured conditional results retain the metadata of the admitted field, including when a compatible leaf sits below differently laid-out subtype parents.

For a statistics-selected bushy plan, a non-aggregate result is also replayed lazily from spill-bounded state. When total count is requested, residual predicates filter into a second bounded buffer whose cardinality is reported before pagination. Residual `WHERE` predicates and `SKIP` / `LIMIT` retain the same logical order; `ORDER BY` uses stable external runs, and both flat computed/`AS` and plain nested projection are evaluated per emitted row. For a flat aliased projection, this changes memory use and first-row delivery, not the result multiset, ordering, or output schema. An unprojected result or plain nested projection exposes the selected plan's `{outer, inner}` tree; use `AS` aliases when the wire schema must remain independent of plan choice.

Before any rows result is published, Mnemic validates and snapshots its complete schema and polymorphic subtype metadata. Unrepresentable nesting, cyclic or malformed field graphs, and duplicate field/subtype identities fail as a query error before a live row stream crosses the client boundary.

**Aliases must be distinct.** A JOIN alias that repeats the FROM alias or an earlier JOIN's alias is rejected at parse time (`SYNTAX_ERROR`: `JOIN relation qualifier 'a' collides with an existing qualifier in the FROM clause at position N. Pick a distinct alias for each joined relation.`) — a duplicate would be silently ambiguous, with the ON clause binding the alias to the earlier source and later clauses binding it to the newer one. Self-joins use two distinct aliases for the same collection (`FROM [T].[A] [a] JOIN [T].[A] [b] ON ...`).

A query accepts at most **16 JOIN / APPLY clauses**. Joined rows use a nested `{outer, inner}` binary layout: a result nests each relation's own layout (up to the 16 levels a schema allows, its `Meta` object included) beneath one envelope level per edge, so a read at the limit returns its whole envelope without a flat `SELECT` whatever its relations nest, while the bound keeps left-deep planning and row-copying work bounded. The bushy optimizer uses a tighter internal planning bound and falls back to the left-deep order when that bound is exceeded.

**Qualified ON keys bind to the named relation.** Every alias-qualified outer key in a JOIN chain is validated against that logical relation before the planner reorders or nests the joins. A missing field is an error even when another already-joined relation has a field with the same leaf name; the qualifier is never discarded to capture that other field. Inner keys and outer/inner equality-domain compatibility are validated before execution too. A leading path segment is an ON qualifier only when it names the FROM alias, a prior JOIN alias, the current JOIN alias, or an unaliased CTE relation at any of those positions. Otherwise the whole operand remains an unqualified nested path: `[bogus].[AId]` binds as `bogus.AId`, never as the root field `AId`, and schema validation reports it when that path does not exist. A collection name is not an ON qualifier either: with `FROM [App].[Orders] [o]`, `[Orders].[Id]` is the path `Orders.Id`. An unqualified outer key reads the FROM relation on the first edge; on a later edge it reads the one earlier relation that declares its complete path, so a key two earlier relations declare is `AMBIGUOUS_FIELD` and one none declares is an unknown outer field; a merged-row spelling such as `[outer].[Id]` is such an unqualified path, never a row address. A stored relation joins on its body, so an ON key under its `Meta` root is an unknown field in every spelling (a CTE or derived relation's produced `Meta` column is an ordinary column). Native and composed joins, statement validation and `EXPLAIN` apply the same rule, and name a missing or incompatible key relative to the relation that owns it. When both operands have recognised qualifiers, one must name an outer relation and the other the current inner relation; two prior aliases or two current-inner references are parse errors. The current inner qualifier may appear on either side of `=`. With one recognised qualifier, the unqualified operand takes the opposite side; with two unqualified operands, the left key remains outer and the right key inner. The direct .NET AST execution surface enforces the same ordered scope: a non-null `JoinClause.OuterAlias` must name the FROM relation or a prior JOIN. Unknown programmatic qualifiers are rejected rather than captured by the first outer source, and duplicate programmatic relation qualifiers are rejected rather than overwriting an earlier binding.

Execution and `EXPLAIN` check the complete relation-relative ON key. For example, `[s].[s].[Code]` reads `s.Code` inside relation `s`; its Object root is not another qualifier. When a key traverses polymorphic subtypes, every subtype that declares the key must give it the same structural schema. A subtype that omits the key does not invalidate the others. Conflicting declarations are rejected even for empty inputs, before a result is published.

Planning preserves those same relative paths. A nested key such as `Detail.Id` does not inherit the uniqueness of an unrelated root `Id` primary key when estimating join fan-out or choosing relation order.

**Metadata belongs to the outer row only.** `[Meta].[ValidFrom]`, `[Meta].[ValidTo]`, `[Meta].[Revision]`, `[Meta].[CreatedAt]`, `[Meta].[CreatedBy]`, `[Meta].[Sealed]`, and `[Meta].[SchemaVersion]` from the `FROM` side remain usable in post-join `WHERE`, field equality, `ORDER BY`, plain or computed `SELECT`, and aggregate arguments, also through the raw merged-row path that holds the `FROM` relation (each JOIN nests the relations before it under `outer`): `[outer].[Meta].[Revision]` after one JOIN, `[outer].[outer].[Meta].[Revision]` after two. An inner-side reference such as `[p].[Meta].[Revision]` is rejected explicitly with `FEATURE_NOT_SUPPORTED`, naming the path as written, wherever a clause reads the joined rows: a plain, `DISTINCT`, computed or wildcard `SELECT`, a `WHERE` leaf, expression, field equality or nested query's correlated reference, and an `ORDER BY` key the joined rows are sorted by, whether the path names its relation by alias, by collection name (`[Products].[Meta].[Revision]`) or by a raw `inner` row path, and whether or not the join is composed over its merged rows (below). A raw `outer`/`inner` spelling in `WHERE` (a comparison with a value, a field-to-field comparison or an expression) names the relation its written-order placement holds (each JOIN nests the relations before it under `outer` and its own input under `inner`), exactly as that relation's alias would, whatever join order the planner chooses and whether or not the join is composed over its merged rows; it is never stripped or re-prefixed to search another relation, so a field only another relation declares is absent from it. Join rows do not carry an independently addressable inner metadata envelope. Statement validation, `EXPLAIN` and execution report the same error. Clauses that read a completed relation see only its columns: in the `ORDER BY` of a `DISTINCT` or grouped result, in `HAVING`, and as a grouping key or aggregate argument, an inner `Meta` path is an unknown field (`UNKNOWN_FIELD`). A join composed over its merged rows (a derived `FROM` input, a scalar or negated `WHERE`, APPLY, a window, `LAST PER` under any projection, a `WHERE` that reads the joined relations from a correlated subquery, whether the engine evaluates it per joined row or rewrites it into set-wise joins over the composed rows, or a consumer that composes the joined rows with their `WHERE` before it reads them: `SELECT` aliases that depend on one another, a `GROUP BY` expression or an aggregate over an expression, `NEAREST`, and a wildcard projected in written order, as an item list holding a wildcard, nested wildcard modifiers or `SELECT DISTINCT *` is) rejects the inner `Meta` path with the same `FEATURE_NOT_SUPPORTED` text. Put that inner read in a CTE and project the needed metadata column before joining when it is needed.

**Relation qualifiers select one relation on every path.** A relation's qualifier is its explicit alias or, for an unaliased CTE reference, the CTE name. It owns its spelling across the whole statement: `ON`, `WHERE`, plain, nested and `AS` `SELECT` items, `ORDER BY`, `GROUP BY`, aggregates and static schema discovery bind it to the same relation, whatever join order or bushy tree executes. Outside `ON`, a spelling that is not a qualifier but is a relation's short or full collection name — or the CTE name of an aliased CTE reference — selects the latest relation carrying it; inside `ON` only a qualifier names a relation, and such a spelling is read as a nested path (`UNKNOWN_FIELD` when the relation has no such Object). Both are resolved before any bare field lookup, so an Object field with the same name on another relation cannot capture the reference; `[d].[Items].[Name]` addresses such an Object explicitly. A qualifier that spells another relation's short collection name claims it, so in `FROM [App].[Nums] JOIN [App].[Pairs] [Nums] ON [Id] = [Nums].[Id]` the spelling `[Nums]` names `[App].[Pairs]` and `[App].[Nums].[W]` names the `FROM` relation, in every clause, in a nested query's outer reference and over a computed field alike.

**Unqualified field references must be unambiguous.** A bare field name in a post-join `WHERE` / `ORDER BY` / `SELECT` binds to the single joined collection that carries it; when two or more sides carry the name, the statement errors with `AMBIGUOUS_FIELD` (PostgreSQL 42702 `ambiguous_column` parity) instead of silently picking a side — qualify the reference with the collection alias (`[a].[Label]`). A bare name carried only by a joined (inner) collection binds to that collection, including in `WHERE`. An alias-qualified reference stays bound to that exact collection under every plan shape, including a statistics-selected bushy plan; colliding names on other relations do not make it ambiguous. Qualification is never discarded to bind a same-named field on a different joined relation.

**A name the relation does not declare is an error in every clause.** A JOIN refuses a name the relation it names does not declare with `UNKNOWN_FIELD` on every route it runs (native, composed over its merged rows, `LAST PER`, `NEAREST`, APPLY, a derived or CTE input), exactly as a single source's `WHERE` refuses one, in every clause that reads the joined relations: every `WHERE` form (a comparison with a value, `IS NULL`, `IN`, `LIKE`, `STARTSWITH`, `MATCH`, `NOT`, either side of an `OR`, an expression, a field-to-field comparison, a conjunct beside a correlated subquery and the subquery's correlated reference), `SELECT` items and expressions (a window's keys and arguments included), `ORDER BY`, `GROUP BY` keys and expressions, aggregate arguments and `FILTER`, and the `NEAREST` field. A name is undeclared when no subtype of the relation it names declares it, when a derived or CTE input does not publish it as a column, when the `FROM` relation carries no such metadata member (`[i].[Meta].[Nope]`), when the relation a raw `outer`/`inner` spelling's written-order placement holds does not declare it, or, unqualified, when no relation declares it. A leading segment that is no relation qualifier, collection name or declared root is part of that unqualified name, never a qualifier to strip: with no relation `[x]`, `[x].[Code]` is `UNKNOWN_FIELD` in every clause, never another relation's `Code`. The diagnostic is the native join's for its clause and names the field as written: a `WHERE` leaf reports `Query filter field 'Nope' does not exist in the collection schema.` (relative to its relation), a top-level field-to-field comparison `WHERE field-to-field equality references 'd.Nope', which does not resolve in the joined result.`, an expression `Unknown field 'd.Nope' in WHERE expression.`, a `SELECT` input of a flattened projection (any `AS` or computed item, a `DISTINCT`, or a join composed over its merged rows, which publishes flat columns) `SELECT field 'd.Nope' could not be resolved in the joined result. Use alias-qualified paths (e.g. [alias].[Field]).`, a plain nested projection's path its layout's own text relative to the relation's envelope, as a single source's plain item reports it (`Column 'Nope' does not exist. Available columns: ...`, listing the envelope's declared fields), an `ORDER BY` key `Cannot sort by 'd.Nope': field does not exist in the joined result schema.`, an APPLY body's outer reference `Unknown outer field 'd.Nope' in subquery.` (a `WHERE` subquery's `... in predicate subquery.` or `... in scalar subquery.`), a grouping key or aggregate input `GROUP BY field 'd.Nope' does not resolve in the joined result.` (`Aggregate Sum field 'd.Nope' ...` for an operand or an input of its expression), and, beside `GROUP BY`, a `SELECT` item or expression reading a child a grouping key does not declare `SELECT field 'd.Dims.Nope' does not exist in the source schema.`; an inner relation's metadata is the `FEATURE_NOT_SUPPORTED` refusal above on each of them. It is reported in its clause's order: a `WHERE` leaf's before the leaf's operator or value checks (a nested query's arity or own mistake, a parameter's value), grouping keys in written order and then each aggregate's inputs after the `WHERE`, and before a `LAST PER` sampled-term refusal. Validation does not depend on the rows: an undeclared name is an error even on empty input, and a mixed OR expression retains its complete post-join admission, including an inner leaf that is always false. A declared field a row lacks still reads NULL: another subtype's field (also unqualified where the subtypes declare its parent differently, as in `[Spec].[Load] IS NULL`), a LEFT JOIN's null-extended side and a NULL value, so `[d].[Code] IS NULL` matches those rows. A single source's computed `SELECT` item, and its grouped `SELECT` expression over a child a grouping key lacks, keep reading an undeclared input as NULL ([nested field access](#nested-field-access)). Execution and EXPLAIN apply the same source-ownership rule. When a cross-side OR forces an outer-qualified predicate to run post-join, the qualifier remains exact for both scalar fields and MATCH array paths. This also applies to polymorphic extension fields that are not present in the merged physical schema: a same-named field on another relation cannot capture the reference during remapping. Native post-join `WHERE` and MATCH bind qualification once against the original source declarations. A recognised alias, including an alias named `Body`, first selects its relation. Within that source, one leading `Body` segment is shorthand only when no original declaration supplies a real Body root. A declared root in any subtype claims its complete suffix: a missing child cannot fall back to a same-named root field or another relation. Prepared paths and MATCH element paths are then exact; the chosen physical JOIN tree does not reinterpret them. The same source paths determine metadata preservation and computed-field preparation, so equivalent predicate spellings observe the same prepared values.

Bound parameters in native post-join `WHERE` predicates and OR groups are validated against the selected original declaration domain on every execution, including plan-cache hits. All declaring subtype candidates participate. A parameter must be accepted by at least one applicable candidate; each row then uses its active field type for comparison. A value that cannot compare with that row's active type does not match it. The merged presentation schema cannot hide a declaring subtype or replace its type with a copied field. Fixed scalar expressions retain their separate compatible-declaration requirement.

**Multi-join chain** — aliases remain in scope for every subsequent JOIN and for post-join clauses:

```sql
FROM [Orders].[Lines] [l]
JOIN [Orders].[Orders]    [o] ON [l].[OrderId]    = [o].[Id]
JOIN [Shop].[Products]    [p] ON [l].[ProductId]  = [p].[Id]
LEFT JOIN [Shop].[Customers] [c] ON [o].[CustomerId] = [c].[Id]
WHERE [o].[Status] = 'shipped' AND [p].[Category] = 'Electronics'
ORDER BY [o].[PlacedAt] DESC
SELECT [o].[Id], [p].[Name], [l].[Quantity], [c].[Name];
```

**Temporal JOIN propagation** — `AS OF` on the outer applies to inner temporal collections automatically, including composed and NEAREST queries:

```sql
-- Historical snapshot of orders joined against the tariff that was active back then
FROM [Orders].[Orders] [o] AS OF '2024-06-01T00:00:00Z'
JOIN [Billing].[Tariffs] [t] ON [o].[TariffId] = [t].[TariffId]
SELECT [o].[Id], [o].[Total], [t].[Name];
```

Only `AS OF` propagates, and only from the query the `JOIN` is written in. Under `IN BETWEEN`, with or without `LAST PER`, a joined temporal collection reads its current versions, not the version each range row was valid at; a derived `FROM`'s `AS OF` stays inside its body, so `FROM (FROM [A] AS OF @t) [a] JOIN [B] ON …` reads `[B]` current ([temporal](temporal.md#in-between-temporal-range)). [Read sources](read-sources.md) report each read's versions.

**Extra equi-join in WHERE (field = field)** — a top-level `WHERE` equality between two **different** joined aliases (`[a].[k] = [c].[k]`) is an extra join condition, not a row-vs-literal filter. It's how you express a join graph with a redundant edge (a *cyclic* graph — e.g. three collections pairwise joined). Ordinary field comparisons, such as `[Price] > [Cost]`, also work on a single collection, in DML WHERE, HAVING, and aggregate FILTER. Partial-index predicates retain their separate stored field/literal contract.

```sql
-- Orders whose customer and shipping warehouse are in the same region:
-- the [c].[Region] = [w].[Region] edge closes the triangle o–c, o–w, c–w.
FROM [Sales].[Orders] [o]
JOIN [Sales].[Customers]  [c] ON [o].[CustomerId]  = [c].[Id]
JOIN [Sales].[Warehouses] [w] ON [o].[WarehouseId] = [w].[Id]
WHERE [c].[Region] = [w].[Region]
SELECT [o].[Id], [c].[Name] AS [Customer], [w].[Name] AS [Warehouse];
```

**Cost-based join ordering (all-INNER).** The planner chooses physical order and shape while preserving every relation dependency and alias binding. The left-deep path uses bounded exact search over dependency-respecting prefixes; a separate connected-subgraph search can pick a **bushy** plan — joining two sub-results independently — for either an acyclic or cyclic graph when that shape has lower estimated intermediate work. Ordering is automatic; written `JOIN` order does not affect matched tuples. Fresh NDV statistics guide both searches; stale NDV is ignored and current collection cardinality is used as fallback. Run `ANALYZE` on joined collections for better estimates. Qualified `WHERE`, `ORDER BY`, and `SELECT` references resolve to the same relation in left-deep and bushy execution, and so does a raw `[outer]`/`[inner]` path in any clause: it names the relation written at that position (in a join of three, `[outer].[inner]` is the second). A raw or plain nested JOIN result follows the selected physical `{outer, inner}` tree; flatten fields with `AS` for a plan-independent output schema. A result whose `ORDER BY`, `SELECT` or wildcard modifiers read a raw path keeps written order, and so does the same result read as a relation (a derived table, a CTE or view body, a set-operation branch), so `[d].[outer].[inner].[x]` names the second written relation whatever plan runs.

Bushy execution pushes a `WHERE` predicate into a leaf scan only when that predicate binds to exactly one relation; the complete predicate is still checked after the join. Mixed-relation OR groups remain post-join. Each bushy hash-build table participates in admission control and spills above `EngineOptions.MaxInMemoryStreamingState`; cumulative spill bytes are reported by `EXPLAIN ANALYZE` / slow-query instrumentation like other buffered operators. GROUP BY / aggregate queries feed bounded row storage directly into hash aggregation; a second full-result input copy is not created, and input spill bytes remain visible on the result. Post-join AND/OR predicates and residual field equalities are evaluated together in one bounded replay first. For unsorted, unprojected left-deep JOIN results with `SKIP` / `LIMIT`, ordinary post-join residuals run directly on the row stream. Production stops at the requested filtered window rather than buffering the complete join. Non-aggregate left-deep JOIN `ORDER BY` uses the stable external sorter shared with bushy joins and set operations. It spills above `EngineOptions.MaxInMemoryStreamingState`, then applies `SKIP` / `LIMIT`. If spill replay and reader cleanup both fail, the replay failure (including cancellation or detected corruption) remains the primary cause and the complete cleanup failure set follows it; cleanup never replaces why the query aborted.

**Flat output with `AS` in joins.** A join `SELECT` that renames a column (`[a].[Field] AS [X]`) or computes one (`[a].[Price] * [b].[Qty] AS [Total]`) emits a **flat** top-level column per item — not the nested `{ outer, inner }` shape. A *plain* (un-aliased) join `SELECT` keeps the nested shape for back-compat; adding any `AS` item flattens the whole list. Qualify colliding field names with `AS` (e.g. `[a].[Id] AS [AId]`). A plain `SELECT DISTINCT` over a join and a join composed over its merged rows publish the same flat leaf-named columns, so two selected paths with one leaf (`SELECT DISTINCT [a].[Id], [b].[Id]`) fail with `DUPLICATE_NAME` before any input is read, with the same text from statement validation, `EXPLAIN` and execution. A [recursive CTE](cte.md#recursive-cte) member's plain items are flat leaf-named columns too, whichever algebra its expansion runs (`SELECT [n].[Id], [p].[Ref]` publishes `Id` and `Ref`), while a set-operation branch keeps the nested shape, which combines with no flat branch ([set operations](#set-operations--union--intersect--except)). A join whose `WHERE` reads its relations from a correlated subquery is composed over its merged rows whatever its `FROM` input and whether that subquery is rewritten into set-wise joins or evaluated per joined row, so its plain `SELECT` publishes those flat leaf-named columns (and `SELECT [a].[Id], [b].[Id]` fails with `DUPLICATE_NAME`), its implicit row the written-order merged `{outer, inner}` row, and adding an `OR` to the subquery or reading the `FROM` input through a CTE never changes the result's shape. The same flat shape applies when one SELECT alias depends on another. Plain `[a].[Detail].[Code]` publishes `Code`; selecting `[a].[Detail].[Payload]` publishes the complete `Payload` Object with its children. A flat column, plain or `AS`, is NOT NULL only when it reads a NOT NULL field of the `FROM` relation through NOT NULL objects ([direct references](#select-projection)); every joined relation's column is nullable, whichever physical join order runs. Physical, derived and CTE JOIN inputs use the same output names and field domains. A compatible nested subtype leaf keeps its declared type and value through dependent aliases, source or result ordering, windows and scalar correlation, even when the complete parent layouts differ. Empty Objects remain present values; absent subtype members and unmatched LEFT JOIN sides remain NULL. An outer query over the final projection can address only its emitted fields. A derived or CTE source also creates a new scope when importing a raw JOIN: use its published `outer`/`inner` fields, not aliases declared inside that query. Every JOIN projection, native, composed or a dependent alias stage, rejects a computed or plain input its relation does not declare before executing rows; a declared input a row lacks reads NULL. In the nested shape, only requested collection leaves are retained, including through a multi-join tree. A side with no requested fields remains present as an empty object (or `null` for an unmatched nullable inner side); fields from that side are never copied into the result.

```sql
FROM [Sales].[Orders] [o]
JOIN [Sales].[Customers] [c] ON [o].[CustomerId] = [c].[Id]
SELECT [o].[Id] AS [OrderId], [c].[Name] AS [Customer], [o].[Total] * 1.1 AS [WithTax];
-- → flat columns [OrderId], [Customer], [WithTax]
```

## ORDER BY

```sql
ORDER BY [Name] ASC                     -- ascending (default)
ORDER BY [Price] DESC                    -- descending
ORDER BY [Category] ASC, [Price] DESC    -- multiple fields
ORDER BY [Address].[City] ASC            -- nested field
ORDER BY [Meta].[ValidFrom] DESC         -- latest versions first (temporal)
ORDER BY [Meta].[Revision] DESC          -- most recently modified
ORDER BY [Meta].[CreatedBy] ASC          -- unsigned attribution bytes
```

With `GROUP BY`, `ORDER BY` ranks aggregated rows and can reference either a grouping field or an aggregate alias (`ORDER BY [Count] DESC`, `ORDER BY [Revenue] ASC`).

Mixing computed output aliases and source fields in ORDER BY preserves every authored expression input. Internal sort columns cannot replace an absent input or conflict with a declared field, including names that resemble internal columns.

Every query-level ordering key must be a scalar field with a defined total order. An array element path (`ORDER BY [Tags][]`) is never a sort key and is rejected with `FEATURE_NOT_SUPPORTED` ([element paths read no single value](#array-element-paths-read-no-single-value)). BYTES keys use unsigned lexicographic byte order: compare the first unequal byte, or put the shorter strict prefix first. No UTF-8 decoding or case folding occurs. NULL sorts before a present empty byte sequence ascending, followed by non-empty values; DESC reverses this. The same comparison applies to `Meta.CreatedBy`, where absent attribution reads as NULL and empty actor inputs are rejected.

`PINNED REFERENCES` fields order by their referenced identifier. Stored revisions do not distinguish ordering keys, so trailing fields and ordinary tie-breaks still order references to the same id. For pinned BYTES, neither the stored length prefix nor revision participates in byte order; present empty identifiers remain distinct from NULL across full, index-assisted, and spilled sorts.

OBJECT, ARRAY, and VECTOR keys are rejected before result publication, including on empty inputs and grouped, joined, CTE, system-collection, in-memory, and spilled sort paths. Aggregate-local ordering inside `COLLECT_ARRAY` / `JOIN_STRING` is a separate raw-value operation described under aggregates. For vectors, order by a projected distance or an explicit `TO_STRING` result when that scalar order is intended.

A query-level `ORDER BY` accepts at most 64 fields. Text parsing and direct AST validation enforce the limit before execution or child-field traversal.

`NULL` and missing fields sort first ascending (and therefore last descending) — matching standard SQL's `NULLS FIRST` default. Applies uniformly across every sort path. A row whose field holds an extreme stored value (`long.MinValue`, `double.NegativeInfinity`, the empty string) is always ordered *after* a NULL row in ASC, never tied with it.

When a secondary index proves the leading `ORDER BY` field, the executor reuses that order and incrementally sorts each equal-leading run by the remaining fields plus the primary-key tie-break. This applies to bounded ranges and unbounded scans over ordered numeric, date/time, and folded-ordinal `STRING` keys. An unbounded nullable index is eligible only when `WHERE` proves the key non-null (for example `IS NOT NULL`, equality, range, or `IN` without NULL members), because null rows are absent from secondary indexes. This includes a `NOT NULL` leaf beneath a nullable object parent. A partial index is eligible only when the query implies its filter. Mixed trailing directions, floating-point NaN and signed zero, case-insensitive non-ASCII string ties, and paging use the same total comparator as a full sort. Paging never truncates an equal-leading run before the trailing tuple is ordered.

Compound-index plans preserve the same primary-key tie-break and page membership as a full sort. A compound index that appends the primary key after the requested ordering fields still requires final sorting; explicitly including the primary key in a matching `ORDER BY` tuple permits a sorter-free scan.

## SKIP and LIMIT

```sql
SKIP 20           -- skip first 20 results
LIMIT 10          -- return at most 10 results
SKIP 20 LIMIT 10  -- pagination: page 3 of size 10
LIMIT @pageSize   -- parameterised bound
SKIP @offset LIMIT @pageSize
```

`SKIP` accepts integers from 0 through 2147483647; `LIMIT` accepts integers from 1 through 2147483647. Integer-valued floating-point parameters must fit that range before conversion. Fractional values, infinities, NaN, and values outside the range are rejected with `INVALID_VALUE`, a larger whole number included: a literal reports `SKIP value must be an integer, got '2147483648'`, a parameter `LIMIT parameter '@n' of type Int64 cannot be converted to a non-negative integer`.

Pair with `ORDER BY` for stable pagination — without an explicit order, SKIP / LIMIT slices an unspecified ordering. `SKIP 0 LIMIT 1` is the idiomatic "top row after filter" query.

When the client/wire requests `IncludeTotalCount`, `TotalCount` reports the complete result cardinality after `WHERE` / `HAVING` and before `SKIP` / `LIMIT`. This invariant also applies to CTE results, CTE-backed JOINs, `[Mnemic]` virtual system collections, and collections whose filters or sorts require read-time computed-column injection. Projection never changes the reported count. A derived/virtual source's own count is not inherited across the outer query boundary: the outer request recomputes its cardinality, and an outer request that did not ask for a count returns no `TotalCount` metadata. `TotalCount` is either absent or a non-negative cardinality. The wire encodes absence with the single canonical `-1` sentinel; values below `-1` and negative plugin DTO counts are rejected. For a base collection, requesting the count consumes the complete filtered input before paging even when the query is unfiltered. When snapshot isolation is disabled, that scan remains fenced through exhaustion; the reported count and emitted rows therefore cannot come from different concurrent-commit cuts. A `WITH` statement reports the count its main query reports on its own, over recursive CTEs too: a query counts before its `SKIP` / `LIMIT`, a [set operation](#set-operations--union--intersect--except) before its trailing `SKIP` / `LIMIT`, and a nested `WITH` statement as its own main query counts. A derived table's own `SKIP` / `LIMIT` is inside the relation: `FROM (… UNION ALL … LIMIT 2) [d]` counts the two rows `[d]` holds, before the outer query's own `SKIP` / `LIMIT`.

### Paging a statement's result

A client that shows a statement's result a page at a time asks for the page with its request, beside the statement's text, not in MQL: `MqlRequestOptions.Page` (an offset and a limit) on `IMnemicClient.ExecuteMqlAsync`, or the page flag and fields of the `ExecuteMql` frame ([connecting](connecting.md#request-options)). The text is sent as written, so a page adds nothing to it and its own `SKIP` and `LIMIT` keep their meaning.

- **One rule.** The page is rows `[offset, offset + limit)` of the result the statement returns, in the order it returns them, after everything the statement does: its own `ORDER BY`, `SKIP` and `LIMIT`, a set operation's trailing tail, a `WITH` statement's main query, `DISTINCT`, `GROUP BY` and `HAVING`, window functions, `LAST PER`, `SERIES` and `NEAREST`'s `TOP` included. `FROM [App].[Orders] ORDER BY [Id] SKIP 10 LIMIT 50` with the page at offset 20 and limit 100 returns the statement's rows 21 to 50, that is 30 rows.
- **Nothing else changes.** The page changes no column, schema, polymorphic envelope, key role, [read source](read-sources.md) or plan of the statement: a range read's wildcard keeps `Meta` on every page, a window computed over the whole result continues (`ROW_NUMBER() OVER ()` on the second page of 100 starts at 101), and a raw join of two or more edges keeps the envelope its plan publishes.
- **Domains.** The offset is 0 to 2147483647 and the limit 1 to 2147483647, `SKIP`'s and `LIMIT`'s domains; a page past the end returns no rows.
- **Where it applies.** A query, a `WITH` statement or a set operation, with or without a trailing `OPTION (…)` list. Around any other statement (`EXPLAIN`, a write with or without `RETURNING`, DDL, `LIST`, `SUBSCRIBE`, transaction control, a plugin's statement) the request is refused with `FEATURE_NOT_SUPPORTED` before the statement runs.
- **Total count.** With `IncludeTotalCount`, a page's `TotalCount` is the number of rows the statement returns, after its own `SKIP` and `LIMIT`, of which the page is a part; the statement's rows are counted in the same pass that keeps the page's, so the count and the page describe the same rows. Without a page the count stays the statement's own (above).
- **Order.** Pages partition a result only under `ORDER BY`, and each page is a separate execution: writes between pages shift rows, and pages of a statement without `ORDER BY` may overlap or miss rows. Without a count, a streamed page stops reading the statement's rows after its last row.
- **Plans.** Every page of one text runs the plan of the statement without a page: the page enters no plan and no syntax-cache key.
- **Execution interceptors.** A plugin's interceptor is asked for the statement's whole result, uncounted (`IncludeTotalCount` false), and must not page it; the engine cuts the page from the result the interceptor returns, once, and counts it.

## SELECT (projection)

A read's result schema is the statement's statically bound output, the schema static discovery and `EXPLAIN` describe, on every execution. Over one stored collection it carries the schema version of the collection generation the statement read, whatever the projection computes; a foreign-key column carries its target collection's identity and no name, which the `CollectionId` of `[Mnemic].[Collections]` names as the target is called now, also after the target was renamed.

Composed polymorphic wildcards include declared base and extension fields. Over a JOIN or APPLY, a polymorphic relation's qualified wildcard (`[v].*`) expands its declared data fields followed by each extension field its subtypes declare alike, as a nullable column, whether the relation is the FROM input, a joined or an APPLY input, and a stored collection or a derived table, CTE or body that keeps the collection's row; it does so on every route, alone or among other items, composed, as a `DISTINCT` wildcard, with a window `REPLACE` and beside `GROUP BY`, and static discovery and `EXPLAIN` publish those columns as execution does. An extension field its subtypes declare differently is no column of the joined row, so a JOIN relation's wildcard has no slot for it, and an `EXCLUDE`, `REPLACE` or `RENAME` naming it reports an unknown wildcard field; a leaf they declare alike beneath it stays readable by its path. Over a single source, exclude incompatible extension fields or replace them with a uniform expression. Array replacements can read compatible leaves from the original active subtype even when a containing object is excluded because its surrounding layouts differ. Private envelope fields are omitted from composed wildcard output. Trivial physical `SELECT *` retains the source's polymorphic result metadata.

Temporary subtype inputs are private to expression evaluation. An authored field name cannot read such an input because its spelling happens to match an internal name; adding a sibling subtype expression preserves the field's source lookup. Temporary SELECT-alias and source-ordering values have the same isolation: introducing a dependent alias preserves authored input lookup and each clause's existing unknown-field rules after source qualification and optional Body shorthand: a missing source field cannot acquire an unrelated intermediate value.

```sql
-- Flat projection
SELECT [Name], [Price]

-- Nested-field projection (engine promotes the parent Object; client navigates)
SELECT [Address].[City], [Address].[Zip]

-- Metadata projection
SELECT [Id], [Name], [Meta].[Revision], [Meta].[ValidFrom], [Meta].[Sealed]

-- Subtype tag on polymorphic collections
SELECT SUBTYPE, [Make], [Year]

-- Extension fields on polymorphic collections
SELECT SUBTYPE, [Doors], [PayloadTons]
```

Without GROUP BY, omitting SELECT returns all source fields. With GROUP BY, it returns only grouping columns. Projecting a non-existent field errors rather than silently dropping it.

An `AS` alias renames a column and keeps its declaration. A direct field reference under `AS` (`[Total] AS [Amount]`, `[o].[Total] AS [Total]`, `[Address].[City] AS [City]`) publishes the field's type, nested layout and nullability as the unaliased projection of that field publishes them, without the primary-key role or the `AUTOINCREMENT` / `SEQUENTIAL` generation only a key carries; a scalar subquery that projects a key, a joined or `APPLY` column and a CTE or derived column read from one carry no key role either. It is NOT NULL exactly when the field is declared NOT NULL and every row holds it: a field the FROM relation itself declares, reached through NOT NULL objects and no array element. A field only a subtype of a polymorphic source declares, a path through a nullable object or an array, any field of a joined relation (a `JOIN` or `APPLY` input, which an unmatched `LEFT JOIN` or `OUTER APPLY` row leaves NULL), a scalar subquery and every other expression publish a nullable column, and grouping and `DISTINCT` keys keep their nullable key schema. A set-operation branch, a recursive CTE member, a view and a materialized view's backing therefore read `SELECT [Id] AS [Id]` as they read `SELECT [Id]`, and static discovery, `EXPLAIN` and execution publish the same declaration.

A wildcard over a CTE, derived query, or plain view selects its declared data fields. The internal `Meta` object retained for explicit expressions is excluded, including for a bare `SELECT *`. Select metadata explicitly, preferably with an output alias when persisting its value. Static schema binding and execution use the same rule, so composed materialized projections do not store hidden metadata as an ordinary backing field. A direct physical-source wildcard retains its row-metadata presentation, including when computed evaluation uses an internal virtual postprocessor.

Explicit SELECT items retain their written order, including mixtures of plain fields, aliases, aggregates, scalar expressions, and windows. For example, `SELECT [Amount] + 1 AS [Next], [Id]` publishes `Next, Id`. A grouped `SELECT COUNT(*) AS [Total], [Region]` publishes `Total, Region`. Printing, static schema discovery, and execution agree on that order. Nested plain fields still retain their promoted parent, placed at its first selected occurrence. Computed `DISTINCT` deduplicates the selected values before final ordering, paging, and total-count reporting; unselected source fields do not distinguish otherwise equal results. Ordering after DISTINCT preserves retained nested paths, such as `[Detail].[Code]`, including a valid source qualifier. Flattened joined fields and grouping keys resolve through their selected source identity; an unknown qualifier or an unselected relation cannot borrow a same-named output column. Over a join a key resolves through the same identities whatever the statement's WHERE reads (a nested query or a negation, which compose the joined rows), so `ORDER BY [b].[Title] SELECT DISTINCT [Title], [a].[Id] AS [X]` orders the selected `Title` on every route. EXPLAIN validates the same final ordering for explicit and wildcard projections.

For grouped DISTINCT, a directly selected key keeps its identity through an alias: after `SELECT DISTINCT [r].[Code] AS [Key]`, ordering may use `[Key]`, `[r].[Code]`, or `[r].[Body].[Code]` when Body is shorthand for that source. Collection-qualified spellings also work. A selected whole Object retains its child paths through an alias. A qualified grouping key that SELECT omits is rejected even if an aggregate or an unrelated output Object publishes the same spelling. Bare output aliases keep precedence.

The same direct-alias rule applies to single-source scalar projections over physical collections and derived or CTE inputs, including compatible subtype fields and schema-computed fields. Explicit SELECT item order preserves these identities through window and scalar-subquery projection. For example, `FROM [App].[Rows] [r] ORDER BY [r].[Body].[Code] SELECT DISTINCT [r].[Code] AS [Key]` orders the selected `Key` values when the source has no declared Body root. A plain `[r].[Detail].[Code]` beside a scalar expression retains the complete `Detail` Object, so its `Note` child can also order the distinct result. Conversely, `SELECT DISTINCT CAST(99 AS INT32) AS [Code]` allows `ORDER BY [Code]` but rejects `[r].[Code]` when that declared source column was omitted. Execution and EXPLAIN apply the same check before returning rows. An imported polymorphic envelope also retains compatible subtype leaves through a direct alias. A flat inner projection exposes only its emitted columns; omitted subtype fields cannot be recovered by qualifying their source name. Dependent JOIN aliases also retain selected direct source identities. After `SELECT DISTINCT [a].[Code] AS [Key], [Key] + 1 AS [Next]`, qualified `ORDER BY [a].[Code]` orders the selected `Key`. A plain nested field in that flat JOIN list retains only the emitted leaf or Object, so an omitted sibling cannot become a DISTINCT sort key. Independent direct AS fields in a composed JOIN over a derived source retain the same selected identities. Missing scalar inputs keep their NULL output behavior but do not acquire a declared source identity.

`[Meta].[Sealed]` is a non-null BOOL available anywhere other virtual metadata is supported: filtering, projection, ordering, grouping, joins, polymorphic envelopes, and streaming/total-count paths. On temporal reads it represents the identity's seal control state visible to the transaction snapshot, not a historical property of the selected body version.

Its scalar comparisons use the ordinary Bool text forms: `'true'` / `'false'` (case-insensitive) and `'1'` / `'0'`. Literal and bound values agree across streaming, buffered, primary-key, and mutation target selection paths.

Source qualification is resolved once. A real Object may have the same name as the relation alias or collection: with alias `[r]`, `[r].[r].[Code]` reads `Code` inside the source's Object named `r`. Execution and EXPLAIN retain that Object path, including when plain fields accompany computed SELECT values.

A dotted plain projection preserves its containing `OBJECT` / `ARRAY` on the wire so the client can navigate the requested child. The same parent-preserving shape applies when the `SELECT` list also contains scalar or window computed items, on both streaming and buffered execution paths; the child is not flattened into a sibling column.

Every output column name must be unique under case-insensitive schema identity. Repeating a field, reusing a plain field's leaf name as a computed alias, or assigning the same alias twice is rejected before any binary row is built. The rule is identical for stored collections, CTEs, joins, and system collections.

One explicit `SELECT` list accepts at most 1,024 combined plain, aggregate, and computed projection items. Wider parsed or programmatic query shapes are rejected before scanning, expression-type inference, or result-schema allocation. A mixed list is also limited to 1,024 expanded output slots. A standalone `SELECT *` remains one wildcard item and resolves only to the source schema's already-valid top-level fields. The row presentation a read appends to a relation's fields (the `Meta` object and a polymorphic source's `_type` lead and `Envelope`) occupies no data slot: a result carries at most 1,024 data columns beside it, so a collection at the 1,024-field limit stays readable by `SELECT *`, by a read that omits `SELECT` and by a wildcard beside items up to exactly 1,024 slots. Its combined `EXCLUDE`, `REPLACE`, and `RENAME` lists accept at most 1,024 targets; a wider modifier list cannot address a valid source schema and rejects before replacement-expression parsing or target validation.

### Scalar subqueries in projections

A parenthesized query is a SELECT expression with one result column. It may appear alone with `AS`, inside arithmetic or functions, in a CASE arm, or as a window value or partition expression:

```mql
FROM [Sales].[Customers] [c]
SELECT [Id],
    (FROM [Sales].[Orders] WHERE [CustomerId] = [c].[Id]
     SELECT COUNT(*)) AS [OrderCount];
```

The result keeps the inner column's declared type and nested schema. No rows produces NULL; more than one row is a `CARDINALITY_VIOLATION` and more than one column an `ARITY_MISMATCH`, both `User` errors. Use an aggregate or an explicitly ordered `LIMIT 1` when a multirow source must yield one value. A scalar pinned-reference column produces its logical identifier without the stored revision, like other expression values. Object and Array results retain their complete nested values, including stored pins. Outer references in the inner WHERE bind to the current source row, joined relation, or grouping key, on either side of a comparison (`[c].[Region] = [Region]` and `[Region] = [c].[Region]` alike). The inner SELECT list may read them too: `(FROM [Ns].[Other] [x] WHERE [x].[OwnerId] = [c].[Id] SELECT [c].[Region] AS [R])` yields the current row's `Region`, typed as that field is declared, also in an expression, a window function, a `* REPLACE` entry, a grouped or DISTINCT body, and an `IN` subquery's projected column. An outer row's array element path (`[c].[Tags][]`) has no single value to bind and is rejected with `FEATURE_NOT_SUPPORTED`; test the outer array in the outer query. A single-source outer collection can be qualified by its alias, its collection name (`[Customers].[Id]`), or its full identity (`[Sales].[Customers].[Id]`). An uncorrelated result is reused within the statement; executing a cached query again binds parameters and reads data afresh.

CASE, AND/OR, COALESCE, and IFNULL evaluate only the branches required by their normal short-circuit rules. AND/OR produces BOOL (or NULL), including when an accepted integer condition short-circuits an unused scalar subquery. The `||` operator evaluates left to right and stops at the first NULL or operand error without executing later scalar subqueries. An empty String remains a value. `CONCAT(...)` still evaluates its arguments and omits NULL values. `IN` and `NOT IN` evaluate the input once and stop at the first matching list member, including a NULL matching NULL. Later scalar subqueries in the list do not execute after that match. Cancellation during input evaluation is checked before required list work, including a cached literal-list lookup. Arithmetic, comparisons, `LIKE`, and `BETWEEN` evaluate operands in order, so `TRY` can recover an earlier arithmetic or conversion failure before a later scalar subquery executes. A NULL operand still allows later operands of these operators to run. Function lookup and argument-count validation happen before argument evaluation. Eager functions evaluate each argument before the next, including arguments containing scalar subqueries; an earlier error prevents later arguments from running. Built-in `ENUM_VALUE` returns NULL for a NULL label without evaluating its enum-name expression. All referenced collections still participate in read admission and view dependency checks before execution. Subqueries in aggregate arguments, aggregate FILTER predicates and grouping expressions also participate in read admission before any source rows are read. DISTINCT applies to the projected values before paging. ORDER BY can sort scalar projection aliases after evaluation and before SKIP / LIMIT, including grouped output. Window arguments use the bounded buffered window path. Persisted computed fields and CHECK constraints remain row-local and reject subqueries.

Grouped SELECT expressions read grouping keys and completed aggregate aliases. For example, `SUM([Amount]) AS [Total], [Total] * 2 AS [Doubled]` evaluates the arithmetic once per group after HAVING. Only selected columns are returned; unselected group keys may still support expressions or final sorting. Sibling computed aliases follow the same dependency rules as ordinary SELECT aliases. This applies to stored, derived, CTE, and joined sources, including scalar subqueries and windows.

**Numeric errors and recovery.** Integer arithmetic, including unary negation and MOD, has an INT64 output type. Mixed numeric arithmetic uses the promoted numeric kind. Overflow, zero division, invalid conversions, and numeric-domain failures raise `User / INVALID_VALUE` errors, whether they end the statement or surface while rows stream; declared computed-field narrowing is checked too. Use `TRY(expression)` to return NULL for an owned numeric/conversion failure or a built-in string-slice boundary error, and `TRY_CAST(value AS type)` for a fallible cast. Binding errors, unknown functions, aggregate (SUM/AVG) overflow, cancellation, resource failures, corruption, cleanup failures, and custom callback exceptions are never recovery inputs. NULL operands still propagate normally; IEEE-representable NaN and infinities remain values in floating-point results, but have no text: converting one to STRING is an `INVALID_VALUE` that `TRY` and `TRY_CAST` recover.

```mql
FROM [App].[Items]
SELECT [Quantity] * [Price] AS [Amount],
       TRY([Amount] / @divisor) AS [Ratio],
       TRY_CAST([Text] AS INT32) AS [Parsed];
```

SELECT aliases may reference earlier or later aliases. A dependency graph rejects cycles and evaluates each alias once per row, while output columns stay in authored order. Ambiguous input/alias names require a qualified input field; an unchanged field passed through by a wildcard retains its input meaning. WHERE, GROUP BY, aggregate arguments and FILTER bind input fields. HAVING binds group keys and aggregate outputs. Window inputs cannot depend on SELECT aliases (`INVALID_STATEMENT`). When SELECT expressions read sibling aliases over a join, outside `DISTINCT` (whose ordering reads its result), an `ORDER BY` key that names no alias reads the joined relations, never another output column: a key its relation does not declare, an inner relation's metadata and a key its relation's subtypes declare with different types report the native join's diagnostics, named as written, on every route. Values held internally to evaluate dependencies or retain source sort keys have no MQL spelling, so no authored input reference reads one, and a diagnostic names such a value as the statement does: `ENUM_LABEL([N])` over an alias `N` of a non-enum expression reports `ENUM_LABEL: field 'N' is not an enum-typed field.`, and a window input or ordering key that reads a grouping key whose output name an aggregate takes reports that output name. Declared subtype fields participate in input/alias ambiguity too. Later aliases can read compatible subtype leaves, including nested leaves; incompatible subtype declarations reject during preparation in both execution and EXPLAIN. An unqualified reference names an alias as written or through optional Body shorthand, in any case, where no relation declares a Body root, over a single source and a join alike: `[Body].[K]` beside `... AS [K]` reads the alias, and `[Body].[Rating]` beside `... AS [Rating]` over a relation that declares `Rating` is `AMBIGUOUS_FIELD` on every route, as `[Rating]` is. An independent window may feed a later alias under the same rules. Generated projection stages preserve nested source names and correlated outer paths.

<a id="alias-repeating-an-input-field"></a>

An alias that repeats an input field's name is therefore ambiguous wherever a computed item reads that name unqualified. Over an ungrouped source, `ENUM_LABEL([Status]) AS [Status]` and `[Salary].[Amount] AS [Salary]` report `AMBIGUOUS_FIELD` ("SELECT reference 'Status' is ambiguous between an input field and an alias; qualify the input field."), because `[Status]` could name either. Qualify the input with the collection name or the relation's alias — `ENUM_LABEL([Employees].[Status]) AS [Status]`, `[e].[Salary].[Amount] AS [Salary]` — or keep the field's slot and replace its value with `SELECT * REPLACE (ENUM_LABEL([Status]) AS [Status])`. Passing a field through under its own name (`[Status] AS [Status]`) is not ambiguous, and neither is a grouped projection, which reads group keys and aggregates (`GROUP BY [Status] SELECT ENUM_LABEL([Status]) AS [Status], COUNT(*) AS [N]`). The rule is the same in views, materialized views, and CTE bodies.

`REPLACE(...)` and `LEFT(...)` can directly start a computed SELECT item and appear on either side of a scalar WHERE comparison. For example, `SELECT LEFT([Name], 3) AS [Prefix]` and `WHERE [Name] = REPLACE('old', 'old', 'new')` use the ordinary function syntax. Computed SELECT expressions require an `AS [Alias]` suffix.

Invalid final paging parameters retain their validation diagnostic and release retained query resources even when SELECT expressions depend on other aliases.

Arithmetic (`+`, `-`, `*`, `/`, `%`) and the unary signs require numeric operands. There is no implicit string-to-number conversion: `1 + '2'` and `'2' + 1` both raise `TYPE_MISMATCH`. The text coercion accepted by numeric comparisons is deliberately comparison-only; cast explicitly (`1 + CAST('2' AS INT64)`) when arithmetic conversion is intended. MQL defines no temporal arithmetic: `[Day] + 1`, `[At] - [At]` and `NOW - [At]` are `TYPE_MISMATCH`; use `DATEADD(unit, count, timestamp)` to move a date and `DATEDIFF(unit, from, to)` to measure one. GUID, DATEONLY, TIMEONLY, DATETIME, BYTES, BOOL, STRING, object, and array operands are rejected independent of operand order — when the statement or definition is bound wherever the operand's type is known (a field, a literal, a CAST, a typed parameter, a nested query's column), in projections, WHERE, HAVING, FILTER, CASE, writes, computed columns, CHECK, views and triggers, and as the value is read otherwise (a CASE with arms of different types). A NULL operand yields NULL. `TRY` does not recover the refusal.

A condition — an operand of `AND`, `OR` or `NOT`, or a `CASE WHEN` — reads a BOOL, or an integer by its truthiness (zero is false); a value of any other type is `TYPE_MISMATCH`, by the same static and per-value admission.

Numeric functions follow the same rule. `POWER`, `SQRT`, and `MOD` accept only numeric arguments; numeric-looking strings and booleans require an explicit `CAST` / `TO_*` conversion. `MOD(7, '3')` is an error, not a numeric recovery result, and argument order does not change the outcome. Every built-in function refuses an argument of a kind it does not read with `TYPE_MISMATCH`, when the statement or definition is bound wherever the argument's type is known (a field, a literal, a CAST, a typed parameter, a nested query's column) — in projections, WHERE, HAVING, FILTER, CASE, writes, computed columns, CHECK, views, triggers and EXPLAIN — and otherwise as the value is read, with one text. Every argument's kind is admitted before any argument's value, so a NULL argument or an unknown unit does not hide a wrong kind (`SUBSTRING([N], NULL)` with an INT64 `[N]` is refused); a NULL `ENUM_VALUE` label is NULL without its enum name being read. The refused kinds: a non-numeric `ABS` / `ROUND` / `FLOOR` / `CEILING` / `SIGN` argument, a non-text `UPPER` / `TRIM` / `SUBSTRING` / `REPLACE` / `LEFT` / `RIGHT` / `POSITION` / `LIKE` / `CONTAINS` operand, a `LENGTH` of a number, a `DATE_TRUNC` / `EXTRACT` / `DATEADD` / `DATEDIFF` timestamp that is neither temporal nor text (timestamp text converts as `TO_TIMESTAMP` converts it, and text naming no timestamp is a conversion failure `TRY` recovers), a non-text unit, a `VECTOR` metric over another kind or over vectors of two dimensions — and a value outside an argument's domain with `INVALID_VALUE`: an unknown unit (`DATEADD('fortnight', …)`), a fractional position or count, a non-finite vector component, a zero-norm cosine operand.

EXACT_EQUALS and TRY are language intrinsics and cannot be replaced. In-process hosts may add or replace other scalar functions through the .NET `FunctionRegistry`. Publication is process-wide and atomic. Each MQL statement pins one function-registry generation at admission and retains it across every row, retry, nested evaluator, and delayed streaming-result drain. A concurrent replacement therefore cannot mix implementations inside one statement; it becomes visible to the next admitted statement, including through expression ASTs that were already cached. Replacing `COALESCE`, `IFNULL`, `CURRENT_TIMESTAMP`, `CURRENT_DATE`, `ENUM_LABEL`, or `ENUM_VALUE` invokes the registered callback with ordinarily evaluated arguments. Built-in short-circuit, statement-clock, and catalog-aware behavior belongs to the original implementation and resumes when that implementation is restored. Ordinary query projections of custom or replacement callbacks use the lossless STRING result schema because registration does not declare a return type; use an explicit CAST for a typed result. Schema computed declarations retain canonical built-in type and shape contracts, and stored computed expressions continue to use their immutable built-in implementations. Names, including directly constructed expression ASTs, are case-insensitive and are canonicalised to upper case; invalid negative or reversed arity ranges are rejected at registration. Statement admission pays one generation read; rows that call no scalar functions perform no function lookup. Function results and evaluation order are independent of arity; the common zero- through-four-argument path uses statement-local scratch, while larger variadic calls use pooled scratch.

Arguments that represent integer positions or counts are exact-value arguments: `SUBSTRING` start/length, `LEFT` / `RIGHT` length, `ROUND` digits, and `DATEADD` count accept `INT*`, `DECIMAL`, or floating-point values only when the value is finite, mathematically integral, and within `INT64` range. Thus `2`, Decimal `2.0`, and Float64 `2.0` are equivalent; `2.9`, `TRUE`, and `'2'` are errors rather than being truncated or implicitly converted. Use `CAST(... AS INT64)` / `TO_INT(...)` when conversion is intentional.

`DATEADD('WEEK', count, timestamp)` expands weeks to days with checked `INT64` arithmetic. If `count × 7` overflows, or if any supported unit would move the timestamp outside the representable date range, the result raises an error; TRY returns NULL for recovery. An oversized interval never wraps to a small valid timestamp.

`DATE_TRUNC(unit, timestamp)` likewise raises an error when the requested offset-local boundary falls outside the representable `DateTimeOffset` instant range. This can occur at the year-1 boundary when a valid minimum instant is viewed through a positive offset and then truncated to local midnight.

`DATEDIFF(unit, from, to)` returns the signed number of date-part boundaries crossed, not a truncated elapsed duration. Supported units are `YEAR`, `MONTH`, `WEEK`, `DAY`, `HOUR`, `MINUTE`, and `SECOND`; names are case-insensitive. Boundaries use each timestamp's offset-local calendar, and `WEEK` begins on Monday (the same ISO convention as `DATE_TRUNC` / `EXTRACT`). Thus `DATEDIFF('DAY', '2024-12-31T23:59:59.9Z', '2025-01-01T00:00:00.1Z')` returns `1`, and reversing the timestamps returns `-1`, even though the elapsed duration is less than one second.

An explicit `NULL` literal is type-neutral when `CASE`, `COALESCE`, or `IFNULL` combines value-producing arms. Thus `CASE WHEN ... THEN [Id] ELSE NULL END` and `COALESCE([Id], NULL)` retain `[Id]`'s nominal wire type instead of becoming `STRING`; an expression whose arms are all `NULL` uses `STRING` as its fallback schema. `CAST(NULL AS STRING)` is an explicit typed arm and therefore does contribute `STRING`. Arms of different numeric types promote; arms of other different types publish a lossless `STRING` result (a number arm as its canonical text, which NaN and the infinities do not have), except that a DATEONLY arm and a TIMEONLY arm share no value domain or order and are refused with `TYPE_MISMATCH` (`CASE WHEN … THEN [Day] ELSE [Clock] END`, `COALESCE([Day], [Clock])`, a `LAG` / `LEAD` default); CAST the arms to one type.

Structured `CASE`, `COALESCE`, `IFNULL`, `NULLIF`, and `TRY` results retain their complete Object, Array, or Vector schema when every possible value arm has a compatible layout. This also applies to wildcard `REPLACE`, empty input, and static EXPLAIN. Incompatible or unproven layouts use `STRING`: packed Objects/Arrays become base64, and Vectors become bracketed component text. A scalar pinned reference these expressions return is its logical ID, without the revision a direct projection keeps; whole pinned arrays retain their stored identifiers and revisions. Replaced function callbacks retain their conservative `STRING` result type.

A bound scalar parameter is likewise statement-stable and contributes its actual parameter type to a computed projection. For example, `@id` bound as a `Guid` projects `GUID`, and `@payload` bound as `byte[]` projects raw `BYTES`, not formatted text. A bound null parameter is type-neutral in the same value-arm forms as literal `NULL`; projected alone, it uses the `STRING` fallback. See [Parameterized queries](parameters.md).

On a polymorphic collection, subtype extension fields are valid operands in scalar and window computed projections, including a SELECT that also contains plain base or extension columns. Evaluation retains the original envelope and uses the union schema: the owning subtype supplies the typed value, while other subtypes evaluate that operand as NULL. For example, `[Seats] * 2` and `SUM([Seats]) OVER (...)` are numeric for `Car` rows and NULL for a subtype without `Seats`; a pushed-down plain projection never discards the envelope before those expressions run. If more than one subtype declares a referenced path, those declarations must be structurally identical; otherwise the fixed projection schema is ambiguous and the query is rejected.

When the wire/client requests `IncludeTotalCount`, scalar and window computed projections retain that metadata on both streaming and buffered execution paths. `TotalCount` is the complete filtered cardinality before `SKIP` / `LIMIT`, not the size of the returned page.

### Wildcard projection, `EXCLUDE`, `REPLACE`, and `RENAME`

`SELECT *` projects every top-level field declared on the source schema — equivalent to omitting `SELECT` entirely. Over a stored collection both also append the virtual [`Meta`](system-collections.md#meta-fields) object column after the declared fields; a derived table, CTE reference or view has no versions of its own, so both publish its declared columns only, and the `Meta` it carries from its producer is read by an explicit reference (`SELECT [Id], [Meta].[Revision]`), and over a polymorphic collection they lead with the `_type` subtype column and end with the virtual `Envelope` column ([polymorphism](polymorphism.md#querying-by-subtype)). `Meta` and `Envelope` are not declared fields, so `EXCLUDE ([Meta])` reports `UNKNOWN_FIELD`; list the wanted columns explicitly to leave them out. A bracket-qualified wildcard such as `SELECT [u].*` projects one logical relation and flattens its top-level fields in schema order. This is especially useful after a join and is independent of the physical join order. After a join no expanded column has a primary-key role, and a column is NOT NULL only when it is a NOT NULL field of the `FROM` relation, as its [direct reference](#select-projection) is, and only the relation's declared fields are expanded: the `Meta` object a CTE, derived or metadata-reading relation carries for explicit references is never a wildcard column, whichever input kind or clause supplies it. A `REPLACE` expression of a qualified wildcard reads that relation's fields first, so `SELECT [u].* REPLACE ([Id] + 1 AS [Id])` is not ambiguous with another relation's `Id`. The wildcard's own mistakes (an `EXCLUDE`, `RENAME` or `REPLACE` target the relation does not declare, or a `REPLACE` target `OMIT INNER KEY` removes) are reported before a `REPLACE` expression's input that no relation declares, on every route. The qualifier follows the same rule as a qualified field: a relation's explicit alias (or the name of an unaliased CTE reference) first, then a short or full collection name that no relation qualifier claims, selecting the latest relation carrying it, so `FROM [App].[Orders] [o] JOIN [App].[Customers] [c] ON [o].[CustomerId] = [c].[Id] SELECT [Customers].*` expands `[c]`. An explicit alias therefore takes precedence over another relation's collection short name, both for its qualified wildcard and for source fields used in `ORDER BY`. A native join sorts its joined rows before projecting a wildcard, so `ORDER BY` reads source fields there and a renamed slot's output name is an unknown sort field (`ORDER BY [T] SELECT [b].* RENAME ([Title] AS [T])`); a join composed over its merged rows sorts by a source field first and otherwise by an output column, so the renamed slot is a sort key there. A wildcard inside an item list (`SELECT [d].*, [e].[Kind] AS [K]`), a `DISTINCT` wildcard, nested wildcard modifiers and a window `REPLACE` always compose the joined rows, so they order by an output column too (a `DISTINCT` wildcard by a column of its `DISTINCT` result). Bare `u.*` is not valid MQL.

In a single-source query, the qualifier may be the bare collection or view name, the CTE name, or an explicit FROM alias, matched case-insensitively. For example, `FROM [App].[Items] SELECT [Items].*` and `WITH [R] AS (FROM [App].[Items]) FROM [R] SELECT [R].*` work without adding an alias. Derived sources use their declared alias. Standalone and mixed wildcards share these rules; a field name is not a relation qualifier.

In a query over a direct, non-polymorphic stored source a column that passes the primary key through keeps the key's declaration, a key that is never NULL, as `SELECT [Id]` does: a wildcard publishes its unreplaced key slot by its declaration, under a `RENAME` too, as it publishes every retained field (below), and an item that names the key under its own name beside a wildcard keeps it too (`SELECT *, [Price] * 2 AS [Double]`, `SELECT * EXCLUDE ([Id]), [Id]`), so a client can tell which rows are stored documents and read them again by that key. A replaced key, an `AS` alias of it, a `DISTINCT` or grouped projection, the columns of a join and a [set operation](#set-operations--union--intersect--except)'s column where a branch's column is no key carry no key role.

Wildcard replacement expressions over a CTE, derived query, or view use the same source qualification as ordinary expressions. A CTE name also qualifies these expressions without an alias: `WITH [v] AS (FROM [App].[Items]) FROM [v] SELECT * REPLACE ([v].[Code] + 0 AS [Code])` works through both buffered and streaming results. If a source aliased `[r]` contains an Object also named `[r]`, `[r].[r].[Code]` selects that Object's `Code` child; the wildcard still retains the Object under its original name. Applying a source alias to a stored replacement expression preserves its bound enum identity, including after the enum is renamed and its former name is reused.

Three modifiers trim or transform a wildcard projection:

- `SELECT * EXCLUDE ([F1], [F2], …)` — drop specific fields from the wildcard. Saves the consumer from typing the full kept list whenever the schema grows.
- `SELECT * REPLACE (expr AS [F1], expr AS [F2], …)` — substitute the named fields' values with arbitrary expressions while every other field flows through unchanged. Canonical patterns: PII masking (`REPLACE (NULL AS [Password])`), normalisation (`REPLACE (UPPER([Name]) AS [Name])`), unit conversion (`REPLACE ([Cents] / 100.0 AS [Cents])`).
- `SELECT * RENAME ([F1] AS [NewF1], [F2] AS [NewF2], …)` — change output names without changing values or types.

Each modifier may appear once. They may be written in any order; canonical printing always emits `EXCLUDE`, then `REPLACE`, then `RENAME`. Execution uses the same ordered pipeline regardless of written order: exclusion removes source slots, replacement changes a retained slot's value and inferred type in place, and rename changes its advertised name in place.

The modifiers name declared data fields. A wildcard over a direct, non-polymorphic stored source keeps its row-metadata presentation (the trailing `Meta` object) and each retained field's declared type under every modifier, `EXCLUDE` alone and a nested modifier path (`EXCLUDE ([Addr].[Zip])`) included, and among other `SELECT` items, outside an aggregate relation, so `FROM [App].[Users] SELECT * EXCLUDE ([Salt])` publishes `Meta` exactly as `SELECT *` does, also when a correlated `EXISTS`, `IN` or scalar comparison in its `WHERE` is evaluated as a join, and `SELECT *, [Id] + 1 AS [Next]` publishes it after the wildcard's fields; a statement with several wildcards publishes `Meta` once, after the first one's fields. `Meta` is not a modifier target, and `EXCLUDE ([Meta])`, `REPLACE (... AS [Meta])` and `RENAME ([Meta] AS ...)` report an unknown source field. The other wildcard forms enumerate the declared data fields only, without `Meta`, each typed by its declaration: as nullable key columns a `DISTINCT` wildcard, whose keys never include per-row metadata, a wildcard among items beside `GROUP BY` or an aggregate and a lone wildcard with modifiers beside `GROUP BY`, whose expanded fields must each be one of the aggregate relation's grouping keys (a lone wildcard without modifiers there, qualified or not, publishes the keys themselves), and, each column published as its [direct reference](#select-projection) is, a polymorphic source's qualified or modified wildcard, whose subtype fields are ordinary nullable columns that a modifier may name (`SELECT * EXCLUDE ([Doors])` over a collection with a `[Car]` subtype declaring `[Doors]`), alike in static schema discovery, `EXPLAIN` and execution, whether the single source reads the collection directly or through a derived table or CTE (`FROM (FROM [App].[Vehicles]) [v] SELECT [v].* EXCLUDE ([Doors])`); a derived table's or CTE's plain `SELECT *` enumerates the slots it emits. A polymorphic source's rows and every wildcard over it are likewise unchanged when a correlated subquery in its `WHERE` is evaluated as a join. Excluding every declared field leaves nothing to project, whatever metadata the source presents. A wildcard modifier mistake is reported after the source's `WHERE`, the clause order static schema discovery, `EXPLAIN` and execution share.

A wildcard that presents `Meta` reserves that output name: the presentation keeps its name, so `SELECT *, [Meta]`, `SELECT [Meta], *`, `SELECT *, [Name] AS [Meta]` and `SELECT * RENAME ([Name] AS [Meta])` report a duplicate output field whose diagnostic names the presented metadata. `SELECT *` already publishes the metadata; name the other item differently with `AS`, or choose another `RENAME` output name. `EXCLUDE` cannot make room, because `Meta` is no modifier target.

```sql
-- Same as omitting SELECT — every declared field
FROM [App].[Users] SELECT *;

-- Suppress sensitive / large fields without re-typing the keep list
FROM [Core.LegalEntity].[LegalEntity]
SELECT * EXCLUDE ([Password], [Salt]);

-- Mask a field while keeping every other one
FROM [Sec].[Users]
SELECT * REPLACE (NULL AS [Password], NULL AS [Salt]);

-- Compose: drop one, substitute another
FROM [Sec].[Users]
SELECT * EXCLUDE ([Salt]) REPLACE (UPPER([Name]) AS [Name], NULL AS [Password]);

-- Rename several result columns without listing the full projection
FROM [X].[Y] [MyCollection]
SELECT [MyCollection].*
RENAME ([MyColumn] AS [NewName], [OtherColumn] AS [OtherName]);

-- Replacement expressions read the original row; rename remains result-only
FROM [Sec].[Users] [u]
SELECT [u].*
REPLACE (UPPER([Name]) AS [Name])
RENAME ([Name] AS [DisplayName]);
```

Every retained field keeps its source position. A replacement expression's inferred type drives that slot's output type and evaluates against the original full input row before exclusion or output renaming. A pure single-source rename therefore preserves the ordered binary layout and can stream the original row bytes with a renamed result schema. Exclusion, replacement, and qualified join extraction rebuild each result row at most once. Replacing a slot with a direct field or scalar-subquery result retains that value's complete Object, Array, or Vector schema. For example, `SELECT * REPLACE ([Box] AS [Box])` keeps `Box`'s child fields available to an enclosing query; `RENAME` also preserves that layout. Standalone and mixed wildcard projections use the same result-schema rules.

Rules and rejections:

- Wildcards and explicit items may be mixed, with multiple wildcards expanded in authored order. Each wildcard has its own EXCLUDE / REPLACE / RENAME plan.
- A wildcard qualifier must be bracketed (`[u].*`); bare `u.*` is invalid.
- Final output names must be unique across all expanded items. For example, `SELECT * EXCLUDE ([Y]), [Y]` is valid; `SELECT *, [Y]` reports a duplicate when the wildcard already contains Y. Rename or exclude overlapping slots. A nested modifier changes only children, so two wildcards that both keep `Addr` repeat it whatever they modify inside it.
- Computed and window expressions may accompany wildcards. With aggregates, expanded plain fields must satisfy the normal GROUP BY rules. DISTINCT deduplicates the expanded values before ordering and paging.
- `EXCLUDE`, `REPLACE`, and `RENAME` accept top-level fields and nested Object paths. `EXCLUDE ([Addr].[Zip])` removes only Zip; `REPLACE (UPPER([Addr].[City]) AS [Addr].[City])` replaces City; `RENAME ([Addr].[City] AS [Town])` renames the child inside Addr. Beside GROUP BY a nested modifier rewrites a grouping key's value once the groups are formed, before `DISTINCT`, whether the statement groups plain fields or a GROUP BY expression, an aggregate argument or a `JOIN_STRING` separator parameter beside them: over a collection of `Id` and `Addr`, `GROUP BY [Addr], [Id] % 2 SELECT * EXCLUDE ([Id], [Addr].[Zip])` returns each group's Addr without Zip, and a REPLACE value may read grouping keys and aggregate aliases. Null parents remain null and untouched siblings retain their types. A replacement may change the target leaf's type. Removing every child leaves a present empty Object, distinct from a null parent. Polymorphic Objects retain their subtype envelopes, and subtype-child modifiers apply only to subtypes declaring that child. Their discriminator may be renamed but cannot be removed or replaced while the subtype payload is retained.
- Object children inside Arrays use explicit `[]` traversal for each dimension: `[Items][].[Price]` or `[Matrix][][].[Price]`. EXCLUDE and RENAME preserve element count and order. REPLACE evaluates for each original element and can read original enclosing elements and full-document fields, including through correlated scalar subqueries. Excluding, replacing, or renaming an outer field does not change those original inputs. Empty Arrays remain empty, null parents remain null, and polymorphic elements retain their active subtype payloads.
- REPLACE can target an entire element, including primitives: `REPLACE ([Values][] * [Factor] AS [Values][])`. Use `[Matrix][][]` for scalar leaves in two consecutive Arrays. The expression determines the output element type; whole Object or Array elements may also be replaced. Count and order remain unchanged. NULL or unrepresentable element results are errors because Array elements have no null bitmap. EXCLUDE and RENAME require named fields, so use the Array field or a named Object child instead of an anonymous `[]` element. Replacing elements of a pinned-reference Array reads the original IDs and returns ordinary values without the original pinned revisions. An expression returning a complete Array preserves that value's element schema and pinned revisions, even when used as a nested output element. No replaced value keeps its source's foreign-key removal action or match mode: element results and a rewritten reference Array are ordinary values, and a complete Array keeps only its target identity and pins. Beside GROUP BY or an aggregate an element REPLACE is refused with `FEATURE_NOT_SUPPORTED`, because its expression reads one source row; replace the whole Array, or replace its elements in a query that reads the grouped rows.
- REPLACE accepts window functions, including references to a trailing named WINDOW. Windows run over source rows; an Array-child target receives the same row's window value in each element. Explicit projections and replacements share the limit of 64 window functions per SELECT. The result still supports 1,024 output fields; internal replacement slots do not consume this public budget. Programmatic SELECT DISTINCT wildcard ASTs use the same expansion and deduplication as parsed MQL. DISTINCT publishes the grouping-key schema: output keys are nullable, scalar pinned references become logical IDs, and whole pinned arrays retain their complete values, including revisions.
- Nested targets bind to original source paths, including when the parent is renamed. Replacing a parent together with modifying one of its descendants is ambiguous and rejected. Renaming or replacing a target below an excluded parent is rejected; redundant descendant exclusions are harmless. Rename output names must be unique within each containing Object.
- A single field cannot appear in both `EXCLUDE` and `REPLACE` — pick one (a field is either dropped or substituted).
- `REPLACE` and `RENAME` may target the same source field. Renaming an excluded field is rejected.
- Duplicate REPLACE targets in one clause (`REPLACE (... AS [F], ... AS [F])`) are rejected at descriptor build.
- Rename mappings apply simultaneously, so swaps such as `[A] AS [B], [B] AS [A]`, case-only renames, and reuse of a name freed by exclusion or another rename are valid. Duplicate rename sources, duplicate final names, and case-insensitive collisions with retained fields are rejected.
- Unknown qualifier aliases and unknown exclude / replace / rename names error rather than silently changing the projection.
- Renamed aliases are result-only. `WHERE`, `GROUP BY`, and ordinary `ORDER BY` reference source names. With `SELECT DISTINCT`, final `ORDER BY` instead addresses selected values: use the renamed output spelling. A qualified source path removed by EXCLUDE or RENAME is rejected even if a computed item publishes the old name. REPLACE retains the slot's source identity, using the replacement's type and child schema. Retained source paths accept aliases, collection qualifications, and an optional `Body` segment.
- Excluding every field is rejected (zero-column results are a UX error, not a feature).

These schema checks are identical for stored collections and derived virtual sources such as CTEs and system collections, including computed and polymorphic fields. On joins, the qualifier resolves through the logical alias map and the selected relation is flattened in its own schema order. Fields from an absent side of an outer join remain nullable in the advertised output schema.

## Set operations — UNION / INTERSECT / EXCEPT

```sql
FROM [Shop].[Customers] SELECT [Email]
UNION
FROM [Shop].[Subscribers] SELECT [Email];
```

`UNION`, `INTERSECT`, and `EXCEPT` combine queries; each operator has an `ALL` variant. Chains are left-associative, with `INTERSECT` binding more tightly than `UNION` and `EXCEPT`. Use `FROM (<query-expression>) alias` to group a subexpression explicitly. Set expressions may appear in CTE definitions, WITH main queries, nested read queries, and view bodies; an APPLY body reads one as its derived `FROM` relation ([CROSS APPLY](#cross-apply)). Both sides must project the same number of columns with matching value layouts. Scalar columns may have different names, source roles or nullability (for example, a primary key may be combined with an ordinary field of the same type), and the output keeps the left column name; a column is nullable when either branch's column is, and keeps a primary-key role only when every branch's column is a primary key, so a key combined with an ordinary field, or with an alias of a key, is no key. For structured values, a matching top-level type is not sufficient: vector dimensions, nested object field names/order, array element schemas, nested nullability, enum/named-type identities, reference targets, pinned-reference width, and polymorphic discriminator/subtype layouts must also match. A mismatch fails before any rows are exposed; right-branch bytes are never decoded through an incompatible left-branch schema.

Static EXPLAIN and nested schema discovery validate those same emitted layouts, including a raw polymorphic result's discriminator and subtype metadata, and report the same error: `ARITY_MISMATCH` for a column-count mismatch, `TYPE_MISMATCH` naming the first position whose type or value layout differs, or a polymorphic shape mismatch. A JOIN branch whose `SELECT` lists only plain fields publishes them nested under its `outer` and `inner` columns, and one without a `SELECT` list (or with an unqualified `SELECT *`) publishes its merged row as those columns ([JOIN](#join)), so it combines only with a branch of that nested layout. Against flat columns it is refused with one of those codes, and the diagnostic names the branch's nested shape and the `AS` spelling that publishes each column flat: `FROM [Shop].[Customers] SELECT [Id], [Email] UNION FROM [Shop].[Orders] [o] JOIN [Shop].[Customers] [c] ON [o].[CustomerId] = [c].[Id] SELECT [c].[Id] AS [Id], [c].[Email] AS [Email]` combines, while the same right branch written `SELECT [c].[Id], [c].[Email]` is refused. A raw set result retains its left output layout when used by a CTE, derived query or APPLY.

A final `ORDER BY` / `SKIP` / `LIMIT` written **after the completed right branch** applies to the combined result. The sort fields must exist in the output schema (whose names come from the left branch); paging happens after deduplication / multiset combination and after the global sort:

```sql
FROM [Shop].[Customers] SELECT [Email]
UNION
FROM [Shop].[Subscribers] SELECT [Email]
ORDER BY [Email] ASC SKIP @offset LIMIT @pageSize;
```

The final ORDER BY / SKIP / LIMIT tail applies to the combined set result, including when written before the right branch's SELECT. Put a branch in a derived query or CTE to apply its own paging. Global paging without ORDER BY streams in the set operator's natural order; global ordering consumes the combined rows before paging.

- `UNION` — all rows from both sides, deduplicated. `UNION ALL` keeps duplicates (and streams — no dedup buffer).
- `INTERSECT` — rows present on both sides, deduplicated. `INTERSECT ALL` uses multiset semantics (a row appearing 3× left and 2× right emits 2×).
- `EXCEPT` — left-side rows with no right-side match, deduplicated. `EXCEPT ALL` subtracts per-occurrence.

**Equality follows the engine doctrine.** Dedup and matching use the same equality as `WHERE =` / `DISTINCT` / `GROUP BY`: strings compare case-insensitively (`'Cafe' UNION 'cafe'` is one row) and floats follow the engine's total order (every NaN payload is one value, `-0` equals `+0`). Decimal scale is not identity (`1.0` equals `1.00`), and `DATETIME` values that name the same UTC instant compare equal even when their stored offsets differ. `VECTOR` values with equal components are one value, including positive and negative zero components. NULL remains distinct from a present empty `BYTES` value. Scalar pinned references compare by identifier, ignoring the stored revision; emitted rows retain the selected complete pin. Whole pinned arrays compare their complete values, including element revisions. These rules also apply to spilled or parallel set operations. `SELECT DISTINCT`, including after correlated filtering, emits typed grouping keys: scalar pinned references become logical identifiers, while whole pinned arrays retain element revisions. `UNION` emits the first-seen representation. Dedup-bearing parallel set operations partition the complete canonical row with XXH3, so low-bit patterns in valid binary values cannot strand half the workers. Canonical rows are built in stack-first, pooled scratch and retain only the single owned key required by the set/multiset; Unicode lowercasing does not create additional per-row managed keys.

`INTERSECT ALL` and `EXCEPT ALL` bound both positive counts and consumed-row state with `MaxInMemoryStreamingState`. Exhausted counts spill as authoritative zero snapshots, preserving per-occurrence matching through later spill and compaction. This local bound applies independently of engine-wide admission.

`ORDER BY`, `SKIP`, and `LIMIT` after the second projection apply to the **combined result**, in that order:

Combined ORDER BY binds the left branch's output names and accepts only scalar sort keys. Missing fields and Object/Array keys fail before combined row enumeration. Static EXPLAIN and nested schema discovery share this validation; empty outer inputs do not bypass nested set ordering or paging-parameter checks. Stored-view dependency checks validate ordering while keeping paging values as runtime inputs.

Set-operation plans own their combination strategy: `Concatenation` for UNION ALL and `HashSetOperation` for deduplicating or multiset operators. Both branch access plans remain children, with a separate `Sort` above the combination for trailing ORDER BY. Combined rows inherit no source index or source early-exit claim. A UNION estimate is unknown when either branch estimate is unknown; ANALYZE executes the complete operator to report actual rows.

When the client/wire requests `IncludeTotalCount`, set operations report the combined cardinality after their `ALL` / distinct / multiset semantics and before trailing `SKIP` / `LIMIT`, also as the main query of a `WITH` statement ([SKIP and LIMIT](#skip-and-limit)). The complete combined result is retained in spill-bounded replay state, so only the requested page is emitted and the count remains exact for `UNION`, `INTERSECT`, and `EXCEPT`. This guarantee is identical for in-process and TCP clients: top-level set-operation AST nodes are query results on the wire, not schema-less statement acknowledgements.

```sql
FROM [Shop].[Customers] SELECT [Email]
UNION ALL
FROM [Shop].[Subscribers] SELECT [Email]
ORDER BY [Email] ASC SKIP @offset LIMIT @pageSize;
```

For compatibility with MQL's normal pre-`SELECT` clause order, placing those clauses before the second `SELECT` also means combined-result ordering/paging; the printer always emits the canonical trailing form. Do not mix the two spellings for the same tail clause: repeating `ORDER BY`, `SKIP`, or `LIMIT` in both positions is a parse error. To order or page a branch independently, enclose it in a derived source: `FROM (FROM [Shop].[Customers] ORDER BY [Email] LIMIT 10 SELECT [Email])`. The left branch may contain its normal query clauses. Paging parameters accept the same integral CLR values as ordinary query paging; `SKIP` is non-negative and `LIMIT` is positive. `EXPLAIN` applies the combined `SKIP` / `LIMIT` to `EstimatedRows`.

Combined paging without ordering stays streaming and stops as soon as `LIMIT` is satisfied. Combined `ORDER BY` is a blocking sort, bounded by `EngineOptions.MaxInMemoryStreamingState`; larger results use checksummed, stable external-merge runs and report their bytes through `SpilledBytes`.

With engine-wide snapshot isolation enabled, collection reads in the two branches observe one statement snapshot. A commit to those collections that lands after the left branch begins cannot make the right branch see a newer instant. Temporal segments resolve at that CSN before valid-time filtering. The combined result is produced before that statement snapshot is released, including otherwise-lazy `UNION ALL` output. Nested query helpers inherit this snapshot through flow-local statement state; a concurrent child cannot replace or clear the parent snapshot while the parent still owns its lease. Any lazy result drained into bounded replay before releasing that lease freezes its result schema and polymorphic subtype metadata first. Replayed bytes cannot be advertised under metadata changed by the producer while it was streaming. The same immutable-metadata boundary applies when an execution interceptor claims a query or a plugin statement handler returns rows: buffered or lazy rows are published with a private schema generation, never the plugin's subsequently mutable DTOs. Buffered plugin results also own a private list and private copies of every row buffer; producer-side edits after return cannot alter row count or contents already accepted by the executor. Every buffered or lazy plugin row is validated recursively against that captured schema before publication; malformed offsets, scalar encodings, nested values, NULL payloads, or trailing bytes fail closed rather than reaching an in-process or wire consumer. A lazy plugin or custom row source that returns a null async enumerator likewise fails its provider contract while releasing any attached owner and retiring its statement cancellation and migration-drain registrations; it is never reported as a successful empty result or an unrelated decorator failure. A wrapper that intentionally delays acquisition reports the provider contract error on the first row request while still releasing its operator state. Every published `Rows` result has exactly one buffered/streaming source and a schema. Non-row results cannot carry schema/count/polymorphic metadata. Every error carries both a defined class and a non-empty stable code; neither field can appear alone. Undefined enum values are rejected. Only `AffectedCount` can carry a nonzero affected-document count, and transaction/subscription session metadata appears only on `Ok`. Polymorphic row metadata is all-or-nothing: its discriminator is non-empty, its subtype list is non-empty, and the published schema contains the virtual `Envelope` field those identities describe. Empty or whitespace field/subtype identities fail before any retained row can be decoded under that schema generation. Every TCP `ResultSchema` path forwards this captured discriminator/subtype generation, including CTE, set-operation, virtual, LIST, and plugin-produced rows; transport dispatch cannot strip the envelope description from otherwise valid row bytes. Every TCP query uses the same executor boundary as in-process MQL, including a plain single-collection `FROM`. Snapshot coordination, execution interceptors, read gates, view/subquery/computed evaluation, active-query registration, timeouts, and schema-generation fencing therefore cannot be bypassed by a simple remote query. An interceptor may claim a query with any valid result kind; rows, errors, and non-row success retain their exact wire grammar.

Plugin read admission presents each distinct logical `(collection, intent, AS-OF instant)` operation once after view expansion, including joins, CTE and set-operation branches, lateral sources, and predicate subqueries. Internal branch execution, optimizer rewrites, and per-row correlated evaluation do not re-fire gates for operations already admitted by the outer statement; an independently initiated statement gets a new admission pass. DML targets remain write-guard operations, while query sources inside their predicates use read gates.

Eligible uncounted queries still frame the owned engine row stream in one pass through the executor's transport preference, including after pass-through execution interceptors. Their advertised schema and descriptor bind to one generation; a rewriting `ALTER` cancels/drains the old statement or trips the identity fence before any replacement-layout row. Counted queries and algebraically buffering operators use bounded replay and spill above the configured streaming-state cap. Streaming cancellation is enforced at the published result boundary before and after every source move. A plugin or custom row source cannot turn a cancelled statement into successful rows by ignoring the token it receives; its owner is still retired through the failure-preserving cleanup path. The remote `IncludeTotalCount` request reaches execution interceptors and plugin statements even when their AST is not a built-in query. If such a statement returns rows, its exact count is preserved in the terminal frame. Every execution interceptor receives an isolated read-only parameter map with private copies of mutable byte-array values. Passing through cannot rewrite the bindings observed by a later interceptor or by core execution. An ordinarily broken interceptor identity getter also remains inside the plugin-fault boundary and cannot replace the stable classified error; direct or nested memory exhaustion and simulated process death escape with their outer exception identity intact. Plugin statement extensions must return an AST whose exact runtime type is declared by that same extension in `SupportedNodeTypes`. An undeclared shape is a parse error; returning `true` with a null AST is also a contract parse error, not a silent decline. An unowned plugin AST fails authorization closed; unknown executable plugin shapes never inherit Reader permission. An undefined plugin permission value is likewise rejected before execution. Each statement extension must also declare whether every owned node is non-mutating, completes an existing scope, mutates through the current scope, commits independently, or opens a new scope. Engine-role admission uses this effect separately from authorization. Missing ownership and undefined effects fail closed; plugin statements never inherit an implicit read-only effect. Plugin-contributed `OPTION(...)` keys follow the same explicit-claim rule: a `true` claim must consume input and return a non-empty, non-whitespace canonical key, or parsing fails with a plugin contract error.

With engine-wide snapshot isolation enabled, both branches execute at one statement snapshot. A commit between the left and right branch cannot make one set-operation result combine two different instants.

Set operations chain and compose with WITH and derived sources. INTERSECT binds more tightly than UNION and EXCEPT; equal-precedence operators associate left to right. Wrap a branch in `FROM (...)` to retain branch-local ordering and pagination. See [cte.md](cte.md) for recursive seed/member syntax.

## CROSS APPLY

`CROSS APPLY (subquery) AS alias` is a *lateral* join: the inline subquery on the right side is re-evaluated **per outer row**. An inner `WHERE`, `SELECT` list or temporal instant (`AS OF`, `IN BETWEEN`) can reference `[outerAlias].[field]`; that reference is bound to the current outer row for each evaluation, so `SELECT [i].[V] AS [V], [o].[N] AS [On]` projects the outer row's `N` with `N`'s declared type (an unaliased `[o].[N]` is named `N`). Use APPLY when the inner result depends on the outer row in a way a positional `JOIN ... ON` cannot express, such as top-N per outer or a parameterised lookup. Nested subqueries keep their own enclosing row scopes: a reference to the APPLY inner alias binds to that inner row, including when it shadows an outer alias. An APPLY body can reference the enclosing FROM and earlier JOINs. Its ON predicate can also reference that APPLY result, and an APPLY inside a subquery or another APPLY body can compare in ON with a column of any enclosing query, as that subquery's WHERE can. An alias introduced by a later JOIN cannot change an earlier reference; the APPLY result alias is not in scope inside its own body. Nested APPLY and scalar subqueries preserve grandparent references separately from immediate-parent references. An EXISTS, scalar or IN subquery remains correlated when its only reference to the caller is inside a nested APPLY or selected expression. It is evaluated for that caller; correlation only between rows inside the subquery does not create an additional dependency on its caller. Execution and EXPLAIN apply the same lexical binding rules.

```sql
-- Latest 3 shipments per order
FROM [Orders].[Orders] [o]
CROSS APPLY (
    FROM [Logistics].[Shipments]
    WHERE [OrderId] = [o].[Id]
    ORDER BY [ShippedAt] DESC
    LIMIT 3
    SELECT [Id], [ShippedAt], [Carrier]
) AS [s];
```

The body is one query: a set operation written directly as the body (`CROSS APPLY (FROM … UNION FROM …) AS [x]`, and likewise under `OUTER APPLY`, `JOIN LATERAL` and `LEFT JOIN LATERAL`) is a parse error. Make the set operation the body's derived `FROM` relation instead: `CROSS APPLY (FROM (FROM … UNION FROM …) [u] SELECT [u].[Id]) AS [x]`, whose branches may still read the outer row.

The raw result always has the canonical `{ outer: Object, inner: Object? }` shape. Statement aliases such as `[o]` and `[s]` identify correlation scopes; they do not rename those public fields. Consumers therefore read `[outer].[Id]` and `[inner].[Carrier]`. Clauses that must run after the merge require the CTE form described below.

**Semantics.** Two variants ship:

- **`CROSS APPLY`** — INNER semantics. Outer rows whose inner subquery returns zero rows are dropped.
- **`OUTER APPLY`** — LEFT-OUTER semantics. Outer rows whose inner subquery returns zero rows survive with the inner Object null-flagged. Reading any `[inner].[field]` off such a row returns SQL `NULL`.

```sql
-- Latest 3 shipments per order; orders with zero shipments survive
-- with inner=null (use this when you need a left-outer projection).
FROM [Orders].[Orders] [o]
OUTER APPLY (
    FROM [Logistics].[Shipments]
    WHERE [OrderId] = [o].[Id]
    ORDER BY [ShippedAt] DESC
    LIMIT 3
    SELECT [Id], [ShippedAt], [Carrier]
) AS [s];
```

PostgreSQL-style `JOIN LATERAL`, `INNER JOIN LATERAL`, and `LEFT JOIN LATERAL` are accepted as portability spellings for the same operator (`JOIN` / `INNER JOIN` lower to `CROSS APPLY`; `LEFT JOIN` lowers to `OUTER APPLY`). The printer normalises every form to APPLY. An optional `ON` accepts a boolean predicate over the current pair, including earlier relation aliases, parameters, expressions, and subqueries. It runs after the inner query's ordering and paging. Only TRUE establishes a match; FALSE and NULL reject the pair. OUTER APPLY emits one null inner when no pair matches, even when the inner query returned rows. ON TRUE is the identity condition.

ON resolves a source alias before optional `Body` shorthand, including an alias named `[Body]`. After selecting the source, a declared `[Body]` field is a real root: a missing child cannot resolve to a same-named field at another root. A source without that field accepts `[Body]` as shorthand. Execution and EXPLAIN apply this rule to both scalar expressions and native predicate roots.

ON expressions and correlations can read compatible nested subtype leaves even when their parent Object has different layouts. Ordinary non-array comparisons require one compatible declared leaf across the source's subtypes, including literal-list IN/NOT IN. This admission rule does not widen native values: integer-width equality and native NULL truth still apply. Native array comparisons and MATCH retain each row's active subtype fields, including pinned reference Id and Revision pseudo-fields. Ordinary native field, operator and parameter errors are checked before rows are delivered, even for empty inputs or a short-circuited predicate. EXPLAIN performs the same checks without executing subqueries or functions to discover metadata.

The merged columns are bound from catalog and projection metadata before row delivery, without executing the inner query or invoking its functions. An empty outer source therefore makes no inner function calls merely to discover columns. The binder and per-row execution retain the same lexical CTE/view definitions; each actual inner result must match the captured schema before its rows are read.

**Composition.** JOIN and APPLY may be chained in one FROM (up to the shared 16-edge limit). Each APPLY can correlate with earlier relation aliases. Physical collections, CTEs, derived queries, and system collections can supply the outer rows. WHERE, grouping/HAVING, projection, windows, ordering, and paging consume the merged result; temporal source clauses continue to select the root source. Per-outer ordering or paging belongs inside the APPLY subquery.

Within that FROM scope, APPLY retains the original fields of earlier sources. A nested leaf with the same declaration in every subtype that defines it can be used for correlation, a later JOIN key, or projection even when its parent Object differs between subtypes. An absent leaf in the current row or a NULL owner yields NULL; selecting a whole parent still requires a compatible complete declaration. The APPLY subquery exposes only its output columns. Importing the merged result through a CTE or derived query exposes its published fields, without the producing query's internal aliases or omitted source fields.

Query nesting is capped at 100 levels across derived tables, set operations, CTE definitions, APPLY, `EXISTS`, scalar and list subqueries. Every derived source, set-operation branch, `WITH` body, CTE definition and nested query is a level, so a chain of derived set operations, each in a branch of the one before, takes three levels per derived table (33 of them fit), and a chain of `WITH` clauses, each inside the previous CTE's definition, two per `WITH` (50 fit); the parser refuses deeper text with `LIMIT_EXCEEDED`, and the same bound is enforced for programmatically supplied ASTs before printing or execution. A chain of relation references, a CTE that reads the CTE before it or a view that reads another view, is no nesting and has no such cap: execution, schema discovery and `EXPLAIN` each walk it link by link, at a cost that grows with its length alone, and the views a statement reads do not count toward the 9,362 definitions a `WITH` list accepts (see [CTEs](cte.md#syntax-ctes)). Within the bound a statement never exhausts the process stack: nested levels of execution, schema discovery and `EXPLAIN` continue on a fresh stack every few levels, so every statement the parser accepts runs on each of them, and a statement whose caller has already used most of its stack is refused with `LIMIT_EXCEEDED` instead of ending the process.

The client/wire `IncludeTotalCount` option counts the exact merged result: `CROSS APPLY` excludes outer rows with no inner match, while `OUTER APPLY` includes each null-inner row. Because the count is eager, merged rows replay from spill-bounded state; requests without a count remain streaming.

**Named intermediate results.** A CTE can name an APPLY result for reuse. Without an explicit SELECT its outer query uses the merged envelope:

```sql
WITH [applied] AS (
    FROM [Orders].[Orders] [o]
    CROSS APPLY (
        FROM [Orders].[Lines]
        WHERE [OrderId] = [o].[Id]
        SELECT [Sku], [Qty]
    ) AS [line]
)
FROM [applied]
ORDER BY [outer].[CreatedAt] DESC, [inner].[Sku]
SKIP 0 LIMIT 50
SELECT [outer].[Id] AS [OrderId], [inner].[Sku], [inner].[Qty];
```

The CTE materialises the raw `[outer, inner]` merged rows; the main query reads them as a virtual collection and the `SELECT` / `ORDER BY` / `SKIP` / `LIMIT` paths apply normally. CTE names use one bracketed identifier whose payload cannot itself begin with `[`; that spelling is reserved so a CTE reference cannot be confused with the canonical `[Namespace].[Collection]` representation.

**Observability.** `EXPLAIN` returns a `Strategy = CrossApply` / `OuterApply` row with the inner collection's `DocumentCount` as a worst-case per-outer-row hint. A nested inner row shows a representative access path computed with a typed correlation placeholder; a real outer value or different statistics can choose another path. The APPLY `EstimatedRows` is `null` when merged cardinality cannot be defended. `EXPLAIN ANALYZE` adds a `LateralApply(<innerCollection>)` stage with actual `RowsProduced` and `ElapsedMicros`; that stage also participates in slow-query attribution.

## SERIES

`SERIES` generates rows, one per step, with no collection behind them. It is a relation wherever one is: the `FROM` of a query, CTE, derived source, set-operation branch, view or APPLY body, the outer source of an APPLY, and the input of `JOIN`, `LEFT JOIN` or `CROSS JOIN`.

```
SERIES <instant> TO <instant> EVERY <n> MINUTE|HOUR|DAY|WEEK|MONTH|YEAR [IN TIMEZONE '<tz>'] [alias]   -- temporal
SERIES <integer> TO <integer> [EVERY <n>] [alias]                                                      -- integer
```

| Form | Columns | Row |
|---|---|---|
| Temporal (a unit follows `EVERY <n>`) | `[Start]` DATETIME, `[End]` DATETIME, both non-null | the half-open step `[Start, End)` |
| Integer (no unit) | `[Value]` INT64, non-null | one value; the step defaults to 1 |

**Rows.** A row exists for every step whose start is before `TO`, so `TO` is exclusive, as in `VALID FROM ... TO`; a start at or after `TO` yields no rows. The last step keeps its whole `[End]`, which may lie past `TO`. An integer series stops before its next value would overflow INT64.

**Stepping.** Step `k` is the start bound advanced by `k · n` units, each computed from the start, never from the previous step: a series anchored on January 31 steps to February 28 and March 31. Without `IN TIMEZONE` a temporal series steps with `DATEADD` arithmetic in the start bound's own offset. With `IN TIMEZONE` (a fixed offset such as `'+01:00'`, `'Z'`, or an IANA zone id such as `'Europe/Stockholm'`, as [`LAST PER`](temporal.md#last-per-temporal-downsampling) accepts and resolves them) `DAY`, `WEEK`, `MONTH` and `YEAR` step the zone's wall clock, `MINUTE` and `HOUR` step fixed elapsed time, a boundary inside a skipped interval moves to the first valid instant after it, and every `[Start]` and `[End]` carries the zone's offset at its own instant, so `EXTRACT`, `DATE_TRUNC` and `CAST(... AS DATEONLY)` read local dates. A quarter is `EVERY 3 MONTH`.

**Operands.** The bounds and the step are constant expressions: literals, `@parameters`, `NOW`, scalar functions (`DATEADD`, `DATE_TRUNC`, `CAST`, …), arithmetic, concatenation and `CASE`, and, in an APPLY body or a correlated subquery, the enclosing row's columns (`SERIES [o].[CheckIn] TO [o].[CheckOut] EVERY 1 DAY`), read at the precedence of a `BETWEEN` operand, so parenthesize a comparison. They are evaluated once per statement, or once per outer row, with the statement's `NOW`; they never read a field of their own query or hold a nested query (`INVALID_STATEMENT`) or a window function (refused as an [instant](temporal.md#instant-expressions) refuses one). A temporal bound is admitted as an [instant](temporal.md#instant-expressions) is: a DATETIME as given, text by the DATETIME text rule, `NULL` or unreadable text `INVALID_VALUE`, any other type `TYPE_MISMATCH`. An integer bound and the step are admitted as a `LIMIT` value is: any integer, an integer-valued number or integer text, anything else (a fraction, `NULL`, a non-numeric value) `INVALID_VALUE`; the step must be positive (`INVALID_VALUE`). An unknown zone is `INVALID_VALUE`, with `LAST PER`'s text. A bound that reads the enclosing row is named as written, in its refusal (`SERIES end value '[o].[CheckOut]' cannot be null.`) and in EXPLAIN's series notes, never by the synthetic parameter its correlation binds it through.

**Temporal clauses.** A series has no version history: `AS OF`, `IN BETWEEN` and `LAST PER` on it are `WRONG_OBJECT_TYPE`, as on a system collection. Per-period reads put the instant inside an APPLY body instead ([per-period reads](temporal.md#per-period-reads)).

**Execution.** Rows are generated as they are read, in constant memory, and observe cancellation, so `LIMIT` ends a long series after its first rows; a step whose `[End]` leaves the DATETIME range is `INVALID_VALUE` when it is reached. As a JOIN input a series is materialised once for the join, like a CTE input. `EXPLAIN` shows a `Series` source row with the exact row count as `EstimatedRows` when the bounds are known, and `null` when they read an outer row ([EXPLAIN](#explain--query-plan-introspection)).

```sql
-- Every month of 2026 in Stockholm, starting at local midnight
FROM SERIES '2026-01-01T00:00:00+01:00' TO '2027-01-01T00:00:00+01:00' EVERY 1 MONTH IN TIMEZONE 'Europe/Stockholm' [m]
SELECT [Start], [End], EXTRACT('MONTH', [Start]) AS [Month], CAST(DATEADD('DAY', -1, [End]) AS DATEONLY) AS [LastDay];

-- The integers 1 to 10, and a calendar of the next 7 days
FROM SERIES 1 TO 11 [s] SELECT [Value];
FROM SERIES DATE_TRUNC('DAY', NOW) TO DATEADD('DAY', 7, DATE_TRUNC('DAY', NOW)) EVERY 1 DAY [d];

-- Nights per booking: the series reads the outer row's bounds
FROM [Hotel].[Bookings] [b]
CROSS APPLY (FROM SERIES DATE_TRUNC('DAY', [b].[CheckIn]) TO DATE_TRUNC('DAY', [b].[CheckOut]) EVERY 1 DAY [d] SELECT [Start]) AS [n]
SELECT [outer].[Id] AS [Booking], CAST([inner].[Start] AS DATEONLY) AS [Night];

-- Days with no orders: a series as a LEFT JOIN's outer
FROM SERIES '2026-03-01T00:00:00Z' TO '2026-04-01T00:00:00Z' EVERY 1 DAY [d]
LEFT JOIN [Sales].[DailyTotals] [t] ON [d].[Start] = [t].[DayStart]
WHERE [t].[DayStart] IS NULL
SELECT [d].[Start];
```

## EXPLAIN — query plan introspection

JOIN key binding checks field existence and the runtime scalar equality domain, including compatible numeric types, against the logical relation aliases. APPLY ON conditions bind the merged pair schema, parameters, functions, and nested subqueries. These checks run for physical, derived, and CTE inputs even when inputs are empty, and invoke no query function. Invalid ON fields are identified as ON predicate errors. Scalar-subquery and lateral result-schema discovery use the same checks before row evaluation.

Schema discovery preserves the flat JOIN output used when a SELECT includes any computed expression or AS alias, including plain selected fields beside it.

Static EXPLAIN also rejects these statements, which execution rejects while binding them, and reports the first failing clause in clause order: a repeated plain SELECT path, ORDER BY of a plain `SELECT DISTINCT` outside its selected keys, SKIP or LIMIT parameters that are not non-negative integers, `AS OF` and `IN BETWEEN` on non-temporal collections, undeclared aggregate operands (including `COUNT`), and HAVING without GROUP BY or an aggregate. A bare field name that more than one joined relation declares fails with `AMBIGUOUS_FIELD`. The plan is analyzed against the schema generation the statement was validated against.

A source-qualified sort key retains its source identity and type even when a computed output uses the same leaf name. A relation qualifier also takes precedence over a same-named computed output. Grouped queries retain their aggregate sorting path; qualified grouping keys in ORDER BY and HAVING bind the published grouping columns.

ORDER BY may name a computed SELECT alias. These values are projected before sorting and final paging. Additional source sort keys keep their original paths in hidden columns that are removed from output; physical, derived, and CTE sources use the same bounded spill-capable result sorter. EXPLAIN represents this as Projection followed by Sort over the unpaged source plan.

Sorting and HAVING also bind before plan rendering or nested schema discovery. ORDER BY uses source columns plus computed aliases for ordinary projections, and the completed aggregate output for grouped queries. Window shape, literal offset/bucket contracts, partition/order fields, and percentile ranked types share execution's schema validator. These checks do not evaluate percentile probability expressions or invoke HAVING functions; their values remain execution inputs. Empty outer rows do not bypass validation of a nested consumer.

CTE, plain-view, and derived-query consumers have their own plan boundary. Their producer remains a child, so a source index is not presented as an index on the produced rows. `VirtualScan`, `Filter`, `Sort`, and `Window` describe consumer work; virtual aggregation uses `HashAggregation`, and a join of produced rows is a `DeferredJoin` boundary over its inputs. Consumer rows report null `Index`, `Direction = None`, and `EarlyExit = false`; any proved source seek or early stop remains visible on its producer child. A Filter row counts its predicate leaves. Filtering, grouping, DISTINCT, HAVING, and joins leave output cardinality unknown without supporting evidence. Scalar aggregation emits one row before HAVING, even for empty input. Sorting and windows preserve cardinality; consumer SKIP/LIMIT adjusts a known estimate using current parameter values. Virtual system sources use the same consumers above a `VirtualScan`, with unknown snapshot cardinality. Static EXPLAIN reads their registered schema without capturing rows; ANALYZE performs ordinary snapshot execution. Both reject temporal clauses on current-state system sources, and composed APPLY remains supported.

When a join reads a CTE, plain view, system collection or `SERIES` on either side, its FROM relation included, `DeferredJoin` marks the join boundary: runtime chooses access and ordering after materializing those inputs. Its children are its inputs, one per relation in written order and named by alias: `Relation input:` for a stored relation, `CTE input:` for a CTE or plain view, `Derived input:` for a derived FROM table, `System input:` for a system collection, `Series input:` for a series and `Dependent input` for an APPLY body. Each produced input's complete plan nests under that input, including derived bodies, grouping, paging, and recursive expansion; a system input is a `VirtualScan` with unknown snapshot cardinality, and a series input a `Series` whose estimate is its exact row count. Physical `RelationInput` rows report input cardinality without claiming a selected scan or index; a temporal relation's count includes every retained version and snapshot isolation can hide or resurrect rows, so either reports `null`. Equality and dependent join output estimates are unknown, except that a known-empty input empties an inner or cross join and a `LEFT JOIN` on a physical relation's primary key keeps the estimate before it; an all-CROSS join multiplies known input estimates, saturating on overflow. Consumer filters, grouping, windows, sorting, and paging appear above this boundary. ANALYZE nests the tree runtime selected from the materialized inputs under the boundary, as an ordinary join's tree nests under its root: each measured `JoinPlan:` node under the node it feeds, and each input runtime materialized (a CTE, view, derived table, system collection or series) under the node that reads it, the deepest node whose aliases include the input's, carrying the rows it held and the time reading and materializing it took. A stored relation has no input row there: the node that reads it measured that read, as in an ordinary join's tree. A join that composes its relations one edge at a time in written order (over a derived or series FROM relation, or for a consumer that reads the joined rows, such as a window) runs the left-deep tree of that order, and ANALYZE lists it so: each edge's tree stands in place of the next edge's scan of the rows joined so far, and every node names the relations it holds and joins on the keys its `ON` clause wrote, so a composed stored join's measured nodes are the nodes its static tree describes. Such a composition reads its FROM relation into the rows its first edge replays, and the tree's row of that relation measures the read: a stored relation, which it reads through the `WHERE` conjuncts that compare only that relation's declared top-level scalar columns (none nested, computed, array-valued or a vector) with literals, parameters or lists of them, under `AND` or `OR`, however each column is spelled (by the relation's alias, its collection name or, where only that relation declares it, its bare name), and through none when the relation is polymorphic or read `IN BETWEEN`, on its `Scan`, as a bushy leaf's read is measured (the relation's row count as `RowsIn`, the rows read as `RowsProduced` and the time reading them took), and a produced relation on its input, with the rows it held and the time reading and materializing it took. Its nodes carry the estimates its static tree carries: the `Scan` of a stored relation is `null` when those conjuncts restrict it or when it is temporal or read under snapshot isolation, and each join estimates over the node below it, never over the exact count of the rows its edge replays. Any other conjunct that reads only the FROM relation (one over a nested path, a computed column or row metadata, or an array `MATCH`) restricts no read and filters the composed rows, so a composition whose read none of those comparisons restricts estimates its `Scan` over the whole relation, where an ordinary join of the same relations that reads such a conjunct at its FROM scan estimates that scan `null`. An ordinary join's FROM scan reads a `WHERE` that holds an `OR` other than equalities of one column only as a whole, and the join evaluates it after joining when any leaf of it reads a joined relation, so there those comparisons restrict the composition's read, whose `Scan` estimates `null`, while the ordinary join's scan reads the whole relation through no conjunct. `LAST PER` reads its FROM relation through the conjuncts its bucket walk samples ([temporal downsampling](temporal.md#last-per-temporal-downsampling)). ANALYZE nests a tree only where execution selected exactly one tree over the boundary's aliases, since a node is identified by the aliases it holds. When it selected more than one, as for a join in a body run once per outer row or for joins over the same aliases anywhere in the statement, such as both branches of a set operation, whether they join the same relations or not, each such boundary keeps its inputs as static EXPLAIN lists them, unmeasured, and the measurements stay stage rows under the statement root: each measured `JoinPlan:` node, and each input runtime materialized as a `JoinInput:<alias>` row of strategy `Materialized` carrying the rows it held and the time reading and materializing it took.

Recursive producers use `RecursiveExpansion`, with a seed child and a `RecursiveStep` boundary for repeated member evaluation. A `Recursive member level` child describes one level as the member runs it, at the catalog generations the statement captured: its reference to the CTE is a `VirtualScan` of the frontier the previous level added, and a member that reads only the frontier's keys reads them through an `IN` query over that reference in its `WHERE`, noted as the key membership each level adds. Their full cardinality is unknown; a seed estimate is not the full expansion's estimate. Static plans never execute the seed, member, or consumer to discover data-dependent counts.

Write-predicate EXPLAIN also binds scalar, negated, and subquery predicates, and predicates that read a virtual computed column, for UPDATE, REPLACE, DELETE, SEAL, UNSEAL, and CANCEL VERSION, including transitive plain views and correlated outer fields. It does not evaluate those predicates. Their final write access depends on resolved values or matched keys, so the root reports `Strategy = DeferredPredicate`, null `Index` and `EstimatedRows`, `Direction = None`, `EarlyExit = false`, and `FilterCount = 0` (no native write filters have been produced yet). Native predicates retain their concrete access plans. ANALYZE executes the ordinary write path and reports affected rows; the deferred root still describes the static boundary. TEXT and JSON agree.

Read-query EXPLAIN expands plain views transitively using the same visible definitions as execution, including private changes inside a migration. Fully qualified view identities stay distinct from same-named lexical CTEs. Static planning reads schemas without executing stored expressions; ANALYZE runs and consumes the expanded query. TEXT and JSON use the same bindings.

Static planning binds output columns from catalog metadata through derived sources, CTEs, logical JOIN aliases, and scalar projection subqueries. It uses the same wildcard expansion as execution, so missing nested targets and duplicate output names fail even on empty collections. Set-operation branches and recursive members must have compatible binary column layouts. NEAREST uses the same target, vector-dimension, finite-value, and cosine non-zero checks as execution. Schema binding also validates WHERE fields, parameters, functions, and nested predicate subqueries. Fixed scalar correlations and lateral inputs use schema-typed placeholders for outer values, admitted by the same outer-operand rules as the row values execution supplies: an outer key of another numeric kind, or text, against a numeric inner field binds as it executes, at every correlation depth. Native residual correlations validate original field presence and the inner schema while deferring row-dependent parameter values until execution. Schema binding does not read query rows or invoke query/subquery functions. EXPLAIN preserves correlated operand rules: an absent outer IN operand is a non-match, and an absent scalar-comparison operand uses NULL. Inner query fields and ordinary predicate siblings are still validated; uncorrelated subqueries do not exempt their outer comparison field from validation. Data-dependent errors, such as a scalar subquery returning multiple rows, still require execution to detect.

Scalar or correlated HAVING is described as a residual stage after aggregation and before paging. It is not pushed into the source access descriptor. Temporal LAST PER joins and aggregations use the same admitted shapes as execution.

Computed-field plans include nested Object/Array values and subtype extensions. Predicate binding accepts source-qualified `Body` paths with the same meaning as execution. EXPLAIN reports the actual storage access before virtual-value enrichment, including index seeks from stored-field filters that execution pushes down. Predicates on virtual values remain above that input. Aggregation is described over the input, and post-enrichment filtered/joined output estimates are unknown. Stored computed values retain ordinary index planning. Scalar residual filters report the native conjuncts retained by execution and any full-row enrichment their input requires. Static EXPLAIN runs no nested query, so a comparison with an uncorrelated scalar subquery's value or an uncorrelated `IN` query's members on a field is reported in the residual filter alone, a negated one adds no proven complement to the scan, and a `WHERE` holding one with no scalar or negated predicate is reported over a scan with no native filter. Execution runs those queries first and filters, and can seek, by every native conjunct, those comparisons and complements included. An `IN` query over an array element still reports its membership access (`ArrayMembership`).

Prefixes a supported statement and returns plan rows describing the planner's decision instead of running the statement. The first row is the statement root; plans with a meaningful nested boundary, such as a lateral inner, append child rows.

```sql
EXPLAIN FROM [Store].[Products] WHERE [Id] = @id;
EXPLAIN FROM [Shop].[Orders] WHERE [Region] = 'north' AND [Status] = 'open';
EXPLAIN FROM [Shop].[Orders]
    GROUP BY [Region] ORDER BY [Region] ASC
    SELECT [Region], COUNT(*);
```

The result row carries the columns:

| Column | Meaning |
|---|---|
| `Operation` | High-level root label (`Select`, `Insert`, `Update`, `UnionAll`, `Intersect`, `Except`, `WithCte`, …). Child plan and ANALYZE stage rows use an indented `└─ <child>` label. Conventional-join nodes use `JoinPlan:join:<sorted-aliases>`; the sorted alias set is the stable node identity shared by static and measured plans. A join tree is listed in pre-order from its root, each node's inputs indented one level below it, for a left-deep tree (its FROM scan deepest) as for a bushy one, and ANALYZE lists the same tree wherever execution selected exactly one tree over its aliases in the statement. |
| `Strategy` | The planner's pick — see table below. |
| `Index` | Exact index field list selected by the planner when an index is used, `Temporal` for `TemporalIndex` and `TemporalRange`, else `null`. For cost-modeled same-family alternatives, this is the path runtime dispatch receives; predicate or index-registration order cannot substitute another equality, range, or compound index. |
| `Direction` | `Ascending` / `Descending` / `None` for ORDER BY pushdown; `Distance` on a `VectorTopK` ranking, and empty on a `JoinPlan:` node. |
| `EarlyExit` | `true` for a naturally bounded primary-key / temporal point seek, or when a positive LIMIT actually caps an ordered scan. Secondary range and ORDER-only scans require a UNIQUE index because non-unique ties need their complete equal-key run for the final primary-key tie-break. Remaining post-scan filters, aggregation, any exact total-count request (including unfiltered scans), temporal visibility, and an overflowing `SKIP + LIMIT` disable the cap. An ordered scan without the cap can still stop once `SKIP + LIMIT` of its rows pass every filter and the equal-key run holding the last of them is read; that point depends on the data, so it reports `false`. |
| `FilterCount` | Number of the `WHERE`'s native `AND` conjuncts. An `OR` group is not a conjunct, so a `WHERE` made of `OR` alone reports `0`. |
| `Notes` | Freeform hints. Static join-plan nodes report `NodeId`, the node's alias set, and the equality edges assigned to that node; measured `EXPLAIN ANALYZE` join-plan nodes report only the alias set and equality edges, their node identity being the `JoinPlan:` suffix of `Operation`. Other notes include missing-index suggestions for FullScan (`WHERE [X] has no index; CREATE INDEX ...`), GROUP BY labels, set-op per-branch counts, partial-index matches, computed-column injection slow paths, how each correlated subquery runs — set-wise as the generated `SEMI`, `ANTI` or COUNT comparison joins it names, or evaluated per outer row, with the reason when the live acceptance rule declines a rewrite the decorrelator formed (a correlation key or membership column that is an Object or Array, an array element path, or of an unrelated scalar type, or a scalar aggregate whose equality domain is not join-compatible or cannot be proven, or whose compared value is an array element path); a key over either relation's metadata forms no rewrite, so only the per-row evaluation is stated, and an undeclared key is the nested query's diagnostic, which EXPLAIN reports instead of a plan — and trigger-fire annotations on DML rows. Numeric fragments use invariant formatting with `.` as the decimal separator, independent of server culture. |
| `EstimatedRows` | Output row count (nullable). Point PK and temporal seeks report `1`, except `PK IS NULL` reports `0` because a primary key cannot be null. A full or ordered scan without a WHERE predicate reports a standard collection's document count; with a predicate it reports a fresh-statistics estimate of the surviving rows where one applies and `null` otherwise, and over a temporal collection, whose count includes every retained version, it reports `null`. Temporal `IN BETWEEN` full scans report `null` without an overlap estimate. Primary-key history uses `TemporalRange`, estimated from fresh retained-version statistics before interval and residual filtering. MVCC snapshot full scans also report `null`: an older snapshot can hide later inserts or resurrect later deletes or temporal segments. A cost-selected `FullScan` preserves the rejected candidate's filtered-output estimate. Statistics-dependent equality/range/compound plans report `null` when no fresh statistics apply. `BitmapAnd` combines independent selectivities and caps the estimate by the smallest input; actual correlation can raise or lower output. `BitmapOr` sums its value-aware input estimates, discounts proven repeated cached probes, and caps the union at collection cardinality. `LIMIT N` caps a known value at N and leaves an unknown one `null`, as a `NEAREST` ranking's `TOP N` does; `SKIP M` subtracts M, including set-level paging. Aggregations report the distinct-group count (compound NDV when available, else per-column NDV product), which `SKIP` / `LIMIT` page as they page rows. A plan row's `Notes` join their annotations with `; ` and never start with a separator. The missing-index hint names only fields no index can seek on: a field that leads a compound index, or an element path an array index covers, is not suggested. Set-ops combine branch counts by operator (`UNION ALL` sums, `INTERSECT` takes the min, `EXCEPT` keeps the left) before applying their combined paging. |
| `Collection` | The stored collection whose access the row describes, as `[Namespace].[Collection]` in the catalog's spelling: the collection a read's, write's or aggregation's access path reads (or an `INSERT` writes), wherever the row stands — the statement root, a CTE's, view's or derived table's own plan below its input, a set operation's branch, an index-intersection input. Any index the row's `Index` names or its `Notes` suggest (`WHERE [X] has no index; CREATE INDEX ...`) belongs to this collection, whichever collections the statement itself names. `null` on a row that reads no stored collection by an access path of its own: a consumer of produced rows (`VirtualScan`, `Filter`, `Sort`, `Window`, `Projection`, `VectorTopK`, `AggregateExpressions`), a `JoinPlan:` node, a `DeferredJoin` with its `RelationInput`, system and series inputs, a set operation's combination, a lateral apply, and every measured stage row. |

Optional join and lateral-inner annotations may be omitted when an ordinary query shape cannot be refined, but EXPLAIN never turns structural corruption (including a detector nested inside another exception) or process-memory exhaustion into a successful partial plan. Corruption returns its stable error classification and quarantines the detector's fault domain.

When engine-wide snapshot isolation is enabled, static `EXPLAIN` reports the physical serial buffered `FullScan` that execution uses for a standard collection. Current indexes cannot reconstruct that snapshot's hidden, substituted, or resurrected rows. Temporal timelines do not carry CSN versions, so they keep their ordinary committed valid-time view and EXPLAIN continues to report eligible temporal point/index strategies rather than a fictitious MVCC full scan.

Planner field identity follows the language's case-insensitive schema identifier rule after stripping an optional `Body.` prefix. This includes the temporal predecessor strategy, but that strategy matches only the collection's declared primary key. If the primary key is `[Key]`, `[Key]`, `[kEy]`, and `Body.Key` produce the same runtime and EXPLAIN path; ordinary fields named `[Id]` or `[DocumentId]` are never reinterpreted as temporal identity aliases.

For a join with only catalog-backed inputs, static EXPLAIN appends the selected physical join tree instead of reconstructing it from written JOIN order. `Scan` leaves, `StreamingLeftDeep` nodes, and `MaterializingBushyHashJoin` nodes carry their aliases, assigned equality edges, and an estimated output cardinality wherever the evidence defends one, `null` otherwise. A `Scan` reports its relation's document count unless its scan applies a WHERE predicate (nothing estimates the surviving rows), the relation is temporal (the count includes every retained version), or snapshot isolation reads it. A cross join multiplies known inputs. An inner equality join scales them by the selectivity its planner derives from fresh `ANALYZE` statistics on the join keys: the inner key's distinct count for a `StreamingLeftDeep` node, both keys' for a `MaterializingBushyHashJoin` node. A `LEFT JOIN` whose ON equality reads the joined relation's primary key produces exactly one row per outer row, matched or null-extended, so it reports its outer estimate without statistics, even when the joined relation is temporal: a join reads at most one version of each key. An equality join without those statistics, any other outer join, a semi or anti join, and every node above an unknown input report `null`, although a known-empty input still empties an inner or cross join. Foreign keys do not inform these estimates. The same immutable representation drives execution.

Grouped expressions appear as a projection note on the aggregate plan; the output estimate includes final literal or parameterized SKIP / LIMIT. Static binding validates their fields and aliases without evaluating the expressions.

Grouped `SELECT DISTINCT` reports a `Distinct` operation with `HashAggregation` strategy and a `Projection input` child holding the aggregate plan. Its output estimate is unknown because different source groups can project identical tuples. The final ordering and paging are validated against the selected distinct output.

`EXPLAIN ANALYZE` runs and fully consumes the inner statement, then appends `Measured` and eight measured columns: `RowsProduced`, `RowsIn`, `ElapsedMicros`, `StreamingMode`, `SpilledBytes`, `AdmissionDecisions`, `RadixDepth`, and `PartitionCount`. `Measured` (`BOOL`) says whether execution measured the row: it is `true` on the statement summary, on every stage row, on every node of a join tree execution ran and on every input it materialized, and `false` on a row execution ran no stage of its own for, which keeps its place in the plan with zero placeholders in the eight measured columns — a produced relation's own plan below its measured input (a CTE's, view's or derived table's `Virtual input`), a set operation's branches, a lateral body's representative plan. Read `Measured`, never a zero, to tell a measurement from a placeholder. `RowsIn` is the actual number of input rows observed at an instrumented stage; it is `0` on the statement summary and on a row `Measured = false`. `StreamingMode` is `Streaming`, `Buffered`, or `n/a`. `SpilledBytes` is the cumulative byte count spilled above `EngineOptions.MaxInMemoryStreamingState` across every operator the statement touched; `0` means everything fit in memory. `AdmissionDecisions` is the engine-wide admission-controller observation during the statement's wall-clock window; it is `null` on the default `NoOpAdmissionController`. A bounded controller reports one coherent policy snapshot as `"reserved=X/max=Y warn=W%/spill=S%/reject=R% crossings=Z"`, its percentages in invariant formatting with `.` as the decimal separator; another non-no-op implementation reports `"reserved=X/max=Y crossings=Z"`. Concurrent sibling statements can contribute to the crossing delta. Per-stage rows leave this field null because tickets have no causal stage attribution. A stage's radix fields report its deepest level and number of non-empty top-level spill partitions; descendant partitions are represented by the depth rather than added to the count. The summary takes the maximum depth and sums partition counts across stages. Both are `0` when no observed stage engaged radix partitioning. Child rows use `StreamingMode = n/a`: the field describes the root result owner's delivery shape, and nested plans or stage statistics do not own a result source.

`ElapsedMicros` is a non-negative `INT64`. Tick conversion remains exact at long durations without overflowing an intermediate product; only a duration beyond the representable result domain saturates at `INT64` maximum. Measured row counters also saturate at `INT64` maximum. `SpilledBytes` is non-negative: additions across operators are checked and a negative late-bound provider value fails the statement/observation instead of being reported as a false small total. It is a lifetime write counter: draining or disposing a lazy result does not subtract spill runs that were already written, including typed membership sets built for `IN (subquery)` evaluation.

Stage attribution is flow-local to the analyzed statement. A nested `EXPLAIN ANALYZE` uses its own collector and cannot add stages to, replace, or clear the parent statement's collector.

When an instrumented parallel stage runs, the summary row's `Notes` includes `Parallel: N workers, rows/worker total=T min=L max=H [c0,c1,...].` The note is based on the workers that actually ran. Merely configuring `EngineOptions.MaxQueryParallelism > 1` does not add it because the selected plan may remain serial.

### `FORMAT JSON` — structured plan output

A parenthesised option list selects the output format (PostgreSQL-shaped). `FORMAT JSON` returns the same plan as a single `Plan` text column holding a nested-JSON document instead of the tabular rows — for plan visualisers and tooling that can't parse the human table:

```sql
EXPLAIN (FORMAT JSON) FROM [Shop].[Orders] WHERE [Region] = 'north';
EXPLAIN (ANALYZE, FORMAT JSON) FROM [Shop].[Orders];
EXPLAIN (FORMAT TEXT) FROM [Shop].[Orders];   -- explicit default; same as bare EXPLAIN
```

The JSON is a one-element array whose object is the root plan node, carrying the same fields as the tabular columns (`Operation`, `Strategy`, `Index`, `Direction`, `EarlyExit`, `FilterCount`, `EstimatedRows`, `Notes`, `Collection`, and — under `ANALYZE` — `Measured`, `RowsProduced`, `RowsIn`, `ElapsedMicros`, `StreamingMode`, `SpilledBytes`, `AdmissionDecisions`, `RadixDepth`, `PartitionCount`). Every row nests in the `Plans` array of the row it feeds: the root's stages and inner plans, a consumer's input, a producer's plan under the input it produces, a set operation's branches and a join tree's nodes. The tabular rendering indents each child row two spaces per level after its `└─ ` branch, so both describe one tree, and an `Operation` carries neither the decorative prefix nor the indentation. Typed columns serialise as their native JSON types — `EarlyExit` and `Measured` are booleans, `EstimatedRows` a number, not strings, and a row with no `Collection` carries `null`. The bare `EXPLAIN` / `EXPLAIN ANALYZE` spellings and `FORMAT TEXT` all produce the tabular rows; only `FORMAT JSON` switches to the document column. `FORMAT` accepts only `TEXT` or `JSON`; anything else is a parse error.

For grouped aggregation, the strategy mirrors the order property proved by the selected inner access path. An `IndexOrderScan`, or an ordered `PkRange` / `SecondaryRange` over the complete grouping key, reports `StreamAggregation`; other inputs report `HashAggregation`. The aggregation node itself never reports `EarlyExit = true` because every filtered input row contributes before group paging.

## Detailed syntax and execution

A scalar WHERE comparison accepts complete expressions on either side, including literal-led arithmetic and concatenation: `[Price] > 10 + 5` and `[Name] = 'A' || 'da'`. Arithmetic binds before comparison. A lone literal or parameter retains the ordinary native comparison and its index eligibility.

Scalar WHERE binding validates function arity and parameter presence before publishing rows, including empty inputs. Polymorphic references read the active envelope and yield NULL for an absent subtype field; incompatible declarations reject during binding. Qualified references use the most specific visible relation prefix, with the inner scope winning ties. An inner source alias leaves an enclosing collection-qualified reference available for explicit correlation. Nested predicates keep references to their own enclosing row; adding a JOIN or naming a nested alias `outer` or `inner` does not change which row a correlation reads. Execution and EXPLAIN use the same scope rules.

A field equality inside OR or NOT remains a row predicate over the merged join schema. Only an equality required by the top-level AND chain may become an additional optimizer join edge. Extracting an equality from one OR branch would incorrectly discard rows admitted by the other branch.

For a single physical, view, derived, CTE, or system source, native predicate fields, alone or beside scalar or correlated WHERE expressions, must exist in the source schema. An empty source or a true OR sibling cannot hide an unknown field. JOIN predicates follow the same rule on every route, named relative to the relation each reads, as described in the JOIN section. Correlated operands retain their own binding rules: an absent outer operand of correlated IN remains a non-match even when the inner result contains NULL, including beside a scalar predicate. Declared NULL operands still use ordinary NULL equality, and NOT IN remains the complement of IN. An IN-to-join optimization declines when that operand is absent from its own source.

### Scalar text predicates

`CONTAINS` and `STARTSWITH` are also infix scalar operators in projections, `CASE WHEN`, and computed expressions. They bind at comparison precedence, accept string expressions on both sides, and produce BOOL. WHERE also accepts field references, function calls, and CASE expressions as the right operand. A null operand produces NULL, including under NOT. Matching uses invariant lowercase folding and ordinal comparison; `%` and `_` are literal characters, not wildcards.

```mql
FROM [Store].[Products]
SELECT CASE WHEN [Name] CONTAINS 'widget' THEN 'Match' ELSE 'Other' END AS [Category];
```



<a id="syntax-clause-ordering--strict"></a>

### Clause ordering — strict

`FROM` → `AS OF` / `IN BETWEEN` → `JOIN` … → `WHERE` → `NEAREST` → `LAST PER` → `GROUP BY` → `HAVING` → `ORDER BY` → `SKIP` → `LIMIT` → `SELECT` → `WINDOW` → `OPTION`

A `WITH` block precedes `FROM`. A `SERIES` source's `TO`, `EVERY` and `IN TIMEZONE` belong to the source and precede its alias: `FROM SERIES @from TO @to EVERY 1 DAY IN TIMEZONE 'Europe/Stockholm' [d] JOIN ...`. The named-window `WINDOW` clause follows `SELECT`, whose `OVER [w]` references it, and the statement-level `OPTION (...)` suffix — its keys `TIMEOUT` and `MAXDOP` ([cancellation](cancellation.md#option---per-statement-options)) — comes last: `FROM [App].[Orders] SELECT [Id], ROW_NUMBER() OVER [w] AS [Rn] WINDOW [w] AS (ORDER BY [Id]) OPTION (TIMEOUT '5s')`. A `WINDOW` before `SELECT`, or after `OPTION`, is a parse error.

<a id="syntax-from"></a>

### FROM

```sql
FROM [Ns].[Collection];            -- bare collection
FROM [Ns].[Collection] [alias];      -- with bracketed alias
FROM [CteName] [alias];              -- a CTE
FROM (<query-expression>) [alias];   -- a derived source
FROM SERIES 1 TO 11 [alias];         -- a generated series (see SERIES)
```

The query-level `ORDER BY` clause accepts at most 64 scalar fields with a defined total order. Text parsing and direct AST validation enforce the count before execution or child-field traversal. BYTES keys use unsigned lexicographic order, with shorter strict prefixes first and no decoding or case folding. NULL sorts before present empty bytes, then non-empty bytes ascending; DESC reverses this. OBJECT, ARRAY, and VECTOR ordering keys are errors before result publication, even when input is empty or the key is a grouped field / aggregate output. These rules apply to base, joined, CTE, system-collection, in-memory, and spilled sorts. Aggregate-local ordering inside `COLLECT_ARRAY` / `JOIN_STRING` remains a separate raw-value operation.

<a id="syntax-join"></a>

### JOIN

```sql
JOIN       [B].[B] [b] ON [a].[X] = [b].[X]   -- inner (INNER JOIN is an accepted synonym)
INNER JOIN [B].[B] [b] ON [a].[X] = [b].[X]   -- explicit synonym for JOIN (PostgreSQL portability)
LEFT JOIN  [B].[B] [b] ON [a].[X] = [b].[X]   -- left outer
CROSS JOIN [B].[B]                          -- cartesian

-- Omit the current joined relation's equality key from wildcard output
JOIN [B].[B] [b] ON [a].[BId] = [b].[Id] OMIT INNER KEY
```

A JOIN input names a stored collection, plain view, CTE, `SERIES`, or virtual `[Mnemic].*` system collection, never a derived table (`JOIN (FROM …) [x]` is a parse error); a system input is read as the same visibility-filtered snapshot as a FROM source, before join planning.

`OMIT INNER KEY` is accepted only on `JOIN` / `INNER JOIN` and `LEFT JOIN`. The marked logical joined relation loses its exact key leaf from an omitted `SELECT`, `SELECT *`, or `SELECT [alias].*`; nested keys preserve their parent Object and siblings, and a key in a polymorphic object's subtype fields leaves every subtype that declares it, while omitting the object's discriminator is refused with `INVALID_STATEMENT`. Operand order and optimizer reorder do not change which relation is "inner" here. An explicit projection of the key restores it.

Omission is result-only. Later JOINs, WHERE, ORDER BY, expressions, and ambiguity checks bind against the original schemas. On a qualified wildcard, a duplicate `EXCLUDE` is harmless, but `REPLACE` / `RENAME` of the omitted slot is rejected, as is an omission that leaves the wildcard empty. CROSS JOIN, lateral APPLY, and internal SEMI/ANTI shapes cannot carry the modifier. It does not count toward the 1,024 wildcard-modifier target limit.

The executor picks each join's algorithm when it runs. An equality on the joined collection's primary key reads that collection by key for each outer row and switches to a hash join once those reads reach the collection's row count, so a long outer side costs at most about twice the cheaper of the two; under snapshot isolation, with several key pairs, or with keys of different types, the key read is not used. Any other `JOIN` reads a joined collection of at most 50 rows once into a nested loop, and a larger one into a hash join. Aliases are bracketed identifiers and must be **distinct** — repeating the FROM alias or an earlier JOIN's alias is a parse error (see [JOIN](#join)); self-joins use two distinct aliases for the same collection.

One query accepts at most **16 `JOIN` / `APPLY` clauses**. Each merging edge adds a level to the nested `{outer, inner}` binary result, so the limit prevents the join wrappers alone from exceeding the schema codec's representable depth and bounds left-deep row-copying work.

**Qualified ON keys are alias-exact.** Every alias-qualified outer key in a JOIN chain is validated against the named logical relation before planning. If that relation lacks the field, the statement errors even when another already-joined relation has a same-named field; the qualifier never falls back to that other relation. Inner keys and outer/inner equality-domain compatibility are also validated before execution. A leading path segment is an ON qualifier only when it matches the FROM alias, a prior JOIN alias, the current JOIN alias, or an unaliased CTE relation at any of those positions. Otherwise the complete operand is preserved as an unqualified nested path, so `[bogus].[AId]` binds as `bogus.AId` and can never capture the root field `AId`; a collection name is no exception. On a later edge an unqualified outer key reads the one earlier relation that declares its complete path. With two recognised qualifiers, exactly one names an outer relation and exactly one names the current inner relation; two prior-relation qualifiers and two current-inner qualifiers are parse errors. The current inner qualifier may appear on either side of `=`; one unqualified operand takes the role opposite a recognised qualifier, while two unqualified operands retain the left-outer/right-inner default. Direct .NET AST execution enforces the same ordered scope: a non-null `JoinClause.OuterAlias` must name the FROM relation or a prior JOIN. Unknown programmatic qualifiers are rejected instead of binding to the first outer source, and duplicate programmatic relation qualifiers are rejected instead of overwriting an earlier binding.

JOIN equality uses lossless mixed-numeric comparison across `INT8` / `INT16` / `INT32` / `INT64` / `DECIMAL` / `FLOAT32` / `FLOAT64`, independent of the selected join strategy. Equal values with different physical widths match; values are never rounded through `FLOAT64` merely to build a hash key. Thus integer `9007199254740993` does not match floating-point `9007199254740992.0`, while decimal `0.5` matches floating-point `0.5`. A STRING key and a number key join on the number's canonical text, exactly as the same two fields compare in one row ([comparison value notes](#comparison-value-notes)): `[a].[Code] = [b].[N]` pairs `'1'` with 1 and never `'01'` or `'1.0'`, and a DECIMAL key `1.0` pairs with `'1.0'` only. This holds for an `ON` key, a top-level `WHERE` equality between two relations and a recursive CTE's key, under every join strategy; such an edge never uses a primary-key probe, and a NaN or infinite key, which has no text, is `INVALID_VALUE` where a present STRING key of the edge meets it, as in one row, and joins nothing where every STRING key is NULL or the STRING side is empty. Outside these domains, both keys must have the same scalar type. `OBJECT` and `ARRAY` are not join keys. Incompatible types reject before execution rather than comparing untagged raw storage bytes.

**Unqualified post-join references must be unambiguous.** A bare field name in post-join `WHERE` / `ORDER BY` / `SELECT` binds to the single joined collection carrying it (an inner-only bare name binds the inner, including in WHERE); a name carried by two or more sides errors with `AMBIGUOUS_FIELD` (PostgreSQL 42702 parity) — qualify with the alias. Qualified references remain bound to that exact relation in every plan shape, including a statistics-selected bushy plan; a colliding field on another joined collection does not make the qualified reference ambiguous. The qualifier is never discarded to capture a same-named field on a different relation. If the named relation does not declare the field, every clause errors with `UNKNOWN_FIELD` on every route, `WHERE` included, as for a single source, naming it as the native join does (a `WHERE` leaf relative to its relation); a declared field a row lacks reads NULL. This remains true when a cross-side OR moves an outer-qualified predicate to post-join evaluation, and when the selected field is a polymorphic extension that is absent from the merged physical schema. Scalar and MATCH array paths retain the same qualifier; neither can fall back to a colliding field on a different relation. A field its relation's subtypes declare with different types is declared: as an `ORDER BY` key it is `TYPE_MISMATCH` on every route, named as written (`Cannot sort by 'g.Rating': field has incompatible schemas across polymorphic subtypes.`), never an unknown field. As a projection input (a plain item, an expression's, a window's keys and arguments, a nested query's outer reference) it is `TYPE_MISMATCH` on every route as well. A flattened projection (any `AS` or computed item, a `DISTINCT`, sibling alias dependencies, or a join composed over its merged rows, which publishes flat columns) names it as written (`SELECT field 'g.Rating' has incompatible schemas across polymorphic subtypes. A JOIN projection has one fixed output schema, so every subtype declaration of the field must be structurally identical.`), as a single source refuses one in a computed projection; a plain nested projection reports its layout's own text relative to the relation's envelope (`Column 'Rating' has incompatible schemas across polymorphic subtypes; use distinct extension names or a common field schema before projecting it.`), as a single source's plain item does. Parameters in post-join `WHERE` predicates and cross-side OR groups are validated against the final alias-remapped joined schema on every execution, including plan-cache hits. Polymorphic extension predicates consider every active subtype schema, so an incompatible binding errors rather than silently acting as a non-match.

**Extra equi-join in WHERE.** A top-level `WHERE [a].[k] = [c].[k]` between **two different** join aliases is an extra join condition (a redundant graph edge, e.g. to close a triangle). The optimizer may use it only when it is required by the top-level AND chain. Such a top-level equality of a native join is one equality edge, so both operands must name declared fields of one equality domain, or a STRING and a number, which key on the number's canonical text: an undeclared or ambiguous operand, inner-side metadata, and two unrelated types (`TYPE_MISMATCH`) are rejected before rows are read, naming the operands as written, by statement validation, `EXPLAIN` and execution alike. A join composed over its merged rows (an `AS` alias that another item reads, a window, a `DISTINCT` wildcard, a correlated subquery in `WHERE`) evaluates the same equality as an ordinary comparison and refuses an undeclared operand, inner-side metadata and two unrelated types with the same pair and text, so whether a join composes never decides whether the statement runs. Equality inside OR or NOT retains its complete Boolean expression and executes against joined rows. A comparison that involves an array element path (`[a].[Tags][] = [c].[Code]`) is never an edge: it compares each element with the other row's value on the joined rows, in WHERE and in an APPLY's `ON`. Ordinary field-to-field comparisons also work on a single collection, in DML WHERE, HAVING, and aggregate FILTER, including in a JOIN query's HAVING and aggregate FILTER, which read completed rows rather than add join edges.

**Join order is automatic + cost-based (all-INNER).** Written `JOIN` order doesn't change matched tuples. The left-deep path uses bounded exact search over dependency-respecting prefixes; a connected-subgraph search may pick a **bushy** plan for an acyclic or cyclic graph when that shape has lower estimated intermediate work. Fresh NDV statistics guide both searches; stale NDV is ignored and current collection cardinality is the fallback. Run `ANALYZE` for better estimates. Plan shape never changes the binding of qualified WHERE / ORDER BY / SELECT paths, nor of a raw `[outer]`/`[inner]` path, which names the relation written at that position in every clause. A raw or plain nested JOIN result follows the selected physical `{outer, inner}` tree; use `AS` aliases for a plan-independent output schema. It keeps written order when its ORDER BY, SELECT or wildcard modifiers read a raw path, and read as a relation (a derived table, a CTE or view body, a set-operation branch). [Read sources](read-sources.md#entries) report no entry under the envelope of such a result over two or more edges returned as it is; read through a derived table, it reports one at each relation's placement. Single-relation WHERE predicates are pushed to the matching bushy leaf (the full WHERE remains a residual correctness check). Bushy hash-build tables are bounded by `MaxInMemoryStreamingState`, admission-accounted as `HashBuild`, and spill above the cap; spill totals survive flat `AS` projection and surface through `MqlResult.SpilledBytes` / `EXPLAIN ANALYZE`. JOIN GROUP BY / aggregates replay bounded row storage directly into hash aggregation, avoiding a second full-input copy while preserving input spill accounting. Post-join AND/OR predicates and residual field equalities are evaluated in one bounded replay before aggregation. Unsorted, unprojected left-deep JOIN results with `SKIP` / `LIMIT` apply ordinary post-join residuals while streaming and stop the join producer after the requested filtered window instead of materialising the complete result. Non-aggregate left-deep JOIN `ORDER BY` uses the same stable external sorter as bushy joins and set operations, spilling above `MaxInMemoryStreamingState` before applying `SKIP` / `LIMIT`. Every rows result is published with a validated private snapshot of its schema and polymorphic subtype metadata; unrepresentable nesting, cycles, malformed field graphs, and duplicate identities fail before the row stream reaches a client.

**Flat output with `AS`.** A join `SELECT` that renames (`[a].[F] AS [X]`) or computes (`expr AS [X]`) a column emits **flat** top-level columns (one per SELECT item); a plain un-aliased join SELECT keeps the nested `{outer, inner}` shape, except over a join composed over its merged rows (such as one whose `WHERE` reads a correlated subquery) and in a recursive CTE member, which publish flat leaf-named columns. Adding any `AS` flattens the whole list — qualify colliding names with `AS`. Every field reference inside a computed JOIN expression is bound eagerly to its exact joined source; unknown fields error instead of evaluating as implicit `NULL`.

JOIN projection preserves a present `OBJECT ()` value through plain, computed, aliased, and wildcard output, including subtype fields and dependent aliases. Window `COUNT(field)` counts that present value. A NULL object, absent subtype field, or unmatched nullable JOIN side remains NULL.

**JOIN metadata is outer-only.** The `FROM` row's `[Meta].*` fields work in post-join WHERE / field equality / ORDER BY / plain or computed SELECT / aggregate arguments. An inner alias's `[Meta].*` is rejected explicitly because the join envelope has no independently addressable inner metadata object. Project that metadata in a CTE before joining when needed.

Plain nested projection keeps only requested leaves through the complete multi-join tree. An unmentioned side is an empty object, or `null` when it is an unmatched nullable inner side.

<a id="syntax-cross-apply-lateral"></a>

### CROSS APPLY (lateral)

```sql
FROM [App].[Orders] [o]
CROSS APPLY (
    FROM [App].[Lines]
    WHERE [OrderId] = [o].[Id]
    ORDER BY [LineNo]
    LIMIT 3
    SELECT [Sku], [Qty]
) AS [line];
```

The inline subquery is re-evaluated per outer row; it is one query, so a set operation is its derived `FROM` relation, never the body itself (a parse error). Its `WHERE` and `SELECT` list may reference `[outerAlias].[field]`; each reference binds to the current outer row, and a projected reference publishes the field's declared type. Nested subqueries retain their own enclosing row scopes, and an inner alias shadows the same outer alias. Execution and EXPLAIN use the same binding rules. The raw result schema is the canonical `{outer:Object, inner:Object?}` shape; statement aliases do not rename those public envelope fields. Two semantics ship: **`CROSS APPLY`** drops outer rows with zero inner matches (INNER); **`OUTER APPLY`** keeps them with the inner Object null-flagged (LEFT-OUTER). PostgreSQL-style portability sugar also accepted: `JOIN LATERAL` / `INNER JOIN LATERAL` mean `CROSS APPLY`, while `LEFT JOIN LATERAL` means `OUTER APPLY`; canonical printing uses APPLY. An optional ON predicate evaluates each actual pair after inner ordering and paging, before null padding. TRUE matches; FALSE and NULL do not. OUTER APPLY preserves an outer row with a null inner when all pairs are rejected. ON may reference earlier aliases and the new lateral alias and use scalar expressions, parameters, or subqueries. ON TRUE remains the identity condition.

The merged columns are bound from catalog and projection metadata before row delivery, without executing the inner query or invoking its functions. An empty outer source therefore makes no inner function calls merely to discover columns. The binder and per-row execution retain the same lexical CTE/view definitions; each actual inner result must match the captured schema before its rows are read.

JOIN and APPLY may be chained in one FROM (up to the shared 16-edge limit). Each APPLY can correlate with earlier relation aliases. Physical collections, CTEs, derived queries, and system collections can supply the outer rows. WHERE, grouping/HAVING, projection, windows, ordering, and paging consume the merged result; temporal source clauses continue to select the root source. Per-outer ordering or paging belongs inside the APPLY subquery.

Query nesting, APPLY bodies included, is capped at 100 levels, counted as [CROSS APPLY](#cross-apply) describes. Programmatic ASTs use the same recursive bound before printing or execution.

Client/wire `IncludeTotalCount` reports the exact merged lateral cardinality: zero-match outers are absent for `CROSS APPLY` and contribute one null-inner row for `OUTER APPLY`. Counted rows use spill-bounded replay; uncounted results retain streaming execution.

A CTE remains useful when later statements should consume a named intermediate result. An unprojected JOIN/APPLY exposes its nested `[outer]` / `[inner]` envelope; an explicit SELECT publishes the named projected columns.

<a id="syntax-where"></a>

### WHERE

Operators (predicates over fields):

`=`, `!=` (also `<>`), `>`, `>=`, `<`, `<=`, `CONTAINS`, `STARTSWITH`, `IN (…)`, `NOT IN (…)`, `LIKE 'pat'`, `NOT LIKE 'pat'`, optional `ESCAPE 'c'`, `IS NULL`, `IS NOT NULL`, `BETWEEN a AND b`, `NOT BETWEEN a AND b`.

Combinators: `AND`, `OR` (precedence: `AND` > `OR`; parens override). Arbitrary AND/OR nesting is supported — same-field equality ORs collapse to `IN`, everything else normalises to disjunctive groups (`[A] = 1 OR ([B] = 2 AND ([C] = 3 OR [D] = 4))` means what it says). Unary `NOT` binds above AND and OR: `NOT ([Value] > 3)` preserves UNKNOWN for NULL values. Scalar functions, arithmetic, scalar subqueries, and field-to-field comparisons work in WHERE, with either operand a field or an expression and with an array element path on either side (`[Tags][] = [Name]`); `IN`, `LIKE` and `BETWEEN` accept field operands as well (`[Code] IN ([Name], 'x')`). The same row expressions are accepted in HAVING and aggregate FILTER, where a field-to-field equality is an ordinary comparison of the completed row. Native indexable AND conjuncts are pushed to the source; scalar residuals stream before grouping/projection. A statement's expression trees are capped at **256 total binary/logical operators**, counted as [Logical operators](#logical-operators) describes (paren nesting separately capped at 100; nested OBJECT / ARRAY schema declarations share this parser cap, while persisted schemas have a separate 16-level recursive depth limit) — a DoS guard; a chain longer than any real query is rejected with a catchable parse error. Use `IN (…)` for large value sets, never a hundreds-way `OR` chain.

Programmatic AST callers are bounded at the same semantic seam: scalar expression trees deeper than 512 nodes reject before printing, public type inference, or execution, and nested DML document/array literals share the text parser's 100-level cap. Explicit `IN` / `NOT IN` lists contain between 1 and 32,766 values, the largest count representable within the 65,536-token statement ceiling; direct AST validation and evaluation enforce those bounds before entry or operand traversal or descriptor allocation. `IN (subquery)` result cardinality is not subject to this syntax limit because the executor uses an admission-controlled spill-backed membership set. Scalar function calls contain at most 32,767 arguments, the largest call representable within the same token ceiling. Registered functions may narrow their arity but cannot widen that direct-AST boundary; excess arguments reject before traversal or evaluator buffer rental. Array literal contents are tokenized independently and contain at most 32,768 elements, the largest comma-separated scalar list representable by the inner 65,536-token lexer. Direct AST validation and serialization reject a larger array before element traversal or capacity calculation. `CASE` expressions contain between 1 and 16,383 `WHEN` branches, the largest searched form representable within the statement token ceiling. Direct AST validation and evaluation reject an invalid count before branch traversal.

Field paths and operator domains are validated before scanning. An unknown `WHERE` field errors instead of evaluating as implicit NULL, and string-only operators (`LIKE`, `CONTAINS`, `STARTSWITH`) reject non-string fields. A NULL right-hand value is a null check only for `=` / `!=`; every other comparison accepts it as a never-match predicate.

LIKE wildcards: `%` zero-or-more, `_` exactly-one character (one Unicode codepoint — an emoji counts as one). Separate `_` wildcards cannot consume the two UTF-16 halves of one emoji, even with `%` between them or non-ASCII literals in the pattern. ESCAPE introduces a literal escape character: `LIKE '50\%' ESCAPE '\'` (a string literal escapes only `''`, so `'\'` is one backslash). The escape must be one well-formed, non-surrogate UTF-16 code unit. Matching is a simple case-insensitive fold of the stored text — no Unicode normalization (decomposed `e`+accent ≠ precomposed `é`) — and is identical in WHERE and in expression position (CASE WHEN / SELECT).

**Subtype tests** (polymorphic collections): `SUBTYPE IS [Name]`, `SUBTYPE IS NOT [Name]`, `SUBTYPE IN ([A], [B], …)`, `SUBTYPE NOT IN (…)`. Names are bracketed identifiers (never string literals — `SUBTYPE = 'x'` is a parse error with guidance); `@parameters` bind where a name goes. Unknown names error at execution (`Unknown subtype 'X' … Known subtypes: …`) instead of silently matching nothing. `SUBTYPE IS NULL` is rejected — every document in a polymorphic collection has a subtype. The same test works inside `MATCH (...)` bodies against the array element's subtypes.

`IN (...)` accepts a literal list or a non-correlated/correlated subquery: `WHERE [CustomerId] IN (FROM [c] WHERE [Region] = 'EU' SELECT [Id])`.

**Scalar subqueries** appear on the RHS of any non-`IN` comparison. The inner query must project exactly one column; zero rows yields `NULL`, as does an aggregate such as `MAX` over no rows, and that `NULL` compares by the [NULL semantics](#syntax-14-null-semantics--null-permissive-not-full-ansi-3vl): an ordered or text comparison is unknown and excludes the row, but the NULL-safe `=` matches a row whose left operand is NULL and `!=` matches every row whose left operand is present. More than one row is a runtime `User / CARDINALITY_VIOLATION` error, reported with the same pair whether it ends the statement or surfaces while rows stream. A correlated scalar operand used with `LIKE`, `NOT LIKE`, `CONTAINS`, or `STARTSWITH` keeps the ordinary WHERE path's field typing, lowercase normalization, `ESCAPE`, and NULL semantics:

```sql
-- Customers whose target equals their largest order. A customer without a target
-- and without orders compares NULL = NULL, which is true; IS NOT NULL leaves it out.
FROM [Sales].[Customers]
WHERE [Target] IS NOT NULL
  AND [Target] = (FROM [Sales].[Orders]
                  WHERE [CustomerId] = [Sales].[Customers].[Id]
                  SELECT MAX([Total]));
```

**`EXISTS` / `NOT EXISTS`** are top-level boolean filters; the inner projection is ignored, only row presence matters:

```sql
FROM [Sales].[Customers]
WHERE EXISTS (FROM [Sales].[Orders] WHERE [CustomerId] = [Sales].[Customers].[Id]);

FROM [Sales].[Customers]
WHERE NOT EXISTS (FROM [Sales].[Orders] WHERE [CustomerId] = [Sales].[Customers].[Id]);
```

**Correlated subqueries.** Inside any of the three forms above, a bracketed RHS in a comparison, or a field of the inner SELECT list, that names an enclosing relation parses as an **outer field reference** — `[Sales].[Customers].[Id]` in the snippet above resolves against the outer scope's row, not the inner FROM. An enclosing relation is named as in its own clauses ([relation qualifiers](#join)): by its alias, or by its short or full collection name, aliased or not, a JOIN input as well as the FROM input (`[Docs].[Id]` over `FROM [Sales].[Orders] JOIN [Sales].[Docs] [d] ON ...`, `[Customers].[Id]` over `FROM [Sales].[Customers] [c]`). The executor rewrites every such outer reference to a synthetic `__corr_<n>` parameter, re-runs the inner query per outer candidate row, and binds the synthetic parameters from the outer row's binary on each call. Name allocation skips caller-owned bindings, so an explicit `@__corr_0` keeps its user value. A synthetic parameter is an operand lifted from the outer row, not a caller parameter: it keeps the outer value's own kind and compares as that value does in one row, so an `INT64` outer key outside an inner `INT32` field's width, or a fractional `FLOAT64` key, equals no inner value instead of failing caller-parameter range admission. A subquery nested inside a correlated subquery keeps every enclosing row's value an operand, so a correlation two levels deep compares the same way. Every plan, set-wise or per row, therefore decides an equality correlation by value. Eligible equality correlations are first decorrelated to set-based SEMI / ANTI joins (or an aggregate CTE for a scalar); only shapes outside that conservative gate re-run per outer row. An inner predicate over the inner collection's metadata (`[o].[Meta].[Revision] > 1`) stays in the set-wise form. A key the set-wise join cannot use is evaluated per outer row: a correlation key, `IN` operand, `IN` column or compared value over either relation's metadata, an Object or Array column, an array element path (`[Tags][]`, with or without a trailing `ALL`), two unrelated scalar types, an undeclared field, and an `IN` column naming a nested path. The statement then returns exactly what its per-row evaluation returns: Objects and Arrays compare whole, an element path matches when any element (with `ALL`, every element) satisfies the equality, text meets a number as the number's canonical text, a correlation value of another type compares as the same two fields of one row do (unequal when the types are unrelated, a BOOL as 0 / 1 against a number), and an undeclared field reports the nested query's own diagnostic. A nested path projects its parent Object, so membership compares that Object; project `[d].[Body].[Size] AS [S]` to compare the leaf. An uncorrelated subquery beside a correlated one is evaluated once and does not prevent the rewrite, nor does one in the correlated subquery's own `WHERE` beside its correlation (`[o].[Amount] > (FROM [App].[Orders] SELECT AVG([Amount]))`), which the set-wise join evaluates once, before it reads any row, as it evaluates the correlated subquery once: its error, such as a `CARDINALITY_VIOLATION`, ends the statement even when no outer row reaches the correlated subquery, as a subquery of the statement's own `WHERE` does, while a correlated subquery evaluated per outer row runs it only for a row that reaches it. The rewrite never makes the nested query's relation a source of the statement: on every plan the statement's `SELECT` and `ORDER BY` read its `FROM` relation alone, as when the nested query runs per outer row. A path spelled like the nested query's relation (`[o].[Amount]`, where `[o]` is the nested query's alias) is a path of the `FROM` relation, which reads that relation's Object of that name when it declares one; a scalar input the `FROM` relation does not declare reads `NULL`, and a plain item or ordering key it does not declare is an `UNKNOWN_FIELD`. Correlated `IN` decorrelates to a multi-key SEMI join: both the correlation pair and the projected-value pair must match the same inner row. Its compound key is length-framed per component, so zero bytes and variable-width numeric keys cannot create cross-component tuple collisions. Both components are checked against the live declarations of both relations before the rewrite is chosen, so a component of unrelated scalar types never reaches compound-key hashing. A key pair of two equality domains, text against a number included (which an authored JOIN keys on the number's text), is never decorrelated: a generated edge keys only on one equality domain, whether it is the correlation pair of `EXISTS`, `NOT EXISTS`, `IN` or a scalar aggregate, or the projected-value pair of `IN`: the predicate keeps its per-row evaluation, where text meets a numeric key as the number's canonical text, over a stored, derived or CTE outer alike, and whether the outer key belongs to the `FROM` source or to a stored, view, CTE or system relation it joins. The rewrite always has exactly two equality components (the primary correlation plus one projected-value pair); hidden/programmatic forms carrying further pairs reject before join setup. Still-correlated WHERE predicates support JOIN, GROUP BY, and aggregate projections. They bind both joined aliases against the merged row after computed-value injection, before grouping, projection, count, and paging. Eligible correlations retain the proven set-wise rewrite. Both 2-segment (`[Customers].[Id]`) and 3-segment (`[Sales].[Customers].[Id]`) references bind to the named outer source; `[Id]` works too when unambiguous. The source qualifier is removed once. In residual predicate binding, the optional `Body` shorthand after that qualifier is removed only when the named source declares no `Body` field. For example, `[r].[Body].[Detail].[Code]` names `[Detail].[Code]` when `Body` is undeclared. A declared `Body` field instead owns the remaining path, even when the requested child is missing or belongs only to another subtype. Missing children cannot borrow same-named fields elsewhere. Derived and CTE inputs use their own published field scope and retained subtype declarations for this rule. A real Object named like the source alias also remains part of the bound path. This rule also applies to inner predicates in optimized `EXISTS` / `NOT EXISTS` queries. An inner `[c].[Body].[Code]` keeps a declared `Body` Object even when `Code` also exists at the root; naming the inner alias `Body` does not remove the Object a second time. Reusing a query after an inner schema change binds both that path and its parameters against the current inner schema. Queries that need virtual computed values retain this field identity both in stored predicate pushdown and in predicates that run after enrichment. Selecting a computed value therefore does not redirect a nested Body field to a same-named root field, whether the stored predicate uses a scan or an index. The outer field doesn't have to appear in `SELECT` — correlation reads against the full row schema, not the projected output, so `SELECT [Id]` with a correlated reference to `[Sales].[Customers].[Region]` works.

Native correlated WHERE and residual aggregate FILTER gates read polymorphic values using the active outer subtype, including values passed into inner queries and comparisons against materialized scalar results. Present empty Bytes or Objects remain values rather than NULL; pinned references supply their logical identifier. Scalar expression fields and their scalar-subquery dependencies still require compatible declarations across subtypes.

EXPLAIN validates the original native field declarations without running the inner queries. A native correlation parameter whose value depends on the outer row is checked against the inner field domain when that row executes; EXPLAIN does not select one outer subtype to stand in for every row. Ordinary supplied parameters are validated on every execution against all native candidate domains.

The same `IN` / scalar / `EXISTS` forms work in `UPDATE`, `REPLACE`, `DELETE`, and `CANCEL VERSION` WHERE clauses. Non-correlated forms execute once. Correlated DML predicates run through the query executor and lower to the exact matched primary-key set before mutation; zero matches remain a no-op. Views inside those subqueries inline transitively. Native comparison predicates use the ordinary DML path directly; scalar and negated predicates retain candidate-row evaluation and normal validation.

Subquery cardinality and comparison boundaries fail closed. A scalar subquery reads only far enough to prove zero, one, or more-than-one rows and errors on the second row. IN/scalar projections must contain exactly one addressable column. A single plain path selected over a JOIN is that column, named by its leaf as `[a].[Id] AS [Id]` would be: the nested `{outer, inner}` envelope a plain JOIN projection publishes is the shape of a statement result, not of an `IN` or scalar operand, in `WHERE`, `SELECT` and DML predicates alike. Per-row correlated scalar evaluation freezes the inner result schema before consuming a lazy stream, so producer callbacks cannot retarget the decode layout between row emission and comparison. Correlated scalar field comparisons use the same native value domain as a subquery evaluated once. Numeric text keeps its own exact domain: binary FLOAT32/FLOAT64 `0.1` differs from text `'0.1'`, tiny text such as `'1e-300'` does not first underflow through DECIMAL, and malformed numeric text is a non-match even for `!=`. A typed floating result retains its binary kind. When the compared field is BYTES or a complete Object/Array, a string operand (a literal, a parameter or a scalar subquery's value) is decoded as Base64; an enclosing row's text field is a value of another type, unequal to an Object or Array. Native predicate validation rejects malformed Base64 when the candidate fields are all binary. A mixed subtype domain can admit the text through another declared type; the operand cannot equal a binary value, and `IN` / `NOT IN` retain their membership polarity. Comparisons and IN membership preserve the complete binary payload; they never compare its UTF-8 interpretation. Composite equality is binary identity within a declared layout, not structural equality across layouts. Present empty values remain distinct from NULL.

Parameter types follow the addressed value. `[Items]` addresses the complete Array, `[Items][]` addresses its elements, and each further `[]` descends one Array level. Parameter validation does not add an implicit element traversal.

Inner queries can target a temporal collection. `AS OF` / `IN BETWEEN` / `LAST PER` resolve fresh per outer-row dispatch with the bound `__corr_*` values flowing into the engine's predecessor probe / overlap scan / bucketing executor, so the temporal-correlated form behaves like the same query run by hand with `@param = outerValue`. The instant itself may read the outer row: `AS OF [o].[At]` or `IN BETWEEN DATEADD('DAY', -7, [o].[At]) AND [o].[At]` binds the outer column as a correlation parameter and evaluates the [instant expression](temporal.md#instant-expressions) once per outer row, so each row reads the versions valid at its own instant; a `DATETIME` or text column is admitted, any other declared type is refused with `TYPE_MISMATCH` before rows are read, and a `NULL` outer value with `INVALID_VALUE`. An enclosing row's column as an unquantified `IN` list member or a `CONTAINS` / `STARTSWITH` operand makes its predicate an expression rather than a comparison with a parameter, so `LAST PER` rejects that predicate in a WHERE term that also reads the inner collection's validity, where the hand-run parameter is accepted ([LAST PER](temporal.md#semantics)).

`EXISTS` and `NOT EXISTS` accept CTE and derived outer sources, and their inner queries may read any relation an uncorrelated subquery accepts: a collection, view, CTE, derived table, set operation, or system collection. Lazy results retain the WITH block's lexical bindings and recursive expansion; separate result streams may safely reuse CTE names without rebinding one another.

A subquery evaluated per outer row is bound before the first row is returned. An unknown inner field or relation, an undeclared outer field it correlates with, or an `IN` or scalar subquery that does not project exactly one column is reported as the statement's error result over every source kind, even when the outer relation is empty or a sibling predicate decides the row first. Such a statement never fails partway through its rows.

Array-element predicates use `[]`: `WHERE [Stations][].[Power] > 100` (any element). `MATCH` for correlated multi-predicate per element: `WHERE [Stations][] MATCH ([Power] > 100 AND [Connector] = 'CCS')`.

Consecutive suffixes descend consecutive array dimensions: `[Matrix][][]` addresses the leaf values of an `ARRAY ARRAY` field. An `OBJECT ()` field accepts a present `()` value, including as an array leaf, and remains distinct from NULL. ANY, ALL, MATCH, and `LENGTH(predicate)` apply across those leaves; MATCH keeps its predicates on the same leaf object. Empty inner arrays contribute no leaves, so ALL is vacuously true and the matching count is zero. Plain `LENGTH([Matrix])` counts outer elements instead, including empty inner arrays. Typed jagged arrays and nested lists preserve this shape through local and remote mutations.

```sql
WHERE [Matrix][][] MATCH ALL ([Value] > 0)
WHERE LENGTH([Matrix][][].[Value] > 0) = 2
```

One `MATCH` body accepts at most 16,382 same-element predicates. Parsing and direct AST validation enforce the count before reading or traversing another predicate. Nested MATCH bodies share the parser nesting limit of 100; direct AST validation enforces the same MATCH bound.

On a polymorphic collection, `MATCH` resolves its outer path against every subtype declaration. A scalar declaration in one subtype does not hide an array declaration in another; each row is interpreted through its active subtype.

A `MATCH` mistake is rejected before any row is read, with one text and code wherever the predicate appears (a `WHERE` over a collection, join, derived table, CTE or view, under `NOT`, an aggregate `FILTER` over any of those, a correlated or uncorrelated `EXISTS`, `IN` or scalar subquery, whether or not it is evaluated as a join, a lateral `APPLY` body, `HAVING`, or an `UPDATE`/`DELETE` filter), and static schema discovery and `EXPLAIN` report the same: an array path the relation does not declare is `UNKNOWN_FIELD` (`Cannot MATCH on 'Nope': field does not exist in the collection schema.`), a declared path that is not an Array is `TYPE_MISMATCH` (`Cannot MATCH on 'Name': MATCH requires an array field.`), and an element field the element does not declare, including any named field of a scalar array, is `UNKNOWN_FIELD` (`Cannot MATCH 'Tags (X)': field 'X' does not exist in the array element schema.`). Over a join the path is named relative to the relation it reads, in `WHERE` and an aggregate `FILTER` alike. A join whose `WHERE` composes its relations first (a negated or scalar `WHERE`) refuses an undeclared array path as every route does, and reads a declared path that is not an Array as a non-match; an element mistake under a declared Array is still rejected.

The bare and MATCH forms are both *existential* — at least one element matches. The trailing `ALL` keyword flips them to *universal*:

```sql
WHERE [Tags][] = 'approved' ALL                          -- every tag is 'approved'
WHERE [Stations][] MATCH ALL ([Power] > 100)             -- every station is high-power
```

`ALL` against an empty array matches vacuously, mirroring LINQ's `.All()` semantics. Typed-client LINQ: `xs.All(p)` translates to the corresponding `ALL` form. Both forms keep this meaning in expression position (`CASE`, projections, `CHECK`) when their operands are literals, parameters, or `NOW`; see [element predicates in expressions](arrays.md#element-predicates-in-expressions).

Consecutive dimensions and arrays in separate Object fields both require explicit markers: `[Matrix][][] = 7` and `[Groups][].[Values][] = 7` match any reached scalar equal to 7. Separate comparisons may match different inner arrays or values. A trailing `ALL` quantifies every explicit array boundary; nested `MATCH` expresses different quantifiers or several conditions on the same element.

**Nested array predicates inside MATCH.** A `MATCH` body may itself carry an array-element predicate over an *inner* array reached through the outer element. Mirrors LINQ's nested `.Any()` chain:

```sql
-- LINQ: hubs.Where(h => h.Stations.Any(s => s.Tags.Any(t => t == 'urgent')))
WHERE [Stations][] MATCH ([Tags][] = 'urgent')
```

MATCH preserves the complete inner predicate: `IN` / `NOT IN` accept literal, non-correlated, and correlated subquery value sources; `LIKE` / `NOT LIKE` preserve an explicit `ESCAPE`; and trailing inner/outer `ALL` quantifiers remain attached to their own scope.


A body can combine comparisons, nested `MATCH` / `MATCH ALL`, and predicate `LENGTH` with `AND`. Every nested path is relative to its enclosing element. Use a nested MATCH when several conditions must hold on one inner element:

```sql
FROM [App].[Items]
WHERE [Groups][] MATCH (
  [Enabled] = true AND
  [Children][] MATCH ([Score] >= 10 AND [Kind] = 'good')
);

FROM [App].[Items]
WHERE [Groups][] MATCH (
  [Enabled] = true AND
  LENGTH([Children][] MATCH ([Score] >= 10 AND [Kind] = 'good')) >= 2
);
```

`LENGTH([Array][] MATCH (...))` counts matching elements of that named array, not matches inside deeper arrays. Its MATCH wrapper has no outer ALL; inner predicates may use ALL over their own arrays. Empty arrays contribute zero to counts, while MATCH ALL on an empty array remains true.

**Count of matching elements via `LENGTH(predicate)`.** A `LENGTH(...)` wrapping an array-element predicate returns the count of matching elements; compare to an integer for filter usage. This is the MQL surface for LINQ `.Count(predicate)` / `.Where(predicate).Count()` on array fields:

```sql
WHERE LENGTH([Tags][] = 'urgent') > 2          -- more than two 'urgent' tags
WHERE LENGTH([Stations][].[Power] > 100) = 0   -- no high-power stations
```

The inner side accepts the usual element-predicate operator set; the outer comparison must be a relational op against an integer literal, integer parameter, or one-column scalar subquery. That scalar subquery may be non-correlated or correlated, returns NULL at zero rows, and errors at row two. The scalar shorthand's inner predicate cannot carry a trailing `ALL` — its count threshold already encodes universality (`LENGTH(p) = N` requires every element of an N-element array to match).

Pinned-FK arrays expose two pseudo-fields on each element — `[Id]` (explicit synonym for the bare `[]` id-half shorthand) and `[Revision]` (per-element 8-byte LE int64 tail). Filter by either in ANY form (`WHERE [TariffRefs][].[Revision] >= 7`) or correlate both on the same element via MATCH (`WHERE [TariffRefs][] MATCH ([Id] = @t AND [Revision] = 7)`). The pseudo-fields are only valid on `PINNED REFERENCES` arrays — using `[].[Revision]` on a plain array is rejected at predicate- build time. Their names follow ordinary schema-identifier rules and are case-insensitive in both ANY and `MATCH` forms. Validation types `[Id]` as the array element key and `[Revision]` as `INT64` in both forms; incompatible literals are rejected before execution.

<a id="syntax-select-projection--explicit-list-and-wildcard-modifiers"></a>

### SELECT projection — explicit list and wildcard modifiers

Composed polymorphic wildcards include declared base and extension fields. Exclude incompatible extension fields or replace them with a uniform expression; a JOIN relation's wildcard has no slot for them. Array replacements can read compatible leaves from the original active subtype even when a containing object is excluded because its surrounding layouts differ. Private envelope fields are omitted from composed wildcard output. Trivial physical `SELECT *` retains the source's polymorphic result metadata.

Explicit items keep their written order when plain fields, aliases, aggregates, scalar expressions, and windows are mixed. `SELECT [Amount] + 1 AS [Next], [Id]` publishes `Next, Id`; `SELECT COUNT(*) AS [Total], [Region]` after grouping publishes `Total, Region`. Printed queries and static schemas preserve that order. Plain nested paths still promote their parent at its first occurrence. Computed DISTINCT compares the selected values before ordering, paging, and counting; unselected source columns do not participate in deduplication. Post-DISTINCT ordering keeps retained nested paths and valid source qualifiers. Flattened grouping keys and joined fields resolve through their selected source identity; an unknown qualifier or another relation's unselected field cannot reuse a same-named output. EXPLAIN applies the same check to wildcard output. Grouped direct field aliases retain that selected identity, including qualified `Body` paths. An omitted grouping key cannot borrow a same-named aggregate or an unrelated output Object's child; bare output aliases retain result scope. Ordinary scalar projections over derived/CTE inputs retain direct field aliases and promoted parents through explicit item ordering as well. Compatible leaves in an imported polymorphic envelope remain addressable; a flat inner projection exposes only its emitted columns. A dependent alias preserves these rules: `Code AS Key, Key + 1 AS Next` still selects the original `Code` for qualified DISTINCT ordering. A computed output named `Code` cannot make an omitted source `Code` eligible for that ordering. Flat JOIN projections preserve direct AS identities and retained Object children through native reordered/bushy execution and ordinary composition over derived inputs as well. A selected source path may qualify DISTINCT ordering; another relation's omitted path cannot borrow an output Object with the same name. Explicit relation aliases take precedence over collection short names. Bare source paths require one complete input match, even when several inputs share the same Object root.

```sql
-- Explicit projection
FROM [App].[Users] SELECT [Id], [Email];

-- Wildcard — all fields of this physical query source
FROM [App].[Users] SELECT *;

-- Wildcard with exclusion — drop sensitive / large fields
FROM [App].[Users] SELECT * EXCLUDE ([Password], [Salt]);

-- Wildcard with substitution — keep every field but transform one or more
FROM [App].[Users] SELECT * REPLACE (NULL AS [Password], UPPER([Name]) AS [Name]);

-- Rename result columns without re-typing the full projection
FROM [App].[Users] [u] SELECT [u].* RENAME ([Name] AS [DisplayName]);

-- All modifiers compose and may be written in any order
FROM [App].[Users] SELECT * RENAME ([Name] AS [DisplayName]) EXCLUDE ([Salt]) REPLACE (NULL AS [Password]);
```

A wildcard over a CTE, derived query, or plain view selects its declared data fields. The internal `Meta` object retained for explicit expressions is excluded, including for a bare `SELECT *`. Select metadata explicitly, preferably with an output alias when persisting its value. Static schema binding and execution use the same rule, so composed materialized projections do not store hidden metadata as an ordinary backing field. A direct physical-source wildcard retains its row-metadata presentation, including when computed evaluation uses an internal virtual postprocessor.

`SELECT *` resolves the top-level fields of its source under these metadata rules. A plain dotted projection retains its parent container, but every named child must exist. Dotted Array child paths permit implicit element navigation; missing children and scalar traversal fail both queries and schema-only validation. `SELECT [alias].*` resolves one logical relation and flattens its fields in schema order, independent of physical join order. The qualifier must be bracketed; bare `alias.*` is invalid. `EXCLUDE` removes named source slots, `REPLACE` changes their values and inferred types in place, and `RENAME` changes their advertised names in place. Each modifier may appear once and may be written in any order; canonical printing uses `EXCLUDE`, `REPLACE`, then `RENAME`, and execution always follows that pipeline.

In a single-source query, the qualifier may be the bare collection or view name, the CTE name, or an explicit FROM alias, matched case-insensitively. For example, `FROM [App].[Items] SELECT [Items].*` and `WITH [R] AS (FROM [App].[Items]) FROM [R] SELECT [R].*` work without adding an alias. Derived sources use their declared alias. Standalone and mixed wildcards share these rules; a field name is not a relation qualifier.

Modifier targets may be top-level fields or nested Object paths, including Object children inside Arrays. For example, `EXCLUDE ([Address].[Zip])` removes only Zip, `REPLACE (UPPER([Address].[City]) AS [Address].[City])` changes City, and `RENAME ([Address].[City] AS [Town])` renames that child within Address. Null parent objects remain null; retained siblings and their types are preserved. Removing every child leaves a present empty Object, distinct from a null parent. Retained empty Object children keep their presence when their containing Object is rebuilt again. Retained pinned references preserve both their identifier and revision when nested Objects or Object elements are rebuilt, including base and active subtype fields. A nested replacement may change the leaf's type. Polymorphic Object projections preserve their discriminator and subtype envelopes; a modifier of a subtype child applies only where that child is declared. The discriminator may be renamed, but cannot be removed or have its value replaced while its subtype payload is retained. Unknown targets, duplicate replacement targets, duplicate rename sources, duplicate final output names, and case-insensitive collisions with retained fields are errors. A field cannot appear in both `EXCLUDE` and `REPLACE` or both `EXCLUDE` and `RENAME`; `REPLACE` and `RENAME` may target the same source. A target below an excluded or replaced parent is invalid; redundant descendant exclusions are harmless. Rename output names are local to their containing Object. Rename mappings apply simultaneously, so swaps, case-only renames, and reuse of a name freed by an exclusion or another rename are valid. Renamed aliases are result-only: earlier `WHERE`, `GROUP BY`, and `ORDER BY` clauses still use source names. Replacement expressions evaluate against the original full row; no field, whatever it is named, reads the original row the element expressions carry or another replacement's value.

Use one `[]` for each traversed Array dimension: `[Items][].[Price]` names Price in each Object element, and `[Matrix][][].[Price]` traverses two Array dimensions. EXCLUDE and RENAME preserve element count and order. REPLACE evaluates separately for each original element; references to an enclosing Array element or to the full document also use original values, even when those fields are excluded, replaced, or renamed in the same SELECT. Correlated scalar subqueries may read the current element. Empty Arrays remain empty and null parents remain null. Polymorphic elements retain each active subtype and the same discriminator rules as other Objects.

A direct field replacement of a named Object child, such as `REPLACE ([Items][].[Ref] AS [Items][].[Copy])`, preserves a pinned reference's identifier and revision. This also applies when the source field belongs to an enclosing element or the original document. NULL source fields remain NULL; ordinary computed expressions continue to use reference identifiers.

REPLACE may target the element itself: `REPLACE ([Values][] * [Factor] AS [Values][])` maps a scalar Array, while `[Matrix][][]` targets each scalar in a nested Array. The replacement expression determines the output element type; whole Object or Array elements may also be replaced. Element count and order are preserved. A NULL or unrepresentable element result is an error, because Array elements have no null bitmap. EXCLUDE and RENAME require a named field: target `[Values]` or `[Items][].[Price]`, not anonymous `[Values][]`. Replacing elements of a pinned-reference Array reads the original IDs and returns ordinary values without retaining their original pinned revisions. An expression returning a complete Array preserves that value's element schema and pinned revisions, including when it becomes a nested output element. No replaced value keeps its source's foreign-key removal action or match mode: element results and a rewritten reference Array are ordinary values, and a complete Array keeps only its target identity and pins.

REPLACE also accepts window functions, including `OVER [w]` with a trailing named WINDOW definition. Windows operate on source rows; an Array-child target receives that row's window value in every element. Explicit window projections and wildcard replacements share the per-SELECT limit of 64 window functions. The public limit remains 1,024 output fields; internal replacement slots do not reduce it. Parsed text and programmatically built SELECT DISTINCT wildcards share the same modifier expansion and deduplicate final projected values. DISTINCT publishes the grouping-key schema: output keys are nullable, scalar pinned references become logical IDs, and whole pinned arrays retain their complete values, including revisions. The same rules apply to explicit projections and correlated predicates; changing source rows or the chosen plan does not change the declared result layout.


Every retained slot stays in source order. Pure single-source renames preserve the ordered binary layout and stream the original row bytes under the renamed schema. Qualified join projection extracts the selected relation; a missing outer-join side remains nullable. The same validation and behavior apply to stored, CTE, system/virtual, computed-column, and polymorphic sources. Wildcards may mix with explicit items and other wildcards in authored order. Each wildcard applies its own modifiers. All expanded output names must be unique: use `SELECT * EXCLUDE ([Y]), [Y]`, or rename overlapping names. Computed/window expressions are supported beside wildcards; aggregate mixes use normal GROUP BY validation. DISTINCT deduplicates expanded output values before ordering and paging. With NEAREST, the required top-k bound is the explicit TOP value during source selection before the mixed projection. Final ordering and paging apply once to that ranked neighborhood.

All projected output names are case-insensitively unique. Duplicate field paths, a computed/aggregate alias colliding with a plain field leaf name, or two identical aliases are rejected for stored and virtual sources before a binary result layout is built.

One explicit `SELECT` list accepts at most 1,024 combined plain, aggregate, and computed projection items. Wider query shapes reject before scanning, expression-type inference, or result-schema allocation. Mixed lists also limit expanded output slots to 1,024. A standalone `SELECT *` remains one wildcard item and resolves only to the source schema's already-valid top-level fields. Its combined `EXCLUDE`, `REPLACE`, and `RENAME` lists accept at most 1,024 targets; a wider modifier list rejects before replacement-expression parsing or target validation.

Selecting an `ARRAY OBJECT` child validates that child and projects the complete parent array so element and sibling-field boundaries remain intact. `SELECT [Items].[Name]` therefore returns the `Items` array; `SELECT [Items].[Missing]` errors.

<a id="syntax-computed-projections"></a>

### Computed projections

A parenthesized query is also a SELECT expression: `SELECT (FROM [Ns].[Other] WHERE [OwnerId] = [o].[Id] SELECT COUNT(*)) AS [Count]`. It must select exactly one column and return at most one row. Zero rows yields NULL; a second row fails. The inner column supplies the declared result type and nested schema. Correlation in the inner WHERE or SELECT list binds the current outer row, joined alias, or grouping key; a projected outer field supplies its own declared type. Uncorrelated values are cached only within one execution. Scalar subqueries compose with arithmetic, CASE, coalescing, window value/partition expressions, and DISTINCT; normal short-circuit rules apply. Outer paths resolve source qualification once, in execution and EXPLAIN. With alias `[r]` and an Object also named `r`, `[r].[r].[Code]` (or `[r].[Body].[r].[Code]`) retains the Object root when used by a scalar subquery. Outer metadata such as `[r].[Meta].[Revision]` also remains available when a correlated WHERE predicate and sorting precede the scalar projection. ORDER BY can sort scalar projection aliases after evaluation and before paging, including grouped output; auxiliary source sort fields need not be selected. Those auxiliary columns cannot capture authored expression inputs or make a declared input ambiguous. Windows with dependent arguments use the bounded buffered path. Every source is included in read admission, view expansion, and stored dependency checks. Persisted computed fields and CHECK constraints reject row-dependent queries.


```sql
SELECT [Name], [Price] * [Qty] AS [Total],
       UPPER([Name]) AS [Display],
       CASE WHEN [Score] >= 90 THEN 'A' ELSE 'B' END AS [Grade]
```

Computed expressions can reference any field; the engine returns full rows when computed projections are present. Three-valued NULL logic applies (NULL propagates through arithmetic).

Structured CASE and original value-preserving built-ins (`COALESCE`, `IFNULL`, `NULLIF`, `TRY`) preserve complete Object/Array/Vector decoding metadata only when all possible value arms have compatible layouts. Untyped NULL arms are neutral. Incompatible shapes use lossless `STRING` output (base64 for packed Objects/Arrays, component text for Vectors). Ordinary projections, wildcard replacements, empty inputs, and schema-only discovery share this rule. A scalar pin such an expression returns becomes its logical ID, while a direct projection of the field keeps the complete pin ([nested field access](#nested-field-access)); whole pinned arrays retain their revision frames.

A dotted plain item mixed into a computed `SELECT` preserves its containing `OBJECT` / `ARRAY` in the output schema and row, exactly like an ordinary plain projection. This holds for scalar streaming and buffered window execution; read the requested child through its original parent path rather than as a flattened top-level leaf.

For polymorphic collections, subtype extension fields work in both scalar and window computed projections, including SELECT lists mixed with plain base or extension columns. The executor retains and expands the row envelope before evaluation, so the owning subtype supplies the correctly typed value and other subtypes see NULL. Thus `[Seats] * 2` and `SUM([Seats]) OVER (...)` stay numeric for `Car` rows even when `[Name]` is projected alongside them. A nested polymorphic Object follows the same rule: a compatible leaf declared only by a later subtype remains available to direct aliases, wildcard `REPLACE`, scalar expressions and windows. Missing subtype fields and NULL parents produce NULL; present empty Object, Bytes and Array values retain their value and type. The declaration used for the result and schema-aware functions is the same one used to read the value.

The client/wire `IncludeTotalCount` option survives scalar and window computed projection on both streaming and buffered paths. It reports the filtered row count before `SKIP` / `LIMIT`, rather than the returned page size.

Built-in functions include `UPPER`, `LOWER`, `SUBSTRING`, `LENGTH`, `OCTET_LENGTH`, `TRIM`, `LTRIM`, `RTRIM`, `CONCAT`, `REPLACE`, `LEFT`, `RIGHT`, `POSITION`, `ABS`, `ROUND`, `FLOOR`, `CEILING` (`CEIL`), `SIGN`, `POWER`, `SQRT`, `MOD`, `DATE_TRUNC`, `EXTRACT`, `DATEADD`, `DATEDIFF`, `CURRENT_DATE`, `CURRENT_TIMESTAMP`, `COALESCE`, `NULLIF`, `IFNULL`, `TO_INT`, `TO_DECIMAL`, `TO_DOUBLE`, `TO_STRING`, `TO_TIMESTAMP`, `ENUM_LABEL`, `ENUM_VALUE`. `CAST(expr AS Type)` is the general form.

`TO_STRING` and `CAST(... AS STRING)` render a number as its canonical text, the text a comparison with a STRING reads ([comparison value notes](#comparison-value-notes)): integer digits, a DECIMAL with its scale (`1.0`), the shortest round-trip FLOAT64 text (`1E+20`), a FLOAT32 as the FLOAT64 holding its exact value and a negative zero as `0`. NaN and the infinities have no text: converting one is `INVALID_VALUE`, and `TRY_CAST` / `TRY` return NULL. Concatenation, `JOIN_STRING` and computed STRING fallbacks use the same text. `TO_STRING` and `CAST(... AS STRING)` accept Vector values and render invariant, round-trip component text such as `[1.25, -2.5]`; NULL remains NULL. Computed String fallbacks use the same vector representation.

`TO_DECIMAL`, `CAST(... AS DECIMAL)` and `TRY_CAST(... AS DECIMAL)` convert a FLOAT64 to the DECIMAL its canonical text names, so a FLOAT64 `0.1` converts to `0.1` and `CAST(CAST([F] AS STRING) AS DECIMAL)` gives the same DECIMAL as `CAST([F] AS DECIMAL)`; a FLOAT32 converts as the FLOAT64 holding its exact value, so a stored FLOAT32 `0.1` converts to `0.10000000149011612`. Digits below the DECIMAL scale of 28 round away. NaN, the infinities and a magnitude from 2^96 up have no DECIMAL: converting one is `INVALID_VALUE`, and `TRY_CAST` / `TRY` return NULL. A comparison converts nothing: a FLOAT64 field and a DECIMAL field compare by their exact values, so a FLOAT64 `0.1` does not equal a DECIMAL `0.1`.

EXACT_EQUALS and TRY are language intrinsics and cannot be replaced. In-process hosts may add or replace other scalar functions through the .NET `FunctionRegistry`. Publication is process-wide and atomic. Each MQL statement pins one function-registry generation at admission and retains it across every row, retry, nested evaluator, and delayed streaming-result drain. A concurrent replacement therefore cannot mix implementations inside one statement; it becomes visible to the next admitted statement, including through expression ASTs that were already cached. Names are case-insensitive and are canonicalised to upper case; invalid negative or reversed arity ranges are rejected at registration. Statement admission pays one generation read; rows that call no scalar functions perform no function lookup. Function results and evaluation order are independent of arity; the common zero- through-four-argument path uses statement-local scratch, while larger variadic calls use pooled scratch.

`ENUM_LABEL([Field])` returns the description string declared by an enum-typed field's `CREATE ENUM … VALUES (1 = 'Low', …)`. The argument must be a bracketed field reference (`ENUM_LABEL('Low')` is rejected), the field must be enum-typed (`ENUM_LABEL([Title])` on a STRING field raises a typed error rather than returning silent NULL). NULL value → NULL; value not enrolled in the enum → NULL. Works in SELECT projection, computed columns, CHECK constraints, and UPDATE RHS expressions (which read the pre-update row). It cannot be used in an INSERT value because its required field reference has no existing row. `WHERE ENUM_LABEL([Pri]) = 'High'` uses scalar predicate evaluation; `WHERE [Pri] = 3` remains eligible for an ordinary enum-key index. See `Docs/MqlReference/enums.md`.

`ENUM_VALUE('label', 'EnumName')` is the inverse: returns the underlying numeric (`INT64`) or `GUID` value for a label in a named enum. Two args — label expression, enum-name string. Case-insensitive label match. A NULL label returns NULL without evaluating the enum-name expression. Unknown label → NULL; unknown enum name → typed error. The enum name is the one `[Mnemic].[Enums]` lists (`'[Ns].[Name]'`, `'[Name]'` at the top level); its segments may also be written without brackets (`'[Ns].Name'`, `'Ns.Name'`). A literal enum name or bound string parameter produces the exact `INT64` / `GUID` projection schema, and a computed column may declare that matching type directly. A row-varying enum-name expression, an enclosing row's field a nested query reads included, uses a stable `STRING` projection so values from numeric and `GUID` enums remain lossless. It works in projection, computed columns, CHECK constraints, and INSERT / UPDATE value expressions.

`LENGTH` returns UTF-16 code-unit count for STRING (including trailing spaces, matching .NET `string.Length`), element count for ARRAY, and raw byte count for BYTES. `OCTET_LENGTH` returns the strict UTF-8 encoded byte count for STRING and raw byte count for BYTES. Both return INT64, propagate NULL, and work in projections, `WHERE`, and `CHECK` predicates. For example, `WITH CHECK (OCTET_LENGTH([Data]) <= 1024)` bounds a binary payload.

`SUBSTRING` positions and `LEFT` / `RIGHT` lengths also count UTF-16 code units. A non-empty slice must begin and end between complete Unicode characters: splitting a surrogate pair raises an argument-range error during evaluation, and `TRY` returns NULL for that error. For example, `LEFT('😀', 2)` returns the emoji, while `TRY(LEFT('😀', 1))` returns NULL. Empty slices remain valid.

`ROUND([Value], digits)` accepts the same digit conventions as PostgreSQL / SQL Server / Oracle. Positive digits round to that many fractional places; zero rounds to integer; **negative digits round to the nearest 10^|digits|** (`ROUND(1250, -2)` → `1300`). Midpoint ties go away from zero (`MidpointRounding.AwayFromZero`). A `NULL` digits argument propagates to `NULL`. Digits outside the type's safe range (`-28..28` for decimal, `-308..15` for double, or below `-28` for integer) raise an error because the requested scale is not representable; TRY returns NULL. For a valid digit range, a Float64 `NaN` / `±Infinity` input is preserved.

DECIMAL midpoint decisions remain exact at maximum fractional precision: `ROUND(4.9999999999999999999999999999, -1)` returns `0`, while `ROUND(5.0, -1)` returns `10`. The corresponding negative values return `0` and `-10`.

FLOAT64 negative-digit rounding decides from the original binary value against the exact power of ten, then represents the rounded result as the nearest FLOAT64. For example, `ROUND(TO_DOUBLE('1.7499999999999999e22'), -21)` returns `1.7e22`; division by the scale must not turn that below-midpoint value into a tie. `ROUND(TO_DOUBLE('2.5e23'), -23)` returns `2e23`, since that binary input is slightly below the exact decimal midpoint. Signed zero and IEEE overflow are preserved.

ABS, ROUND, FLOOR, CEILING and CEIL return INT64 for integer arguments, including INT8/INT16/INT32 inputs. Thus `ABS(CAST(-128 AS INT8))` returns 128 and `ROUND(CAST(127 AS INT8), -1)` returns 130. Int64 overflow remains an error.

Integer-valued scalar arguments (`SUBSTRING` start/length, `LEFT` / `RIGHT` length, `ROUND` digits, `DATEADD` count) accept Int, Decimal, or Float values only when finite, mathematically integral, and inside Int64 range. `2`, Decimal `2.0`, and Float64 `2.0` are equivalent; `2.9`, `TRUE`, and `'2'` error rather than truncating or implicitly converting. Use `CAST(... AS INT64)` / `TO_INT(...)` for intentional conversion.

`MOD(x, y)` raises on a zero divisor, matching `%`. Float-returning functions preserve representable IEEE NaN and infinities. SIGN(NaN) and conversions to an integer or DECIMAL raise when the target cannot represent the result. Wrap the expression in TRY, or use TRY_CAST, to return NULL for these numeric failures. Integer MOD results use INT64; DECIMAL and floating operands retain their promoted result types.

`CAST(x AS DATETIME)` and `CAST(x AS GUID)` on an unparseable string fail with `INVALID_VALUE` (`Cannot convert String value '...' to DateTimeOffset.` / `... to Guid.`), as `TO_TIMESTAMP` and the other string conversions do, in the keyword and the function spelling alike; `TRY_CAST` and `TRY` return NULL instead.

Converting a DATETIME to DATEONLY or TIMEONLY uses the timestamp's offset-local date or time. For example, `2031-01-05T00:30:00+02:00` yields January 5 and 00:30, including in computed columns and RETURNING rows. Native DATEONLY and TIMEONLY results retain their logical type; use an explicit `CAST(... AS DATETIME)` when a timestamp anchor is intended.

`CURRENT_TIMESTAMP()` and `CURRENT_DATE()` honour the same per-query `ctx.Now` timestamp `NOW` resolves through, so a query mixing the keyword form and the function form sees consistent values across rows. ANSI SQL specifies these as "current value of the system datetime within the statement"; all forms therefore resolve from the statement's captured clock value rather than sampling wall-clock time per row.

`COALESCE(x, y, z, …)` and `IFNULL(x, y)` short-circuit — arguments are evaluated in turn, the first non-null is returned, and later args are NOT evaluated. This matches PostgreSQL / SQL Server / Oracle / SQLite semantics. `COALESCE([F], CAST('foo' AS INT))` returns `[F]` without throwing from the unused cast when `[F]` is non-null. `NULLIF` stays eager (both args required to compare equality) and compares its arguments exactly as `=` does, a literal or parameter argument read as a value of the other argument's type: `NULLIF([Count], '05')` is NULL for a `[Count]` of 5, and `NULLIF([Code], [N])` compares a STRING with a number as text.

The **projected type** of `COALESCE` / `IFNULL` unifies across every argument (same all-arm rule as `CASE`): all-numeric arms promote to the widest numeric type, and mixed non-numeric arms degrade to `STRING` so whichever arm fires survives verbatim — `COALESCE([IntField], 'n/a')` projects `'5'` or `'n/a'`, never a NULLed-out fallback. For a typed result over mixed arms, CAST the fallback (`COALESCE([When], CAST('2031-01-05T00:00:00Z' AS DATETIME))`). A **declared computed column** whose `AS` expression infers a different type than the declaration is rejected at DDL time with the inferred type named — add the explicit CAST.

A literal `NULL` arm contributes no nominal type: `CASE ... THEN [GuidField] ELSE NULL`, `COALESCE([GuidField], NULL)`, and `IFNULL([GuidField], NULL)` remain `GUID` projections. If every value arm is literal `NULL`, the stable fallback schema is `STRING`. A cast such as `CAST(NULL AS STRING)` is intentionally typed and participates in unification as `STRING`.

Bool ↔ string text comparisons use the same accept set everywhere: `[Active] = 'true'` (also `'false'` / `'1'` / `'0'`, case-insensitive) matches the stored Bool in `WHERE`, `CHECK` constraints, `CASE`, `HAVING`, and computed columns alike. Text outside the accept set is a typed query error — it never degrades to a silent non-match or truthy/falsy interpretation.

Implicit conversion into a declared BOOL result accepts native booleans, integer zero or one, and the same `'true'` / `'false'` / `'1'` / `'0'` text forms across computed columns and RETURNING, including when another computed column requires a variable-width row rebuild. Decimal, floating, and other integer values require an explicit BOOL cast.

`CAST(x AS BOOL)` on a `STRING` source accepts the boolean keyword spellings (`'true'` / `'false'`, case-insensitive) and the exact digit spellings `'1'` / `'0'`. Other strings, including `'2'`, `'-1'`, `'01'`, and whitespace-padded digits, fail with `INVALID_VALUE` (`Cannot convert String value '...' to Bool.`). TRY_CAST and TRY return NULL for this conversion failure. Numeric (Int / Decimal / Double) sources stay on the `!= 0` truthy/falsy interpretation.

Unary `NOT` and `CASE WHEN <cond> THEN ...` require a boolean (or integer truthy/falsy) condition. A `STRING` / `GUID` / `DATETIME` / `BYTES` / `ARRAY` / `DECIMAL` / `DOUBLE` operand is a `TYPE_MISMATCH` (`A condition (AND, OR, NOT, CASE WHEN) needs a BOOL operand; got a STRING value.`), when the statement is bound wherever the operand's type is known and otherwise when the value is read, instead of folding to silent `TRUE` / `FALSE`. Wrap a non-boolean condition in an explicit comparison (`WHERE NOT ([F] = 'value')`) or cast.

`TO_INT`, `TO_DECIMAL`, and `CAST` raise on non-finite or out-of-range values that the target cannot represent, and on invalid text conversions. Integer CAST truncates fractional input toward zero. Floating-point inputs are truncated directly, preserving exact representable integers such as `9007199254740992` without an intermediate Decimal rounding step. `TRY(expr)` and `TRY_CAST(expr AS type)` explicitly recover these failures as NULL. They do not suppress binding, cancellation, resource, corruption, or custom function callback failures.

`DATE_TRUNC('week', [Ts])` floors to **Monday** (ISO 8601 week start), matching `EXTRACT('week', [Ts])` which uses `ISOWeek.GetWeekOfYear`. `GROUP BY DATE_TRUNC('week', …)` and `GROUP BY EXTRACT('week', …)` bucket the same row identically.

`DATEADD(unit, count, [Ts])` accepts an exact integer-valued numeric `count` in Int64 range — sub-day units (`SECOND`, `MINUTE`, `HOUR`, `DAY`, `WEEK`) apply the count directly without an intermediate Int32 cast, so a parameter beyond Int32 range no longer wraps silently. Year / Month variants still require the count to fit Int32 (the underlying `DateTime.AddYears` / `AddMonths` API takes int); larger values raise an error. Any unit that pushes the result outside the DateTime range also raises an error. WEEK uses checked Int64 multiplication for count × 7. TRY(DATEADD(...)) returns NULL for these range failures.

`DATE_TRUNC(unit, timestamp)` likewise raises an error when the requested offset-local boundary falls outside the representable `DateTimeOffset` instant range. This can occur at the year-1 boundary when a valid minimum instant is viewed through a positive offset and then truncated to local midnight.

`DATEDIFF(unit, from, to)` returns the signed count of date-part boundaries crossed, not elapsed duration truncated to `unit`. It accepts `YEAR`, `MONTH`, `WEEK`, `DAY`, `HOUR`, `MINUTE`, and `SECOND` case-insensitively. Boundaries use each timestamp's offset-local calendar; `WEEK` starts on ISO Monday, consistent with `DATE_TRUNC` / `EXTRACT`. A sub-second interval crossing midnight therefore returns `1` for `DAY`, `HOUR`, `MINUTE`, and `SECOND`; reversing the operands returns `-1`.

<a id="syntax-set-operations"></a>

### Set operations

Combined ORDER BY binds the left branch's output names and accepts only scalar sort keys. Missing fields and Object/Array keys fail before combined row enumeration. Static EXPLAIN and nested schema discovery share this validation; empty outer inputs do not bypass nested set ordering or paging-parameter checks. Stored-view dependency checks validate ordering while keeping paging values as runtime inputs.

Set-operation plans own their combination strategy: `Concatenation` for UNION ALL and `HashSetOperation` for deduplicating or multiset operators. Both branch access plans remain children, with a separate `Sort` above the combination for trailing ORDER BY. Combined rows inherit no source index or source early-exit claim. A UNION estimate is unknown when either branch estimate is unknown; ANALYZE executes the complete operator to report actual rows.

`UNION`, `UNION ALL`, `INTERSECT`, `INTERSECT ALL`, `EXCEPT`, `EXCEPT ALL` combine read queries and may be chained: `FROM [a].[A] SELECT [Id] UNION FROM [b].[B] SELECT [Id]`. Both branches must project the same column count and matching complete value layouts; a JOIN branch whose SELECT lists only plain fields, or that has no SELECT list, publishes its nested `{outer, inner}` columns, and a refusal against flat columns names that shape (name the columns with `AS`). Top-level scalar names, source roles and nullability may differ (the left name wins, and a column is nullable when either branch's is), but vector dimensions, `OBJECT` nested fields, `ARRAY` element schemas, nested nullability, enum/named type identity, pinned width, and polymorphic subtype layouts must match. Layout mismatch errors before any row is exposed; MQL never interprets right-branch structured bytes using the left branch's incompatible schema. A failure while preparing the combined result releases both branch streams even before enumeration begins, including after modeled process death. Dedup and probe equality follow the engine-wide doctrine: strings compare case-insensitively ('Cafe' UNION 'cafe' is ONE row, exactly like DISTINCT) and floats follow the total order (NaN payloads are one value). Decimal scale variants compare equal, DATETIME offsets are normalized to the UTC instant, and NULL is distinct from present empty BYTES. Scalar pins compare by identifier while emitted rows retain the stored revision and reference metadata; whole pinned arrays keep element revisions in their equality identity. Spilled or parallel sets share these rules. `SELECT DISTINCT`, including after correlated filtering, emits typed grouping keys with identifier-only scalar pins and complete pinned-array values. UNION emits the first-seen representation. Canonical rows are built in stack-first, pooled scratch and retain only the one owned set/multiset key; Unicode lowercasing creates no additional per-row managed keys. Positive counts and consumed-row state for `INTERSECT ALL` / `EXCEPT ALL` share the `MaxInMemoryStreamingState` bound. Spilled zero-count snapshots prevent later copies from matching an already consumed right-side occurrence. `ORDER BY`, `SKIP`, and `LIMIT` following the second `SELECT` order and page the COMBINED result: `FROM [a].[A] SELECT [Id] UNION ALL FROM [b].[B] SELECT [Id] ORDER BY [Id] SKIP @s LIMIT @n`. With client/wire `IncludeTotalCount`, the exact combined cardinality is reported after `ALL` / distinct / multiset semantics and before trailing paging. Counted combined rows replay from spill-bounded state. In-process and TCP execution have the same behavior: a top-level set operation is dispatched as a query result and its count is carried in the terminal result frame. The historical pre-`SELECT` spelling on the right branch is accepted with the same combined-result meaning; the printer canonicalises it to the trailing form. Repeating the same tail clause in both positions is a parse error. The right branch cannot be independently ordered or paged in this syntax. Paging without ordering streams and early-exits; ordering is a blocking, stable external sort bounded by `MaxInMemoryStreamingState`, with checksummed spill runs above the cap. Set-level paging is reflected in EXPLAIN's estimated row count. Under engine-wide snapshot isolation, collection reads in both branches share one statement snapshot, and the combined result is produced before that lease is released. Temporal segments resolve at that CSN before valid-time filtering. Any lazy result drained into bounded replay before lease release first freezes its result schema and polymorphic subtype metadata, so producer callbacks cannot retarget the layout advertised for retained bytes. Rows supplied by an execution interceptor or plugin statement handler cross the same boundary before publication; later plugin metadata mutation cannot retarget the wire schema. Buffered plugin results additionally copy the list and every row buffer, and lazy rows are copied before publication, so later producer mutation cannot change published cardinality or bytes. Both shapes are recursively validated against the captured schema; malformed binary fails before that row can reach an in-process or wire consumer. A lazy plugin or custom row source that returns a null async enumerator fails its provider contract while releasing any attached owner and retiring its statement cancellation and migration-drain registrations; it cannot become a successful empty result or an unrelated decorator failure. A deliberately deferred wrapper reports the contract error on the first row request while still releasing its operator state. The result algebra is closed: `Rows` has exactly one row source and a schema; non-row results have no row metadata; error classification appears only on errors, and every error carries both a defined class and a non-empty code; undefined result/error enum values are invalid. Only `AffectedCount` may carry a nonzero affected-document count; transaction/subscription session metadata is confined to `Ok`. Polymorphic result metadata is either absent or carries a non-empty discriminator, at least one subtype, and a virtual `Envelope` field in the published row schema. Empty or whitespace schema/subtype identities fail before retained bytes can be decoded under an ambiguous generation. Every TCP schema emission forwards that captured generation, including CTE, set-operation, virtual, LIST, and plugin-produced rows; no executor-mediated result may silently lose its envelope description. Every TCP query crosses the same executor boundary as in-process MQL, including a plain single-collection `FROM`. Snapshot coordination, execution interceptors, read gates, view/subquery/computed evaluation, active-query registration, timeouts, and schema-generation fencing therefore cannot be bypassed by a simple remote query. An interceptor claim preserves any valid result kind on the wire.

Plugin read admission presents each distinct logical `(collection, intent, AS-OF instant)` operation once after view expansion, including joins, CTE and set-operation branches, lateral sources, and predicate subqueries. Internal branch execution, optimizer rewrites, and per-row correlated evaluation do not re-fire gates for operations already admitted by the outer statement; an independently initiated statement gets a new admission pass. DML targets remain write-guard operations, while query sources inside their predicates use read gates.

Eligible uncounted queries still frame the owned engine row stream in one pass through the executor's transport preference, including after pass-through execution interceptors. The advertised schema and descriptor bind to one generation; a rewriting `ALTER` cancels/drains the old statement or trips the identity fence before any replacement-layout row. Counted and algebraically buffering queries retain bounded replay with spill above the configured streaming-state cap. The remote `IncludeTotalCount` request reaches execution interceptors and plugin statements even when their AST is not a built-in query. If such a statement returns rows, its exact count is preserved in the terminal frame. Every execution interceptor receives an isolated read-only parameter map with private copies of mutable byte-array values. Passing through cannot rewrite the bindings observed by a later interceptor or by core execution. An ordinarily broken interceptor identity getter also remains inside the plugin-fault boundary and cannot replace the stable classified error; direct or nested memory exhaustion and simulated process death escape with their outer exception identity intact. Plugin statement extensions must return an AST whose exact runtime type is declared by that same extension in `SupportedNodeTypes`. An undeclared shape is a parse error; returning `true` with a null AST is also a contract parse error, not a silent decline. An unowned plugin AST fails authorization closed; unknown executable plugin shapes never inherit Reader permission. An undefined plugin permission value is likewise rejected before execution. Each statement extension must also declare whether every owned node is non-mutating, completes an existing scope, mutates through the current scope, commits independently, or opens a new scope. Engine-role admission uses this effect separately from authorization. Missing ownership and undefined effects fail closed; plugin statements never inherit an implicit read-only effect. Plugin-contributed `OPTION(...)` keys follow the same explicit-claim rule: a `true` claim must consume input and return a non-empty, non-whitespace canonical key, or parsing fails with a plugin contract error. Set-expression chains preserve every branch. `INTERSECT` has higher precedence than `UNION` and `EXCEPT`; equal-precedence operators associate left to right. `FROM (<query-expression>) alias` creates an explicitly grouped derived source, including branch-local ordering/paging and nested WITH definitions.

<a id="syntax-explain--explain-analyze"></a>

### EXPLAIN / EXPLAIN ANALYZE

ORDER BY and HAVING bind their actual source or aggregate schemas before plan rendering. Window shape, partition/order fields, literal offset/bucket arguments, and percentile ranked types share runtime's pure schema validator. EXPLAIN never invokes HAVING functions or evaluates percentile probability expressions; those values are checked during execution. Empty nested inputs retain these checks.

A source-qualified sort key retains its source identity and type even when a computed output uses the same leaf name. A relation qualifier also takes precedence over a same-named computed output. Grouped queries retain their aggregate sorting path; qualified grouping keys in ORDER BY and HAVING bind the published grouping columns.

Ordering by a computed SELECT alias happens after projection, then SKIP/LIMIT. Additional source sort keys retain their exact paths in hidden columns, which are removed from output. Physical, derived, and CTE inputs use the same bounded spill-capable result sorter. Static plans show Projection followed by Sort, with the unpaged source access retained underneath.

JOIN key binding checks field existence and the runtime scalar equality domain, including compatible numeric types, against the logical relation aliases. APPLY ON conditions bind the merged pair schema, parameters, functions, and nested subqueries. These checks run for physical, derived, and CTE inputs even when inputs are empty, and invoke no query function. Invalid ON fields are identified as ON predicate errors. Scalar-subquery and lateral result-schema discovery use the same checks before row evaluation.

CTE, plain-view, and derived-query consumers have their own plan boundary. Their producer remains a child, so a source index is not presented as an index on the produced rows. `VirtualScan`, `Filter`, `Sort`, and `Window` describe consumer work; virtual aggregation uses `HashAggregation`, and a join of produced rows is a `DeferredJoin` boundary over its inputs. Consumer rows report null `Index`, `Direction = None`, and `EarlyExit = false`; any proved source seek or early stop remains visible on its producer child. A Filter row counts its predicate leaves. Filtering, grouping, DISTINCT, HAVING, and joins leave output cardinality unknown without supporting evidence. Scalar aggregation emits one row before HAVING, even for empty input. Sorting and windows preserve cardinality; consumer SKIP/LIMIT adjusts a known estimate using current parameter values. Virtual system sources use the same consumers above a `VirtualScan`, with unknown snapshot cardinality. Static EXPLAIN reads their registered schema without capturing rows; ANALYZE performs ordinary snapshot execution. Both reject temporal clauses on current-state system sources, and composed APPLY remains supported.

When a join reads a CTE, plain view, system collection or `SERIES` on either side, its FROM relation included, `DeferredJoin` marks the join boundary: runtime chooses access and ordering after materializing those inputs. Its children are its inputs, one per relation in written order and named by alias: `Relation input:` for a stored relation, `CTE input:` for a CTE or plain view, `Derived input:` for a derived FROM table, `System input:` for a system collection, `Series input:` for a series and `Dependent input` for an APPLY body. Each produced input's complete plan nests under that input, including derived bodies, grouping, paging, and recursive expansion; a system input is a `VirtualScan` with unknown snapshot cardinality, and a series input a `Series` whose estimate is its exact row count. Physical `RelationInput` rows report input cardinality without claiming a selected scan or index; a temporal relation's count includes every retained version and snapshot isolation can hide or resurrect rows, so either reports `null`. Equality and dependent join output estimates are unknown, except that a known-empty input empties an inner or cross join and a `LEFT JOIN` on a physical relation's primary key keeps the estimate before it; an all-CROSS join multiplies known input estimates, saturating on overflow. Consumer filters, grouping, windows, sorting, and paging appear above this boundary. ANALYZE nests the tree runtime selected from the materialized inputs under the boundary, as an ordinary join's tree nests under its root: each measured `JoinPlan:` node under the node it feeds, and each input runtime materialized (a CTE, view, derived table, system collection or series) under the node that reads it, the deepest node whose aliases include the input's, carrying the rows it held and the time reading and materializing it took. A stored relation has no input row there: the node that reads it measured that read, as in an ordinary join's tree. A join that composes its relations one edge at a time in written order (over a derived or series FROM relation, or for a consumer that reads the joined rows, such as a window) runs the left-deep tree of that order, and ANALYZE lists it so: each edge's tree stands in place of the next edge's scan of the rows joined so far, and every node names the relations it holds and joins on the keys its `ON` clause wrote, so a composed stored join's measured nodes are the nodes its static tree describes. Such a composition reads its FROM relation into the rows its first edge replays, and the tree's row of that relation measures the read: a stored relation, which it reads through the `WHERE` conjuncts that compare only that relation's declared top-level scalar columns (none nested, computed, array-valued or a vector) with literals, parameters or lists of them, under `AND` or `OR`, however each column is spelled (by the relation's alias, its collection name or, where only that relation declares it, its bare name), and through none when the relation is polymorphic or read `IN BETWEEN`, on its `Scan`, as a bushy leaf's read is measured (the relation's row count as `RowsIn`, the rows read as `RowsProduced` and the time reading them took), and a produced relation on its input, with the rows it held and the time reading and materializing it took. Its nodes carry the estimates its static tree carries: the `Scan` of a stored relation is `null` when those conjuncts restrict it or when it is temporal or read under snapshot isolation, and each join estimates over the node below it, never over the exact count of the rows its edge replays. Any other conjunct that reads only the FROM relation (one over a nested path, a computed column or row metadata, or an array `MATCH`) restricts no read and filters the composed rows, so a composition whose read none of those comparisons restricts estimates its `Scan` over the whole relation, where an ordinary join of the same relations that reads such a conjunct at its FROM scan estimates that scan `null`. An ordinary join's FROM scan reads a `WHERE` that holds an `OR` other than equalities of one column only as a whole, and the join evaluates it after joining when any leaf of it reads a joined relation, so there those comparisons restrict the composition's read, whose `Scan` estimates `null`, while the ordinary join's scan reads the whole relation through no conjunct. `LAST PER` reads its FROM relation through the conjuncts its bucket walk samples ([temporal downsampling](temporal.md#last-per-temporal-downsampling)). ANALYZE nests a tree only where execution selected exactly one tree over the boundary's aliases, since a node is identified by the aliases it holds. When it selected more than one, as for a join in a body run once per outer row or for joins over the same aliases anywhere in the statement, such as both branches of a set operation, whether they join the same relations or not, each such boundary keeps its inputs as static EXPLAIN lists them, unmeasured, and the measurements stay stage rows under the statement root: each measured `JoinPlan:` node, and each input runtime materialized as a `JoinInput:<alias>` row of strategy `Materialized` carrying the rows it held and the time reading and materializing it took.

Recursive producers use `RecursiveExpansion`, with a seed child and a `RecursiveStep` boundary for repeated member evaluation. A `Recursive member level` child describes one level as the member runs it, at the catalog generations the statement captured: its reference to the CTE is a `VirtualScan` of the frontier the previous level added, and a member that reads only the frontier's keys reads them through an `IN` query over that reference in its `WHERE`, noted as the key membership each level adds. Their full cardinality is unknown; a seed estimate is not the full expansion's estimate. Static plans never execute the seed, member, or consumer to discover data-dependent counts.

Write-predicate EXPLAIN also binds scalar, negated, and subquery predicates, and predicates that read a virtual computed column, for UPDATE, REPLACE, DELETE, SEAL, UNSEAL, and CANCEL VERSION, including transitive plain views and correlated outer fields. It does not evaluate those predicates. Their final write access depends on resolved values or matched keys, so the root reports `Strategy = DeferredPredicate`, null `Index` and `EstimatedRows`, `Direction = None`, `EarlyExit = false`, and `FilterCount = 0` (no native write filters have been produced yet). Native predicates retain their concrete access plans. ANALYZE executes the ordinary write path and reports affected rows; the deferred root still describes the static boundary. TEXT and JSON agree.

Read-query EXPLAIN expands plain views transitively using the same visible definitions as execution, including private changes inside a migration. Fully qualified view identities stay distinct from same-named lexical CTEs. Static planning reads schemas without executing stored expressions; ANALYZE runs and consumes the expanded query. TEXT and JSON use the same bindings.

Static planning binds output columns from catalog metadata through derived sources, CTEs, logical JOIN aliases, and scalar projection subqueries. It uses the same wildcard expansion as execution, so missing nested targets and duplicate output names fail even on empty collections. Set-operation branches and recursive members must have compatible binary column layouts. NEAREST uses the same target, vector-dimension, finite-value, and cosine non-zero checks as execution. Schema binding does not read query rows or invoke query/subquery functions. Data-dependent errors, such as a scalar subquery returning multiple rows, still require execution to detect.

`EXPLAIN <statement>` returns the root plan row, followed by any child-plan rows, with columns: `Operation`, `Strategy`, `Index`, `Direction`, `EarlyExit`, `FilterCount`, `Notes`, `EstimatedRows`, `Collection`. `Collection` names the stored collection a row's access path reads, which an index the row names or suggests belongs to, and is `null` on a row with no access path of its own. `EXPLAIN ANALYZE <statement>` runs and fully consumes the inner statement and adds `Measured` and eight measured columns (`RowsProduced`, `RowsIn`, `ElapsedMicros`, `StreamingMode`, `SpilledBytes`, `AdmissionDecisions`, `RadixDepth`, and `PartitionCount`) plus per-stage rows. `Measured` is `false` on a row execution ran no stage of its own for, whose measured columns are zero placeholders rather than a measurement, and `true` on every other row. `RowsIn` is the actual input cardinality observed by an instrumented stage and is zero on the statement summary and on a row `Measured = false`. `StreamingMode` is `Streaming`, `Buffered`, or `n/a`. `AdmissionDecisions` is null on `NoOpAdmissionController`. A bounded controller reports one coherent policy snapshot as `"reserved=X/max=Y warn=W%/spill=S%/reject=R% crossings=Z"`; another non-no-op implementation reports `"reserved=X/max=Y crossings=Z"`. The crossing delta is engine-wide for the statement's wall-clock window, so concurrent sibling statements can contribute. Stage rows leave this field null because tickets have no causal stage attribution. A stage's radix fields report its deepest level and non-empty top-level spill partitions; descendant partitions are represented by depth rather than added to the count. The summary takes the maximum depth and sums partition counts across stages. Both are zero without observed radix partitioning. Child rows use `StreamingMode = n/a` because that field describes the root result owner's delivery shape; nested plans and stage statistics do not own a result source. Works on SELECT, DML, CTE, and set-ops. `ElapsedMicros` is a non-negative `INT64`; overflow-safe tick conversion saturates only when the mathematical duration exceeds `INT64` maximum and never wraps a long-running statement or stage negative. Measured row counters also saturate at `INT64` maximum. `SpilledBytes` is non-negative; cross-operator sums are checked and a negative late-bound value fails closed instead of being exposed as a false small total. It is a lifetime write counter: draining or disposing a lazy result does not subtract spill runs that were already written, including typed membership sets built for `IN (subquery)` evaluation. A join's root row describes its FROM relation's access path over the WHERE its outer scan runs: each conjunct that reads that relation alone, whichever qualifier spells it (the relation's alias, its collection name, its namespace-qualified name or none), at the field the scan reads (a leaf under the relation's declared `Body` root reads that root's child), and the OR groups only when none of their leaves reads a joined relation. A predicate the join evaluates over merged rows selects no access path and enters neither the row's `Notes` nor its `EstimatedRows`; `FilterCount` still counts every native `AND` conjunct of the WHERE. Joins with only catalog-backed inputs append the physical tree selected by execution. Operations use `JoinPlan:join:<sorted-aliases>` so the alias set gives each node one stable identity in static and measured plans. Static nodes distinguish `Scan`, `StreamingLeftDeep`, and `MaterializingBushyHashJoin`, and their notes carry the alias set and equality edges assigned to that node. ANALYZE renders the tree execution ran in place of those static rows, each node's measurement where the static row of its identity stands and at its depth, so both report one tree, a left-deep tree's FROM scan measured as a bushy leaf is; it retains the edge metadata, estimates each node by the same rule over the inputs it read (an input it materialized, such as a CTE, has an exact count), and refines a streaming strategy with the algorithm that actually ran (for example `StreamingLeftDeepHashJoin`). Optional join and lateral-inner annotations may be omitted for an ordinary unrefinable query shape, but structural corruption (including a detector nested inside another exception) and process-memory exhaustion always fail EXPLAIN; corruption retains its stable classification and quarantines its fault domain.

When an instrumented parallel stage runs, the ANALYZE summary note reports the actual worker count and row distribution as `Parallel: N workers, rows/worker total=T min=L max=H [c0,c1,...].` Configuring a maximum DOP does not itself add the note because the selected plan may remain serial.

`EarlyExit` is true for naturally bounded primary-key / temporal point seeks, or when a positive LIMIT actually caps an ordered scan. Secondary range and ORDER-only scans require a UNIQUE index because non-unique ties need their complete equal-key run for the final primary-key tie-break. Post-scan filters, aggregation, any exact total-count request (including an unfiltered scan), temporal visibility, and an overflowing `SKIP + LIMIT` disable the cap. A filter on the ordered key still counts as post-scan work unless the scan consumes it or index membership proves it. For example, a range scan consumes its range bounds and key membership proves `IS NOT NULL`, but `!=` and `IN` remain residual filters before final paging. Without the cap, an ordered scan with a positive LIMIT, outside aggregation and exact counts, still stops once `SKIP + LIMIT` of its rows pass every filter and the equal-key run holding the last of them is read, except a compound-index scan whose key extends past a non-unique ORDER BY tuple, which reads its whole range; where a scan stops depends on the data, so `EarlyExit` stays `false`.

For grouped aggregation, the strategy mirrors the order property proved by the selected inner access path. An `IndexOrderScan`, or an ordered `PkRange` / `SecondaryRange` over the complete grouping key, reports `StreamAggregation`; other inputs report `HashAggregation`. The aggregation node itself never reports `EarlyExit = true` because every filtered input row contributes before group paging.

Planner field identity is case-insensitive after stripping an optional `Body.` prefix, including PK and temporal predecessor strategies. The temporal strategy matches only the collection's declared primary key: for a primary key named `[Key]`, `[Key]`, `[kEy]`, and `Body.Key` produce the same runtime and EXPLAIN path. Ordinary fields named `[Id]` or `[DocumentId]` are not temporal identity aliases.

If converting a numeric comparison operand to an index key would change its value, runtime uses an exact scan and EXPLAIN reports `FullScan`, a null `Index`, and `EarlyExit = false`. This applies to scalar, temporal, partial, array, compound, and OR access paths. Current parameter types matter: a stored `FLOAT64` value `0.1` equals a Double parameter `0.1` but differs from Decimal `0.1`, so identical printed parameters can have different results and index eligibility. An operand that survives key conversion retains ordinary index eligibility.

For cost-modeled same-family alternatives, `Index` is the exact field or ordered compound field list selected by the chooser and passed to runtime dispatch. EXPLAIN does not reselect by predicate or index-registration order; equal-cardinality equality candidates can therefore be separated by physical leaf cost while range and compound candidates retain the chooser's exact path.

A parenthesised PostgreSQL-style option list selects the format: `EXPLAIN (FORMAT JSON) <statement>` returns the same plan as a single `Plan` text column holding a nested-JSON document (root node + a `Plans` array of stage / inner-plan children, `└─ ` prefix stripped, typed columns as native JSON bool/number) instead of the tabular rows. Composes with ANALYZE: `EXPLAIN (ANALYZE, FORMAT JSON) …`. `FORMAT TEXT` (or the bare `EXPLAIN` / `EXPLAIN ANALYZE` spelling) is the default tabular output; `FORMAT` accepts only `TEXT` or `JSON`.

`EstimatedRows` is nullable. Point PK and temporal seeks report `1` (`PK IS NULL` reports `0` because primary keys cannot be null). A full or ordered scan without a WHERE predicate reports a standard collection's document count, the rule a join's `Scan` leaf follows; a scan with a predicate reports a fresh-statistics estimate of the surviving rows where one applies and `null` otherwise; a scan of a temporal collection reports `null`, because its document count includes every retained version. Primary-key equality with `IN BETWEEN` uses `TemporalRange`, whose fresh primary-key statistics estimate the identity's complete retained history before interval and residual filtering. Without that key path, the temporal full scan has no overlap estimate. `ANALYZE` includes all retained past, current, and future versions; temporal `DocumentCount` counts retained slots, and PK distinctness counts identities. An MVCC snapshot full scan also reports null because an older snapshot can hide later inserts or resurrect later deletes or temporal segments. Static EXPLAIN reports that physical serial buffered `FullScan` whenever engine-wide snapshot isolation will open or reuse a snapshot; it does not label that query with a latest-committed point/index strategy. When the cost model rejects an equality, range, compound, or bitmap-union index path in favour of `FullScan`, the scan still reads the collection but `EstimatedRows` preserves the rejected candidate's estimated filtered output. Statistics-dependent equality/range/compound plans report null when no fresh statistics apply. `BitmapAnd` intersects cost-effective, freshly estimated scalar equality/range or compound-prefix inputs. Its child rows name each exact selected index. Disjoint predicate fields prevent double-counting, and partial-index filters must be implied. Independent-selectivity estimates are capped by the smallest input; correlation may change actual output. Bounded bitmap preparation may decline to the heap before publishing rows; predicates and visibility are rechecked and page order does not satisfy `ORDER BY`. Temporal/snapshot paths retain their version-aware behavior. A cross-field `BitmapOr` sums its value-aware input estimates, discounts proven repeated cached probes, and caps the union at collection cardinality. `LIMIT N` caps a known value at N and leaves an unknown one `null`, as a `NEAREST` ranking's `TOP N` does; `SKIP M` subtracts M (including after set-op branch estimates are combined); aggregations report the distinct-group count (compound NDV when a matching compound index exists, else per-column NDV product); set-op operators combine branches (`UNION ALL` sums, `INTERSECT` takes the min, `EXCEPT` keeps the left).

Range estimates parse bounds by field type and encode them into the same ordered key space as the index / ANALYZE histogram before combining lower and upper bounds. Compound partial-prefix estimates also encode the leading equality probe before consulting its MCV. A nonzero leading estimate narrowed by a nonzero trailing-range fraction is ceil-rounded to at least one row.

`Notes` is freeform and surfaces:
- Physical join-node identity, aliases, and assigned equality edges
- Missing-index suggestions for FullScan (`WHERE [X] has no index; CREATE INDEX ...`)
- Set-op per-branch row counts
- Partial-index match (`PartialIndex: WHERE ...`)
- Cost-ranked candidate count (`Cost-ranked N candidates; picked chooser-selected path` in production; `picked most-selective path` only for the fallback explainer ranker, which reports `Kept N candidates in written order; a candidate has no usable estimate` when a candidate has no estimate)
- Lateral-apply inner subquery (`Lateral apply; inner subquery on '[B]' re-evaluated per outer row`)
- Correlated scalar aggregates retained per outer row because their live equality domains cannot use a set-wise join key
- Correlated predicates that remain in a residual filter after decorrelation
- Computed-column injection slow path

Computed dependency discovery includes nested Objects/Arrays and subtype extensions. Predicate binding accepts source-qualified `Body` paths with the same meaning as execution. The access strategy describes the actual input before enrichment, including seeks from eligible stored-field filters. Virtual-value filters remain after enrichment and cannot claim their own stored index. Aggregation retains its strategy over that input; post-enrichment filtered/joined output estimates stay unknown. STORED computed fields retain normal index planning. Scalar residual plans keep runtime's native conjuncts and report any full-row enrichment required by the residual source.

Numeric fragments embedded in `Notes` use invariant formatting with `.` as the decimal separator. TEXT and JSON plans therefore remain identical across server process cultures.

<a id="syntax-order-by"></a>

### ORDER BY

Query ordering accepts at most 64 scalar fields with defined total order. OBJECT, ARRAY, and VECTOR keys are rejected, including on empty input, and an array element path key (`[Tags][]`) is `FEATURE_NOT_SUPPORTED`. `NULL` / missing values sort first ASC and last DESC. When a secondary index proves the leading key, numeric, date/time, and folded-ordinal `STRING` order can be reused for bounded ranges or an unbounded scan. The executor incrementally sorts each equal-leading run by the remaining mixed-direction tuple plus the primary-key tie-break. An unbounded nullable index requires a `WHERE` proof that the key is non-null (`IS NOT NULL`, equality, range, or `IN` without NULL). Object parents participate in the path's nullability proof. A partial index requires query implication of its filter. NaN, signed zero, non-ASCII case-folded ties, and paging use the same comparator as a full sort; paging does not truncate a run before its trailing order is complete.

<a id="syntax-skip--limit"></a>

### SKIP / LIMIT

`SKIP n LIMIT m`. Both accept integer literals or `@param` inside the 32-bit range [SKIP and LIMIT](#skip-and-limit) gives. Default SKIP=0; no default LIMIT (unbounded). Always cap LIMIT for queries that could match a lot of rows.

The client/wire `IncludeTotalCount` option reports cardinality after `WHERE` / `HAVING` and before `SKIP` / `LIMIT`. It is preserved for base collections, CTEs, CTE-backed JOINs, `[Mnemic]` virtual collections, read-time computed-column injection, and plain or computed projection. A virtual source's own count belongs to its inner relational scope and is discarded at the outer query boundary; the outer request either recomputes its own count or returns no `TotalCount` metadata. Counts are absent or non-negative; the wire's only negative encoding is canonical `-1` for absence, and values below it are invalid. Base-collection count requests consume the complete filtered input before paging, including unfiltered queries. Without snapshot isolation the counted scan remains fenced through exhaustion, so `TotalCount` and emitted rows cannot describe different concurrent-commit cuts.

On a plain JOIN result with no residual filter, field equality, sort, aggregate, total-count request, or projection, `SKIP` / `LIMIT` streams and stops the join producer at the limit. Whole-result operators such as `ORDER BY` still complete before pagination.

The client/wire `IncludeTotalCount` option on a JOIN counts the complete filtered joined result before `SKIP` / `LIMIT`. A non-polymorphic left-deep JOIN without aggregation evaluates ordinary post-join residuals while storing the count input in spill-bounded state. Optional `ORDER BY` uses stable external runs, and plain or computed/`AS` projection happens after ordering during replay. Only the page is returned through `RowsAsync`.

A non-aggregate JOIN tree with polymorphic collections on any side uses spill-bounded replay for plain nested and flat computed/`AS` `SELECT`, `SKIP` / `LIMIT`, ordering, and total count. Envelope-aware post-join predicates, including mixed outer/inner OR groups, run before counting and optional stable external `ORDER BY`, then pagination; projection applies per emitted row. Subtype fields on either side are read from that side's original envelope and evaluate to null for other subtypes. The physical joined side is a valid base document plus a private byte-exact `Envelope`; private typed extension sort keys are stripped before output. Incompatible cross-subtype projection and ordering schemas are rejected before replay. Matches, ordering, projection values/shape, and pre-pagination count remain exact.

Every selected left-deep or bushy tree carries one alias-to-physical-envelope map through later merges. WHERE/MATCH, typed sort and aggregation keys, aggregate FILTER, plain nested projection, and flat computed/`AS` projection resolve through that same map at arbitrary join depth. Unmatched LEFT sides remain NULL. Typed sort, aggregation and projection inputs require compatible complete declarations; native WHERE/MATCH and native aggregate FILTER use the active subtype.

A non-aggregate bushy JOIN replays spill-bounded final state lazily. When total count is requested, residual predicates filter into a second bounded buffer whose cardinality is reported before pagination. Residual `WHERE` predicates run before optional stable external `ORDER BY`, then `SKIP` / `LIMIT`, followed by flat computed/`AS` or plain nested projection. Flat aliased output keeps the same multiset, ordering, and schema across plan shapes; raw or plain nested output intentionally exposes the selected `{outer, inner}` tree.

<a id="syntax-14-null-semantics--null-permissive-not-full-ansi-3vl"></a>

### NULL semantics — null-permissive, NOT full ANSI 3VL

One doctrine, applied identically in WHERE, expression position (CASE WHEN / SELECT / computed columns / CHECK), and aggregate / window `FILTER (WHERE …)`:

- Equality is NULL-safe: NULL equals NULL and differs from present values.
- IN is a disjunction of equality; NOT IN is its exact complement, including NULL list members. IN (NULL) selects NULL rows and never means IN ('').
- IS NULL / IS NOT NULL are synonyms for = NULL / != NULL, including inside array predicates, MATCH bodies, and predicate LENGTH.
- Ordered and text predicates remain UNKNOWN for NULL, including under NOT.
- `BETWEEN a AND b` is `>= a AND <= b`; `NOT BETWEEN a AND b` is `< a OR > b`. A NULL bound is therefore UNKNOWN only while the other bound does not decide the result: `5 BETWEEN NULL AND 3` is FALSE.
- Arithmetic: `NULL + 1` = `NULL`. Any null operand poisons the result.
- Boolean combos: `TRUE AND NULL` = `NULL`; `FALSE AND NULL` = `FALSE`; `TRUE OR NULL` = `TRUE`; `FALSE OR NULL` = `NULL`.
- WHERE / FILTER gating: a row is included only when the predicate is `TRUE`. Both `FALSE` and `NULL` exclude.
- Aggregates: `COUNT(*)` counts every row; `COUNT(field)` skips nulls; `SUM` / `AVG` / `MIN` / `MAX` skip nulls and return `NULL` if the group has no non-null inputs.

<a id="syntax-15-numeric-promotion"></a>

### Numeric promotion

Arithmetic between two integers of any width yields `INT64`: `INT8 + INT8` is an `INT64`, never a narrower integer. Any other numeric pair takes the wider kind in the order `FLOAT64` > `FLOAT32` > `DECIMAL` > integer: `INT64 + DECIMAL` → `DECIMAL`, `DECIMAL + FLOAT64` → `FLOAT64`, and `FLOAT32 + FLOAT32` or `FLOAT32 + INT32` stays `FLOAT32`.

<a id="syntax-18-syntax-reminders"></a>

### Syntax reminders

These forms follow the current parser:

- **`CONFIRM REPLACE ALL`** — does not exist. `REPLACE` *requires* a `WHERE` clause; the parser explicitly rejects bare `REPLACE`.
- **Block comments** use `/* ... */` and may nest up to 100 levels. Unterminated comments reject; quoted delimiters remain literal content.
- **Cross-field `OR` is unsupported** — false. Same-field equality ORs rewrite to `IN`; cross-field OR evaluates each branch independently with arbitrary AND/OR nesting (DNF), and a BitmapOr index merge serves it when every branch is a single indexed equality. See [WHERE](queries.md#syntax-where) and the usage pitfalls below.
- **`SELECT *` is unsupported** — false: `SELECT *`, qualified `[alias].*`, and the `EXCLUDE`, `REPLACE`, and `RENAME` wildcard modifiers are all wired — see [SELECT projection](queries.md#syntax-select-projection--explicit-list-and-wildcard-modifiers). Omitting the `SELECT` clause entirely still returns the whole row.

<a id="syntax-change-a-computed-expression"></a>

### Change a computed expression

`ALTER COLLECTION ... ALTER FIELD [path] SET COMPUTED (<expr>)` replaces an existing computed expression while preserving its type, nullability, and virtual or STORED mode; `STORED` after the expression also makes a virtual field stored, and on a plain field the statement makes the field computed ([Change a computed expression or mode](ddl.md#change-a-computed-mode)). Dotted OBJECT paths, ARRAY OBJECT paths with `[]`, and collection `SUBTYPE [value]` scopes are supported. The complete dependency graph and result shape are validated before publication. Virtual changes retain physical rows; STORED changes recompute current and historical rows and rebuild existing indexes. A failed expression, CHECK, or rewrite rolls back the schema, data, and indexes.

`ALTER TYPE [Ns].[Type] ALTER FIELD [Field] SET COMPUTED (<expr>)` applies the same change atomically to inherited and composed uses, including repeated object, array, and subtype occurrences. Alter an inherited field on its declaring type.

<a id="syntax-sequential-schema-and-data-changes-in-a-migration"></a>

### Sequential schema and data changes in a migration

A migration may write rows, rewrite the same collection more than once, and build or change offline indexes in sequence. Each operation reads the owning transaction's current rows, including private append pages and overflow bodies. All changes publish together at `COMMIT MIGRATION`; abort restores the original rows, schema, index definitions, and logical write sequence numbers.

<a id="syntax-aggregate-local-ordering-tuples"></a>

### Aggregate-local ordering tuples

`COLLECT_ARRAY` and `JOIN_STRING` accept up to 64 inner `ORDER BY` field paths, each with its own `ASC` or `DESC`. Keys compare lexicographically using the field types' ordinary ordering. NULL sorts first for ASC and last for DESC on each key. Equal keys retain input traversal order; supply a final unique key when the result must be independent of the selected access path.

```sql
FROM [App].[Tags] GROUP BY [Bucket]
SELECT [Bucket], JOIN_STRING([Tag], ',' ORDER BY [Score] DESC, [Tag] ASC, [Id] ASC) AS [Tags];
```

Sort paths can refer to computed fields, joined aliases, and CTE inputs. Per-aggregate FILTER still controls which rows contribute. Retained values and sort tuples share the aggregate spill store; sorting uses the same spillable sorter as single-key ordering. One multi-key row tuple has a 64 MiB bound, checked before allocation; this bounds transient row work independently of `MaxInMemoryStreamingState`.

<a id="syntax-base-fields-in-polymorphic-collections"></a>

### Base fields in polymorphic collections

`ALTER COLLECTION … ADD FIELD` and `DROP FIELD` work on the base schema of polymorphic collections, including nested base-object paths. Rewrites migrate the base portion of every current and historical envelope while preserving its subtype extension. Ordinary defaults and stored computed values are backfilled under the same migration; indexes and rollback share that outcome.

A base field cannot reuse an active subtype extension's name. The discriminator and primary key remain mandatory. Drop or rename is rejected when a subtype's computed expression depends on that base field, just as for base computed fields.

```sql
BEGIN MIGRATION 2;
ALTER COLLECTION [App].[Vehicles] ADD FIELD [Color] STRING DEFAULT 'Blue';
ALTER COLLECTION [App].[Vehicles] DROP FIELD [Description];
COMMIT MIGRATION;
```

Extending an existing collection subtype with `ADD SUBTYPE` recomputes stored values and rebuilds affected indexes when the collection has stored expressions. This includes base consumers of an extension field that previously read NULL. Rows, indexes, and schemas commit or roll back together. `DROP SUBTYPE` and later schema edits must preserve valid computed bindings in every remaining subtype.

A scalar WHERE comparison accepts complete expressions on either side, including literal-led arithmetic and concatenation: `[Price] > 10 + 5` and `[Name] = 'A' || 'da'`. Arithmetic binds before comparison. A lone literal or parameter retains the ordinary native comparison and its index eligibility.

Scalar WHERE expressions and unary NOT filter the source before NEAREST admits rows to its bounded top-k state. The source scan has no paging of its own; removing a nearer row cannot prevent the next qualifying vector from filling TOP. Native conjuncts remain eligible for ordinary source access paths.

Native predicate fields beside scalar or correlated WHERE expressions bind before row evaluation for physical, derived, and CTE sources. Unknown fields fail even for empty inputs or short-circuited Boolean branches. JOIN predicates follow the same rule on every route, each named relative to the relation it reads. An absent outer operand of correlated IN remains a non-match in both residual and optimized execution; a scalar sibling does not change that rule.

Scalar WHERE binding validates function arity and parameter presence before publishing rows, including empty inputs. Polymorphic references read the active envelope and yield NULL for an absent subtype field; incompatible declarations reject during binding. Qualified references use the most specific visible relation prefix, with the inner scope winning ties. An inner source alias leaves an enclosing collection-qualified reference available for explicit correlation. Nested predicates keep references to their own enclosing row; adding a JOIN or naming a nested alias `outer` or `inner` does not change which row a correlation reads. Execution and EXPLAIN use the same scope rules.

Trigger OLD/NEW references can read stored computed fields. Both timings observe the already materialized value, including generated identities and stored subtype dependencies. An extension field absent from the active subtype reads NULL. Image paths require compatible declarations and durable containing fields; a child of a virtual computed container is not stored image data. The same binding checks run before trigger catalog hydration publishes executable bodies.

Computed dependencies bind to their containing object scope. `Details.Total AS ([Rate] * 2)` protects `Details.Rate`, including within ARRAY OBJECT elements; it does not refer to a root `Rate` field. The dependency walk includes nested subtype extensions. Dropping a whole container removes its owned expressions, and renaming that container preserves their local sibling bindings. Expressions outside the container still protect every field they reference. Nested Object CHECK constraints protect their local field dependencies too. A subtype-qualified field change checks base expressions and that subtype's expressions; an unrelated subtype's same-named field is a separate binding.


Persistent vector-index membership cannot call runtime-replaceable functions, including built-in names that an embedded host can replace. Define the expression as a STORED computed field and filter that field instead. Stored computations bind immutable built-in implementations, so membership changes only when the source row changes and index maintenance can reconcile it.

Stored computed fields can be UPSERT conflict targets when backed by a matching UNIQUE index. The probe uses the fully materialized proposed key even though the INSERT literal cannot assign that computed field. NULL key parts retain ordinary UNIQUE semantics and take the insert path. This applies to DO NOTHING and DO UPDATE.

SET expressions evaluate referenced virtual computed fields against the current row at each mutation retry; EXCLUDED reads the independent proposed image. Derived read values stay in a separate evaluation buffer, so unassigned virtual slots remain NULL in the stored mutation image.

RETURNING accepts the optional Body qualifier for base and subtype fields. For example, `RETURNING [Body].[Extra]` captures the same extension value as `RETURNING [Extra]`, including UPSERT DO NOTHING through a secondary unique key.

<a id="syntax-scalar-contains-and-startswith"></a>

### Scalar CONTAINS and STARTSWITH

`expression CONTAINS expression` and `expression STARTSWITH expression` are comparison-precedence scalar predicates, including inside CASE WHEN. WHERE also accepts field references and function calls as their right operand. Both operands must be strings; parameters are read at each execution. Their result is BOOL, or NULL when either operand is NULL. Matching uses invariant lowercase folding and ordinal comparison, with literal `%` and `_`.

## Usage pitfalls


<a id="pitfall-series-anchor-is-an-instant"></a>

### A SERIES start is an instant, also in a zone

`IN TIMEZONE` decides how a temporal series steps and which offset its values carry, not where it starts: `SERIES '2026-01-01T00:00:00Z' TO ... EVERY 1 MONTH IN TIMEZONE 'Europe/Stockholm'` starts at 01:00 Stockholm time and every month starts at 01:00 local. Write the start in the zone's offset (`'2026-01-01T00:00:00+01:00'`) to step from local midnight.

<a id="pitfall-series-month-end-anchor"></a>

### Month steps anchored on the 31st keep the 31st

Steps are computed from the start bound, so a series anchored on January 31 yields February 28, March 31, April 30. For per-month rows, anchor on the 1st and read the last day as `DATEADD('DAY', -1, [End])`.

<a id="pitfall-series-skipped-date"></a>

### A date a zone skips is an empty step

A temporal series yields one row per step even where a zone skips a whole local date (a dateline change): that step's `[Start]` and `[End]` are the same instant, an instant read at it reads the next valid instant's state, and `IN BETWEEN [Start] AND [End]` over it is refused as an [empty range](temporal.md#in-between-temporal-range). Which dates a zone skips comes from the host's time-zone database, so a historical transition can fall on another date on a Windows server ([`IN TIMEZONE`](temporal.md#last-per-temporal-downsampling)).

<a id="pitfall-like-character-counts"></a>

### LIKE character counts

`é😀` does not match `LIKE 'é__'` or `LIKE 'é_%_'`: the emoji is one character, not two independently matchable UTF-16 units. `é😀x` matches both. WHERE, NOT LIKE, and projected CASE expressions use the same character count.

<a id="pitfall-expected-in-square-brackets"></a>

### "Expected … in square brackets (e.g., [Name])"

The parser saw a bare identifier where a bracketed one was required; `FROM Shop.Orders` reports `Expected namespace or CTE name in square brackets (e.g., [Name]) but found 'Shop'`.

```sql
FROM Shop.Orders;                 -- bad
FROM [Shop].[Orders];             -- good
```

Relation aliases require brackets too. Built-in keywords, function names, and grammar options retain their unbracketed spelling.

Prefer canonical `[Address].[City]` and `[Items][]` paths. Compact `[Address.City]` and `[Items[]]` spellings are accepted and normalize to those forms, but empty logical segments such as `[Address..City]` and nested bracket syntax inside one path token are rejected.

<a id="pitfall-unexpected-token-x"></a>

### "Unexpected token 'X'"

Almost always a clause-ordering mistake. Order is strict: `FROM → AS OF/IN BETWEEN → JOIN | CROSS APPLY → WHERE → NEAREST → LAST PER → GROUP BY → HAVING → ORDER BY → SKIP → LIMIT → SELECT → WINDOW → OPTION (TIMEOUT, MAXDOP)` ([clause ordering](#syntax-clause-ordering--strict)). Out-of-order = parser error.

<a id="pitfall-an-alias-that-repeats-an-input-field-needs-a-qualified-input"></a>

### An alias that repeats an input field needs a qualified input

`FROM [HR].[Employees] SELECT [Id], ENUM_LABEL([Status]) AS [Status]` and `SELECT [Id], [Salary].[Amount] AS [Salary]` report `AMBIGUOUS_FIELD`: inside the projection, `[Status]` and `[Salary]` name both the input field and the alias. Read the input through its relation — `ENUM_LABEL([Employees].[Status]) AS [Status]` — or replace the field's value in place with `SELECT * REPLACE (ENUM_LABEL([Status]) AS [Status])`. A plain pass-through (`[Status] AS [Status]`) and a grouped projection are not affected ([alias rules](#alias-repeating-an-input-field)).

<a id="pitfall-cross-apply-vs-outer-apply"></a>

### CROSS APPLY vs OUTER APPLY

Two semantics ship — `CROSS APPLY` is INNER (outer rows whose inner returns zero rows are dropped), `OUTER APPLY` is LEFT-OUTER (outer rows with zero inner matches survive with `[inner].*` returning NULL). Choose by whether you need outer-row preservation when the inner is empty.

<a id="pitfall-lateral-apply-composition"></a>

### Lateral-apply composition

Preparing APPLY binds the inner columns without running the inner query. Registered functions are invoked by actual inner evaluation only; an empty outer source does not invoke them merely to determine the result shape. Sorting or a derived source inside APPLY does not add a hidden schema-discovery execution.

JOIN and APPLY may be chained in one FROM (up to the shared 16-edge limit). Each APPLY can correlate with earlier relation aliases. Physical collections, CTEs, derived queries, and system collections can supply the outer rows. WHERE, grouping/HAVING, projection, windows, ordering, and paging consume the merged result; temporal source clauses continue to select the root source. Per-outer ordering or paging belongs inside the APPLY subquery.

`JOIN LATERAL`, `INNER JOIN LATERAL`, and `LEFT JOIN LATERAL` are accepted as portability spellings. ON accepts a boolean predicate over the current pair. It runs after the inner query's sorting and paging, before outer null padding. FALSE and NULL reject a pair. If no pair passes, OUTER APPLY still emits one outer row with a null inner; moving that condition to WHERE would discard it.

APPLY is still a nested query scope. More than 100 nested APPLY / `EXISTS` / scalar / list-subquery levels are rejected before recursive printing or execution; split such generated queries into CTE-backed statements.

<a id="pitfall-expected-from-but-found-select"></a>

### "Expected FROM but found 'SELECT'"

MQL queries begin with `FROM`, not `SELECT`. The `SELECT` clause is **last** in the canonical order.

<a id="pitfall-order-by-an-unknown-field-is-an-error-never-a-silent-no-op"></a>

### ORDER BY an unknown field is an error, never a silent no-op

`ORDER BY [Typo]` errors on every path — base collections, CTE / system-collection results, and joined results. Computed SELECT aliases are valid sort keys even when joined source fields share that name. Qualify a source field to sort by the source value. Grouped expressions and HAVING use grouping keys and aggregate aliases; WHERE and aggregate inputs use the source scope. EXPLAIN, saved views, and nested queries retain these distinctions.

<a id="pitfall-order-by-uses-raw-byte-order-for-bytes-and-rejects-composite-values"></a>

### ORDER BY uses raw byte order for BYTES and rejects composite values

BYTES keys use unsigned lexicographic order, with shorter strict prefixes first. There is no UTF-8 decoding or case folding. A present empty BYTES field sorts before non-empty bytes and after NULL ascending; DESC reverses this order. `Meta.CreatedBy` uses the same comparison. Unattributed metadata reads and sorts as NULL; empty CREATEDBY inputs are rejected. Range predicates use the same byte order, but never match NULL operands. Text operators require STRING.

OBJECT and ARRAY ordering keys error before reading rows, including empty input, grouped output, joins, CTEs, system collections, and spilled execution. Select a scalar child or compute a scalar key to order composite values. This does not change aggregate-local ordering inside `COLLECT_ARRAY` / `JOIN_STRING`, which compares the aggregate's raw values.

A leading-order secondary index is not automatically complete. An unbounded nullable index, including a required leaf under a nullable object, is usable only when `WHERE` excludes nulls, and a partial index is usable only when the query implies its filter. Otherwise the engine full sorts the complete row set. Incremental sort also finishes the whole equal-leading run before applying paging, so a LIMIT cannot cut off rows that still need trailing-field or primary-key tie ordering.

<a id="pitfall-field-comparisons-and-scalar-predicates-use-the-current-row"></a>

### Field comparisons and scalar predicates use the current row

`[A] = [B]`, `[Price] > [Cost]`, and `LENGTH([Name]) >= 4` work in query and DML WHERE, HAVING, and aggregate FILTER. A top-level equality between joined aliases can also become an equi-join edge. Partial-index WHERE retains its separate stored field/literal contract.

Unary `NOT` preserves unknown comparisons: `NOT ([Value] > 3)` excludes NULL values. MQL equality remains two-valued, so `NOT ([Value] = 3)` includes a NULL value. Use `IS NOT NULL` when nulls must be excluded.

<a id="pitfall-strings-comparing-case-insensitively"></a>

### Strings comparing case-insensitively

`'café' = 'CAFÉ'` matches. `WHERE [Name] = 'foo'` returns rows whose Name is `'Foo'`, `'FOO'`, `'foo'`, etc. This is Unicode case-insensitive equality — the active .NET invariant simple-lowercase mapping then an **ordinal** compare — applied everywhere: `WHERE`, `ORDER BY`, secondary index probes, GROUP BY, COUNT(DISTINCT), expression-level `=` / `<` / `>` in `CASE` / computed columns / `CHECK`, and the `POSITION` / `REPLACE` functions (so `POSITION(...) > 0` agrees with `CONTAINS(...)`). It is neither linguistic collation nor Unicode Default Case Folding: ignorable characters (e.g. soft hyphen `U+00AD`) stay significant, no normalization occurs, and ordering is by code point. The database header fingerprints the exact effective mapping and policy. If the runtime or globalization backend changes it, open durably invalidates and rebuilds all derived indexes from original documents before publishing the new profile; a crash repeats that work on reopen. If you genuinely need binary case-sensitive equality you'll need to think — there isn't a built-in case-sensitive operator in MQL today.

`BYTES` literals are Base64, not strings: their letter case is data. This also applies to partial-index filters and their `ANALYZE` statistics identity, so `WHERE [Payload] = 'AQ=='` and `WHERE [Payload] = 'aQ=='` describe different binary populations even though ordinary STRING equality is case-insensitive. Large `IN` lists over `BYTES` or `ARRAY` hash each complete binary value, so equal-length values sharing a long prefix do not form one lookup chain. A hash collision remains harmless because equality compares the complete payload.

<a id="pitfall-like-lowercases-but-never-canonical-normalizes-unicode"></a>

### LIKE lowercases but never canonical-normalizes Unicode

`LIKE` uses the same invariant-lowercase mapping as `=` — and, like `=`, it does NOT canonical-normalize: a pattern with precomposed `é` (U+00E9) will not match stored text holding decomposed `e` + combining accent (U+0301), and ignorable characters (soft hyphen) stay significant. `_` matches exactly one Unicode character — an emoji or other astral character counts as one, not two. Semantics are identical whether the LIKE sits in WHERE or in an expression (`CASE WHEN [N] LIKE '%x%' …`).

<a id="pitfall-null-semantics-are-null-permissive-not-ansi-3vl"></a>

### NULL semantics are null-permissive, not ANSI 3VL

Equality is NULL-safe: NULL equals NULL and differs from every present value. IN is a disjunction of equality tests; NOT IN is its exact complement. Thus `IN (NULL)` selects NULL rows, while `NOT IN ('x', NULL)` selects only present values different from 'x'. Ordered and text predicates remain UNKNOWN for NULL and do not select the row, including when negated. See [WHERE operators](#where-operators) for the maintained truth table.

<a id="pitfall-or-across-different-fields"></a>

### `OR` across different fields

Same-field equality ORs collapse to `IN` (`[S] = 'a' OR [S] = 'b'` → `[S] IN ('a','b')`). Cross-field OR (`WHERE [A] = 1 OR [B] = 2`) is supported — each branch evaluates independently and a row matches if any branch does. Arbitrary AND/OR nesting normalises to disjunctive groups: `[A] = 1 OR ([B] = 2 AND ([C] = 3 OR [D] = 4))` works and means what it says.

<a id="pitfall-unary-not-preserves-unknown-results"></a>

### Unary `NOT` preserves unknown results

`WHERE NOT ([F] > 1)` negates an ordered comparison. If `[F]` is NULL, the comparison and its negation remain unknown, so WHERE excludes the row. Equality retains MQL's two-valued NULL rules: `NOT ([F] = 1)` includes NULL. `!=`, `NOT IN`, `NOT LIKE`, `NOT BETWEEN`, and `IS NOT NULL` retain their documented operator semantics.

<a id="pitfall-join-projection-shape-nested-vs-flat"></a>

### JOIN projection shape: nested vs flat

A *plain* (un-aliased) join `SELECT [o].[Id], [c].[Name]` keeps the nested `{ outer, inner }` result shape (read `outer.Id` / `inner.Name`). Only requested leaves are retained. If SELECT mentions just one side, the other side is an empty object (or `null` for an unmatched nullable inner side), not a copy of every field on that collection. Multi-join projection applies the same rule recursively through the nested join tree. Adding **any** `AS` rename or computed expression (`SELECT [o].[Id] AS [OrderId], [c].[Name] AS [Customer]`) flattens the **whole** list to top-level columns. When two collections share a field name, qualify with `AS` (`[o].[Id] AS [OId], [c].[Id] AS [CId]`) — a flat list with two same-named columns is rejected; a nested (plain) list shadows one. Fields used inside computed JOIN expressions are validated before row execution; a misspelled alias field is an error, never an implicit `NULL`. A set-operation branch keeps the nested shape, so a plain JOIN branch combines with a flat branch only once its columns are named with `AS`; a recursive CTE member's plain items are named by their leaf ([CTEs](cte.md#recursive-cte)).

Schema discovery preserves the flat JOIN output used when a SELECT includes any computed expression or AS alias, including plain selected fields beside it.

<a id="pitfall-omit-inner-key-does-not-hide-the-key-from-the-query"></a>

### `OMIT INNER KEY` does not hide the key from the query

`JOIN ... ON ... OMIT INNER KEY` removes only the relation introduced by that JOIN's exact key leaf from implicit or wildcard output. It does not change matching or source binding: the key remains valid in later JOINs, WHERE, ORDER BY, expressions, and an explicit SELECT. A bare key name also remains ambiguous when more than one relation declares it.

With `SELECT [joinedAlias].*`, do not `REPLACE` or `RENAME` the omitted key; that slot is dead and the query is rejected. Repeating it in `EXCLUDE` is allowed. Nested keys remove only the leaf, not the parent Object; a polymorphic object keeps its discriminator, so joining on it with the modifier is rejected wherever the object is published. The modifier belongs after an INNER/LEFT equality and cannot follow CROSS JOIN or APPLY.

Polymorphic fields in a multi-JOIN tree retain their source envelope through left-deep and bushy rewrites. Qualify extension paths with the relation alias; the same alias map drives WHERE/MATCH, ordering, grouping/FILTER, and both nested and flat projection. A referenced path whose declared shape differs across subtypes still errors, and an unmatched LEFT side remains NULL.

<a id="pitfall-group-by--aggregates--distinct-work-over-joins-and-ctes"></a>

### GROUP BY / aggregates / DISTINCT work over JOINs and CTEs

`GROUP BY`, aggregate functions, `HAVING`, and `SELECT DISTINCT` apply to a `JOIN` result and to a CTE / system-collection reference, not just a single base collection. Qualify grouping keys and aggregate arguments with the join alias (`GROUP BY [o].[Region]`, `SUM([i].[Price])`); the grouping key's default output name is its leaf (`[o].[Region]` → `Region`). Use distinct SELECT aliases for same-leaf grouping keys, or omit those keys from SELECT. Hidden keys do not conflict with aggregate aliases. `HAVING` references source grouping paths, unambiguous key leaves, or aggregate `AS` aliases. Bare aggregate aliases take precedence over same-named keys; qualify the source key to distinguish them. Grouping happens after `WHERE`, before `ORDER BY` / `SKIP` / `LIMIT`. `SELECT DISTINCT` can also deduplicate grouped or scalar aggregate output: it compares only the selected columns after HAVING and projection. Two groups with the same selected total become one row even if their unselected keys differ. Final ORDER BY columns must be selected, and paging and TotalCount observe the distinct result. Over a JOIN, the DISTINCT result's own column names come first: an unqualified key such as `ORDER BY [Region] SELECT DISTINCT [o].[Region]` names that output column even when several joined relations declare `Region`. Any other key, such as `[o].[Region]` or `[Orders].[Region]`, must address a selected path and then names that path's column, for every input kind (stored, CTE, derived or system); a key that does neither is an unknown field of the DISTINCT result. A key that names an output column keeps that column's own children, so `ORDER BY [Body].[Size] SELECT DISTINCT [d].[Body]` orders by the selected `Body` Object's `Size` in a native or composed join alike. A single source's plain `SELECT DISTINCT` orders its result the same way: a key that addresses a selected path, such as `[Dims].[W]`, `[r].[Dims].[W]` or (when the source declares no Body root) `[r].[Body].[Dims].[W]` after `SELECT DISTINCT [r].[Dims].[W]`, orders that path's leaf column `W`, over a stored, polymorphic, derived or CTE input and beside a scalar, negated, membership or correlated WHERE alike. A correlated WHERE only decides which rows are deduplicated, whether it is evaluated per row or rewritten into joins: `WHERE EXISTS (...) SELECT DISTINCT [Dims].[W]` publishes the column `W`, as the statement without that WHERE does, never the whole `Dims` Object; write `SELECT DISTINCT [Dims]` to deduplicate the parent. Selected keys and ORDER BY keys resolve Body the way every other source path does: under a declared Body root, `SELECT DISTINCT [Body].[Code]` deduplicates that root's `Code` child, never a same-named top-level `Code`, and `ORDER BY [Body].[Id]` names the root's `Id` child, an unknown field of the DISTINCT result unless that path is selected. DISTINCT does not make ungrouped source fields valid alongside aggregates. Write `HAVING [Revenue] > 10000` with `SUM([Amount]) AS [Revenue]`; inline aggregate calls in HAVING are not the predicate syntax.

Explicit grouped SELECT returns only selected columns; it does not expose unselected group keys. `[Region] AS [Label]` retains the requested alias. Expressions run after HAVING over grouping keys and completed aggregate aliases: `SUM([Amount]) AS [Total], [Total] * 2 AS [Doubled]` is valid. An ungrouped source field or an alias from another computed expression is not an input. Scalar subqueries and windows use the same grouped relation. Correlations in SELECT and HAVING read emitted grouping keys, including keys qualified by a JOIN alias; execution and EXPLAIN bind those references to the same output slots. Without DISTINCT, unselected group keys can still drive ORDER BY before final paging.

Leaf names must remain unique. `GROUP BY [Billing].[City], [Shipping].[City]` and `GROUP BY [Address].[Count] SELECT [Address].[Count], COUNT(*) AS [Count]` error instead of returning duplicate/unaddressable columns. `COLLECT_ARRAY` preserves a structural input field's complete nested element schema.

JOIN carries the outer row's `[Meta].*` through filters, sorting, projection, and aggregation, but does not expose inner-alias Meta. Project inner metadata into a normal CTE column before joining.

`EXISTS` and `NOT EXISTS` work with CTE and derived outer sources as well as physical collections. Correlated or not, the inner query may read a collection, a view, a CTE, a derived table (including a set operation or nested `WITH`), or a system collection. An equality-correlated `EXISTS`, `NOT EXISTS`, or `IN` reads an inner relation that does not itself reference the outer row once per statement, so duplicate inner rows never duplicate outer rows. A derived inner body that references the outer row is evaluated per outer row. Correlated predicates bind to each outer row; deferred row reads retain the WITH block's lexical definitions and recursive results. Interleaved result streams keep their own bindings even when two WITH blocks reuse the same CTE names.

Correlated scalar `SUM` / `AVG` / `MIN` / `MAX` / `COUNT` equality can decorrelate through an aggregate CTE, including fully qualified inner paths, when the live outer and aggregate fields share a join equality domain, whichever relation kind the inner query reads: the aggregate field's domain is its declaration in that collection, view, CTE, derived table or system collection. `SUM` / `AVG` require numeric fields; widened results retain ordinary lossless numeric equality. `COUNT` uses a null-preserving grouped form: a missing group becomes zero, while a real `COUNT(field) = 0` and a null correlation key retain their ordinary semantics. These membership conditions also apply before selected window functions: ranking and other window values use the rows that passed the correlated predicate, including zero-count matches, without exposing the internal grouped columns. Cross-domain coercions stay per-row rather than becoming an incompatible join. The aggregate operand's equality domain is proven from what the nested query selects over its inner relation, a stored collection's declaration or a CTE, view, derived or system relation's bound output; `COUNT(*)` has no operand and needs no such proof. Adding aggregate `FILTER` also keeps the per-row path; the filter is part of the answer and is never removed as an optimization.

<a id="pitfall-bare-field-names-after-a-join-error-when-ambiguous"></a>

### Bare field names after a JOIN error when ambiguous

A bare (unqualified) field reference in post-join `WHERE` / `ORDER BY` / `SELECT` binds to the single joined collection that carries the name — an inner-only bare name binds the inner side, including in WHERE. When two or more joined collections carry the name, the statement errors with `AMBIGUOUS_FIELD` (PostgreSQL 42702 `ambiguous_column` parity) instead of silently picking a side. Qualify with the alias (`[a].[Label]`). Always qualifying post-join references is the safe habit — self-joins make EVERY field name collide.

Qualification is plan-stable: `[a].[Label]` remains bound to `a` even when `ANALYZE` causes the optimizer to switch from a left-deep join to a bushy plan. A qualified predicate must never acquire `AMBIGUOUS_FIELD` merely because another relation has `Label`.

The raw nested JOIN envelope is physical, however. An unprojected result or a plain nested projection can have a different `{outer, inner}` tree after a plan change. Use flat `AS` aliases when consumers require a plan-independent schema. A raw `[outer]`/`[inner]` path is not physical: in any clause it names the relation written at that position, and a result that reads one outside `WHERE` keeps written order.

JOIN ON treats a leading segment as a qualifier only when it matches the FROM alias, a prior JOIN alias, the current JOIN alias, or an unaliased CTE relation at any of those positions. Any other prefix remains part of an unqualified nested path: `[bogus].[AId]` never degrades to root `AId`, and errors during schema validation if `bogus.AId` does not exist. If both operands have recognised qualifiers, one must name an outer relation and one the current inner relation; two prior aliases or two references to the current inner qualifier are parse errors. The inner qualifier may be written on either side of `=`; one unqualified operand is oriented opposite the recognised qualifier. Programmatic AST callers do not bypass this scope: `JoinClause.OuterAlias` must name the FROM relation or a prior JOIN, otherwise query-shape validation rejects it before execution. Their public relation qualifiers must also remain unique; a duplicate cannot overwrite an earlier alias-map binding.

On a bushy plan, predicates that bind to exactly one alias are also evaluated at that relation's leaf to reduce intermediate cardinality; the full WHERE is rechecked after the join. Mixed-relation OR groups are not split. Internal bushy hash builds spill above `MaxInMemoryStreamingState` and participate in the engine-wide admission domain because each build side can span several relations.

<a id="pitfall-fieldfield-where-is-a-join-edge-not-a-filter"></a>

### Field=field WHERE is a join edge, not a filter

`WHERE [a].[k] = [c].[k]` between two distinct join aliases is an extra equi-join condition used to express cyclic join graphs. Ordinary scalar comparisons, including `[A] = [B]` without a JOIN, `[A] > [B]`, a comparison with an array element path, and a field equality in HAVING or an aggregate FILTER, use row predicate evaluation. The optimizer's extra join-edge form still requires an equality condition in the query's top-level AND conjunction.

<a id="pitfall-float-nan-uses-a-total-order-greatest-equal-to-itself"></a>

### Float `NaN` uses a total order: greatest, equal to itself

`NaN` (insertable into `FLOAT32`/`FLOAT64` fields via parameters or the typed client — never as an MQL literal) compares under a total order with `NaN` greatest, PostgreSQL/DuckDB parity: `WHERE [F] = @nan` matches NaN rows, `WHERE [F] > @x` for finite `@x` INCLUDES NaN rows, finite-bound `<`/`<=` excludes them, and `ORDER BY [F]` puts NaN last ascending / first descending. Aggregates and joins follow the same order: `MAX([F])` returns NaN when any input row is NaN, `MIN([F])` returns the smallest non-NaN value, `GROUP BY [F]` folds all NaN rows into ONE group, `COUNT(DISTINCT [F])` counts all NaN rows as one value, and `JOIN … ON [a].[F] = [b].[F]` matches NaN rows to each other (all of these also treat `-0.0` as `+0.0`). Identical on every plan and join strategy, and in every expression context — `CASE WHEN [F] > @x …` / computed projections flag the same rows the `WHERE` path admits, window `ORDER BY` places NaN where the query-level `ORDER BY` does, window `PARTITION BY` treats all NaN rows as peers, and `MIN`/`MAX` `OVER (…)` return the same extremum as their aggregate forms. `WHERE [F] IN (subquery)` follows too: a NaN yielded by the inner query matches stored NaN rows exactly like `IN (@nan)` does. Don't expect SQL-standard `NaN ≠ NaN` semantics anywhere.

Float-returning expressions do not turn IEEE specials into NULL. `/`, `%`, `ABS`, `ROUND`, `FLOOR`, `CEILING` / `CEIL`, `POWER`, `SQRT`, and `MOD` preserve `NaN` / `±Infinity`, including through computed columns. Exact zero divisors raise. SIGN(NaN) and unrepresentable integer/DECIMAL conversions raise; TRY explicitly recovers them as NULL. SIGN of the two infinities is `1` / `-1`.

<a id="pitfall-integer-valued-function-arguments-never-truncate-implicitly"></a>

### Integer-valued function arguments never truncate implicitly

`SUBSTRING` start/length, `LEFT` / `RIGHT` length, `ROUND` digits, `DATEADD` count, `LAG` / `LEAD` offset, and `NTILE` bucket count require an exact finite numeric integer. Decimal / Float `2.0` accepts; `2.9`, `TRUE`, and `'2'` reject. Use `CAST(... AS INT64)` / `TO_INT(...)` when truncation or text conversion is deliberate. Window arguments retain their additional constant-literal, Int32-range, and sign constraints. `DATEADD('WEEK', n, ts)` checks the `n × 7` day expansion; an Int64 overflow raises an error; TRY returns NULL. `NTILE(n)` permits `n` larger than the partition: each row uses one of the first buckets. Buffered and streaming plans agree at Int32.MaxValue; there is no zero-sized-bucket division.

`DATEDIFF` counts crossed calendar/time boundaries; it does not truncate the elapsed duration. A sub-second interval that crosses midnight differs by one DAY, HOUR, MINUTE, and SECOND. Boundaries are offset-local, ISO weeks begin on Monday, and reversing the operands reverses the sign.

<a id="pitfall-integer-range-comparisons-must-use-an-in-range-literal"></a>

### Integer range comparisons must use an in-range literal

A range comparison (`>` `>=` `<` `<=`) requires the literal to fit the field's signed range (`INT8`: −128…127, `INT16`: −32768…32767, `INT32`: ±2,147,483,647, `INT64`: ±9,223,372,036,854,775,807). All integer types store signed, so an out-of-range literal — `[Status] > 200` on an `INT8`, `[Count] < 5000000000` on an `INT32` — has no defined ordering and is REJECTED with `RANGE_LITERAL_OUT_OF_SIGNED_RANGE`, not silently returning zero rows, in a `WHERE` leaf and in an expression (`CASE`, a projected comparison) alike. Equality against an out-of-range literal is still allowed and exact: `=` matches no row and `!=` matches every row, NULL values included (equality is NULL-safe), in every position (except the native `INT8`/`INT16` bit-pattern case: `200` matches stored `INT8` `-56`, including an enum member declared as `-56`). Primary-key, secondary-index, and heap predicates agree. The rejection is decided before any row is read, over collections, views, CTEs (including polymorphic ones), derived tables, system collections, and a CTE or view read by a correlated `EXISTS`, `NOT EXISTS`, or `IN` subquery alike, so it never depends on the data, on which subtypes are present, or on whether `AND`/`OR` short-circuiting lets a row reach the comparison. Bound parameters, including strings, must still fit the signed range. The rule concerns integral literals; a fractional literal such as `[Count] > 0.5` keeps its exact value and is valid.

<a id="pitfall-offset-less-datetime-literals-are-utc-not-server-local"></a>

### Offset-less DateTime literals are UTC, not server-local

A DateTime/DateTimeOffset literal with no offset — `'2024-06-15T10:30:00'` — is interpreted as UTC (a literal with `Z` or `+hh:mm` keeps its offset). Comparison is by instant (UTC ticks), so the same predicate selects the same rows on every host regardless of server time zone. The same rule covers temporal clauses and string parameters, DateTimeOffset document values, cached scalar rebinding, expression comparisons, `CAST(... AS DATETIME)`, and `TO_TIMESTAMP`. `DATETIME` is not a legal primary-key type.

<a id="pitfall-floating-point-sumavg-order-is-unspecified"></a>

### Floating-point `SUM`/`AVG` order is unspecified

`SUM`/`AVG` over a `FLOAT32`/`FLOAT64` field use a SIMD batch reduction, so values may be summed in any order and the low-order bits of the result can differ from a strict row-order sum (floating-point addition is not associative — same contract as every parallel SQL engine). The result is Kahan-Babuška-Neumaier-compensated and saturates to `±Infinity` on overflow (never errors, never returns NaN-from-overflow). A non-finite SIMD lane or horizontal-fold result retries the aggregate in row order, so vector- order overflow cannot turn a finite row-order result into `±Infinity` or NaN. `SUM`/`AVG` over **integer** fields are exact and order-independent. Don't assert a byte-exact floating-point total across runs; round to a fixed precision or aggregate a fixed-scale `DECIMAL`/integer column instead.

<a id="pitfall-cascade-is-rejected-for-pinned-references"></a>

### `Cascade` is rejected for `PINNED REFERENCES`

A pinned FK value explicitly binds a target revision; cascading the referencing document when that revision is reclaimed defeats the pin's intent. Use `Restrict` or `SetNull`.

<a id="pitfall-insert--update--replace-on-a-computed-field-is-rejected"></a>

### INSERT / UPDATE / REPLACE on a computed field is rejected

The user must never supply a value for a computed column. `SchemaSerializer.ValidateSetFields` throws `"Cannot assign to computed field 'X'"` from every DML write path (INSERT, UPDATE, REPLACE, UPSERT). The value is derived from the AS expression at its declared write or read boundary. The raw binary engine boundary repeats this recursively: every physical virtual computed slot must be NULL. Stored computed slots are derived by the engine on every write, including raw binary ingress. For a virtual computed slot, a non-NULL incoming value is `DOCUMENT_PAYLOAD_INVALID`; a non-NULL persisted value is `DOCUMENT_PAYLOAD_CORRUPT`, never a value retained when the expression itself evaluates to NULL.

Computed-expression plans are bound to the exact schema generation. A `DROP COLLECTION` followed by `CREATE COLLECTION` under the same name uses the new `AS` expressions immediately, even if the recreated schema has the same version; callers do not need a new session or process. Plan construction revalidates semantic bindings, including schemas published programmatically after executor startup, and fails instead of resolving an unknown dependency to NULL. Recursive plans carry both enum resolver directions, so `ENUM_LABEL([F])` and `ENUM_VALUE(label, enumName)` work consistently in nested, array, subtype, RETURNING, and event scopes.

<a id="pitfall-lengthpredicate-count-filter--lengthfield-scalar"></a>

### `LENGTH(predicate)` count filter ≠ `LENGTH(field)` scalar

`LENGTH` carries two distinct shapes depending on its argument:

- `LENGTH([ArrayField])` — element count of the whole array. Lives in scalar WHERE / SELECT / CHECK / computed-column / HAVING expressions.
- `LENGTH([ArrayField][] OP value)` — count of matching elements. A filter form: in WHERE and, compared with a count, in expression position (CASE, computed projections), with the same [element-predicate semantics](arrays.md#element-predicates-in-expressions).

The first is a value-producing function; the second is a filter form (must be compared with a count, e.g. `LENGTH([Tags][] = 'urgent') > 2`). `LENGTH(<predicate>)` standalone (no comparison) is rejected — a parser error in WHERE and an evaluation error in expression position — so use `LENGTH(<predicate>) > 0` for "at least one match". Use the scalar `LENGTH([ArrayField])` form for an unconditional element count.

The count threshold can be a literal, read as against an `INT64` field (`> 1.5`, `> '1.0'` and `> TRUE` compare with 1.5, 1 and 1; `NOW` is refused), a caller's parameter naming an integer, or a one-column scalar subquery, correlated or not. A subquery returns NULL at zero rows and errors at row two. MATCH bodies preserve IN/NOT IN subquery sources and LIKE ESCAPE; do not rewrite those forms to a literal-only predicate when generating MQL.

A nested `MATCH` body can contain another MATCH or predicate LENGTH joined with AND. `LENGTH([Children][] MATCH ([Score] > 0 AND [Kind] = 'good'))` counts children satisfying both conditions. Each child MATCH keeps its own same-element scope; independent inner-array comparisons can match different children. Parameter and subquery values retain those scopes through rewrites.

<a id="pitfall-drop-field-is-rejected-while-a-partial-indexs-filter-references-the-field"></a>

### DROP FIELD is rejected while a partial index's filter references the field

`ALTER COLLECTION … DROP FIELD [F]` errors when any partial index's `WHERE` filter references `[F]` — even when the index is *keyed* on a different field (keyed indexes are dropped automatically; the filter reference is what blocks). Drop that index first, or recreate it with a different filter. `RENAME FIELD` needs no such care: partial filters follow the rename automatically, like key paths do. On reopen, every persisted `Ready` index definition is revalidated against the schema. An unparseable filter or unsupported key/INCLUDE extraction (out-of-band catalog damage or older incompatible metadata) is quarantined — queries stay correct via scans, and `CREATE INDEX` over the same fields replaces the quarantined row.

Array indexes with an incompatible key format (`arrayidx_` or untyped `array1_`) instead refuse database open with `ARRAY_INDEX_FORMAT_UNSUPPORTED`, preserving their constraints. The database must be recreated in the current format; these indexes are not silently quarantined or upgraded.

<a id="pitfall-expected-revision-mismatch-throws"></a>

### `EXPECTED REVISION` mismatch fails the statement

Optimistic concurrency. If the matched row's revision differs, or its current version is gone by the time the write claims it, the statement fails with `User / REVISION_MISMATCH`; a `WHERE` that matches no row (the row was deleted before the statement read it) writes nothing and reports 0 affected rows instead ([EXPECTED REVISION](dml.md#expected-revision)). The statement carries the stale revision, so rerunning it unchanged fails again: re-read the row (or pair the write with `RETURNING [Meta].[Revision]`) and decide whether to reapply the change with the new revision.

<a id="pitfall-length-counts-native-elements-octet_length-counts-bytes"></a>

### `LENGTH` counts native elements; `OCTET_LENGTH` counts bytes

`LENGTH([StringField])` returns UTF-16 code-unit length, including trailing spaces, matching .NET `string.Length`. `LENGTH([ArrayField])` returns element count; `LENGTH([BytesField])` returns the raw byte count. `OCTET_LENGTH` accepts STRING (strict UTF-8 encoded byte count) and BYTES (raw byte count), without allocating an encoded buffer. Both functions return INT64 and propagate NULL. `LENGTH(TO_STRING([BytesField]))` counts Base64 characters, not source bytes. Use `WITH CHECK (LENGTH([Tags]) > 0)` to bound array cardinality or `WITH CHECK (OCTET_LENGTH([Data]) <= 1024)` to bound a binary payload.

<a id="pitfall-mixed-wildcards-require-unique-final-output-names"></a>

### Mixed wildcards require unique final output names

Wildcards and explicit projections may be mixed in authored order, including multiple qualified wildcards. `SELECT *, [Y]` is valid syntax but duplicates Y when it is already in the source. Use `SELECT * EXCLUDE ([Y]), [Y]` or rename the extra slot. A wildcard over a direct stored source also publishes `Meta`, which no modifier excludes, so `SELECT *, [Meta]` is a duplicate in either order: `SELECT *` alone already carries it, and `AS` renames any other item named `Meta`. Each wildcard's modifiers apply independently; uniqueness is checked across the full expanded result. Aggregates still require every expanded plain field to be grouped: a wildcard among items beside `GROUP BY` or an aggregate, and a lone one with modifiers beside `GROUP BY`, expands the declared data fields only, without `Meta`, also beside a grouping expression or an aggregate argument, so `FROM [App].[Lines] GROUP BY [OrderId] SELECT COUNT(*) AS [Count], * EXCLUDE ([Id], [Sku])` publishes `Count` and `OrderId`, and `FROM [App].[Lines] GROUP BY [OrderId] SELECT * EXCLUDE ([Id], [Sku])` publishes `OrderId`. DISTINCT operates on expanded values.

Only bracketed qualifiers are valid: write `SELECT [u].*`, not `SELECT u.*`. A single-source wildcard can also use the bare collection/view or CTE name: `FROM [App].[Items] SELECT [Items].*` needs no explicit alias. Unknown relation names reject even on empty input; qualifiers never expand a nested field. On a join, each qualified wildcard flattens its logical relation in schema order and keeps nulls when that relation has no matching row.

<a id="pitfall-rename-is-simultaneous-and-result-only"></a>

### `RENAME` is simultaneous and result-only

`SELECT * RENAME ([A] AS [B], [B] AS [A])` is a valid swap. Case-only renames and reuse of a name freed by `EXCLUDE` or another rename are also valid. Duplicate sources, duplicate final names, collisions with retained fields, and renaming an excluded field are rejected case-insensitively. `REPLACE` and `RENAME` may target the same source field; the replacement expression sees the original full row, and the renamed name is visible only in the output. Continue to use the source name in `WHERE`, `GROUP BY`, and `ORDER BY`.

<a id="pitfall-select-output-names-must-be-unique"></a>

### SELECT output names must be unique

Do not repeat a projected field or reuse a plain field's leaf name as an aggregate/computed alias. Output schema names are case-insensitive, and the same collision gate runs for stored collections, CTEs, joins, and system collections before binary rows are constructed. For a plain nested SELECT that retains its parent Object or Array, computed aliases must also be distinct from that emitted parent's name. Multiple plain children may still coalesce to their shared parent.

<a id="pitfall-explain-does-not-execute-a-write-predicate-to-predict-its-result"></a>

### EXPLAIN does not execute a write predicate to predict its result

UPDATE, REPLACE, DELETE, SEAL, UNSEAL, and CANCEL VERSION accept EXPLAIN with scalar, negated, and subquery predicates, predicates that read a virtual computed column, and plain views. Static binding validates the read graph without invoking its functions. `DeferredPredicate` means the write access path depends on resolved values or candidate keys: `Index` and `EstimatedRows` are null, `EarlyExit` is false, and `FilterCount` is zero because native write filters have not been produced. It does not mean zero matching rows. ANALYZE performs the real mutation and reports its affected count; it retains the static root strategy and adds runtime measurements.

<a id="pitfall-explain-checks-join-predicates-even-when-inputs-are-empty"></a>

### EXPLAIN checks join predicates even when inputs are empty

A valid SELECT list cannot make an invalid ON clause valid. Static EXPLAIN rejects missing JOIN keys and incompatible scalar key types using runtime's equality rules; mixed numeric keys remain supported. APPLY ON conditions also validate fields, bound parameters, function names/arity, and nested subqueries without invoking them. These checks run during scalar/lateral schema discovery too, independent of whether the outer input produces rows.

<a id="pitfall-when-a-update-silently-affects-more-than-expected"></a>

### When a UPDATE silently affects more than expected

1. Run the same `WHERE` as a SELECT first.
2. Check for `CONFIRM UPDATE ALL` — easy to type by reflex.
3. Check that fields you didn't intend to clear are in your `SET` list (REPLACE is full-replace; UPDATE is partial).

<a id="pitfall-alter-rename--drop-field-is-rejected-when-the-collections-own-check-or-computed-column-references-the-field"></a>

### ALTER RENAME / DROP FIELD is rejected when the collection's own CHECK or computed column references the field

Symmetric with the trigger / view / IVM guards, but for the collection's *own* constraints. The schema rewrite re-targets index + FK metadata only — it does **not** rewrite CHECK / computed **expression text**. A silent rename would leave the CHECK predicate resolving the now-missing field to `NULL`, which under ANSI 3VL "passes", disabling the constraint for every future row (a computed column would likewise resolve its dependency to `NULL`). Drop the dependent CHECK constraint ([`DROP CHECK`](ddl.md#add-and-drop-check-constraints)) or computed column first, then rename / drop the field. Renaming or dropping the computed column *itself* is allowed when no other expression depends on it.

Computed dependencies bind to their containing object scope. `Details.Total AS ([Rate] * 2)` protects `Details.Rate`, including within ARRAY OBJECT elements; it does not refer to a root `Rate` field. The dependency walk includes nested subtype extensions. Dropping a whole container removes its owned expressions, and renaming that container preserves their local sibling bindings. Expressions outside the container still protect every field they reference.

If an embedded host or inconsistent restore leaves a persisted CHECK or computed expression that cannot be parsed, RENAME / DROP FIELD fails closed with `CHECK_EXPRESSION_INVALID` or `COMPUTED_EXPRESSION_INVALID`. The engine does not waive dependency protection merely because the metadata needed to prove safety is unreadable.

MQL executor initialization independently parses every persisted CHECK and computed expression in every collection. Invalid catalog metadata therefore fails before a statement executes or a change event can substitute `NULL` for an unreadable computed expression. Those parser boundaries convert only ordinary syntax/semantic failures into validation or persisted-metadata errors. Direct or wrapped structural detectors keep their original code, and direct or wrapped process-memory exhaustion reaches the executor's terminal failure policy instead of masquerading as bad CHECK/default/computed metadata.

Typed structural corruption also survives plugin and cleanup wrappers. If an interceptor, DDL observer, core handler, or lazy stream wraps a corruption in an `AggregateException`/inner exception, the engine still quarantines the detector's domain and returns or throws its stable code rather than `UNCLASSIFIED`. Streaming index reads retain their original read, cancellation, or corruption cause when pointer-source or row-buffer cleanup also fails. Independent owners are still released, and successful release is not repeated during disposal retry. A derived-query failure preserves its original cause after its input has been consumed. If cleanup also fails, that actual failure remains reported with the query failure. Local validation, best-effort cleanup, and statement-specific error conversion walk the complete exception graph before handling a failure, so neither nested corruption nor nested process-memory exhaustion can become a routine local validation result or warning-only cleanup result. Nested cancellation and simulated-crash signals likewise escape generic local conversion; all four classes reach the executor's terminal failure policy. Execution interceptors return `HOOK_EXECUTIONINTERCEPTOR_FAILED` only for ordinary plugin failures. Wrapped memory exhaustion and simulated-crash signals escape with their outer exception identity intact. An ordinary failure in the interceptor fault-attribution sink remains subordinate to that plugin error, but memory exhaustion or simulated process death from the sink escapes after any health transition already published. When an interceptor instead exposes structural corruption, ordinary failures in the corruption health reporter or logger cannot replace the detector's stable result. Memory exhaustion or simulated process death from either diagnostic surface escapes after any quarantine transition already published. The core statement funnel follows the same process-terminal rule after it has completed required statement poisoning and migration auto-rollback. If that rollback also fails, both failures escape in one aggregate instead of either being converted into an error result. Post-publication DDL observers still return `HOOK_DDLOBSERVER_FAILED` for ordinary replication or audit propagation failures, while wrapped memory exhaustion and simulated-crash signals escape after the local catalog change has committed and the observer fault has been attributed. Query-descriptor and result-schema shaping, plus DDL field, index, and rename adapters, follow the same rule: their `InvalidOperationException` compatibility catches convert only recoverable local failures. Cancellation is not an exception to this policy: a cancellation wrapper is rendered as `Statement cancelled` only when its complete inner exception graph contains no corruption proof, process-memory exhaustion, or simulated-crash signal. Statement-result validation after core dispatch remains inside the same health boundary, so a nested corruption proof quarantines its domain before the validation exception escapes to the caller. Background and teardown work has the same supervision contract. Auto-analyze, index checkpoint, incremental defrag, cold-page scrub, read-epoch tasks, deferred-WAL durability timers, temporal cascade/retry dispatch, change-tracker dependency scans, plugin service/shutdown callbacks, parallel-query owner joins, and statement/migration cancellation callbacks report every direct or wrapped structural detector to `[Mnemic].[Health]` immediately; ordinary work may be retried, but corruption cannot remain only a warning log while writes stay admitted. Exception wrapping depth is not a correctness boundary, and an aggregate with proofs for several domains quarantines every one rather than only its first branch. Early result-stream abandonment still joins every producer, worker, and merge pump before spill/admission state is released; corruption found during that teardown is not suppressed by the consumer stopping early. A throwing cancellation callback cannot veto required terminal cleanup or hide its nested detectors.

An async plugin-hook timeout does not cancel the callback. If its detached task later faults, health records `HOOK_<NAME>_LATE_FAILED`; any nested corruption proof still quarantines its exact domain. Do not treat the initial timeout row as evidence that the callback stopped running.

Computed enrichment also fails closed after startup. Each computed-bearing document, nested Object, array element, and polymorphic envelope is structurally validated before evaluation. A malformed layout, missing plan binding, or runtime evaluator fault aborts the read/RETURNING/event presentation; it never becomes a plausible NULL. This does not change normal expression NULL propagation or the documented NULL result when a valid numeric value cannot fit its declared output width.

<a id="pitfall-budget-requires-incremental-scoped-full-defragment-is-rejected"></a>

### `BUDGET` requires `INCREMENTAL`; scoped full `DEFRAGMENT` is rejected

```sql
DEFRAGMENT BUDGET 5;                 -- parse error: BUDGET needs INCREMENTAL
DEFRAGMENT [App].[Items];            -- execution error: plain DEFRAGMENT is all-collections
DEFRAGMENT INCREMENTAL [App].[Items]; -- correct: scoped reclamation
```

Plain `DEFRAGMENT` always drains every collection; only the `INCREMENTAL` form accepts a `[Namespace].[Collection]` scope and a `BUDGET n` cap.

<a id="pitfall-scalar-text-matching-preserves-null-and-literal-characters"></a>

### Scalar text matching preserves NULL and literal characters

In CASE WHEN and projections, `CONTAINS` and `STARTSWITH` take string expressions and propagate NULL. `NOT (NULL CONTAINS 'x')` is still NULL. Use LIKE for wildcard patterns; `%` and `_` have no wildcard meaning in these operators. A CASE WHEN takes its ELSE branch for an unknown condition.
