# Database management (TCP server)

> **In this section** — `CREATE` / `DROP` / `REOPEN` / `LIST DATABASE` for the TCP server's multi-database surface, and `LIST PLUGINS` for the plugins the server loads.

```sql
CREATE DATABASE [MyShop];
DROP DATABASE [MyShop];
REOPEN DATABASE [MyShop];
LIST DATABASE;
LIST PLUGINS;
```

Database names require brackets in MQL identifier positions. On the TCP server, the client connects to a specific database via the `Connect` opcode. A `Connect` naming a database that does not exist creates it only for `sa` (`ServerAdmin` is never granted through a role); any other user receives `User / INSUFFICIENT_PRIVILEGE` and nothing is created ([connecting](connecting.md)). `LIST DATABASE` returns the databases on which the authenticated caller has `Read` permission. A server-wide Reader and `sa` see every database; a database-scoped Reader sees only the databases covered by that caller's grants.

`CREATE DATABASE`, `DROP DATABASE`, `REOPEN DATABASE`, and `LIST DATABASE` are **server-level** statements — they operate on the server, not on any one database. They work on a connection bound to a database **and** on a database-less (server-level) connection opened with an empty database segment (`tcp://user:pass@host:port/`, no name — see [Connecting](connecting.md#the-database-segment-is-optional--server-level-connections)). A server-level connection is the natural place to `LIST DATABASE` before choosing one; database-scoped statements (`FROM … SELECT`, `INSERT`, DDL) on such a connection return **"No database selected."** until you `Connect` with a name.

Database names compare case-insensitively. `CREATE DATABASE` of a name the server already holds fails with `User / DUPLICATE_NAME` (`Database 'MyShop' already exists.`), and `DROP DATABASE` of a name it does not hold fails with `User / UNKNOWN_OBJECT` (`Database 'MyShop' does not exist.`). Neither statement has an `IF EXISTS` / `IF NOT EXISTS` form; `LIST DATABASE` first when a script must tolerate either state.

A database name must also work as a file name on every platform. MQL text cannot spell a blank name (`CREATE DATABASE []` and `CREATE DATABASE [ ]` are a `SYNTAX_ERROR`); a blank name a programmatically built statement carries, a path separator or `..`, `:` or a NUL character, one of `< > * ? " |`, a control character, or a trailing dot or space fails with `User / INVALID_VALUE` (`Invalid database name: 'a/b'. Names must not contain path separators.`); `_master`, which the server's internal catalog uses, and a Windows device name such as `CON`, `NUL` or `COM1`, alone or before an extension (`CON.db`), fail with `User / RESERVED_NAME`. The same rules apply to `CREATE DATABASE`, `DROP DATABASE`, and a `Connect` that would create the database.

`DROP DATABASE` is refused with `User / OBJECT_IN_USE` while you are connected to that database — disconnect first. While a drop is in flight (the server is still closing the engine and deleting the files), any concurrent connect, `CREATE DATABASE`, or `DROP DATABASE` for the same name fails with the retryable `Transient / DATABASE_DROP_IN_PROGRESS` (`Database 'MyShop' is being dropped. Retry once the drop has completed.`); retry once the drop completes, after which the name is free for reuse.

`DROP DATABASE` terminates every other session connected to the database instead of refusing the drop, like PostgreSQL's `DROP DATABASE … WITH (FORCE)`. A statement such a session is running is cancelled with `Cancellation / CANCELLED` (`Statement cancelled: database dropped.`), requests it has queued never run, and the server then sends its final termination notice and closes the connection: every request of that session the client has not seen complete, and every later one, fails with `Cancellation / SESSION_TERMINATED` (`The session was terminated: database 'MyShop' was dropped.`). The drop returns once every such session has released the database. A terminated session never continues against a database later re-created under the same name; open a new connection, which binds whatever database then holds the name, and a pooled client never leases a terminated connection again ([connection pooling](connecting.md#connection-pooling)). The server terminates sessions the same way when it closes a database, as [`REOPEN DATABASE`](#reopening-a-database) does (`Statement cancelled: database closed.`, `… was closed.`), after which the next open serves the name again, and when it shuts down (`… the server is shutting down.`). A statement that cannot settle — one blocked sending results to a client that stopped reading — has its connection closed after a short grace, so a client cannot hold a drop open.

`DROP DATABASE` revokes every grant on the database in the same step as it removes the database from the server's registry, so a crash keeps both or neither; a database created again under the same name is a new database and starts with no grants ([auth administration](auth-admin.md#grant)). A server plugin that keeps state bound to the database retires it in the same step; when a plugin fails there, the drop fails with that plugin's error and leaves the database, its grants and every plugin's state as they were, so the drop can be retried at once.

Successful `DROP DATABASE` removes the database file, WAL control and checkpoint files, WAL segment directory, pending-restore artifacts, and a pending orphan-page reclamation request. A server whose host keeps databases in process memory releases the dropped database's pages and WAL the same way, so a database later created under the name starts empty, while closing a database or stopping the server keeps them for the next open in the same process. A deletion failure retains a durable drop intent and blocks reuse in the current server; restart finishes the committed removal before reopening databases. Cleanup of a symlinked WAL segment directory removes the alias and preserves its target.

## Reopening a database

```sql
REOPEN DATABASE [MyShop];
```

`REOPEN DATABASE` closes a database and opens it again before it returns. That open is the one a server restart would run: it promotes a restore that `RESTORE … VERIFY` staged for the database's next open ([maintenance](maintenance.md#restore--verify)), runs recovery and the reconstruction a recovery-required fault waits for ([health](health.md#clearing-quarantine--alter-engine-resume)), and runs a requested `RECLAIM ORPHAN PAGES`. A database that is not open is opened. It requires `ServerAdmin`, which only `sa` holds, and like `DROP DATABASE` it runs on a server-level connection or on one bound to another database; it is admitted while the database is quarantined, since it runs on the server rather than in the database's engine.

Every session connected to the database is terminated as `DROP DATABASE` terminates them, with the close as the reason: a statement it is running reports `Cancellation / CANCELLED` (`Statement cancelled: database closed.`), and each of its unsettled and later requests fails with `Cancellation / SESSION_TERMINATED` (`The session was terminated: database 'MyShop' was closed.`). Clients connect again, and a pooled client opens a new connection, which binds the reopened database. A server plugin's own connections, such as Studio's, are ordinary sessions and are terminated the same way. A connect, `DROP DATABASE`, or another `REOPEN DATABASE` of the same database that arrives while the reopen runs waits for it: a connection made meanwhile binds the reopened database and is not terminated, a drop removes the reopened database, and a second reopen closes and opens it once more.

It returns exactly one row:

| Column | Type | Meaning |
|---|---|---|
| `TerminatedSessions` | `INT64` | The sessions connected to the database that the reopen terminated. |
| `RestorePromoted` | `BOOL` | Whether the open promoted a restore staged for it. |

A refused reopen changes nothing: the connection's own database is refused with `User / OBJECT_IN_USE` (`Cannot reopen database 'MyShop' while connected to it. Reopen it from a server-level connection or one bound to another database.`), a name the server does not hold with `User / UNKNOWN_OBJECT` (`Database 'MyShop' does not exist.`), which creates nothing, `_master` and any other name no database could hold as `CREATE DATABASE` refuses it (`RESERVED_NAME`, `INVALID_VALUE`), a database being dropped with `Transient / DATABASE_DROP_IN_PROGRESS`, and every user other than `sa` with `User / INSUFFICIENT_PRIVILEGE`. When the open fails, the database stays closed and the statement reports the open's failure as a `Connect` would: structurally corrupt files report the detector's classified pair, such as `StructuralCorruption / PAGE_CHECKSUM`, recorded against that database alone ([connecting](connecting.md#a-database-that-cannot-be-opened)), and the next `Connect` or `REOPEN DATABASE` opens the files again. A single in-process engine has no server to reopen it and refuses the statement with `FEATURE_NOT_SUPPORTED`; dispose the engine and open it again instead.

## Server plugins

`LIST PLUGINS` lists the plugins the server loads, each once and ordered by name, so a client can tell what the server offers before it chooses a database:

| Column | Type | Meaning |
|---|---|---|
| `Id` | `GUID` | The plugin's identity, which `SUBSCRIBE TO PLUGIN` names it by. |
| `Name` | `STRING` | The name people read. |
| `Version` | `STRING` | The plugin's release, such as `1.0.0`. |
| `ContractVersion` | `STRING` | The version of what the plugin offers clients, as `major.minor`: the major part changes when a client written for the previous contract could break, the minor part when the plugin only adds to it. |
| `Server` | `BOOL` | Whether the plugin runs with the server process. |
| `Database` | `BOOL` | Whether the plugin loads into the databases the server opens. |

The list always holds the auth plugin, which every server loads. A client compares a plugin's contract version with the one it was written for: the same major works, a higher minor on the server adds what the client does not use, and another major means one side needs an upgrade. Like `LIST DATABASE`, it is a server-level statement and requires `Read` at the connection's scope; a single in-process engine, which has no server, refuses it with `FEATURE_NOT_SUPPORTED`.

## Detailed syntax and execution


<a id="syntax-database-management"></a>

### Database management

```sql
CREATE DATABASE [name];
DROP   DATABASE [name];
REOPEN DATABASE [name];
LIST DATABASE;
```

`CREATE DATABASE` of a taken name (compared case-insensitively) reports `DUPLICATE_NAME`, `DROP DATABASE` of a missing name `UNKNOWN_OBJECT`, and `DROP DATABASE` while connected to that database `OBJECT_IN_USE` (disconnect first); all three are `User`-class, as are a malformed name (`INVALID_VALUE`) and a reserved one (`RESERVED_NAME`). While a drop is in flight, a concurrent connect, `CREATE DATABASE`, or `DROP DATABASE` for the same name fails with `Transient / DATABASE_DROP_IN_PROGRESS` — retry after the drop completes. The drop revokes every grant on the database, and a database created again under the name starts with none. Every other session connected to the dropped database is terminated: its running statement reports `Cancellation / CANCELLED` (`Statement cancelled: database dropped.`), and the server's final `SessionTerminated` frame (`0x75`) fails each of its unsettled and later requests with `Cancellation / SESSION_TERMINATED` before the connection closes.

`REOPEN DATABASE` requires `ServerAdmin`, refuses the connection's own database with `OBJECT_IN_USE`, a missing name with `UNKNOWN_OBJECT`, and a drop in flight with `Transient / DATABASE_DROP_IN_PROGRESS`. It terminates every session connected to the database as a drop does, with `Statement cancelled: database closed.` and `The session was terminated: database '…' was closed.`, opens the database again, promoting a staged restore, and returns one row of `TerminatedSessions INT64` and `RestorePromoted BOOL`. An open that fails leaves the database closed and reports the open's failure.

`CREATE` / `DROP` / `REOPEN` / `LIST DATABASE` are **server-level** statements: they operate on the server, not on a bound database, and run on a database-less (server-level) connection too. Connecting with an empty database segment (`tcp://user:pass@host:port/`, no name) authenticates the user but binds no engine — the SSMS-style "browse the server" handshake. On that connection `LIST DATABASE` / `CREATE DATABASE` / `DROP DATABASE` / `REOPEN DATABASE` and the auth-admin statements work, while any **database-scoped** statement (`FROM … SELECT`, `INSERT`, DDL) returns **"No database selected."** until you `Connect` with a name. The server-level handshake replies with schema level `0`. Every successful `Ok` frame carries a non-negative schema level; negative values are protocol faults rather than sentinels. Every Connect carries exact protocol version `1`; any other value returns the typed `PROTOCOL_VERSION_UNSUPPORTED` error before authentication. Connect-Ok returns that exact version plus the server semantic version, which the .NET remote client exposes through `RemoteClient.Diagnostics`. A client retires the transport if the response is not exactly `1`. The current-v1 Connect and Connect-Ok byte shapes are the sole accepted contract; incomplete or trailing pre-handshake payloads are rejected.

`LIST DATABASE` returns only databases on which the authenticated caller has `Read` permission. A server-wide Reader and `sa` see every database; a database-scoped Reader sees only databases covered by that caller's grants. Pre-authentication frames are capped at 16 KiB; after a successful `Connect`, the ordinary 16 MiB MQL frame allowance applies. Database name, username, and password therefore must fit together within the handshake cap. Client and server validate the signed 32-bit frame length as soon as all four prefix bytes arrive. A non-positive or oversized prefix faults the connection without waiting for an opcode or body, so withholding the next byte cannot retain a connection with an already-invalid frame. Authentication must succeed within the server's absolute deadline (30 seconds by default); pre-authentication `Ping` frames do not extend it. Failed Connect attempts are admitted ahead of PBKDF2 through bounded token buckets for the source address (default burst 32) and source-address + case-insensitive username (default burst 8), each replenishing one token every 2 seconds. Successful credentials refund both tokens. Exhaustion returns the same generic `Authentication failed.` response as every other credential failure and performs no password derivation; the separate `MaxConcurrentAuthentications` ceiling (default 4) bounds attempts that pass admission. The standalone server host binds `127.0.0.1` and provisions automatic TLS by default. It requires exactly one root credential source: `MNEMIC_ROOT_PASSWORD` or `MNEMIC_ROOT_PASSWORD_FILE`; there is no fallback password. Secret files are strict UTF-8 and lose terminal CR/LF characters. Plaintext requires `MNEMIC_TLS=off` plus `MNEMIC_ACCEPT_PLAINTEXT_CREDENTIALS=true`. A non-loopback plaintext listener also requires `MNEMIC_UNSAFE_ALLOW_REMOTE_PLAINTEXT=true`. The executable uses validated named `--data-dir`, `--spill-dir`, `--port`, `--diagnostics-port`, and `--listen-address` options, and keeps its temporary files under `--spill-dir`, by default `spill` inside the data directory; help and version modes initialize neither storage nor networking. A fixed IPv4-loopback diagnostics listener defaults to port 5151 and serves `/health/live`, `/health/ready`, and label-free Prometheus `/metrics`. `--check-ready` probes readiness without opening storage and exits 0 only for a ready server. TLS server endpoints accept only TLS 1.2 and TLS 1.3; startup rejects platform-selected defaults and older protocols. Their handshake timeout must be positive and finite so a silent peer cannot retain a pre-authentication connection slot indefinitely. Remote clients enforce the same TLS 1.2/1.3-only floor and reject non-positive or infinite handshake timeouts before opening a socket. Remote clients build server-certificate chains with online revocation checking by default; OS trust rejects chain errors, and built-in pin validators reject a definitive revoked status while permitting a pinned self-signed root. Operators may explicitly select cached offline checking or disable it only for a PKI with no revocation mechanism. The policy is part of the connection-pool identity. Custom certificate-validator callbacks are keyed by process-local instance identity: the same callback can share pooled connections, while different callbacks and OS trust never reuse one another's authenticated transport. The transport configurator runs once per open, and the captured settings drive both pool identity and any new handshake; stateful configuration cannot create a transport under a different policy than its key. Remote request identifiers are nonzero and unique for the full lifetime of a TCP transport. Exhausting the 32-bit identifier space retires the transport instead of wrapping, and a duplicate active identifier is rejected before any frame is written so response handlers cannot be overwritten across single and streaming requests. Every response must resolve to its exact active owner; never-issued IDs and duplicate responses for completed IDs fault the connection as protocol desynchronization. A correlated response shorter than the four-byte identifier is a connection fault that fails pending statements rather than becoming an identifier-zero frame. Request-ID exhaustion and protocol/read-loop faults are permanent transport taints that `ResetSession` cannot clear; reset clears only the transaction, migration, subscription and session-setting state that existed when the reset began. Error, result-schema, and terminal response bodies are fully validated on the transport read loop before delivery. Truncated lengths, invalid UTF-8, unknown markers/classes, and trailing bytes fault the connection and prevent pool reuse rather than surfacing partial results. Outbound text uses strict UTF-8 conversion: invalid UTF-16 is rejected instead of replacement-encoded into different MQL, credentials, parameter names/values, or notification identities, and unknown `ExecuteMql` flag bits fail locally. An incoming parameter count must fit the remaining minimum wire shape before dictionary allocation. DateTimeOffset UTC ticks and offset must also combine to a representable local timestamp, not merely pass their independent ranges. EOF is clean only between complete frames; residual bytes fault the transport. Once bytes are advanced, a canceled flush or completed peer permanently faults the writer, preventing an uncertain delivery from being retried as a duplicate or reordered frame. Response opcodes must also match their request class: Connect/reset accepts only Ok/Error, while streamed MQL accepts only Error, schema, row, and terminal responses. Unknown or cross-class opcodes fault the connection even when their payload resembles a valid response of another class. Streaming response order is strict: query = one schema, zero or more rows, `ResultEnd`; schema-less statement = `MqlOk`; `Error` terminates either active state. Rows/end before schema, duplicate schemas, and `MqlOk` after schema fault the connection before consumer dispatch. `MqlOk` carries an explicit `Ok` / `AffectedCount` kind plus an exact non-negative Int64 affected count. There is no alternate Int32 layout; a negative count or a partial/unknown tail is a protocol fault. Zero-row DML therefore remains `AffectedCount`. Request registration is atomic with transport shutdown: EOF, protocol failure, read-loop cancellation, and disposal either drain an already-registered single/streaming/Pong waiter or reject it before writing. No request is admitted after the response reader exits. When mTLS is enabled, the server checks client-certificate revocation online by default; operators may explicitly select cached offline checking or disable it only for a private PKI with no revocation mechanism. Auto-generated certificates backdate their validity start for clock skew without subtracting that backdate from the configured remaining lifetime. Operator-supplied certificates outside their validity window are rejected at server startup and rotation. Built-in client pins replace CA-chain and hostname validation with exact certificate identity, but still reject expired, future-dated, and definitively revoked server certificates. SHA-256 is the sole built-in pin identity; SHA-1 thumbprints are neither accepted nor persisted.
