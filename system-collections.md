# System virtual collections + Meta fields

> **In this section** — the read-only virtual collections under `[Mnemic]`, the persistent `[Mnemic].[Migrations]` collection, and the `Meta` fields appended to every SELECT result.

## Virtual collections

Read-only virtual collections under the `[Mnemic]` namespace, queryable via standard `FROM` syntax and usable as any [JOIN](queries.md#join) input:

The table shows canonical spelling; system collection names resolve under the same case-insensitive identifier rules as other collection names. Every spelling remains read-only.

They honor the client/wire `IncludeTotalCount` option: filtered cardinality is reported before outer `SKIP` / `LIMIT`, including through plain or computed projection.

A virtual collection joined to another relation is the same snapshot, under the same caller visibility, as when it is the FROM source. It is read once per statement before join planning, so it takes part in INNER, LEFT and CROSS joins, reordered and bushy join trees, APPLY bodies and correlated `EXISTS` / `IN` subqueries. Static `EXPLAIN` shows it, on either side of the join, as a `System input:` beneath a `DeferredJoin`, which `EXPLAIN ANALYZE`, where execution selected exactly one tree over the join's aliases in the statement, places beneath the node of that tree that reads it with the rows its snapshot held, and its registered schema is the one execution publishes.

Virtual collections are point-in-time snapshots with no version history — `AS OF`, `IN BETWEEN`, and `LAST PER` on a `[Mnemic].*` source are rejected with an error rather than silently returning current state. Catalog-backed snapshots retain one catalog-publication admission lease for their full capture. A concurrent migration or standalone catalog publish is observed wholly before or wholly after the result, never as an old collection name list combined with new schema rows. `DESCRIBE COLLECTION` has the same single-generation guarantee across metadata lookup and row encoding.

Snapshot row storage is bounded by `EngineOptions.MaxInMemoryStreamingState` and charged to engine-wide admission. Small snapshots use buffered `Rows`; larger snapshots spill to authenticated insertion-ordered runs and replay through `RowsAsync`. The same rule covers `LIST QUERIES` / `[Mnemic].[ActiveQueries]` and `[Mnemic].[Sessions]`. Capture remains eager (a stable point-in-time source), while cancellation, replay corruption, failure, or early disposal stops the query and releases its spill resources. This changes transport ownership, not MQL row order or query semantics.

Every column that names a named type or an enum — `[Mnemic].[Types]` `Name`, `BaseTypes` and `Checks.DeclaredBy`, `[Mnemic].[Enums]` `Name`, the `BaseTypes` of `[Mnemic].[Collections]`, the `EnumName` and `TypeName` of the `Fields` entries both list, `[Mnemic].[Constraints]` `DeclaredBy` — spells it as MQL writes it, exactly as collections are named: `[Ns].[Name]` in a namespace, `[Name]` at the top level. A name read from a catalog can therefore be pasted back into MQL, filtered on (`FROM [Mnemic].[Enums] WHERE [Name] = '[Billing].[ChargeStatus]'`) and passed to `ENUM_VALUE`; DESCRIBE, stored-definition text and statement messages use the same spelling.

Catalog views list only the collections a user sees. Engine-internal collections and the generation a materialized view's replacement retired, from the replacing commit until its drop reclaims it, never appear in `[Mnemic].[Collections]`, `[Mnemic].[Indexes]`, `[Mnemic].[IndexBuilds]`, `[Mnemic].[Constraints]`, `[Mnemic].[ForeignKeys]`, `[Mnemic].[CollectionStats]`, `[Mnemic].[StatisticsDefinitions]` or `[Mnemic].[Statistics]`, nor among the relations [`COMPLETE`](editor-assistance.md) offers, so a catalog read right after a migration that refreshed a view names only the view ([materialized views](materialized-views.md#refresh-transaction-scope)).

All process-lifetime totals in `[Mnemic].[Metrics]`, including sums across independently owned index trees, saturate at `INT64` maximum rather than wrapping negative.

`PageReads` counts completed page-manager copy reads (checksum-arbitration retries are separate observations) plus successful verified zero-copy and optimistic acquisitions; an empty scope attempt is excluded. `PageWrites` counts full-page accessor writes that returned successfully. These are logical page-manager operation totals across every page-store mode. Buffer-pool `CacheHits` / `CacheMisses` instead attribute where those acquisitions were served, so they are not substitutes for `PageReads`.

`[Mnemic].[Migrations]` is a real engine collection (not virtual) that stores migration history. Schema: `Level` (INT32 PK), `Statements` (STRING nullable at the storage-schema level), `Timestamp` (DATETIME). Current history writers always store a framed non-blank value, including an explicit zero-statement group for an empty migration. SCRIPT/MERGE reject a present row whose `Statements` value is null, blank, or malformed with `DDL_CATALOG_STRING_INVALID` rather than silently treating it as empty history.

### `[Mnemic].[WalArchive]`

This virtual collection always returns exactly one row, allowing a monitor to distinguish an explicitly disabled archive from a missing or inaccessible system view:

```sql
FROM [Mnemic].[WalArchive];
```

The fields are grouped as follows:

- Configuration and identity: `Enabled`, `State`, `DatabaseId`, `TimelineId`, `ProviderScheme`, `Compression`, `ArchiveIntervalSeconds`, `FailureTimeoutSeconds`, and `OperationTimeoutSeconds`.
- Health and progress: `LastSuccessAtUtc`, `FirstFailureAtUtc`, `FailureAgeSeconds`, `LastFailureType`, `ConsecutiveFailures`, `PendingSegments`, `PendingBytes`, `CoveredEndLsn`, `LastPhysicalCommitCsn`, `LastPhysicalCommitUtc`, `CoveredThroughUtc`, and `AchievedRecoveryLagSeconds`.
- Provider and protection: `ImmutableCreateSupported`, `ConditionalReplaceSupported`, `DurableReadbackSupported`, `BoundedStreamingReadsSupported`, `ProtectionMode`, `ProtectionAlgorithm`, and `ProtectionKeyId`.
- Extension contracts: `CutFenceConfigured`, `ParticipantConfigured`, and `SupportedExtensionNamespaceCount`. These fields report whether a plugin has activated the optional cut-fence and PITR-participant contracts.
- Retention and admission: `ProgressGeneration`, `RecoveryFloorGeneration`, `EarliestAcceptedBaseLsn`, `RetainedWalHighWatermarkBytes`, `RetainedWalLowWatermarkBytes`, `RetainedWalBytes`, `AdmissionHeadroomBytes`, `WriteBlocked`, and `BlockReason`.
- Clock diagnostics: `DecisionClockLeadSeconds` reports non-negative lead of the ordered decision clock over wall UTC after a clock rollback.

`State` is `Disabled`, `Healthy`, `Degraded`, or `Blocked`. Treat `WriteBlocked = true`, falling `AdmissionHeadroomBytes`, growing `PendingBytes`, or achieved lag approaching `FailureTimeoutSeconds` as paging signals. Timeline IDs and key IDs intentionally stay in this system row and logs, not metric labels, to keep telemetry cardinality bounded. See the [operator guide](https://mnemic.io/docs/wal-archiving-pitr/).

`[Mnemic].[Triggers]` is a real engine collection that stores trigger definitions registered via [`CREATE TRIGGER`](triggers.md). Schema: `Id` (GUID PK), `Name`, `CollectionId` (INT32; zero for a materialized target), `MaterializedViewId` (GUID; empty for an ordinary target), `CollectionName`, `Timing` (INT8: executable definitions require `0`=Before or `1`=After), `Event` (INT8: nonempty bitmask of `1`=Insert, `2`=Update, `4`=Delete), `BodyText`, `WhenText` (nullable row condition), `CreatedAt`. Names and executable text are rendered from the caller's catalog snapshot; persisted source and structural ID bindings remain unchanged on rename. The catalog carries a UNIQUE secondary index on `Name` (case-insensitive) so the catalog enforces trigger-name uniqueness at the storage layer. Definitions survive engine restart — `BodyText` is re-parsed on first use after reopen. Read-only from userland; mutate via `CREATE TRIGGER` / `DROP TRIGGER` only. Hydration requires non-blank, exactly framed strict-UTF-8 `Name`, and `BodyText`; invalid required text fails with `DDL_CATALOG_STRING_INVALID` before any trigger is published.

`[Mnemic].[Views]` is a real engine collection that stores view definitions registered via [`CREATE VIEW`](views.md). Schema: `Id` (GUID PK), `Name` (the current qualified bracketed view name), `NamespaceId`, `BodyText` (the SELECT body rendered with current object names), `CreatedAt`, `LastAlteredAt`. Storage retains the local name, namespace identity and structural bindings; its case-insensitive unique key is `(NamespaceId, Name)`. Definitions survive engine restart and are inlined at query time when their name appears in a `FROM` or `JOIN` clause. Read-only from userland; mutate via `CREATE VIEW` / `ALTER VIEW` / `DROP VIEW` only. Hydration applies the same strict rule to `Name` and `BodyText`, so malformed text cannot become an anonymous view or empty executable body.

`[Mnemic].[MaterializedViews]` is a real engine collection that stores materialized-view definitions registered via [`CREATE MATERIALIZED VIEW`](materialized-views.md). Schema: `Id` (GUID PK), `Name`, `NamespaceId`, `BodyText`, `PrimaryKeyField`, `RefreshMode` (INT8: `0`=Manual, `1`=Incremental), `CreatedAt`, `LastRefreshedAt`. The public name and body use current catalog names. The mat view's *backing* lives at the user-chosen `Name` as a real collection — query it via `FROM [Ns].[Name]` like any other — and that collection holds the view's one name: storage retains the backing's collection ID in place of `Name` and `NamespaceId`, with structural bindings, and has a unique key on that ID. Hydration fails closed with `IVM_BACKING_MISSING` when the ID names no collection, and applies the same strict rule to `BodyText` and `PrimaryKeyField` before classifying the backing or publishing maintenance.

`[Mnemic].[Diagrams]` is a real engine collection that stores the [database diagrams](diagrams.md) `CREATE DIAGRAM` defines, created by the first one. Schema: `Id` (GUID PK), `Name`, `Revision` (INT64; 1 at creation, raised by one by each change, a drop of a box's relation included), `Fields` (`All`, `Keys` or `None`), `Boxes` (ARRAY OBJECT, in stored order: `Collection`, `CollectionId` INT32, `MaterializedViewId` GUID, `X` INT32, `Y` INT32), `CreatedAt`, `LastAlteredAt`. Storage binds each box to its relation's identity alone, a collection's ID with an empty GUID or a materialized view's definition GUID with a zero ID, and the read gives each box the name the caller's catalog has for it, a migration's private names included; a box whose relation no longer exists is left out. Before the first diagram the catalog does not exist and reads return no rows with this schema. The catalog carries a UNIQUE secondary index on `Name` (case-insensitive). Read-only from userland; mutate via `CREATE` / `ALTER` / `DROP DIAGRAM` only. A row whose schema, framing, `Fields` text, box identities or timestamps are not exactly what the statements write is corruption (`DDL_CATALOG_SCHEMA_INVALID`, `DDL_CATALOG_SCALAR_INVALID`, `DDL_CATALOG_STRING_INVALID`, `DDL_CATALOG_ID_INVALID`, `DDL_CATALOG_DATETIME_INVALID`), never a diagram drawn in part.

All three executable catalogs (`Triggers`, `Views`, and `MaterializedViews`) and the `Diagrams` catalog validate their synthesized identities before bootstrap publishes either the unique identity index or executable metadata. `Id` must be a non-empty GUID, decoded IDs must be unique, and local names must be unique case-insensitively within their namespace (globally for triggers), as must a materialized view's backing collection. Impossible or repeated IDs fail as `DDL_CATALOG_ID_INVALID`; duplicate names, and two materialized views naming one backing, fail as `DDL_CATALOG_DUPLICATE_NAME`. Hydration never guesses a winner or deletes competing metadata.

`[Mnemic].[ActiveQueries]` is a virtual collection backed by the server's registry of running statements. One row per in-flight statement: `QueryId` (GUID), `ConnectionId` (GUID nullable), `Username` (STRING nullable), `DatabaseName` (STRING nullable), `Mql` (canonical-printed statement text, in which a credential such as a `PASSWORD` literal prints as `'***'`), `StartedAtUtc`, `ElapsedMs`. Non-admin users see only rows attributed to their own username; unattributed rows fail closed. `UserAdmin` sees every query. State is mutated indirectly via `CANCEL QUERY` / `SET STATEMENT TIMEOUT` and the per-connection `SocketHealthMonitor`. See [cancellation.md](cancellation.md).

`[Mnemic].[Health]` is a virtual collection backed by the engine's in-memory health surface. One row per faulted domain (healthy domains are absent). Columns: `Domain` (STRING — canonical fault-domain form, e.g. `EngineWide`, `PageStore{[Shop].[Orders]}`, `Index{[Shop].[Customers]/secondary_Email}`; see [health](health.md#mnemichealth)), `State` (STRING — `Degraded` or `Quarantined`), `Code` (STRING, e.g. `PAGE_CHECKSUM`), `Resumable` (BOOL — whether `ALTER ENGINE RESUME` can clear the fault; `FALSE` for a recovery-required code below), `ReadsAdmitted` (BOOL — whether ordinary reads stay admitted while the fault stands; they run exactly while every row's is `TRUE`), `Message`, `FirstObservedAtUtc`, `LastObservedAtUtc`. While any domain is `Quarantined` the executor normally refuses all ordinary reads and mutations; only a direct health query plus rollback/abort/cancel/resume controls and verified `RESTORE FROM '<backup>' VERIFY` staging remain. A lone `WAL_FLUSH_FAILED` retains bounded query/metadata/integrity reads while every mutation, backup, and subscription registration stays refused; any coexisting quarantine closes reads. Indeterminate append/fsync and incomplete post-marker apply therefore pair it with `WAL_WRITE_FAILED` or `COMMIT_APPLY_FAILED_AFTER_MARKER`, respectively. Recovery-required codes (`COMMIT_APPLY_FAILED_AFTER_MARKER`, `IMPLICIT_ROLLBACK_CLEANUP_FAILED`, `ROLLBACK_CLEANUP_FAILED`, `CATALOG_PUBLICATION_FAILED_AFTER_COMMIT`, `REBUILD_INCOMPLETE`, `REBUILD_REPEATED_FAILURE`, `WAL_WRITE_FAILED`, `WAL_FLUSH_FAILED`, and `PLUGIN_RECOVERY_REQUIRED`) cannot be resumed in place and require reopen; their rows read `Resumable = FALSE`, by the rule `ALTER ENGINE RESUME` refuses with. State is in-memory and resets to `Healthy` on restart. See [health.md](health.md).

The catalog also includes carrier errors: `PROTOCOL_VERSION_UNSUPPORTED` (`User`) refuses an incompatible handshake, `AUTHENTICATION_FAILED`, `AUTHENTICATION_REQUIRED`, and `NO_DATABASE_SELECTED` (`User`) refuse a connection's credentials or binding, `REQUEST_QUEUE_FULL` (`ResourcePressure`) refuses pending work before execution, and `INTERNAL_ERROR` (`Internal`) is the generic server handling fallback. The latter and the engine classifier's `UNCLASSIFIED` code both require conservative handling. It also registers the `User` codes of ordinary statement mistakes, from `SYNTAX_ERROR` and `UNKNOWN_FIELD` through DDL codes such as `DEPENDENT_OBJECTS_EXIST` to `INSUFFICIENT_PRIVILEGE`; see [errors.md](errors.md).

`[Mnemic].[ErrorCatalog]` is a static virtual collection — one row per stable error code the engine emits. Columns: `Class` (STRING, one of `User`, `Transient`, `Conflict`, `Cancellation`, `Validation`, `ResourcePressure`, `StructuralCorruption`, `ContractViolation`, `PluginFault`, `Internal`), `Code` (STRING — the stable token that appears in error messages and in `[Mnemic].[Health].[Code]`), `Description` (STRING — what the code means and what the operator should do). Useful for tooling: an admin UI can pull the full classification surface without grepping engine source. Constant for the lifetime of the engine; new codes appear only when the engine binary changes. See [errors.md](errors.md).

`[Mnemic].[SlowQueries]` is a virtual collection backed by an in-engine bounded ring buffer populated by the slow-query log emitter. A host threshold or `ALTER ENGINE SET SLOWQUERY` enables the ring; otherwise it returns zero rows. The initial capacity is `EngineOptions.SlowQueryRingCapacity` (default 1024). Durable runtime configuration supersedes that capacity; resizing retains the newest events and overflow drops the oldest. Disabling the default threshold keeps history and events selected by session overrides. Events are not persisted across reopen. See [runtime policy](maintenance.md#alter-engine-set-slowquery). Columns: `At` (DATETIMEOFFSET), `StatementType` (STRING — `Select`, `Insert`, … with the trailing `Node` stripped), `ElapsedMs`, `ThresholdMs`, `ResultType` (STRING), `RowCount` (INT64 nullable), `SpilledBytes` (INT64), `Username`, `ConnectionId`, `DatabaseName`, `TransactionId` (all nullable; `TransactionId` is the identity `BEGIN TRANSACTION` returned), `SlowestStage` / `SlowestStageMs` (dominant per-stage attribution when the statement ran through any instrumented streaming operator; null + 0 otherwise), `SpillingStage` / `SpillingStageBytes` (dominant per-stage spill attribution; null + 0 when no stage spilled), `Mql` (canonical-printed statement text, capped at the 4,096-character observability bound, with credentials masked as in `[Mnemic].[ActiveQueries]`). Rows arrive in oldest-first order; paginate with `ORDER BY [At] DESC` for newest-first dashboards. The same events are also written as `LogLevel.Warning` structured-log lines under the `Mnemic.Mql.SlowQuery` category — this collection is the in-MQL sibling for operators who don't want to scrape the log sink. Visibility mirrors `LIST QUERIES` / `[Mnemic].[ActiveQueries]`: a non-admin reader sees only their own events (the `Mql` text carries inlined literals), and unattributed events are hidden; `UserAdmin` and in-process hosts see every user's events.

`[Mnemic].[StatementStats]` is the PostgreSQL `pg_stat_statements` analogue: a running per-statement-*shape* execution aggregate. Returns **zero rows** unless `EngineOptions.StatementStatsCapacity` is set to a positive value (the aggregate is opt-in because, unlike the slow-query log, it tracks *every* statement, not just slow ones). Each row keys on a **fingerprint** — the statement's canonical text with every constant literal replaced by `?`, so `WHERE [id] = 5` and `WHERE [id] = 9` fold into one bucket `WHERE [id] = ?` (parameter references like `@id` and the structural `NULL` / `NOW` are preserved — they change the statement's meaning, not just a constant), and a credential such as a `PASSWORD` literal prints as `'***'`. Oversized fingerprints retain a readable prefix plus `…sha256:<digest>` of the complete normalised text, so shapes first differing beyond the display prefix avoid deterministic aliasing while the key stays within the 4,096-character observability bound. Columns: `Fingerprint` (STRING — that bounded normalised identity), `StatementType` (STRING — `Select`, `Insert`, … with the trailing `Node` stripped), `ExecutionCount` (INT64), `TotalElapsedMicros`, `MeanElapsedMicros`, `MinElapsedMicros`, `MaxElapsedMicros`, `StdDevElapsedMicros`, `P95ElapsedMicros` (all INT64 microseconds; p95 from a fixed log-bucketed latency histogram, exact below 10 µs and within about 12.2% value quantisation error above it across the INT64 domain), `TotalRows` (INT64 — summed result/affected rows), `FirstSeen` / `LastSeen` (DATETIMEOFFSET). The elapsed time is end-to-end and, for streaming results, measured post-drain (the work the engine actually did, not the pipeline-setup time). Running INT64 totals and counts saturate at their maximum rather than wrapping negative. Mean/standard deviation remain independent of a saturated total, and concurrent observations expose the minimum `FirstSeen` and maximum `LastSeen` rather than recorder lock order. At most `StatementStatsCapacity` distinct fingerprints are tracked; once full, new shapes are counted on the `mnemic.statement_stats.dropped` meter and otherwise ignored while existing buckets keep accumulating. Typical queries: the slowest shapes (`ORDER BY [MeanElapsedMicros] DESC`), or the highest-volume shapes (`ORDER BY [ExecutionCount] DESC`). Because buckets aggregate all users and carry no owner dimension, this view is `UserAdmin`-only: other users receive a correctly shaped zero-row result. In-process executors retain full visibility.

`[Mnemic].[LockTimeoutsBySite]` is a virtual collection giving the per-site breakdown of the engine-wide `LOCK_TIMEOUT` counter. One row per bounded-wait lock site that has fired at least one timeout since engine open — healthy engines return **zero rows**, so it pairs with `[Mnemic].[Metrics].[LockTimeoutCount]` (the engine-wide sum) as a hotspot list rather than a full site enumeration. Columns: `SiteName` (STRING — the canonical lock-site label, e.g. `EngineCollection._commitFlushLock`, `EngineCollection._writeLock`, `DiskBPlusTree._structuralGate@<index>`), `Count` (INT64). Rows are returned in stable `SiteName` order. A site names the contended resource, not the operation that waited: every wait on one lock or gate — read or write, admission or drain, query or commit — reports the same `SiteName`. For a lock or gate acquisition that `SiteName` is also the resource's key in the engine's per-site lock-timeout overrides. A wait that spans several resources under one end-to-end budget, such as a backup start taking its gates, reports a held gate under the gate's own site unless the budget is configured shorter than the gate's deadline; a budget configured shorter, or one that runs out while the start waits for its applied prefix rather than a gate, reports the budget's site. With the default configuration a stalled holder of a backup gate is therefore reported as that gate, and an unresolved applied-prefix wait as `TransactionManager._backupPrefixDrain`. Drains that a structural publisher runs over already-admitted work are the exception to the override contract. They report the resource they wait on, but their budget is the engine's migration-drain timeout, so a per-site override keyed on that row does not change how long the drain waits; a statement or storage operation waiting to be admitted behind the same fence still uses the row's override. The exceptions are exactly these sites:

- `MigrationDrainCoordinator.BeginMigrationDrain` — a migration entry's drain of the statements in flight when it began.
- `MigrationDrainCoordinator.CatalogPublication` — a catalog publication's wait for a preceding publisher and its drain of admitted statements.
- `MnemicEngine.CatalogPublicationReadAdmission` — the same publication's wait for a preceding publisher and its drain of admitted direct-storage operations (point reads, lazily consumed results, backup page reads).

An engine-maintenance publication that waits without preempting statements drains both fences within at most a quarter of the shorter admission deadline of the two publication fences, so an override on a fence's site shortens it. The same per-site attribution rides the `Mnemic.Engine` meter as `mnemic.lock.timeouts` tagged by `site`. See [health.md](health.md) and the bounded-wait-locks design. Per-site process-lifetime counts and the cross-site sum saturate at `INT64` maximum rather than wrapping negative.

`[Mnemic].[MigrationDrains]` reports the current per-engine migration drain. It returns zero rows when no migration is active and one row otherwise. Columns are `ActiveMigrationCount` (migrations sharing the drain), `BlockingActiveStatementCount` (distinct pre-entry statements still present in an active entry snapshot; post-entry statements are excluded), and `IsDraining`. The three values come from one coordinator snapshot, so a row never combines states observed at different instants. See [migrations.md](migrations.md).

`[Mnemic].[Metrics].[DeadlocksDetected]` (INT64) is the engine-wide count of participating waits-for cycle detections that selected a victim since open; a cycle counts only once the detector confirmed that all its edges held at one instant. Selection uses the lowest current dirty-page count as a work proxy and requests the transient `DEADLOCK` error (see [errors.md](errors.md)); the lock timeout remains the liveness backstop. A commit takes its collections in one canonical order, so the count stays **zero** unless implicit statements that reuse their sessions' append pages also write each other's collections, as cross-writing `AFTER` triggers do: such a statement holds its own collection from before its work, outside that order. Each such cycle counts once, and its victim statement is retried, which counts in `RetriedDeadlocks`. It is zero when detection is disabled (`DeadlockDetectionIntervalMs = 0`). The same count rides the `Mnemic.Engine` meter as `mnemic.deadlocks` — the PostgreSQL `pg_stat_database.deadlocks` precedent.

`[Mnemic].[Metrics].[RetriedConflicts]`, `[RetriedDeadlocks]`, `[RetriedLockTimeouts]` and `[RetriedOtherTransients]` (INT64) count since open the server-side retries: the attempts of work the server discarded and ran again on a caller's behalf, one per retry, by the code of the failure that ended the attempt — a write-write conflict (`TX_CONFLICT_FWW`, `TX_CONFLICT_SERIALIZABLE`) or a lost insert race (`UNIQUE_VIOLATION`), a deadlock victim (`DEADLOCK`), an expired lock wait (`LOCK_TIMEOUT`), and every other transient code — `WRITE_CONTENTION` from a nested retry that gave up, `STRUCTURAL_WRITE_UNAVAILABLE`, `CATALOG_PUBLICATION_RETRY`, `SCHEMA_GENERATION_CHANGED`, `FK_CASCADE_SOURCE_CHANGED`, `MIGRATION_CONFLICT`, `WAL_ARCHIVE_UNAVAILABLE`, or a nested statement's transient result, which counts by the code it carries. Every boundary that retries counts the same way: a statement outside an explicit transaction writes in an implicit one, which the engine retries up to eight times with a jittered pause before its client sees a failure ([transactions](transactions.md)); a standalone `UPSERT` re-probes its conflict target after losing its insert race and retries its transient failures within the same bound ([UPSERT](dml.md#insert--on-conflict-upsert)); a `DIAGRAM` statement retries its catalog work ([diagrams](diagrams.md#diagram-statements-stand-alone)); the server's authorization-audit batch retries its rows in a fresh master transaction, counted on the master database; a relational subscription retries its observation after a serializable conflict up to twice ([subscriptions](subscriptions.md)); and a server plugin's collection upsert retries a lost insert race. These totals and the server log, which records each retry at `Information` naming the boundary, the collection, the code and the attempt, are where that contention shows. The attempt that exhausts a budget is not counted: its work then fails, a statement with `WRITE_CONTENTION` or the failure it met. Background maintenance that defers its next pass after a transient failure retries on no caller's behalf and counts in none of them. The engine never retries a client's explicit transaction, so a conflict or deadlock victim in one reaches its caller and counts in none of them; `RetriedDeadlocks` therefore stays at or below `DeadlocksDetected`. The same retries ride the `Mnemic.Engine` meter as `mnemic.retries`, tagged by `cause` (`conflict`, `deadlock`, `lock_timeout`, `other`) and `collection`.

### Schema / catalog introspection

`[Mnemic].[Indexes]` lists ready catalog indexes across every collection — the PostgreSQL `pg_indexes` analogue. Columns: `CollectionName`, `IndexName`, `Kind` (`PrimaryKey` / `Temporal` / `Revision` / `Secondary` / `ArrayInverted`), `KeyFields` and `IncludeFields` (comma-joined dotted field paths, so they filter and sort as plain text), `IsUnique`, `IsPrimaryKey`, `IsTemporal`, `IsRevision`, `FilterText` (the partial-index `WHERE` predicate, nullable), `ExpireAfterTicks` (nullable INT64; zero is an absolute deadline, NULL has no expiry policy), and `RootPageId`.

Automatic `IndexName` values are owner-local: `pk`, `temporal`, and `revision`. They remain unchanged when the owning collection is renamed or moved.

`[Mnemic].[IndexBuilds]` returns one row per registered online CREATE or ALTER index build. Administrators and embedded operators can read it; non-admins receive the same schema with zero rows, before filtering or aggregation. Columns are `BuildId` (GUID, stable for that build), `CollectionName`, `IndexName`, `KeyFields` (comma-joined paths), `State`, `RowsScanned` / `RowsIndexed` (INT64), `TrackedPointers` / `TrackedPointerLimit` (INT32), and `OwnershipWaits` / `OwnershipWaitMs` (INT64).

`State` is `Registered`, `Backfilling`, `Publishing`, or `Failed`. Rows disappear when registration retires, including after cancellation or failure; this is not a durable build history. `RowsScanned` counts live, nonempty slots visited before filtering. `RowsIndexed` counts rows inserted by the reconciled backfill, not array postings or concurrent dual writes. The counters do not describe the current index cardinality. Concurrent writes can change the scan population, so these observations do not provide an exact completion percentage or remaining row count. Reconciliation counters show distinct retained pointer claims and the configured capacity. `OwnershipWaits` counts the times the backfill waited for a transaction that still owned an index page a row needed, and `OwnershipWaitMs` the milliseconds spent in those waits, including one in progress, so a build parked behind an owner shows a growing value. A committed write gives its pages back before the backfill can meet them, so a nonzero count means a transaction kept a page past its own commit. Each wait lasts at most the lock-acquisition deadline of the `IndexMutationContext.TransactionOwnership` site; when that deadline expires, the build fails with `LOCK_TIMEOUT` ([online index build](indexes.md#online-index-build--with-online--on)). Each build's counters are captured together; different builds may be observed at different instants. Ordinary non-temporal MQL operators apply, and the result uses bounded snapshot storage.

```mql
FROM [Mnemic].[IndexBuilds]
SELECT [CollectionName], [IndexName], [State], [RowsScanned], [RowsIndexed], [TrackedPointers], [TrackedPointerLimit];
```

`[Mnemic].[Constraints]` lists every collection-level constraint — the PostgreSQL `pg_constraint` analogue; a CHECK declared on an OBJECT or ARRAY OBJECT field is enforced but not listed here: the `Checks` of that field's `Fields` entry list it. Columns: `CollectionName`, `ConstraintType` (`PrimaryKey` / `Check` / `Unique` / `ForeignKey`), `ConstraintName` (nullable — anonymous CHECKs have no name), `Columns` (comma-joined target field path(s) where meaningful, nullable), and `Expression` (the CHECK predicate text, or an FK target description like `CategoryId -> [Shop].[Categories] (Cascade)`; nullable), and `DeclaredBy` (for a CHECK the collection inherits through `EXTENDS`, the type that declares it, which `ALTER TYPE` changes; null for the collection's own CHECKs and other constraints). Foreign keys also appear in the dedicated `[Mnemic].[ForeignKeys]` view.

`[Mnemic].[ForeignKeys]` lists every foreign-key constraint. Columns: `SourceCollection`, `SourceField` (the dotted FK field path), `ReferencedCollection` (the target's current name, resolved from the identity the constraint stores), `OnRemove` (`Restrict` / `Cascade` / `SetNull`), `IsArray` (an array / collection FK), and `IsPinned` (a pinned `[id][revision]` FK).

`[Mnemic].[CollectionStats]` is one row per collection combining catalog structure, the live document count, and the planner-statistics summary — the PostgreSQL `pg_stat_user_tables` / `pg_class` analogue. Columns: `Name`, `DocumentCount` (committed rows only), `IndexCount`, `FieldCount`, `SubTypeCount`, `CheckConstraintCount`, `ForeignKeyCount`, `IsTemporal`, `IsAutoIncrement`, `AnalyzedColumnCount`, `LastAnalyzedAt` (nullable), and `AvgRowWidthBytes` (nullable). `AnalyzedColumnCount` is 0 and `LastAnalyzedAt` / `AvgRowWidthBytes` are null until [`ANALYZE`](analyze.md) has run for the collection.

`IsAutoIncrement` in `[Mnemic].[Collections]`, `[Mnemic].[CollectionStats]`, and `DESCRIBE COLLECTION` describes the declared primary key, including a nested primary-key path created through the raw engine API.

### Server metadata

`[Mnemic].[Capabilities]` is a key/value feature matrix — one row per advertised capability — reflecting the engine's effective configuration. Columns: `Name`, `Value`, `Category` (`Query` / `Storage` / `Transactions` / `Security` / `Observability` / `ResourcePressure` / `Plugins`). Rows include `IsolationLevel`, `MaxQueryParallelism`, `PageStore`, `DeadlockDetection`, `SlowQueryLog`, `SlowQueryRingCapacity`, `StatementStats` (whether `[Mnemic].[StatementStats]` collects), `AutoAnalyze`, `StatementTimeout`, `AdmissionController`, `Encryption`, `Plugins`, and `MaxInMemoryStreamingState`. `PageStore` names the page store the engine opened (`BufferPool` or `InMemory`), including one a `:memory:` path selected. `SlowQueryLog` reflects current engine default selection, independent of session overrides. `SlowQueryRingCapacity` reports retained history capacity, or zero before the ring is enabled. These two rows come from one coherent policy snapshot.

`[Mnemic].[Version]` is a single row of server / engine build metadata — the PostgreSQL `version()` analogue. Columns: `Product` (`Mnemic`), `Version` (assembly version), `FormatVersion` (on-disk format version), `PageSize`, `Runtime` (.NET framework description), `Os`, `ProcessArchitecture`, and `AppliedCommitSequenceNumber` (the durability high-watermark).

### Live operational state

`[Mnemic].[Transactions]` lists every **explicit** in-flight transaction — the PostgreSQL `pg_stat_activity` (xact_start / state) analogue. Columns: `TransactionId` (the identity `BEGIN TRANSACTION` returned, which `JOIN TRANSACTION`, `TX_CONFLICT_SERIALIZABLE`, `[Mnemic].[Locks]` and `[Mnemic].[SlowQueries]` use too), `StartedAtUtc`, `IsolationLevel` (`Snapshot` / `Serializable`), `DirtyPageCount` (work done so far), and `TouchedCollectionCount`. Implicit single-statement transactions are deliberately **absent** (they are sub-millisecond and would flood the surface); the view is empty when no explicit transaction is open. An open migration is listed too, under the transaction its statements run in; that identity is no `JOIN TRANSACTION` handle. Engine-owned work that runs in a transaction of its own, such as a multi-row `UPDATE` outside `BEGIN TRANSACTION` or a relational subscription's observation, appears while it runs; a multi-row `INSERT` outside `BEGIN TRANSACTION` runs in the session's implicit transaction and does not. This global runtime view is `UserAdmin`-only; other users receive zero rows.

`[Mnemic].[Locks]` is the participating lock view — a scoped PostgreSQL `pg_locks` analogue — built from the deadlock detector's waits-for bookkeeping. It is not a list of every engine latch. One row per granted hold or pending wait. Columns: `Resource` (the tracked resource key, e.g. `commitflush:42`), `TransactionId`, `Granted` (`true` = held, `false` = waiting), and `Cost` (victim-selection cost for a waiter, 0 for a hold). Commit-flush ownership participates: a commit's hold on the collections it publishes, the hold an implicit statement takes on a collection when it reuses its session's append page there, from before the statement's work through its commit, and the holds of a collection's chained implicit commits, each of which holds the collection's resource and its own apply resource (e.g. `commitflush:42:apply:<transaction>`, which the next chained commit waits on before it applies) from joining until it has applied. So do waits for a removal: a write whose unique key another transaction is deleting or moving waits on that transaction's `indexowner:<transaction>` resource, held on its behalf from the first such wait until it has committed or rolled back. So do waits for a page: a statement outside an explicit transaction that needs a data page another transaction is writing waits on that transaction's `pageowner:<transaction>` resource, held on its behalf from the first such wait until it has released its page claims. The view is therefore **empty** while no write is in flight. A granted row means the tracked resource is active; only `Granted = false` demonstrates contention. Empty when deadlock detection is disabled (`DeadlockDetectionIntervalMs = 0`). This global runtime view is `UserAdmin`-only; other users receive zero rows.

`[Mnemic].[Sessions]` lists every live client connection — the PostgreSQL `pg_stat_activity` analogue at the connection grain (one row per connection; in-flight statements are `[Mnemic].[ActiveQueries]`). Columns: `ConnectionId`, `Username` (nullable), `DatabaseName` (nullable), `RemoteEndpoint` (nullable), `ConnectedAtUtc`, and `LastActivityUtc` (nullable). **Server-only** — the in-process (embedded) engine has no connection layer, so this view returns **zero rows** there, the same shape as `[Mnemic].[ActiveQueries]`. Over the server, non-admin users see only sessions attributed to their own username; unattributed/pre-authentication entries are hidden. `UserAdmin` sees all sessions.

`[Mnemic].[Statistics]` is a real engine collection populated by [`ANALYZE`](analyze.md). One row per collection + scalar/compound/array-component population + path + optional exact partial-filter population. Columns: `Id` (GUID PK, derived from the collision-free length-framed identity), `CollectionId` (INT32 owner identity), `CollectionName` (resolved from the caller's catalog snapshot), `FieldPath`, `TotalCount`, `NullCount`, `DistinctCount`, `MinValue` (BYTES nullable, encoded), `MaxValue` (BYTES nullable, encoded), `LastAnalyzedAt`, `CollectionDocCountAtAnalyze`, required exact-v1 state `IsCompound`, `IsArrayComponent`, `CompoundCorrelationRatio`, `IsIncremental`, plus the nullable extended-statistics columns `HllSketch`, `Histogram`, `Mcv` (opaque encoder blobs), `PartialFilterText`, `LastAnalyzedWriteCsn`, and the cost-model page-packing inputs `AvgRowWidthBytes` (collection-level average document width) + `AvgKeyWidthBytes` (per-column average encoded-key width). `LastAnalyzedWriteCsn` is the gap-free commit cut covered by the row. `IsIncremental` distinguishes additive HLL/count state from an authoritative full-scan population. Read-only from userland — DDL on `[Mnemic].*` is rejected; the catalog is rebuilt only by `ANALYZE` or background auto-analyze.

The `Fields` arrays on collection rows use a fixed-depth, non-polymorphic element schema. `FieldPath` encodes nesting using dots plus `[]` for array-element boundaries (`Address.City`, `Items[].Label`). `SubType` is null for base schema fields and holds the discriminator value for subtype extension fields. A subtype that declares no fields has no entry, so a polymorphic field's own entry lists every subtype in its `SubTypes`, as a collection row's `SubTypes` lists the collection's.

```sql
-- List all collections with their nested Fields and SubTypes
FROM [Mnemic].[Collections];

-- DESCRIBE a specific collection (returns one row with the Fields array)
FROM [Mnemic].[Collections] WHERE [Name] = '[Shop].[Products]';
DESCRIBE COLLECTION [Shop].[Products];

-- Migration history on this database
FROM [Mnemic].[Migrations] ORDER BY [Level] ASC SELECT [Level], [Statements], [Timestamp];
```

## CreatedBy policy and collection participation

`[Mnemic].[Collections]` and DESCRIBE expose `CreatedByEnabled` as BOOL. New collections default to FALSE. This is independent of temporal versioning.

`[Mnemic].[CreatedBy]` is a read-only singleton captured from one consistent policy/catalog snapshot. A migration owner sees its provisional configuration; other sessions see committed configuration.

| Field | Type | Meaning |
|---|---|---|
| `Mode` | STRING | `NONE`, `EXTERNAL`, or `COLLECTION` |
| `MaxSize` | INT32? | External actor byte limit; otherwise NULL |
| `ReferencedCollection` | STRING? | Current qualified actor collection name in COLLECTION mode |
| `PrimaryKeyField` | STRING? | Actor primary-key path in COLLECTION mode |
| `PrimaryKeyType` | STRING? | Native actor key type, such as `INT64`, `GUID`, or `BYTES` |
| `Display` | STRING? | In COLLECTION mode, the canonical text of the policy's [display](maintenance.md#createdby-display) expression over one actor document, with current names; otherwise NULL |

```mql
FROM [Mnemic].[CreatedBy];

```

## Meta fields

`[Meta].[CreatedAt]` records when the stored revision was authored. It is available on both standard and temporal collections. A write defaults to statement-pinned UTC `NOW`; INSERT and UPSERT can supply `CREATEDAT` to preserve an imported timestamp. It is distinct from original document creation, validity start, and commit time. See [creation timestamps](dml.md#createdat-creation-timestamps).

A query without `SELECT`, and a `SELECT *` wildcard, append a virtual `Meta` object column to each row after the declared fields, containing slot metadata. An explicit SELECT list carries `Meta` only when it names it:

| Field | Type | Description |
|-------|------|-------------|
| `Meta.ValidFrom` | DateTimeOffset? | When this document version became valid; NULL on a standard (non-temporal) collection |
| `Meta.ValidTo` | DateTimeOffset? | When this document version was ended (null = current) |
| `Meta.Revision` | Int64 | Document version number (monotonically increasing) |
| `Meta.CreatedAt` | DateTimeOffset | UTC creation time of this authored revision, independently of validity |
| `Meta.CreatedBy` | Bytes? | Exact opaque attribution bytes, in every policy; null when absent. Under the `COLLECTION` policy they are the actor's primary key in its binary form |
| `Meta.Sealed` | Bool | Reversible identity-level workflow guard; always non-null |
| `Meta.SchemaVersion` | Int32 | The collection schema version this document version was written with; always non-null |

A plain `[Meta].[Revision]` item returns the whole `Meta` object, like any nested path, under the column name `Meta`; give it an alias to project the scalar member as its own column:

```sql
-- Access Meta fields in queries: alias each member to get a scalar column
FROM [HR].[Employees] SELECT [Name], [Meta].[Revision] AS [Revision], [Meta].[ValidFrom] AS [ValidFrom];

-- Filter by revision
FROM [HR].[Employees] WHERE [Meta].[Revision] > 5;

-- Filter by validity start time
FROM [Store].[Products] WHERE [Meta].[ValidFrom] > '2024-06-01T00:00:00Z';

-- Exact byte filters: parameters contain bytes; literals use base64
FROM [Store].[Products] WHERE [Meta].[CreatedBy] = @actor;
FROM [Store].[Products] WHERE [Meta].[CreatedBy] IN ('YWRtaW4=', 'cm9vdA==');

-- Find records protected from ordinary logical mutation
FROM [Archive].[Records] WHERE [Meta].[Sealed] = TRUE;

-- Find documents that have been ended (temporal collections)
FROM [HR].[Contracts] WHERE [Meta].[ValidTo] != NULL;
```

The `Meta` field is appended to implicit and wildcard projections automatically, and `SELECT * EXCLUDE ([Meta])` is `UNKNOWN_FIELD` because `Meta` is not a declared field. It is **not** included for internal UPDATE / DELETE queries, and is excluded from `DESCRIBE COLLECTION` output (it's virtual, not a schema field). `Meta.CreatedBy` preserves raw bytes even when they are not valid UTF-8. Equality and IN use exact byte identity; ORDER BY uses unsigned lexicographic byte order, as for any BYTES field. Range operators use that same byte order and never match NULL operands. Text operators require STRING. Unattributed metadata reads as NULL; NULL/empty actor inputs are rejected. Supply attribution through the [DML CREATEDBY clause](dml.md#createdby-attribution). For temporal collections `Meta.Sealed` is identity-level control metadata: an `AS OF` body read reports the seal state visible to the current transaction snapshot, rather than a historical per-version value.

## Detailed syntax and execution

Array-component statistics reject postings for an empty source and individual MCV frequencies above the source row count. Different values can make their summed frequency exceed that count. Collection and namespace renames update statistics IDs in both the durable catalog and its cache.

### System virtual collections

Variable-cardinality `[Mnemic].*`, `LIST QUERIES`, and `[Mnemic].[Sessions]` snapshots are eager but memory-bounded. They retain buffered `Rows` below `MaxInMemoryStreamingState`; above it they use engine-admission-accounted, authenticated insertion-order spill and a cancellation-aware `RowsAsync` replay. Replay corruption or early termination never yields a successful partial snapshot and always retires the owned spill resources. Catalog-backed system snapshots and `DESCRIBE COLLECTION` are bound to one catalog-publication generation for the complete capture; concurrent catalog publication is observed wholly before or wholly after the result, never mixed between its name enumeration and encoded metadata rows.

The table uses canonical spelling. System collection names resolve case-insensitively, remain read-only under every spelling, and represent current snapshots; `AS OF`, `IN BETWEEN`, and `LAST PER` are rejected on virtual sources.

| Name | Source | Purpose |
|------|--------|---------|
| `[Mnemic].[Collections]` | catalog | every collection's schema and behavior, including `IsTemporal`, `SkipUnchangedUpdates` and the `BaseTypes` it extends; nested field rows include nullable `VectorDimensions`, `TypeName` and `DefaultValue` and an object field's `Checks`; `DocumentCount` reports committed rows only |
| `[Mnemic].[Enums]` | catalog | every enum, with its `Id`, `Name`, `UnderlyingType` and `Values` |
| `[Mnemic].[Types]` | catalog | every named composite type, with `Id`, `Name`, `FieldCount`, `BaseTypes` (ordered direct base names), its fields in the `[Mnemic].[Collections]` field-entry shape, and its `Checks` with the base type that declares each inherited one |
| `[Mnemic].[Metrics]` | engine | runtime counters — `PageReads` counts completed page-manager copy-read observations (including checksum retries) plus successful verified zero-copy/optimistic acquisitions; `PageWrites` counts successful full-page accessor writes. Includes `LockTimeoutCount` (engine-wide `LOCK_TIMEOUT` sum), `DeadlocksDetected` (participating waits-for cycles that selected a lowest-dirty-page-count victim with the transient `DEADLOCK` error; 0 unless implicit statements cross-write each other's collections, and when `DeadlockDetectionIntervalMs = 0`; mirrors the `mnemic.deadlocks` meter), `RetriedConflicts`, `RetriedDeadlocks`, `RetriedLockTimeouts` and `RetriedOtherTransients` (attempts of server-side work the engine discarded and ran again on a caller's behalf, by the failure that ended them; mirror the `mnemic.retries` meter), and the buffer-pool residency counters `CacheHits`/`CacheMisses` (frame hit/miss), `BufferPoolEvictions` (clock-sweep victims — sustained climb = working set exceeds the pool's capacity, `BufferPoolBytes` or its share of the automatic budget), `BufferPoolWriteBacks`, `BufferPoolUnderPinWriteBacks` (all 0 under the in-memory store), the recovery-log publication counters and the page-logging counters (page-record bytes by encoding, `Checkpoints`, `WalPageImageCoverageDrops`) described under [virtual collections](#virtual-collections). |
| `[Mnemic].[Migrations]` | real collection | migration history |
| `[Mnemic].[Statistics]` | real collection | per-collection / per-field statistics populated by `ANALYZE`. Drives `EXPLAIN`'s `EstimatedRows` column and the cost-based planner's index-vs-scan decision. |
| `[Mnemic].[Diagrams]` | real collection | the [database diagrams](diagrams.md) `CREATE DIAGRAM` stores, created by the first one: `Id`, `Name`, `Revision`, `Fields`, `Boxes` (each with its relation's current `Collection` name, `CollectionId` or `MaterializedViewId`, `X`, `Y`), `CreatedAt`, `LastAlteredAt`. <a id="syntax-meta-fields-on-every-row-backed-result"></a>

### Meta fields on every row-backed result

Every row of an implicit or wildcard projection, and an explicit `[Meta]` item or DML `RETURNING [Meta].[...]` projection, carries an automatically-populated `Meta` object with seven virtual sub-fields. They're queryable via the dotted path `[Meta].[<sub>]`:

| Path | Type | Meaning |
|------|------|---------|
| `[Meta].[ValidFrom]` | `DATETIME?` | When this version became valid; `NULL` on a standard (non-temporal) collection. |
| `[Meta].[ValidTo]` | `DATETIME?` | When the version was ended; `NULL` for the current version. |
| `[Meta].[Revision]` | `INT64` | Monotonically-increasing version number — the optimistic-concurrency token. |
| `[Meta].[CreatedAt]` | `DATETIME` | UTC creation time of this authored revision; non-null. |
| `[Meta].[CreatedBy]` | `BYTES?` | Exact opaque attribution bytes in every policy; null when absent. |
| `[Meta].[Sealed]` | `BOOL` | Reversible identity-level workflow guard; always non-null. |
| `[Meta].[SchemaVersion]` | `INT32` | The collection schema version this version was written with; always non-null. |

`Meta` is implicit — you don't declare it in `WITH SCHEMA`. Use it in `WHERE`, `ORDER BY`, `SELECT`, `EXPECTED REVISION`, grouping keys, and aggregate arguments. A JOIN exposes only its outer row's Meta; inner Meta must be projected through a CTE first. Aggregated result rows themselves have no implicit `Meta` (the row no longer corresponds to a single version). `[Meta].[Revision]` compares exactly like an `INT64` field: fractional, numeric-text, and out-of-range whole-number operands give the same rows in `WHERE`, `IN` lists, and `CASE`, and an ordered comparison with a whole number outside the `INT64` range is refused with `RANGE_LITERAL_OUT_OF_SIGNED_RANGE` in each of them.

The underlying value is opaque metadata. The internal (`COLLECTION`) policy stores the actor's primary key in its binary form, so binary `INT8`, `INT16`, `INT32`, `INT64`, and `GUID` identities do not have a canonical string rendering here: an `INT64` key is its 8 little-endian bytes, so actor `7` reads back as the BYTES value whose Base64 literal is `'BwAAAAAAAAA='`. DML `CREATEDBY` supplies the actor; `Meta.CreatedBy` preserves its exact encoded bytes. For temporal reads, `Meta.Sealed` is current control metadata in the transaction snapshot, not a historical property of the selected body version.

```sql
FROM [HR].[Employees] SELECT [Name], [Meta].[Revision] AS [Revision], [Meta].[ValidFrom] AS [ValidFrom];
FROM [HR].[Employees] WHERE [Meta].[ValidFrom] > '2024-06-01';
FROM [Archive].[Records] WHERE [Meta].[Sealed] = TRUE;
UPDATE [App].[Items] SET (...) WHERE [Id] = @id EXPECTED REVISION @rev RETURNING [Meta].[Revision];
```

## Usage pitfalls


<a id="pitfall-mnemic-namespace-is-reserved"></a>

### `Mnemic` namespace is reserved

DDL on `[Mnemic]` or `[Mnemic.*]` collections is blocked. The virtual system collections are read-only via SELECT. The engine persists its `ALTER ENGINE SET ADMISSION`, `ALTER ENGINE SET SLOWQUERY` and `SET CREATEDBY` configuration in internal `[Mnemic.Configuration]` collections (`Admission`, `SlowQuery` and `CreatedBy`); they are storage, not a query surface: change them only through those statements, and read the effective configuration through `[Mnemic].[Capabilities]` and `[Mnemic].[CreatedBy]`.

<a id="pitfall-large-system-snapshots-can-use-rowsasync"></a>

### Large system snapshots can use `RowsAsync`

Variable-cardinality `[Mnemic].*`, `LIST QUERIES`, and Sessions snapshots stay buffered below `MaxInMemoryStreamingState` but spill above it. Consumers must drain or dispose the returned async enumerator exactly as for ordinary streamed queries. This is an ownership detail only: capture stays eager and the logical snapshot/order is unchanged.
